# GLM-OCR — руководство по модели

Рабочие заметки по GLM-OCR в том виде, в каком его использует LLocr: что это
за модель, откуда берётся GGUF, как запросы собираются вокруг обученных
префиксов задач и чего модель принципиально не умеет (лейаут, координаты).
Всё здесь — из карточки модели, PR в llama.cpp или измерено в этом проекте.

Английский оригинал — [`19-glm-ocr.md`](19-glm-ocr.md).

## 1. Что это за модель

- **GLM-OCR** (Z.ai, `zai-org/GLM-OCR`), лицензия MIT. Специализированная
  VLM для разбора документов на ~0,9 млрд параметров: декодер класса GLM 0.5B
  (16 слоёв, GQA с 8 KV-головами) плюс визуальный энкодер CogViT с коннектором
  даунсемплинга токенов — «под капотом просто GLM4V с несколькими
  дополнениями» (PR #19677 в llama.cpp). Класс в transformers —
  `GlmOcrForConditionalGeneration`; в GGUF архитектура называется `glm4`.
- Обучена на разбор документов — текст, формулы, таблицы — и извлечение
  информации. Бенчмарк карточки: OmniDocBench V1.5 **94.62** (заявлен #1 на
  момент выхода); в карточке отмечены сложные таблицы, документы с кодом,
  печати, перекошенные/мятые сканы. Модель помещается в 4 ГБ VRAM.
- **Только распознавание, без детекции.** Модель не выдаёт ни layout-токенов,
  ни координат; официальный SDK-конвейер сочетает её с внешней моделью лейаута
  (PP-DocLayoutV3) и скармливает ей кропы. Поэтому LLocr не даёт ей задачу
  layout, а постраничные ответы разбираются парсером `raw`.
- **Динамическое разрешение**: процессор масштабирует изображения в границах
  `shortest_edge` 12544 px … `longest_edge` 9633792 px (патч 14, merge 2 →
  28 px на визуальный токен). mtmd в llama.cpp применяет то же масштабирование,
  так что пинить `--image-min/max-tokens` не нужно.
- В весах есть один MTP/nextn-слой, но llama.cpp грузит его «сохранённым, но
  неиспользуемым», а GGUF-репозиторий не поставляет файл драфтера —
  спекулятивное декодирование для этой модели недоступно.

## 2. Файлы и репозитории

| Репозиторий | LLocr скачивает | Назначение |
| --- | --- | --- |
| [`ggml-org/GLM-OCR-GGUF`](https://huggingface.co/ggml-org/GLM-OCR-GGUF) | `GLM-OCR-Q8_0.gguf` (q8_0, 950 МБ), `GLM-OCR-f16.gguf` (f16, 1,79 ГБ), `mmproj-GLM-OCR-Q8_0.gguf` (484 МБ) | Рекомендованный квант, полноточные веса и визуальный проектор. |

Примечания:

- `minBuild` — **b8096**: поддержка `glm4`/`GlmOcrForConditionalGeneration`
  появилась в llama.cpp 18.02.2026 (`Add support for GLM-OCR Model` #19677,
  коммит `eeef3cf`), и тег b8096 того же вечера её уже содержит (compare API:
  тег на 3 коммита впереди слияния, позади на 0).
- Оценщик памяти читает GGUF-метаданные `glm4.*` — предупреждение мастера
  настройки считает реальные 16 слоёв / 8 KV-голов, а не универсальный
  фолбэк.

## 3. Запуск llama-server

Референсная команда сообщества (обсуждение #19721 в llama.cpp):

```sh
llama-server -m GLM-OCR-Q8_0.gguf --mmproj mmproj-GLM-OCR-Q8_0.gguf \
  -c 12000 -ngl 99 --flash-attn off -fit off
```

Что LLocr запускает на самом деле (платформенный слой из `serverLaunch.json`,
модельный слой из профиля):

```sh
llama-server \
  --model <…>/GLM-OCR-Q8_0.gguf \
  --mmproj <…>/mmproj-GLM-OCR-Q8_0.gguf \
  --alias llocr-glm-ocr --host 127.0.0.1 --port <n> \
  --n-gpu-layers 99 --ctx-size 16384 \
  --flash-attn on --image-min-tokens 456 --image-max-tokens 6144 \
  --cache-reuse 0 --no-context-shift
```

По слоям:

- `--model / --mmproj / --alias / --host / --port` — базовые поля,
  единый источник — настройки активации/установки.
- **Модельный слой** (`glm-ocr.json`, в обеих задачах одинаково):
  - `--flash-attn on` — машинный слой позволяет пользователю выключить flash
    attention, и без него граф внимания материализует
    ctx² × 16 голов × F32 — **~17 ГБ при машинных 16384** — и Metal отказывает
    в аллокации на первом же запросе. Flash attention on проверен на
    корректность на актуальной сборке (b11564, страница со смесью
    английского и русского распознана точно): февральские-2026 жалобы
    «flash-attn must be off» в текущих сборках исправлены.
  - `--image-min-tokens 456 --image-max-tokens 6144` — нативный динамический
    диапазон 16…12288 визуальных токенов (§1). Нижняя граница не даёт мелким
    кропам блоков проваливаться в грубые 16 токенов (задача blockRecognition
    шлёт кропы); верхняя удерживает страницу A4 ~240 dpi вместе с
    `max_tokens` 8192 внутри машинного контекста 16384 — при некапированных
    12288 одно изображение его переполнило бы.
- Без `--special`: парсер `raw` читает обычный контент, а не det-токены.
- Без `--jinja` и флагов мышления: GGUF-шаблон сам рендерит ходы
  `<|user|>/<|assistant|>`, и модель не рассуждает.
- Политика: `--parallel 1 --cache-reuse 0 --no-context-shift --no-warmup`
  (платформенный слой).

## 4. Составление запросов

### Раскладка сообщения

- **Изображение перед текстом** — шаблон чата карточки ставит часть с
  изображением первой, поэтому профиль не задаёт `promptBeforeImage`
  (порядок семейства Gemma/Qwen; LFM2.5 из архива ставит текст первой).
- Запрос OCR — одно сообщение пользователя: изображение страницы плюс весь
  промпт.
- Запросы распознавания блока несут системный промпт профиля (контракт
  транскрипции) и одно сообщение пользователя с кропом и блочным промптом.
  `GeneralPurposeModel` вдобавок шлёт
  `chat_template_kwargs: {"enable_thinking": false}` в каждом таком запросе —
  GLM-шаблон игнорирует неизвестный kwarg, это безвредно.

### Обученные префиксы задач

GLM-OCR переключается между тремя обученными режимами промптом, и профиль
отображает типы блоков приложения на них:

| Префикс | Где используется |
| --- | --- |
| `Text Recognition:` | постраничный промпт и все текстовые типы блоков (text, title, list, подписи, код, колонтитулы, …) |
| `Table Recognition:` | блоки `table` |
| `Formula Recognition:` | блоки `equation` / `formula` / `equation_block` |

Список `prompts` постраничной роли содержит единственную запись
(`text-recognition`); другого режима на всю страницу у модели нет — конвейер
SDK с покрас областей заменяет команда «Разметить», и она остаётся за MinerU
(дефолт задачи разметки; в архиве её сначала несла TeleOCR).

### Параметры запроса

| Параметр | Значение | Зачем |
| --- | --- | --- |
| `temperature` | 0.0 | Детерминированное жадное декодирование для транскрипции (0.02 из гайда сообщества о том же намерении; конвенция репозитория — greedy, как у gemma и у teleocr из архива). |
| `repeat_penalty` / `presence_penalty` / `frequency_penalty` | 1.0 / 0.0 / 0.0 | Нейтрально. |
| `max_tokens` | 8192 | Плотные страницы и большие HTML-таблицы. |
| `stream` | false | Парсер потребляет один полный ответ. |
| `cache_prompt` | true | Страницы/блоки разделяют системное сообщение; драфтера, с которым можно конфликтовать, нет. |

## 5. Форматы вывода

- **Обученный полностраничный режим** (задачи с ADR 252 нет — однопроходное
  распознавание страницы вырезано): ответ — транскрипция страницы — простой
  текст или Markdown
  (таблицы могут прийти HTML- или Markdown-таблицей). Ни layout-токенов, ни
  координат; весь ответ становится одной текстовой страницей через парсер
  `raw`. Полностраничный промпт несёт обученный префикс `Text Recognition:`.
- **Задача blockRecognition**: ответ — текст блока (таблицы таблицей, формулы
  LaTeX), читается `BlockRecognitionModel::parseResponse`, который снимает
  служебные токены и Markdown-забор вокруг всего ответа.

## 6. Роль в конвейере проверки

- **blockRecognition** — единственная объявленная задача: после того как
  decision-модель пометила блок как несовпадение (или по ручным командам
  «Распознать»), кроп перераспознавается с обученным префиксом его типа, и
  ответ становится текстом блока.
- **layout** — не объявлена: модель не производит боксов (§1).
- **decision** — неприменима: задача проверки говорит на визуальном диффе
  MiniCPM-OCR Jev (ADR 254).

## 7. Где что живёт в LLocr

| Кусок | Расположение |
| --- | --- |
| Профиль модели (файлы, префиксы, слой запроса) | `resources/profiles/models/glm-ocr.json` |
| Состав запроса/ответа, порядок модальностей | `OcrModel::buildRequestBody` (`src/models/`) |
| Запрос/ответ распознавания блока | `BlockRecognitionModel` (`src/models/`) |
| Raw-разбор (без фрагментов) | `RawParser` (`src/parsers/`) |
| Оценка памяти (ключи glm4) | `ModelMemoryEstimator` |
| Строки установщика | `ModelQuantModel` (по списку на задачу — назначение в «Модели по задачам», управление в «Модели») |

Проектные решения: ADR 88 (модели — данные, профиль — весь контракт), 112
(новая модель — один JSON-профиль плюс, если форма ответа новая, один парсер —
здесь хватает существующего `raw`), 126 (машине принадлежат
`flash-attn`/`ctx-size`; пустой модельный launch-слой — норма).
