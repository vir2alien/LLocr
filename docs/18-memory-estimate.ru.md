# 18. Требование по видеопамяти: как оно вычисляется и как было откалибровано

> Английский оригинал: [docs/18-memory-estimate.md](18-memory-estimate.md)

> Число, которое показывает выпадающий список квантов (`VRAM ≥ 11.4 GiB`), —
> свойство всего сервера, а не файла. Документ объясняет, из чего складывается
> число, откуда берётся каждый коэффициент, как измерить модель, которой ещё
> нет в каталоге, и какие ловушки лежат между измерением и профилем.
> Само решение:
> ADR 191 в `docs/07-glossary.md`.

## 1. Что означает число

Строка выпадающего списка квантизации читается так:

```
✓ Q8_0 — 9.1 GiB · VRAM ≥ 11.4 GiB
```

Первое число — размер файла, второе — **минимум видеопамяти, который должен
быть у карты**, чтобы запустить модель, к которой относится файл: веса,
проектор, драфт и его собственный контекст, KV-кэш, рабочий набор графа,
зрительный энкодер и собственные накладные расходы сервера. В большинстве
случаев файл — самая маленькая часть этого.

К одному и тому же числу ведут два пути:

- **файл** — модель, которая лежит на диске, читается из её заголовка GGUF
  (`ModelMemoryEstimator::shapeFromFile`);
- **профиль** — у квантизации, которая ещё только скачивается, заголовка
  нет, поэтому профиль модели несёт архитектуру и измеренные коэффициенты
  (`resources/profiles/models/<id>.json`, блок `memory`).

Для каталога побеждает профиль (`RuntimeController::estimateModelMemory`),
потому что он несёт и то, чего заголовок сказать не может: стоимость
зрительного энкодера, драфта и кэша со скользящим окном.

Требование — **не** сумма буферов. Это сумма плюс накладные расходы
сервера, чтобы число называло карту, на которой модель работает, а не
карту, на которой она едва запускается:

```
required = buffers + (64 MiB + 8 % of the buffers)
```

## 2. Формула

Каждое слагаемое `ModelMemoryEstimator::estimateMemory` (`src/runtime/`):

| Слагаемое | Формула | Откуда берётся коэффициент |
| --- | --- | --- |
| Веса | размер файла GGUF | файл (`sizeBytes` кванта в профиле) |
| Проектор | размер файла `mmproj` | файл (`files.mmproj.sizeBytes`) |
| Драфт | размер файла драфта | файл (`memory.draftBytes`) |
| Контекст драфта | `draftContextBytes + draftKvBytesPerToken × ctx` | измерено (см. §5) |
| KV-кэш | `kvBytesPerToken × ctx + kvBytesFixed` | архитектура, для обычных моделей точно |
| Рабочий набор | `ubatch × workingSetBytesPerToken + ctx × ubatch × workingSetContextBytes` | измерено, либо выведено из формы |
| Зрительный энкодер | `visionTokens × visionBytesPerToken`, либо `visionBufferBytes` | измерено (см. §4) |
| Накладные расходы | `64 MiB + 8 %` | собственные аллокации сервера и запас аллокатора |

Выведенные значения по умолчанию, когда профиль не несёт измеренного:

```
kvBytesPerToken         = 2 × nKvLayers × nKvHead × headDim × bytesPerValue
workingSetBytesPerToken = (nEmbd × 24
                           + headDim × (nHead + 2 × nKvHead) × 4
                           + nFf × 8
                           + nMoeLayers × nExpertUsed × nExpertFf × 12) × 1.12
workingSetContextBytes  = 2            (the f16 attention mask per context token)
```

Множитель 1.12 — запас, который превращает смоделированный рабочий набор в
требование: планировщик llama.cpp резервирует до 12 % больше, чем
предсказывает форма, и оценка не должна никогда занижать.

Окно контекста, ubatch и типы кэша берутся из профиля запуска
(`ModelMemoryEstimator::budgetFromLaunch`): платформенный профиль владеет
`ctx-size`, профиль модели — `ubatch-size`, а `cache-type-k/v = f32`
удваивает KV-кэш.

## 3. Блок `memory` в профиле модели

```json
"memory": {
  "nLayer": 48, "nKvLayers": 8, "nHead": 16, "nKvHead": 8, "headDim": 64,
  "nEmbd": 3840, "nFf": 15360,
  "visionTokens": 1120, "visionBytesPerToken": 55419,
  "draftBytes": 253708800, "draftKvBytesPerToken": 2048, "draftContextBytes": 387994092,
  "workingSetBytesPerToken": 267320, "workingSetContextBytes": 2,
  "kvBytesFixed": 1006632960
}
```

| Поле | Что означает |
| --- | --- |
| `nLayer` | слои декодера |
| `nKvLayers` | слои, чей кэш **следует за контекстом** (0 = все). Гибридная архитектура держит их меньше: остальные хранят скользящее окно |
| `nHead`, `nKvHead` | головы внимания и KV-головы этих слоёв |
| `headDim` | ширина одной KV-головы. Это `attention.key_length` из GGUF — **сумма по головам, а не ширина одной головы** (см. ловушки) |
| `nEmbd`, `nFf` | ширина эмбеддинга и feed-forward (рабочий набор) |
| `nMoeLayers`, `nExpertUsed`, `nExpertFf` | слагаемые mixture-of-experts (рабочий набор) |
| `visionTokens` | токены изображения, которыми задача страницы наполняет бюджет |
| `visionBytesPerToken` | рабочий набор энкодера на токен изображения |
| `visionBufferBytes` | весь рабочий набор энкодера — для проектора, чья стоимость не следует за числом токенов |
| `draftBytes` | веса драфта (отдельный GGUF) |
| `draftKvBytesPerToken` | KV-кэш **собственного контекста драфта**, на токен контекста |
| `draftContextBytes` | что ещё держит этот контекст: ячейки скользящего окна и буфер вычислений |
| `workingSetBytesPerToken` | измеренная стоимость одного токена рабочего набора графа (0 = вывести) |
| `workingSetContextBytes` | измеренная стоимость одного токена контекста в маске внимания (0 = 2) |
| `kvBytesPerToken` | измеренный KV-кэш на токен контекста (0 = вывести) |
| `kvBytesFixed` | ячейки скользящих слоёв: за контекстом они **не** следуют |

## 4. Измерение модели, которой нет в каталоге

Работу делают два скрипта:

- `scripts/measure-memory.sh` — поднимает llama-server с флагами приложения
  и пишет лог;
- `scripts/memory-from-log.py` — читает лог (или несколько) и печатает
  числа, включая поля блока `memory`.

Разобранный ниже пример измеряет LFM2.5-VL — модель из трёх файлов (веса,
проектор, драфт), поэтому walkthrough самый полный; модель лежит в архиве
(`archive/models/profiles/lfm25-vl-3b.json`, ADR 251), ход работы для любой
модели каталога тот же.

```sh
scripts/measure-memory.sh \
  --model "LiquidAI__LFM2.5-VL-3B-GGUF/LFM2.5-VL-3B-Q8_0.gguf" \
  --mmproj "LiquidAI__LFM2.5-VL-3B-GGUF/mmproj-LFM2.5-VL-3B-F16.gguf" \
  --draft  "LiquidAI__LFM2.5-VL-3B-GGUF/LFM2.5-VL-3B-DSpark-F16.gguf" \
  --ctx 16384 --flash-attn on --spec-type draft-dspark --spec-draft-n-max 8 --special
```

```
-- kv caches (main context)
      256.00 MiB   16384 cells    8 layers   -> 16384 B/token (follows the context)
-- vision (clip)
   warmup image 512x512   patch 16   merge 2   -> 1024 patches = 256 tokens
   vision           30.31 MiB   -> 124150 B/token
-- profile fields
   kvBytesPerToken 16384
   draftKvBytesPerToken 8192
   draftContextBytes 533190410
   draftBytes 567205280
   visionBytesPerToken 124150
```

Готовый лог разбирается без всякого запуска:

```sh
scripts/measure-memory.sh --parse build/measure/app-gemma4-12b.log
```

### Флаги

Измерение должно использовать флаги, с которыми приложение запускает
сервер: они меняют резервирования.

| Флаг | Откуда он | Почему важен |
| --- | --- | --- |
| `--parallel 1 --cache-reuse 0 --no-context-shift` | политика запуска (`resources/profiles/serverLaunch.json`) | один контекст, без переиспользования |
| `--ctx-size` | платформенный профиль (16384 на macOS) | от него масштабируются KV-кэш и маска |
| `--ubatch-size` | профиль модели (512 по умолчанию, 2048 у gemma-4 12B, 512 у minicpm-jev; decision-профили архива несли 6144–8192) | от него масштабируется рабочий набор |
| `--flash-attn on\|off` | платформенный профиль, перекрывается профилем модели (gemma-4 E4B выключает **его**) | с выключенным flash attention энкодер держит матрицу внимания по всей странице |
| `--image-min-tokens` / `--image-max-tokens` | профиль модели | бюджет страницы модели |
| `--spec-type` / `--model-draft` | профиль модели | драфт получает контекст своего собственного |
| `--special` | профиль модели (MinerU, Qwen3.5; из архива тоже LFM2.5-VL) | некоторым моделям он нужен |
| `--device none --n-gpu-layers 0` | только для измерения | размеры буферов те же, а числа читаются без карты |

### Строки лога

| Строка | Что она даёт |
| --- | --- |
| `llama_context: n_ctx / n_ubatch / n_batch` | бюджет, которым воспользовался сервер |
| `print_info: n_layer / n_embd / n_head / n_head_kv / n_embd_head_k / n_swa` | архитектура |
| `llama_kv_cache: size = X MiB (N cells, L layers)` | KV-кэши: тот, у которого `N == n_ctx`, следует за контекстом, остальные — ячейки скользящего окна |
| `sched_reserve: CPU compute buffer size = X MiB` | рабочий набор (первый — основной контекст, те, что после `loading draft model`, — драфта) |
| `reserve_compute_meta: CPU compute buffer size = X MiB` | зрительный энкодер (первый) и, у gemma-4, аудиобашня (второй) |
| `get_dummy_batch: warmup with image size = W x H` | изображение, под которое сделан резерв зрения |
| `load_hparams: patch_size / n_merge` | геометрия сетки патчей |
| `[mtmd] estimated worst-case memory usage of mmproj is X MiB` | веса проектора плюс резерв clip — бесплатная перекрёстная проверка |

### Зрительный энкодер

Резерв clip-графа определяется **сеткой пикселей изображения**, а не
бюджетом токенов. Число токенов изображения, которое даёт картинка, равно

```
tokens = (W / patch_size) × (H / patch_size) / n_merge²
```

поэтому ставка проектора, который масштабируется вместе с токенами, равна

```
visionBytesPerToken = the clip reservation / tokens
```

Warmup-изображение сервер масштабирует под бюджет изображения модели,
поэтому измерение должно идти с тем бюджетом, который использует
приложение (бюджет страницы для задачи страницы). Модель, чей проектор не
следует за числом токенов, несёт вместо ставки `visionBufferBytes` — см.
ловушки.

## 5. Собственный контекст драфта

Драфт, который является **отдельным GGUF** (MTP-драфтеры gemma-4; DSpark-
драфтер LFM2.5-VL лежит в архиве), работает в собственном контексте:
llama.cpp даёт ему свой KV-кэш и свой буфер вычислений. Профиль несёт все
три части:

```
draftBytes          the weights of the draft file
draftKvBytesPerToken the KV cache of that context, per context token
draftContextBytes   the rest of that context: the sliding cells and the
                    compute buffer of the speculative graph
```

Числа берутся из лога: кэши после `loading draft model` и наибольший
`sched_reserve` после него (спекулятивный граф резервирует больше, чем один
драфт).

MTP-блок **внутри** модели (Qwen3.5) — это слой самой модели, а не контекст
своего собственного: у него нет ни кэша, ни собственного буфера вычислений.

decision-профили архива (`clef-flash`, `d3-flash`, `d3-mini`) просили
большой ubatch (8192 и 6144 токена), и рабочий набор был их крупнейшим
слагаемым. minicpm-jev — контрпример: она несёт те же два изображения, но
работает при ubatch 512, потому что при 8192 llama.cpp переносил 768 МиБ
графа вычислений на хост, и карте не хватало места под веса. Модели страниц
выглядят дешёвыми, потому что зрительный энкодер при их бюджете невелик, и
дорогими, когда проектор нарезает страницу (Unlimited-OCR так делал — его
плоский зрительный буфер на 2 981 117 952 байта лежит в архивном профиле).

## 7. Ловушки

Каждый пункт здесь стоил измерения, чтобы его найти.

1. **Dummy-изображение — не настоящая страница.** Резерв clip-графа
   делается под dummy-изображение warmup, которое сервер масштабирует под
   бюджет изображения модели. Ставка — это резерв, делённый на **токены,
   которые даёт это изображение** (`(W/patch) × (H/patch) / n_merge²`), а
   не на бюджет: warmup у gemma-4-12B — 768×768 с патчем 48 и merge 1 —
   256 токенов, а не 1120.

2. **С выключенным flash attention энкодер держит всю матрицу внимания.**
   gemma-4-E4B работает с `--flash-attn off`, поэтому стоимость квадратична
   по числу патчей. Её warmup-резерв (276.77 MiB на 2304 патчах) — линейная
   часть плюс attention-член; attention-член — разница с прогоном при
   включённом flash attention (101.27 MiB), и он растёт как квадрат:

   ```
   linear    = 101.27 MiB / 2304 patches      = 46 089 B/patch
   attention = (276.77 − 101.27) MiB / 2304²  = 35 B/patch²
   the app's page: 1120 tokens × 9 patches = 10 080 patches
   → 46 089 × 10 080 + 35 × 10 080² = 3 802 MiB  (visionBufferBytes 3 986 933 350)
   ```

   `scripts/memory-from-log.py --app-patches N` считает это по двум логам
   (с включённым flash attention и с выключенным).

3. **Проектор, нарезающий страницу, не масштабируется вместе с числом
   токенов.** Проектор Unlimited-OCR (модель лежит в архиве) режет страницу
   на три окна плюс общий вид: стоимость следует за пикселями плиток
   (9600 патчей), а не за токенами. Вместо ставки он несёт
   `visionBufferBytes` (2 981 117 952).

4. **KV-кэш гибридной архитектуры — это два кэша.** Модели gemma-4 держат
   кэш для полно-attention слоёв (он следует за контекстом) и второй — для
   скользящих слоёв (фиксированное число ячеек: 3072 ячейки у 12B, 1024 у
   E4B). Фиксированную часть профиль несёт отдельно (`kvBytesFixed`);
   остальное масштабируется с контекстом.

5. **Длина ключа — сумма по головам.** Ширина ключа у gemma-4-12B была
   вчетверо больше настоящей, и её кэш был завышен на 4 GiB. Ширина на
   голову — то, что держит кэш:
   `headDim = the K bytes per cell per layer ÷ 2 (f16) ÷ nKvHead`.

6. **Слои с KV-кэшем — не слои модели.** В рекуррентном гибриде состояние
   живёт в SSM-тензорах, и у этих слоёв K/V нет вовсе (LFM2.5-VL из
   архива: кэш есть у 8 из её 30 слоёв); скользящий слой несёт K/V, но в
   собственном кэше (модели gemma-4). Голова спекулятивного декодирования
   (блок `nextn`) — отдельный слой-драфт: llama.cpp запускает его отдельным
   графом и **не** держит для него кэша.

7. **Драфт, который является отдельным файлом, имеет контекст своего
   собственного** — с KV-кэшем и буфером вычислений. Профиль объявлял веса
   драфта, но долго их не читал: драфт ничего не стоил.

8. **Ячейки скользящего окна зависят от ubatch.** Число ячеек, которое
   сервер выделяет скользящему слою, — не размер окна; это кратное ему
   число, зависящее от батча. Читайте его из лога, не вычисляйте.

9. **Спекулятивный граф резервирует больше, чем один драфт.** Драфт LFM
   (модель лежит в архиве) резервирует 258 МиБ на себя и 508.49 МиБ на
   граф, который гонит цель и драфт вместе. Применимо большее из чисел.

10. **`--no-warmup` прячет резерв зрения.** Политика запуска приложения
    пропускает warmup, поэтому clip-граф резервируется под первый
    настоящий запрос. Измерению нужен warmup (скрипт запускает его по
    умолчанию).

11. **Файловый путь оценщика неверно описывает гибридную архитектуру.**
    Путь по заголовку считает слои, несущие тензоры K и V, а за контекстом
    следуют только полно-attention слои — у gemma-4-12B это 48 слоёв вместо
    8, так что её кэш выходит вшестеро больше, а фиксированная часть
    скользящего окна не учитывается вовсе. Авторитетен путь каталога
    (профиль).

12. **Бюджет изображения зависит от задачи.** Задача страницы наполняет
    собственный бюджет модели (`image-max-tokens`); кроп блока
    масштабируется вверх до нижней границы, которую объявляет модель
    (`image-min-tokens`), и иначе остаётся маленьким. Число в выпадающем
    списке — бюджет страницы, то есть худший случай.

## 8. Чек-лист для новой модели

1. **Установить модель и проектор** (Настройки → Модели в приложении), а
   если модель несёт драфт — и его файл.
2. **Прочитать архитектуру** из заголовка GGUF (или с карточки модели):
   слои, KV-слои, KV-головы, длину ключа, ширину эмбеддинга и
   feed-forward, слагаемые mixture-of-experts.
3. **Измерить** с флагами приложения:
   ```sh
   scripts/measure-memory.sh --model "<repo>/<file>.gguf" \
       --mmproj "<repo>/<mmproj>.gguf" [--draft "<repo>/<draft>.gguf"] \
       --ctx <the platform's context> --flash-attn <on|off> \
       --image-max-tokens <the model's page budget> [--ubatch <the model's>]
   ```
4. **Сверить KV-кэш** с формулой
   `2 × nKvLayers × nKvHead × headDim × 2 × ctx`: он должен совпасть с
   логом. Если не совпал — неверно разбиение по слоям или ширина головы
   (§7.4–7.6).
5. **Взять ставку зрения** из лога: резерв ÷ токены warmup-изображения.
   Если модель работает с выключенным flash attention или её проектор
   нарезает страницу, вместо ставки несите `visionBufferBytes`
   (§7.2–7.3).
6. **Взять рабочий набор** из лога: строка `sched_reserve`. Один лог не
   разделяет два слагаемых — сделайте второй прогон с другим ubatch или
   контекстом и решите два уравнения, либо оставьте вывод по умолчанию и
   проверьте, что он не ниже измерения.
7. **Добавить три части драфта**, если он у модели есть (§5).
8. **Записать блок `memory`** в профиль, а курируемые размеры — в `files`
   (`sizeBytes` кванта, проектора и драфта).
9. **Проверить результат**: требование должно быть выше суммы буферов, а
   требование самого крупного кванта — выше карты, которую рекомендует
   руководство модели. Формулу и выпадающий список защищают
   `test_model_memory_estimator` и `test_model_installer`.
10. **Записать числа** в таблицу этого документа (§6), а если у модели
    есть собственное руководство — и в него.

## 9. Чего не может оболочка агента

Песочница агентской сессии блокирует инструменты, измеряющие resident
memory, поэтому измерение приходится брать из собственного отчёта
llama.cpp:

| Заблокировано | Вместо этого |
| --- | --- |
| `ps`, `pgrep`, `pkill` | читать собственный лог сервера; буферы печатаются там |
| `/usr/bin/time -l` (строка RSS требует запрещённого `sysctl`) | строки `sched_reserve` и `reserve_compute_meta` |
| `DYLD_INSERT_LIBRARIES` (интерпозер malloc вырезается) | резервирования в логе |
| запись в `/tmp` | каталог `build/` (в gitignore) или любой другой доступный для записи путь |
| `timeout` | `sleep` + `kill $!` |
| Metal (карта агенту недоступна) | `--device none --n-gpu-layers 0`: размеры те же |
| фоновая задача, живущая дольше вызова | один вызов с достаточно длинным таймаутом — параллельная сборка того же дерева губит вторую задачу |

Логи измерений лежат в каталоге `build/` (`build/measure/*.log`). Они в
gitignore и теряются вместе с чистым деревом — важные числа лежат в
профилях и в §6.
