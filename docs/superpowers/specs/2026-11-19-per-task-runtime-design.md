# Per-task рантайм: у каждой задачи свой выбор — управляемый или внешний

Дата: 2026-11-19. Утверждено пользователем: подход A (per-task ключ +
единый `RuntimeController`), настройки внешнего сервера — в параметрах задачи,
выбор визарда применяется ко всем задачам, окно логов показывает оба
источника.

## Замысел

Сегодня режим один на всё приложение: `SettingsStore::connectionMode()`
(`provider/mode`) выбирает между управляемым рантаймом (локальный
llama.cpp) и внешним сервером, и **все** задачи — `layout`,
`blockRecognition`, `decision`, `fix` — работают в рамках этого выбора.
Переключатель живёт в «Настройки → Рантайм».

Цель: **каждая задача сама выбирает рантайм**. Разметка страницы может
идти через локальный MinerU, проверка блока — через локальную MiniCPM, а
исправление — через внешний API с облачной Qwen. Управляемые задачи делят
один локальный llama-server (он умеет переключать модель при смене роли),
внешние идут на собственные endpoint'ы со своими ключами и алиасами.

**Не-цели**: второй локальный сервер (два управляемых рантайма на разные
модели одновременно); собственный HTTP-клиент для внешних задач (инфраструктура
per-task уже есть); переработка протоколов задач (`docs/09`); работа RAG
(отложена, ADR 6).

**Анти-цель**: двусмысленность «какой режим сейчас». Глобальный
`provider/mode` остаётся, но как значение по умолчанию и как единственный
источник при миграции — у каждой задачи после миграции есть явный режим.

## Подходы

1. **Per-task ключ + единый `RuntimeController` (выбран).** Ключ
   `tasks/<role>/runtimeMode` в `QSettings`. `RuntimeController` читает
   режим по роли: `modeForRole(role)` вместо `modeFromSettings()`. Всё
   решение-making уже идёт per-task (`ensureConnectionReady(role)`,
   `taskModelAvailable(role)`), поэтому переход локален. Глобальный
   `provider/mode` живёт как default и для миграции.
2. **Два независимых провайдера** (`ManagedProvider` + `ExternalProvider` +
   реестр задач). Чище по разделению ответственности, но это рефакторинг
   всего `RuntimeController`: resolve, кэш, старт/стоп сервера, логи,
   self-test. Большой риск регрессий, длинный путь, и выигрыш в
   архитектурной чистоте не окупает его при одном локальном сервере.
3. **Глобальный переключатель + переопределение на строку.** Минимум
   правок, но переключатель остаётся в интерфейсе (прямое противоречие
   требованию) и появляется двусмысленность: что задаёт глобальный режим,
   если у каждой строки свой.

## Дизайн

### Модель данных

Новый ключ на задачу: `tasks/<role>/runtimeMode` со значениями `managed` |
`external`. Имя роли пишется по существующему правилу `taskKeyName()`:
`blockRecognition` → `check`, остальные — как есть. Это тот же префикс,
который уже используют `tasks/<role>/baseUrl` и `provider/apiKey/<role>`,
так что все per-task ключи задачи лежат рядом.

Глобальный `provider/mode` (`kConnectionMode`) не удаляется: он становится
**значением по умолчанию** для задач без явного режима и источником
миграции.

**Миграция.** При чтении режима задачи, у которой ключа нет, берётся
глобальный режим и **записывается явно**. Миграция идемпотентна и
однократна: у пользователя с внешним режимом все четыре задачи станут
внешними, с управляемым — управляемыми; второй запуск ничего не меняет.
Глобальный `provider/mode` после миграции — значение по умолчанию для
новых задач и для визарда.

Сброс настроек к умолчаниям (`resetToDefaults()`) возвращает и per-task
ключи к глобальному режиму: сброс не должен оставлять задачу в режиме,
который пользователь уже сбросил.

### SettingsStore

Новое API рядом с существующим per-task API (`baseUrlForRole`,
`apiKeySetForRole`, `modelNameForRole`):

- `runtimeModeForRole(role)` → `"managed"` / `"external"` (с миграцией при
  чтении).
- `setRuntimeModeForRole(role, mode)` → пишет ключ, шлёт
  `taskRuntimeModesChanged`.
- `setRuntimeModeForAllRoles(mode)` → пишет все четыре роли одним
  изменением (используется визардом); шлёт один сигнал.
- `managedRoles()` / `externalRoles()` → списки ролей в каноническом порядке
  (`layout`, `blockRecognition`, `decision`, `fix`) для UI и для логики.

Глобальный `mode()` / `setMode()` остаются: `setMode()` меняет значение по
умолчанию и **больше не** сбрасывает и не восстанавливает
`provider/lastExternalBaseUrl` — общего URL больше нет как «скрытого», он
всегда на виду в разделе «Рантайм».

Секреты не затрагиваются (правило 8 AGENTS.md): режим задачи — обычная
настройка, ключи остаются в OS-хранилище.

### RuntimeController

`modeFromSettings(settings)` заменяется на `modeForRole(role)`. Все места,
где сегодня читается глобальный режим, становятся per-task:

| Место | Новое поведение |
| --- | --- |
| `ensureConnectionReady(role)` | `external` → `resolveExternalReady(role)`; `managed` → текущий путь локального сервера |
| `taskModelAvailable(role)` | `managed` → файл модели на диске существует; `external` → задан непустой алиас |
| `roleConfigError(role)` | проверка модели/сборки только для `managed`-роли; для `external` — пустая строка (ошибок тут нет) |
| `canRecognize` | `true`, если управляемых задач нет (всё внешнее); иначе как сейчас: сервер готов либо может подняться |
| `recomputeConfigValid` | валиден, если сервер есть и (управляемых задач нет, либо у них корректные пути модели) |
| `launchCommandPreview` | пустая строка, если управляемых задач нет |
| `cancelPendingStart` | касается только managed-пути (сервер) |

**Локальный сервер в смешанном режиме.** Один llama-server обслуживает
только управляемые задачи и переключает модель при переходе между ними.
Механизм `serverRunsRole` / `beginRoleSwitch` уже это делает — логика не
меняется, меняется только то, какие роли до него доходят. Внешние задачи
сервер не трогают и его не поднимают.

Если управляемых задач нет, сервер не поднимается вовсе: кнопка Start/Stop
скрывается, `launchCommandPreview` пуст, `configValid` не требует модели.

**Ручной старт.** `startServer()` без роли сегодня стартует с
`ConnectionRole::BlockRecognition`. В смешанном режиме это может быть
внешняя задача — тогда запускать нечего. Новое правило: сервер стартует с
**первой управляемой задачи** в каноническом порядке; если управляемых
задач нет, ручной старт недоступен.

**Self-test.** Проверяет управляемый рантайм — разрешён, если есть хотя бы
одна managed-задача. В сообщении об отказе — «Self-test is available only
when a task uses the managed runtime».

**Кэш соединений.** `m_resolvedCache` уже per-role. Сигнал
`taskRuntimeModesChanged` обязан сбрасывать его: задача, переведённая с
external на managed, иначе продолжила бы брать старое внешнее соединение из
кэша. Сброс — через существующий `invalidateResolvedCache()`.

**Авто-инвалидация.** `RuntimeController` подписан на сигналы
`SettingsStore` через `connectEveryChangeSignal` — новый
`taskRuntimeModesChanged` подключается тем же способом, а
`taskModelsChanged` пересчитывается, потому что доступность модели
зависит от режима.

### Логи

`RuntimeLog` сегодня выбирает **один** источник по глобальному режиму:
`externalMode()` переключает между выводом сервера и журналом запросов.
В per-task мире это больше не верно: журнал запросов (`RequestJournal`)
наполняется всеми запросами клиента — и к локальному серверу, и к
внешним, — а вывод сервера существует, только когда сервер запущен.

Новое поведение: `RuntimeLog` отдаёт **оба** источника раздельно
(вывод сервера и строки журнала запросов), а окно логов показывает их
вертикальным сплитом: сверху вывод llama-server, снизу журнал запросов.
Правило действует во всех режимах, включая чисто управляемый: журнал там
показывает запросы к локальному серверу.

`clearServerLog()` очищает оба источника; копирование в буфер берёт оба
вместе.

### Настройки → Рантайм

Глобальный `SegmentedControl` («Connection mode») **убирается**. По
макету — одно окно с двумя карточками, обе всегда видны:

- **«Управляемый · llama.cpp»** — активная сборка, установленные сборки,
  обновления, канал и бэкенд. Это сегодняшний `RuntimeTabInternal`
  без изменений по сути.
- **«Внешний · общий сервер»** — базовый URL, общий API-ключ, кнопка
  проверки, пояснение «этот адрес используют только внешние задачи; другой
  сервер можно указать в параметрах задачи».

Карточка **«Tasks»** с per-task строками (`TaskConnectionRow`) из этого
раздела **уезжает** в параметры задачи (см. ниже). Здесь остаётся только
общий сервер — он как раз и является «общим» для всех внешних задач.

Таймауты (`connectionTimeoutMs`, `responseTimeoutMs`) остаются в этом же
разделе — они общие для обоих рантаймов.

`RuntimeSection` (снапшот/откат настроек окна) больше не снимает и не
восстанавливает `connectionMode`: глобального режима в UI нет. Снапшот
остаётся для `RuntimeInstaller.backend` и `selectedRelease`.

### Настройки → Модели

Таблица задач (`TaskModelsTable`) получает колонку **«Рантайм»** — в
каждой строке переключатель «Управляемый | Внешний» (он же в макете).

Колонки строки зависят от режима задачи:

- **managed** — как сегодня: профиль модели (комбобокс) + квантование
  (комбобокс) в колонке «Параметры».
- **external** — алиас модели (текстовое поле) в колонке «Модель», а в
  колонке «Параметры» — подпись «Общий сервер» (или адрес, если у задачи
  свой endpoint).

Текущий код прячет колонку квантования и показывает колонку имени по
**глобальному** `externalMode`; теперь решение per-row. Колонки таблицы
не исчезают целиком — они остаются на своих местах, чтобы колонки не
«прыгали» между строками; в строке заполняется только та часть, которая
относится к её режиму.

Над таблицей — счётчик «Локально: 3 · Внешний API: 1». Под таблицей —
строка «Внешний API получат данные задачи: «Исправление блока».» и
ссылка «Настроить рантаймы», ведущая в раздел «Рантайм».

**Попап задачи (⚙)** получает третью вкладку **«Подключение»**: endpoint,
API-ключ, алиас модели — то, что раньше жило в карточке «Tasks» раздела
«Рантайм» (`TaskConnectionRow` + `TaskEndpointForm`). Вкладка «Запуск»
(launch-параметры) показывается только для managed-задачи, вкладка «Запрос»
— всегда. Это то решение, которое принял пользователь: per-task настройки
внешнего сервера живут рядом с задачей.

Выбор режима в строке — часть черновика таблицы (`draft`), применяется на
Save, как остальные столбцы; Cancel откатывает его вместе с остальным
черновиком.

### Мастер первой установки

Выбор на первом шаге применяется **ко всем четырём задачам**
(`setRuntimeModeForAllRoles`) — так решил пользователь: сначала общий
выбор, потом каждая задача меняется отдельно в «Модели».

Шаги мастера, зависящие от режима, работают как сегодня: внешний режим →
шаг внешнего сервера, управляемый → шаг железа и загрузки моделей.

### Футер

Бейдж статуса рантайма: все задачи внешние → «External»; все управляемые →
текущий статус сервера (как сегодня); смешанный режим → «Смешанный» с
уточнением в подсказке (сколько задач локальных, сколько внешних).

Кнопка Start/Stop сервера видна, **только** когда есть хотя бы одна
управляемая задача: в полностью внешнем режиме сервера нет, и кнопка
вводила бы в заблуждение.

### Тесты

Новые:

- `SettingsStore`: per-task режим, миграция (глобальный режим разворачивается
  в четыре ключа один раз), `setRuntimeModeForAllRoles`, сброс к умолчаниям.
- `RuntimeController`: смешанный режим — задача с external идёт по внешнему
  пути, managed — поднимает сервер; `taskModelAvailable` зависит от режима
  задачи; смена режима сбрасывает кэш соединений; ручной старт берёт первую
  управляемую задачу.
- QML: колонка «Рантайм» в таблице задач, обе карточки раздела «Рантайм»,
  вкладка «Подключение» в попапе задачи.

Перевод существующих тестов с глобального режима на per-task:
`test_ensure_connection`, `test_settings_store`, `test_task_models_table_qml`,
`test_runtime_tab_external_qml`, `test_settings_window_qml`,
`test_footer_banner_qml`, `test_launch_tab_qml`, `test_setup_wizard_qml`.

## Ограничения и следствия

- Слоёная архитектура: `llocr_config` (`SettingsStore`), `llocr_runtime`
  (`RuntimeController`, `RuntimeLog`, `SelfTestController`), `llocr_app`
  (`AvailabilityPresenter`), QML; тесты линкуют те же таргеты (ADR 106).
- Управляемые задачи по-прежнему делят один локальный сервер: две
  управляемые задачи с разными моделями означают перезапуск сервера при
  переходе между ними. Это поведение уже есть (`beginRoleSwitch`) и не
  меняется — но в смешанном режиме оно видно пользователю чаще.
- Внешняя задача без алиаса модели недоступна (`taskModelAvailable` → false),
  и её флажок в «Проверке» гаснет — так же, как сегодня в глобальном
  внешнем режиме.
- Правило 6 AGENTS.md: размеры и шрифты — только `Theme.*`.
- Правило 7 AGENTS.md: комментарии только там, где без них не понять
  (миграция, per-task кэш, разделение источников логов).
- CI: `scripts/check.sh` — полный цикл; новые тесты регистрируются в
  `tests/CMakeLists.txt` с `TIMEOUT` (ADR 99).

## Что осталось билдеру

- Точные русские строки UI («Рантайм», «Управляемый», «Внешний», «Локально:
  %1 · Внешний API: %2») — по образцам соседних строк.
- Разбивка карточки «Внешний · общий сервер» на компоненты: сегодня общая
  часть лежит в `RuntimeTabExternal` вместе с per-task карточкой, которая
  уезжает — перенос разделяет файл на два.
- Порядок вывода карточек в разделе «Рантайм» (макет: управляемый сверху,
  внешний под ним) и поведение ссылки «К назначениям моделей →».
- Нумерация ADR — 318 и дальше, по текущему логу `docs/07-glossary.md`.
