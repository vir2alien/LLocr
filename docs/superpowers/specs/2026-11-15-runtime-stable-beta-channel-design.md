# Канал рантайма: стабильный по умолчанию, бета по выбору

Дата: 2026-11-15. Утверждено пользователем: подход 1 (канал как стратегия
загрузки), канал по умолчанию — **стабильный**.

## Замысел

llama.cpp вышел на версию 1.0: помимо привычных бета-сборок `b<N>`
(`prerelease: true`, десятки в день) публикуются стабильные релизы `v1.0.0`
(`prerelease: false`). Проверено по GitHub API 2026-11-15:

- стабильный релиз **не несёт бинарников** — один ассет `nightly-tag.txt`
  (7 байт) с текстом `b12359`; реальные сборки лежат в бета-релизе `b12359`;
- бет с момента `v1.0.0` уже ~60, поэтому стабильный релиз за пределами
  `releases?per_page=10` — окна, которое запрашивает LLocr, и «не видит» его
  структурно, а не эпизодически;
- если релиз всё же попал в список (вручную через страницу GitHub), установка
  падает с «No %1 build available for this platform in release %2»
  (`RuntimeInstaller.cpp`) — у релиза нет ассетов, которые ищет `pickAsset`;
- `extractBuildNumberFromTag("v1.0.0")` возвращает −1 («1.0.0» — не число),
  поэтому сравнение обновлений `latestBuild > cur` и сортировка на
  семвер-тегах не работают.

**Цель**: в окне «Модели» и в мастере первой установки выбирается канал
рантайма — «Стабильный» (по умолчанию) или «Бета»; на стабильном канале
программа сама резолвит `nightly-tag.txt` до бета-релиза с бинарниками и
ставит сборку `b12359`, показывая её как «v1.0.0 (b12359)».

**Не-цели**: выбор произвольного старого стабильного релиза (только последний;
старые — через страницу релизов GitHub); внешние эндпоинты (`docs/10`) не
затрагиваются; автообновление по расписанию; защита от «даунгрейда» (установка
более старого канала по явной кнопке разрешена — бейдж обновления просто не
загорается).

**Анти-цель**: смешение каналов в одном списке «Release» — бейдж «есть
обновление» и сравнение версий должны считать только релизы своего канала.

## Подходы

1. **Канал как стратегия загрузки (выбран).** Ключ `runtime/channel` в
   `QSettings`. Beta — текущий запрос `releases?per_page=10`. Stable —
   композиция из трёх запросов: `releases/latest` → чтение `nightly-tag.txt` →
   `releases/tags/<b-тег>`. `ReleaseInfo` собирается с `tagName = v1.0.0`,
   номером сборки от указанного бета-релиза и его ассетами (с дайджестами из
   API — ADR 212 продолжает работать). Кэш уже привязан к `sourceUrl`, каналы
   разойдутся сами. Минус: новый код фетча и композиции.
2. **Один запрос, разбор на клиенте** (`per_page=100`, делить по `prerelease`).
   Отклонён: тяжёлый запрос; резолва `nightly-tag.txt` всё равно не избежать;
   за пределами 100 бет (~2 дня) стабильный релиз выпадает из окна.
3. **Минимальный, без канала** — стабильный релиз закреплён сверху
   существующего комбобокса. Отклонён: каналы смешаны, бейдж обновления и
   сравнение версий неоднозначны, дефолт «стабильный» ничем не выражен.

## Дизайн

### Устойчивая идентичность сборки — b-номер

Установка остаётся помеченной b-номером (`out.build`, каталог
`llama.cpp-b12359-<backend>`): бинарники стабильного `v1.0.0` и беты
`b12359` идентичны, одинаковая нумерация даёт дедупликацию каталогов и
сквозное сравнение. `installedBuild()` в настройках продолжает хранить
`b12359`. Дополнительно сохраняется `runtime/installedTag` (`v1.0.0`) —
только для показа «v1.0.0 (b12359)» в списке установленных.

`ReleaseInfo::build` для стабильной композиции берётся от указанного
b-релиза; на чтении из кэша — резервное восстановление: если тег не
числовой (`v1.0.0`), номер берётся от первого бинарного ассета
(`parseAssetName` уже извлекает `b12359` из имени
`llama-b12359-bin-…`). Это правило живёт в `parseReleasesJson` и чинит
и живой фетч, и кэш.

### ReleaseCatalog

- `ReleaseInfo` получает флаг `prerelease` (поле `prerelease` из API;
  парсится в `parseReleasesJson`). **Бета-фетч отбрасывает записи с
  `prerelease == false`** до возврата и до записи кэша — иначе сразу после
  каждого будущего стабильного релиза он сутки возглавлял бы бета-список
  (пока не выйдут 10 новых бет): голова списка без бинарников, бейдж
  обновления ослеп (`build == −1` у v-тега). Составленный стабильный объект
  кэшируется с `"prerelease": false`, поэтому повторный парсинг кэша его
  сохраняет. Список `m_releases` всегда одноканальный.
- Новая статическая функция `fetchStableReleaseLocal(nam, cacheDir, error,
  timeoutMs, apiUrl = QString())` — симметрична `fetchReleasesLocal`
  (включая параметр `apiUrl` — шов для тестового мок-сервера):
  1. `GET releases/latest` → единственный объект релиза (не массив —
     парсинг отдельной функцией поверх `parseReleasesJson`);
  2. в его ассетах ищется `nightly-tag.txt`; содержимое (после обрезки
     пробелов — ожидаемая форма `b<N>`; иначе — ошибка «стабильный релиз не указывает
     на сборку») берётся через `browser_download_url`;
  3. `GET releases/tags/<тег>` → релиз с бинарниками; ассеты и дайджесты —
     его, `tagName`/`publishedAt`/`body` — стабильные;
  4. композиция кэшируется в тот же формат `{"sourceUrl": …, "releases":
     [собранный объект]}`;
  5. **фолбэк на бету (решение пользователя)**: если стабильный релиз не
     резолвится (404 на `releases/latest`, нет `nightly-tag.txt`, содержимое
     не `b<N>`, сеть недоступна и кэша нет), функция возвращает результат
     `fetchReleasesLocal` (список бет), а ошибка преобразуется в примечание
     «стабильный релиз недоступен — показаны беты». Мастер первой установки
     на дефолтном канале не упирается в тупик; пользователь ставит бету
     осознанно (примечание видно в статусе). Причина фолбэка не глушится —
     она попадает в статус.
- При любом шаге с ошибкой, когда кэш есть — прежнее поведение
  `failWithCache` (оффлайн-фолбэк на собранный кэш стабильного канала).
- Кэш TTL (6 ч), таймауты, заголовки — без изменений; три
  последовательных запроса укладываются в лимиты неаутентифицированного API.
- Ассеты без бинарников (`nightly-tag.txt`) у стабильного объекта
  отбрасываются на композиции — `pickAsset` их и так не выбирает, но
  чистый список избавляет `releaseLabel`/подсчёты от мусора.

### RuntimeInstaller

- `Q_PROPERTY(QString channel … NOTIFY channelChanged)`; чтение из
  `SettingsStore::runtimeChannel()` (по умолчанию `stable` —
  миграции нет: у существующих пользователей ключ отсутствует, они
  попадают на стабильный канал; их установленная бета просто не получает
  бейдж обновления, пока не выйдет более новый стабильный релиз).
- `setChannel` → сохранение в настройки, сброс `m_releases` и
  `m_selectedRelease`, рефetch каталога (если окно уже грузило список).
- `startCatalogFetch` выбирает стратегию по каналу: beta —
  `fetchReleasesLocal`, stable — `fetchStableReleaseLocal`.
- `releaseLabel(index)` для стабильного релиза показывает
  `v1.0.0 · 2026-11-13 (b12359)` — резолвнутый номер виден пользователю.
- Статус после загрузки каталога (его видит и мастер) содержит резолвнутый
  номер: `Latest release: v1.0.0 (b12359) (2026-11-13)`. На фолбэке —
  примечание «стабильный релиз недоступен — показаны беты» с причиной.
- `updateBuild()` возвращает `tagName` текущего канала; `recomputeHasUpdate`
  сравнивает числовые b-номера (у стабильного — резолвнутый номер), что
  покрывает оба канала одной логикой: у пользователя с бетой `b12400` на
  стабильном канале бейджа нет (12359 < 12400), при выходе `v1.0.1`
  (допустим, `b12500`) — есть.
- `installUpdate()` и мастер (`m_installAfterCatalog`) без изменений:
  ставят головной релиз канала.
- После установки на стабильном канале — `setInstalledTag("v1.0.0")`.

### Настройки

`SettingsStore`: ключи `runtime/channel` (значения `stable`/`beta`, дефолт
`stable`) и `runtime/installedTag` (строка, пусто = неизвестно) — по
образцу `runtimeBackend`/`installedBuild` (таблица значений по умолчанию,
геттер/сеттер с NOTIFY). `resetToDefaults()` сохраняет в списке
`preserved` и `runtime/installedTag`, и `runtime/channel` — наравне с
`installedBuild`/`runtimeBackend` (сброс схемы не должен молча возвращать
бета-пользователя на стабильный канал и не должен терять показ версии).
Секреты не затрагиваются (правило 8 AGENTS.md).

`installedTag` — **только для активной сборки** (список установленных
сканирует каталоги и показывает их b-теги; метка в файле каталога не нужна).
Правила очистки: установка через бета-канал очищает тег; установка через
стабильный канал ставит его; `activateBuild()` другой сборки очищает
(честная деградация показа до b-тега, переустановка со стабильного канала
возвращает метку). Установленная бета с меткой «v1.0.0» — неверный показ,
недопустим.

### QML

- `RuntimeTabInternal.qml`: в ряд установки перед «Backend» — комбобокс
  «Канал» (Стабильный/Бета), привязка к `RuntimeInstaller.channel`,
  `enabled: !busy`; смена канала перезагружает список (уже идёт через
  `onCatalogChanged`). Размеры — `Theme.*Size`, никаких захардкоженных
  значений (правило 6).
- Мастер (`Setup/StepCheck.qml`): без переключателя канала — первая
  установка идёт по дефолту (стабильный); QML мастера не меняется — он
  показывает `RuntimeInstaller.statusMessage`, который после загрузки
  каталога уже несёт резолвнутый номер (см. RuntimeInstaller).
- Список установленных сборок: где сохранён `installedTag` — показывает
  «v1.0.0 (b12359)».

### ServerCapabilities

Предположение (проверить при имплементации на реальном бинарнике):
`llama-server --version` стабильной ветки сохраняет `build: 12359` в
выводе — `extractBuildNumber` уже понимает эту форму; `buildAtLeast` при
неразбираемом теге не отказывает в старте (уже так). Изменений не ожидается.

### Ограничения

- Слоёная архитектура: изменения в `llocr_runtime` (`ReleaseCatalog`,
  `RuntimeInstaller`), `llocr_config` (`SettingsStore`), QML; связи тестов
  — через те же таргеты (ADR 106).
- Кэш-файл один (`releases.json`) на каталог кэша; два канала требуют
  разных каталогов кэша (или префикса имени файла) — иначе чтение чужого
  кэша отсечётся по `sourceUrl` и стабильный канал останется без оффлайн-фолбэка.
  Решение: каталог кэша на канал (`releases-stable/`, `releases-beta/`)
  на стороне `RuntimeInstaller`.
- CI: `scripts/check.sh` — полный цикл; новые тесты регистрируются в
  `tests/CMakeLists.txt` с `TIMEOUT` (ADR 99).

## Тесты

Шов: фетч-путь каталога разрешает `http://127.0.0.1` (loopback) —
`HttpClient::get` сейчас режет не-HTTPS (`allowInsecure=false` по умолчанию),
поэтому существующие тесты со `StatusServer` доходят только до пути отказа:
любая ошибка, включая отказ, приводит к `failWithCache`, и консервированный
ответ мока не парсится ни одним тестом. Каталог передаёт `allowInsecure`,
когда хост запроса — loopback (прод-URL всегда HTTPS, ослабления нет).
Заодно добавляется **успешный** тест бета-фетча (консервированное тело
действительно парсится) — существующие тесты остаются как есть.

- `test_release_catalog`: композиция стабильного релиза (v-тег + b-ассеты →
  `build = 12359`, резервное восстановление номера из имени ассета);
  парсинг `nightly-tag.txt` (пробелы/пустой/битый → ошибка); фетч по мок-HTTP
  (QTcpServer): наблюдение трёх запросов стабильного фетча, кэш-запись и
  чтение, оффлайн-фолбэк на собранный кэш, фолбэк на бету (404 → список
  бет + примечание), фильтр не-prerelease в бета-фетче (стабильный релиз
  в списке API не попадает в результат).
- `test_runtime_installer`: переключение канала сбрасывает список и
  рефетчит; `recomputeHasUpdate` на паре каналов (бета новее стабильного —
  бейджа нет; новый стабильный — бейдж есть); очистка/установка
  `installedTag` при установке и активации; сохранение тега и канала в
  `resetToDefaults()`; `TestSettingsIsolation` первым членом там, где нужен.
- Формат/линт: `scripts/check.sh` перед сдачей.

## Что осталось билдеру

- Точный текст русских строк UI («Канал», «Стабильный», «Бета») — по
  образцам соседних строк; подпись рекомендаций бэкенда не меняется.
- Размещение комбобокса канала в ряду установки (до «Backend»);
  поведение `LLOComboBox` при сбросе индекса — как у существующих боксов
  (sync из источника истины).
- Разбивка `fetchStableReleaseLocal` на вспомогательные функции — на
  усмотрение, при соблюдении стиля (правило 7: комментарии только в
  крайних случаях).
- Проверка фактического вывода `--version` у стабильного бинарника
  (предположение выше) — зафиксировать в тесте мока, если форма иная.
