# Реворк MD-редактора: WYSIWYG через Vditor в существующем WebEngine

Дата: 2026-11-08. Статус: черновик на ревью. На реализацию — ADR в `07-glossary.md` по обычному правилу.

## Замысел

Сегодня текст страницы редактируется сырым markdown (plain `TextArea`,
`WorkPanel.qml:145`), а рендер живёт на отдельной вкладке «Предпросмотр»
(`MarkdownPreview.qml`: `WebEngineView` + marked + DOMPurify + KaTeX,
полный re-parse всей страницы на каждый пуш, дебаунс 250 мс, только чтение).
Проверка распознанного формируется по паре «взгляд туда-сюда»: правка — в
сыром тексте, проверка рендера — на другой вкладке.

Цель: **один WYSIWYG-редактор в духе Typora/MarkText** — правишь сразу по
рендеру, синтаксис скрыт, формулы и таблицы видны. Заодно уходит главный
источник латентности при вводе: полный re-parse всей страницы на каждый
пуш (в блочном редакторе патчится только изменённый блок).

Движок остаётся веб (исследование показало: MarkText/Muya сами веб —
snabbdom vdom в браузере; «как MarkText, но не веб» не существует). Выигрыш
даёт не смена движка, а инкрементальность и объединение редактора с
превью. Полностью нативный путь (QTextDocument markdown) отвергнут: он не
рендерит LaTeX вообще, а формулы в этом приложении — контент первого
класса; остальные причины см. «Рассмотренные подходы».

## Цели

1. WYSIWYG-редактирование текста страницы: заголовки, списки, жирный/
   курсив, таблицы, код, **рендер формул `$$…$$` / `$…$`** (KaTeX) прямо
   в редакторе.
2. Ввод без полного перепарса страницы (инкрементальный патч блока).
3. Вкладка «Текст (MD)» — существующий raw `TextArea` — сохраняется без
   изменений: tap-to-block («тап по тексту → рамка») и подсветка
   диапазона блока работают там ровно как сегодня; WYSIWYG становится
   новой вкладкой на месте «Предпросмотр».
4. Вся существующая семантика редактирования сохраняется: эхо-гвард,
   `PageEditStore`/«Отменить правки», отложенная подгрузка фоновых
   перестроек до ухода фокуса (ADR 190), `markPageEdited` только по
   факту правки, запрет дублирования текста другой страницы.
5. Оффлайн: никаких обращений к сети (сейчас CSP `default-src 'none'`
   в `preview.html` — уровень сохраняется).

## Не-цели (в этой итерации)

- Замена экспорта: HTML/PDF остаются на headless `QWebEnginePage` +
  текущем JS-конвейере (ADR 63) — не трогаются.
- Отказ от WebEngine в UI (Chromium остаётся; RAM/старт не улучшаются).
- Приложение уровня Daino/Notion: блок-перетаскивания, канбан, вложенные
  произвольные блоки.
- Рендер Mermaid/ECharts/диаграмм (не отключаем в сборке, но и не
  вендорим — контент их не производит).
- Ориентация на короткие страницы OCR здесь не гарантия: страницы могут
  быть большими (сотни блоков, base64-кропы) — деградация по ним
  приемлема, но не катастрофична.

## Анти-цели (что сделает итерацию провалом)

- Потеря рендера формул в редакторе (иначе смысл WYSIWYG для OCR-контента
  теряется).
- Ложные «Изменено» страницы от одной нормализации markdown при открытии
  без правок.
- Сеть или внешние CDN в рантайме.
- Регрессия «Отменить правки» / edited-флагов / mergePipelineChange.

## Ограничения

- Стек менять нельзя (AGENTS.md): Qt6/C++/QML, CMake, слоёная архитектура.
- UI не ходит в сеть/файлы напрямую — всё через контроллер.
- Ресурсы без JS-сборки: текущие бандлы (`marked.min.js`, `katex.min.js`)
  коммитятся готовыми файлами; Vditor должен подключаться так же —
  готовый `dist`, без node-инструментария в проекте.
- Секреты/настройки не при делах; `Theme.*Size`/`Theme.*` для всего, что
  попадает в QML (в самом веб-контенте — свои CSS-переменные, как сейчас).
- Windows: только MSVC (MinGW не поддерживается — WebEngine, ADR 54) —
  не меняется, WebEngine остаётся.

## Рассмотренные подходы

| | **A. Vditor в существующем WebEngineView** (выбран) | **B. Нативный QTextDocument WYSIWYG** | **C. Нативный + формулы-картинки** |
|---|---|---|---|
| WYSIWYG | Настоящий, Typora-style | Базовый | Базовый + формулы |
| Формулы | KaTeX в редакторе | ❌ сырой текст | Предрендер в SVG |
| Скорость ввода | Инкрементальный патч | Мгновенно | Мгновенно |
| RAM/старт | как сегодня | −150–300 МБ | как B |
| Экспорт | не трогаем | всё равно WebEngine (ADR 63) | всё равно WebEngine |
| Зависимость | 1 готовый dist-бандл | нет | KaTeX-рендер + custom QTextObject |
| Ключевой риск | вес бандла, WASM из qrc | потеря математики, round-trip QTBUG-123133, rowspan | самая дорогая работа |

Muya отброшен: репозиторий архивирован 29.05.2026, API объявлен
нестабильным, «не рекомендован для продакшена». Milkdown отброшен по
инфраструктуре: требует JS-сборку (Vite/ProseMirror-плагины), а в проекте
принципиально нет node-тулчейна. Vditor: MIT, живой (B3log/СиYuan),
`mathBlockPreview` рендерит математику прямо в wysiwyg/ir, UMD-дистрибутив
подключается тегом как текущие `marked.min.js`, `sanitize` по умолчанию
включён, 12 языков UI.

## Решённые части дизайна

### 1. Компонент

- Новый `src/qml/MainWindow/MarkdownEditor.qml` — `WebEngineView`
  (наследует каркас `MarkdownPreview.qml`: тот же URL-фильтр, подавление
  контекстного меню, баннер ошибки загрузки), грузит `qrc:/editor/editor.html`.
- В `WorkPanel.qml` вкладка «Предпросмотр» заменяется вкладкой WYSIWYG
  (`MarkdownEditor`); вкладка «Текст (MD)» — существующий plain `TextArea`
  — **сохраняется без изменений**: tap-to-block, подсветка диапазона
  блока, undo и отложенная подгрузка работают в ней ровно как сегодня.
  Старый `MarkdownPreview.qml` остаётся в дереве как основа экспортного
  конвейера (его QML никто не лоадит).
- Сегментированный переключатель становится «Текст (MD) | WYSIWYG».

### 2. Вендоринг и CSP

- `resources/editor/` (qrc-префикс `/editor`, регистрация в
  `src/CMakeLists.txt` рядом с `/preview`): `editor.html`, `editor.js`
  (наш мост), `vditor/index.min.js`, `vditor/index.css`, **и весь набор
  cdn-ассетов**: `lute/lute.min.js` (WASM-движок markdown), `katex/`
  (js+css+fonts), `highlight/`. Опция `cdn` в конфиге Vditor указывает на
  `qrc:/editor/vditor/` — так гасится единственный найденный риск «тяжёлые
  рендереры по умолчанию тянутся с unpkg.com».
- CSP `editor.html`: разрешены только `'self'` + `data:` для картинок +
  `wasm-unsafe-eval` (нужен Lute/WASM). Никакой сети.
- Ожидаемый вес ресурсов: ~6–10 МБ (Lute WASM ~2 МБ, KaTeX+fonts ~1 МБ,
  highlight, сам бандл). Приемлемо: в бинарнике и так 700+ КБ превью.
- Резервный путь, если WASM из qrc не заводится (fetch/`application/wasm`
  mime из qrc): раскладывать ассеты на диск рядом с бинарём и грузить
  `file://` с `localContentCanAccessFileUrls` — решение фиксируется в
  первой стадии плана.

### 3. Поток данных

Вход (модель → редактор):
- QML-свойство `markdown` → дебаунс-таймер (как сегодня 250 мс) →
  `runJavaScript("pushPage(<json md>, <json theme>)")`.
- Кропы: ссылка `![alt](image://ocr/crop/<N>)` переписывается в data-URL
  **существующим** `AppController::encodePreviewMarkdown` (кэш по
  image/crop-revision сохраняется). Обратная подмена при вычитке — по
  той же карте (data-URL → `image://ocr/crop/<N>`), неизвестные data-URL
  проходят как есть.
- **Два варианта одного документа**: raw-вкладка редактирует модельный
  текст с `image://ocr/crop/<N>` (компактный, совместимый с позициями
  блоков — как сегодня); WYSIWYG-вкладка получает переписанный вариант с
  data-URL и возвращает его же. Переключатель вкладок: при входе в
  WYSIWYG сначала флашатся незакоммиченные правки raw-вкладки (та же
  семантика, что blur сегодня), затем запрашивается закодированный
  вариант; при выходе TextArea перепривязывается к модельному тексту
  (вычитка из WYSIWYG его уже обновила).
- Фоновые перестройки (`applyPageTextChanged`, mergePipelineChange):
  страница не в фокусе → `setValue` сразу; в фокусе → отложить до blur
  (та же семантика `pendingReload`, что в `WorkPanel.qml:160–195`).

Выход (редактор → модель):
- JS → QML: `QWebChannel` (объект-мост `EditorBridge`, `qwebchannel.js` из
  `qrc:///qtwebchannel/`); событие `input` Vditor → троттлинг ~300 мс →
  `bridge.textChanged(markdown)`. Это первое событие из веба в QML в
  приложении (сегодня превью только читает).
- QML → `Controller.setCurrentPageText(...)` — существующий путь целиком:
  echo-гвард, `PageEditStore::reset`, запрет дублей, `markPageEdited`.
- **Нормализация без правки**: `getValue()` Vditor может нормализовать
  markdown (форматирование списков, экранирование) без фактической правки
  пользователем. При пуше кэшируется «эталон» `V(value(modelText))` —
  markdown, пропущенный через ту же нормализацию; если пришедший текст
  совпадает с эталоном, запись и `markPageEdited` не выполняются. Без
  этого анти-цель «ложное Изменено» гарантированно пробивается.
- Ревёрс-маппинг data-URL выполняется до сравнения/записи.
- **Решено: принять нормализацию при правке.** Первая фактическая правка
  в WYSIWYG сохраняет всю страницу в lute-нормализованном виде — в том
  числе нетронутые блоки. Осознанные последствия: якоря
  `mergePipelineChange` (ADR 190) и поиск по тексту блока в raw-вкладке
  могут после этого чаще не находить совпадений. Проверка-гейт первой
  стадии плана: дифф вычитки против модельного текста на реальных
  страницах (OCR_TEST); если нормализация нетронутых машинных блоков
  оказывается нетождественной, по-блочная запись через якоря блоков
  становится этапом v2 (запасной путь описан, сразу не строится).

### 4. Режимы

- Веб-компонент живёт только в режиме `wysiwyg` Vditor; переключатели
  режимов самого Vditor отключены (`ir`/`sv` не используются).
- Тулбар Vditor ограничивается (`toolbar`-конфиг): undo/redo и форматные
  кнопки первой необходимости; всё остальное (embed, диаграммы,
  переключатели режимов, экспортные кнопки Vditor) исключено.
- «Текст (MD)» — это существующая raw-вкладка QML, а не режим Vditor:
  tap-to-block (`boxIndexForTextPosition`) и подсветка диапазона блока
  работают там без изменений.
- Линковка блоков с рамками в WYSIWYG — полноправная функция, в обе
  стороны. Таблица соответствия box→блок строится в C++ при пуше из тех
  же данных, что собирают текст страницы (порядок блоков
  `renderPageText`); DOM-блоки помечаются атрибутами. Клик по блоку в
  редакторе → `bridge.blockClicked(index)` → выбор рамки на канвасе;
  выбор рамки на канвасе → `bridge.highlightBlock(index)` + scroll into
  view. После правок соответствие перестраивается по текущим блокам с
  поиском по тексту блока — деградация той же природы, что у
  сегодняшнего поиска в raw-вкладке (после серьёзных правок часть
  блоков перестаёт подсвечиваться), не хуже существующего поведения.

### 5. Тема и шрифты

- `theme: 'classic' | 'dark'` + `setTheme` на смену `Theme.dark`;
  цвета поверхности/текста передаются как сейчас (`bgColor`/`fgColor`) и
  маппятся в CSS-переменные контента (как делает `preview.js:18–33`).
- Типографика контента в редакторе выравнивается на `preview.html`
  (тот же системный стек и размеры) — заодно закрывается найденное
  расхождение «шрифт превью ≠ шрифт UI». Кегли/отступы — числами в CSS
  редактора, зеркалят `Theme`-лестницу; расхождение с px-лестницей (ADR
  293) осознанное: веб-контент живёт в своём масштабе, как превью сегодня.

### 6. Экспорт

Не трогается: `export.html`/`export.js` и headless `ExportRenderer`
продолжают использовать текущий конвейер marked+KaTeX. Ресурсы `/preview`
остаются в дереве. Унификация CSS редактора/превью/экспорта — отдельно
после стабилизации.

### 7. Undo/Revert

- Внутри WYSIWYG-вкладки — собственный undo-стек Vditor; raw-вкладка —
  стандартный TextArea-стек, как сегодня.
- Кнопка «Отменить правки» панели продолжает работать по `PageEditStore`
  без изменений: `revertCurrentPageEdits` кладёт baseline-текст, пушится
  в редактор.

## Что осталось билдеру

- Точная структура `editor.html`/`editor.js` и моста (имена, JSON-схема
  сообщений, обработка ошибок канала).
- Разрезка тулбара Vditor (какой минимальный набор кнопок) и placeholder.
- Порядок стадий и тесты (см. план; e2e-поведение WebEngine в юнит-тестах
  не тестируем — тестируем QML-обвязку/контроллер, ручная приёмка
  остаётся за пользователем, как принято в проекте).
- Локаль Vditor: ru в списке 12 языков отсутствует → либо патч словаря
  i18n, либо английские подсказки тулбара (решение билдера, не критично).

## Открытые риски

1. **WASM из qrc** — если fetch `lute.min.js`/wasm-компиляция из qrc не
   заработает, переключаемся на disk-layout (см. §2). Проверяется первой
   стадией.
2. **Вес бандла** ~6–10 МБ ресурсов — осознанно принято.
3. **Крупные data-URL** в каждом `getValue` (мегабайты base64) — троттлинг
   вычитки; при проблемах — второй риск-митигейт: регистрация
   `QWebEngineUrlScheme` для `image://ocr/…`, чтобы кропы отдавались
   схемой без base64 (за рамками v1).
4. **Нормализация lute** может расходиться с `rebuildPageText` на
   экзотике (вложенные списки) — эталон-сравнение из §3 гасит ложные
   правки; принятая запись нормализованного текста (§3) может ослабить
   якоря `mergePipelineChange` — гейтится эмпирическим диффом первой
   стадии, запасной путь — по-блочная запись v2.
