# Порядок блоков: новый блок занимает своё место в тексте страницы

Дата: 2026-11-12. Утверждено пользователем: правило вставки — «освободившееся место +
геометрия по полосам»; объём — только новые блоки (без действия «пересортировать»).

## Замысел

Текст страницы — производная величина: `renderPageText` склеивает блоки **в порядке
списка** (ADR 296). Модель разметки (MinerU) отдаёт блоки уже в порядке чтения, поэтому
после разметки порядок списка совпадает с порядком чтения и текст страницы собран
правильно.

Нарисованный пользователем блок в этот список **добавляется в конец**
(`src/app/AppController.cpp:1173` — `boxes.append(box)`). Поэтому его распознанный текст
и стоит в конце текста страницы, в конце WYSIWYG-документа и в конце экспорта — хотя
сам блок нарисован посередине. Распознавание при этом не виновато: кроп берётся по
индексу блока, результат пишется в тот же блок (`applyRecognitionToBox` →
`applyBoxTransition`), текст попадает именно туда, куда надо. Расходится именно
**место блока в списке**.

Второй сценарий — тот же самый: удалить существующий блок и нарисовать новый на его
месте — даёт тот же результат, потому что новый блок опять оказывается последним в
списке, а не на месте удалённого.

**Цель**: блок, нарисованный пользователем, занимает в списке то место, которое
занимает его положение на странице; его распознанный текст появляется в тексте
страницы на этом месте, а не в конце.

**Не-цели**: переупорядочивание уже существующих блоков (их порядок приходит от
модели разметки и он в порядке чтения); распознавание; ручная перестановка блоков
вверх/вниз в редакторе (она есть и остаётся); определение колонок страницы (отложено,
см. «Ограничения»).

## Правило

Новый блок `N` (прямоугольник в координатах страницы, 0..1) вставляется в список
блоков страницы на позицию, которая вычисляется двумя шагами.

### Шаг 1 — освободившееся место

Удаление блока оставляет **слот** — его прежнее место в списке и его прямоугольник.
Слоты живут на странице (`QHash<int, QList<FreeSlot>>` по индексу страницы), переживают
переключение страниц и накапливаются.

Слот подходит новому блоку, если площадь пересечения прямоугольников не меньше половины
площади **меньшего** из двух прямоугольников (слота и `N`). Среди подходящих выбирается
тот, у которого доля пересечения больше; при равенстве — с меньшим индексом. Тогда
новый блок встаёт **на индекс слота**, слот снимается.

Мерка «меньшего прямоугольника» вместо «прямоугольника слота» — чтобы одинаково
работать в обе стороны: маленький блок, нарисованный на месте большой удалённой
таблицы, и большой блок, нарисованный поверх маленького удалённого.

### Шаг 2 — геометрия по полосам

Если подходящего слота нет, место вычисляется по геометрии.

1. **Колонка блока.** Выбираются блоки, у которых горизонтальное пересечение с `N` не
   меньше половины ширины меньшего из двух прямоугольников. Это блоки той же колонки.
   Если таких нет (блок перекрывает «жёлоб» или ни с чем не пересекается по X) — за
   кандидатов берутся все блоки страницы.
2. **Полоса.** По кандидатам в порядке списка ищется первый блок `B`, который лежит
   **после** `N`:

   - `B.top ≥ N.bottom − ε` — блок целиком ниже `N`;
   - либо вертикальные полосы `B` и `N` пересекаются и `B.left ≥ N.right − ε` — блок
     правее `N` в одной полосе.

   `ε = 0.005` (полпроцента страницы) — допуск на округление координат.

   Первый такой блок — точка вставки: новый блок встаёт **перед ним**. Если такого
   блока нет — новый блок встаёт **после последнего кандидата** (а если кандидатов не
   было вовсе — в конец списка).

Порядок списка при этом не меняется: ни один существующий блок не двигается, меняется
только позиция вставки.

Шаг 2 с ограничением кандидатов своей колонкой — это тот же «сверху вниз, в одной
полосе слева направо», но в пределах колонки, в которой нарисован блок. На
одноколоночной странице колонка — это вся страница, и правило совпадает с
общестраничным. На двухколоночной странице (порядок чтения — колонка за колонкой)
новый блок в левой колонке встаёт после последнего блока этой колонки, а не в конец
страницы, — иначе он снова оказался бы в хвосте.

### Индексы слотов при изменении списка

Индекс слота — это позиция в списке, и список меняется:

- **удаление** блока с индекса `i`: новый слот `{i, rect удалённого}`; индексы слотов
  больше `i` уменьшаются на единицу;
- **вставка** блока на индекс `k`: индексы слотов не меньше `k` увеличиваются на
  единицу;
- **перемещение** блока `from → to`: индекс слота пересчитывается тем же правилом, что и
  индексы блоков (`remapIndexAfterMove`);
- **разметка страницы заново** (модель вернула новые блоки): слоты страницы
  сбрасываются — они описывают места старой разметки.

Слоты — временная подсказка интерфейса, в файл проекта они не пишутся.

## Что меняется в коде

### `src/core/BlockPlacement.h` / `.cpp` (новый слой `core`)

Чистые функции без QObject — по правилам слоёв `core` ничего выше себя не знает:

```cpp
struct FreeSlot { int index = -1; QRectF rect; };

struct Placement { int index = 0; int slot = -1; };

Placement placementFor(const QList<BoundingBox> &boxes, const QRectF &rect, const QList<FreeSlot> &slots);
QList<FreeSlot> slotsAfterRemoval(const QList<FreeSlot> &slots, int removedIndex, const QRectF &removedRect);
QList<FreeSlot> slotsAfterPlacement(const QList<FreeSlot> &slots, const Placement &placement);
QList<FreeSlot> slotsAfterMove(const QList<FreeSlot> &slots, int from, int to);
```

`placementFor` выполняет оба шага: слот (с его правилом совпадения) и геометрию. В
результате — не только индекс вставки, но и номер занятого слота: вызывающий снимает
его со списка и сдвигает остальные.

### `src/app/AppController.h` / `.cpp`

- новое поле `QHash<int, QList<core::FreeSlot>> m_freeSlots;` — слоты по страницам;
- `addBlockAt` — вместо `boxes.append(box)` вставка на вычисленный индекс
  (`boxes.insert(index, box)`), выбор нового блока на этом индексе, обновление модели
  блоков;
- `removeBlock` — запись слота освободившегося места, пересчёт индексов остальных
  слотов;
- `moveBlock` — пересчёт индексов слотов;
- разметка страницы — сброс слотов этой страницы.

### `src/app/BoxListModel.h` / `.cpp`

`insertBox(int row, const BoundingBox &box)` с `beginInsertRows`/`endInsertRows` — как
уже сделано для `removeBox` и `moveBox`, чтобы полотно не пересобиралось целиком при
добавлении блока. Если модель разошлась со списком (число строк не совпадает с числом
блоков), остаётся прежнее полное обновление `updateBoxesForCurrent()`.

## Что остаётся неизменным

- **Порядок существующих блоков** не меняется: правило меняет только позицию вставки.
- **Распознавание** не трогаем: кроп по индексу, результат в тот же блок — как есть.
- **Ручная перестановка** (кнопки вверх/вниз в редакторе) работает как раньше.
- **Текст страницы** остаётся производной от списка блоков (ADR 296): правило не
  трогает рендер, оно меняет только состав и порядок списка.

## Согласованность индексов

В списке индекс блока — это его адрес в модели блоков, в тексте страницы (ordinal'ы
диапазонов `BlockTextRange`), в ссылках на кропы `image://ocr/crop/N` и в
`blockBoxMap` редактора. Поэтому после вставки:

- **текст страницы пересобирается** (`refreshPageDocument`) — ссылки на кропы получают
  новые индексы, и экспорт (`Exporter::referencedCrops` → `croppedImage`) разрешает их
  по тому же списку: ссылка `image://ocr/crop/0` указывает на первый блок и после
  вставки;
- **редактор** получает новый join через существующую цепочку push (текст страницы →
  raw-вкладка → `requestEditorMarkdown` → `editorMarkdownReady` → `pushDocument`): при
  вставке в середину порядок блоков в WYSIWYG-документе меняется сам, без ручной
  перестановки;
- **`m_editorCropRefs`** (карта «data: URI → компактная ссылка») пересобирается на
  каждой выдаче — устаревших ссылок не остаётся;
- **выделение** переносится на вставленный блок (`selectedBoxIndex` = индекс вставки);
- **очереди блоков** (распознавание, проверка, правка, чтение) держат задачи парами
  `{страница, индекс}`. Структурные изменения и так запрещены на время прогона
  (`checkBusy()` в `addBlockAt`/`removeBlock`/`moveBlock`), поэтому сдвиг индексов не
  может попасть под работающую очередь. Этот инвариант сохраняется.

## Ограничения

- **Многоколоночные страницы**: правило «колонка + полоса» работает для колонок, чей
  x-диапазон пересекается; блок, нарисованный точно в «жёлоб» между колонками, попадёт
  в общий перебор и встанет по общему правилу (может оказаться не там). Определение
  колонок по вертикальным промежуткам — отдельная задача, отложена.
- **Блок, нарисованный поверх существующего** (без удаления): правило ставит его
  относительно перекрытого блока; если перекрытие не оставляет сомнений, место
  определяется по геометрии, иначе остаётся ручная перестановка.
- **Порядок от модели разметки** не проверяется: если разметка вернула блоки не в
  порядке чтения, приложение их не переставляет (это за рамками задачи).

## Тесты

**`tests/test_block_placement.cpp`** (новый) — чистые правила:

- вставка выше первого блока → индекс 0; между двумя → их середина; ниже всех → конец;
- та же полоса: левее первого → перед ним; правее последнего → после него;
- двухколоночная страница: блок в левой колонке → после блоков этой колонки, а не в
  конец; блок в правой колонке → после левой колонки;
- слот: пересечение ≥ половины меньшего прямоугольника → индекс слота; без пересечения
  → геометрическое правило; при нескольких слотах выбирается лучший;
- пересчёт индексов слотов: удаление, вставка, перемещение.

**`tests/test_app_import.cpp`** — поведение приложения:

- нарисованный посередине блок: его текст оказывается между текстами соседей в тексте
  страницы (порядок проверяется по позициям подстрок, а не по наличию);
- удаление блока и рисование нового поверх него: текст нового блока занимает место
  удалённого в тексте страницы;
- ссылки на кропы после вставки в середину остаются верными: `image://ocr/crop/0`
  разрешается в кроп первого блока (проверка через экспорт/кроп, а не только по
  строке);
- существующие тесты `drawnBlockReachesThePageTextOnAMarkupPage` и
  `drawnBlockReachesThePageTextAfterARemoval` — ожидания индексов обновляются под новое
  правило (сейчас они утверждают индекс «в конце списка»).

## Отношение к ADR

Новый ADR 310 дополняет существующие: ADR 296 (документ = join блоков) задаёт, что порядок
текста — это порядок списка; ADR 92 (удаление блока) и ADR 189 (блоки на канвасе) —
про операции со списком. ADR 310 уточняет, где в списке появляется блок, нарисованный
пользователем.
