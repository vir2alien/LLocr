# Внешний рантайм: шесть задач и безопасное хранение ключей

> План (октябрь 2026). Постановка: во внешнем рантайме заданы не все роли —
> нужны те же шесть задач, что и во внутреннем (ADR 215), и для каждой — свой
> эндпоинт, свой API-ключ и свой алиас; API-ключи должны храниться безопасно.
> Документ описывает реализацию; кодирование начинается после утверждения.

## 1. Что нужно

1. **Шесть задач во внешнем рантайме** — те же, что и во внутреннем:
   `pageOcr` (распознавание с разметкой), `rawPageOcr` (распознавание без
   разметки), `blockRecognition` (распознавание блока), `layout` (разметка),
   `decision` (проверка), `fix` (исправление).
2. **У каждой задачи — свой эндпоинт, свой API-ключ и свой алиас** (имя модели
   на стороне сервера).
3. **API-ключи — в системном хранилище секретов**, а не открытым текстом в
   `QSettings`. Это закрывает отложенное H.5 / ADR 48.

## 2. Что есть сейчас

| Что | Где | Сейчас |
|-----|-----|--------|
| Роли задач | `core/ConnectionRole.h` | шесть ролей, список — единственный источник (ADR 215) |
| Эндпоинт | `provider/baseUrl` (`SettingsStore`) | **один на всё приложение** |
| API-ключ | `provider/apiKey` (`SettingsStore`) | **один на всё приложение**, открытым текстом в `QSettings` |
| Алиас | `model/name`, `tasks/<role>/modelName` | **уже по задачам** (ADR 216) |
| Разрешение подключения | `RuntimeController::resolveExternal(role)` | берёт общий URL + общий ключ + алиас роли |
| Путь запроса | `LlamaClient::endpointUrl(baseUrl, path)` | путь фиксирован протоколом: `/v1/chat/completions`, для `decision` — `/v1/systemone` |

То есть **алиас по задачам уже есть**, а вот эндпоинт и ключ — общие на все
шесть. Именно это и нужно развести.

## 3. Целевая модель

### 3.1 Что и где хранится

**Открытые данные — в `QSettings` (как сейчас):**

| Ключ | Что это |
|------|---------|
| `provider/baseUrl` | общий базовый URL — значение по умолчанию для всех задач |
| `tasks/<role>/baseUrl` | базовый URL конкретной задачи; **пусто → берётся общий** |
| `model/name`, `tasks/<role>/modelName` | алиас (имя модели) задачи — уже есть |

**Секреты — в системном хранилище секретов, в `QSettings` их больше нет:**

| Идентификатор секрета | Что это |
|-----------------------|---------|
| `provider/apiKey` | общий API-ключ (миграция со старого `provider/apiKey`) |
| `provider/apiKey/<role>` | API-ключ конкретной задачи |
| `hf/token` | токен Hugging Face (ADR 48 называл его вторым; переносим тем же механизмом — см. §4.3) |

Ключ `provider/apiKey` из `QSettings` **удаляется** после переноса (см. §4.3).

### 3.2 Правило разрешения (одно место — `RuntimeController::resolveExternal`)

```
эндпоинт(роль) = tasks/<role>/baseUrl  ?:  provider/baseUrl
алиас(роль)   = tasks/<role>/modelName
ключ(роль)     = секрет(provider/apiKey/<role>)  ?:  секрет(provider/apiKey)
```

Правило «пусто → общий» читается в интерфейсе буквально: пустая ячейка
эндпоинта в поле-подсказке показывает общий URL, пустая ячейка ключа —
«используется общий ключ». Обратного правила нет: задача не может получить
общий ключ, если у неё свой.

Путь запроса остаётся частью протокола и не настраивается: `/v1/chat/completions`
для всех задач, `/v1/systemone` для проверки. Провайдер с нестандартным
префиксом выражается самим базовым URL (`https://api.example.com/openai` →
`https://api.example.com/openai/v1/chat/completions`).

### 3.3 Почему «общий + переопределение», а не «только по задачам»

У пользователя часто один сервер на все задачи (сейчас так и есть). Если
требовать шесть заполненных эндпоинтов, то обычный случай превращается в
рутину. Общее значение + необязательное переопределение даёт оба случая и
сохраняет текущие настройки без миграции: старый `provider/baseUrl` становится
общим, а задачи с пустым переопределением работают как раньше.

## 4. Хранение секретов

### 4.1 API

Новый класс `src/config/SecretStore.h` (слой `llocr_config` — это хранилище,
рядом с настройками):

```cpp
class SecretStore {
public:
    static QString backendName();            // "macOS Keychain" / "Windows Credential Manager"
                                             // / "Secret Service" / "" (нет)
    static bool isAvailable();               // системное хранилище пригодно
    static bool exists(const QString &id);
    static bool read(const QString &id, QString *value);
    static bool write(const QString &id, const QString &value);   // false = система отказала
    static bool remove(const QString &id);
    static bool readFirst(const QStringList &ids, QString *value); // «свой ключ, иначе общий»
    static QString lastError();
    static void forgetAllCached();
};
```

Один интерфейс — четыре реализации (общая + три платформенные). Секрет
идентифицируется строкой; конкретное хранилище решает платформенный код.

### 4.2 Бэкенды

| Платформа | API | Детали |
|-----------|-----|--------|
| macOS | Security.framework: `SecItemAdd` / `SecItemCopyMatching` / `SecItemDelete`, `kSecClassGenericPassword` | сервис `org.llocr.app`, аккаунт — идентификатор секрета; `kSecAttrAccessibleWhenUnlocked` |
| Windows | Credential Manager: `CredWriteW` / `CredReadW` / `CredDeleteW`, `CRED_TYPE_GENERIC` | имя цели `LLocr:<id>`, `CRED_PERSIST_LOCAL_MACHINE` (per-user, переживает перезагрузку), блоб — UTF-8; ссылка `advapi32` |
| Linux | Secret Service API поверх D-Bus (`org.freedesktop.secrets`) через `Qt6::DBus` | `OpenSession("plain")` → `CreateItem`/`SearchItems` → `Unlock` → `GetSecret`; нужен запущенный keyring (gnome-keyring, KWallet) |

Зависимостей не добавляем: только системные API и `Qt6::DBus` (только Linux,
`find_package(Qt6 COMPONENTS DBus)` под Linux). Qt своего хранилища секретов
не имеет, а `QtKeychain` — сторонняя библиотека, которую пришлось бы тащить
в сборку.

### 4.3 Миграция

`SettingsStore::applyStartupMigration()` (уже есть точка входа):

1. В `QSettings` есть непустой `provider/apiKey`:
   - системное хранилище доступно → записать секрет `provider/apiKey`,
     **удалить** ключ из `QSettings`, сообщить в статус: «ключ перенесён в
     системное хранилище»;
   - хранилище недоступно → ключ **останется** в `QSettings` (данные не
     уничтожаем), а интерфейс честно скажет, что он всё ещё лежит открытым
     текстом.
2. То же для `hf/token` → секрет `hf/token`.
3. Ключ, уже лежащий в системном хранилище, в `QSettings` не возвращается
   никогда.

### 4.4 Если системного хранилища нет

Тогда ключ **не сохраняется вовсе** и живёт только в памяти до перезапуска
приложения; интерфейс говорит об этом прямо («системное хранилище секретов
недоступно — ключ будет сохранён только до перезапуска»). Вариант «зашифровать
файл своим ключом» сознательно **не делаем**: Qt не умеет AES, а самодельная
реализация шифра — это ровно тот «фальшивый уровень защиты», от которого
проект отказался в ADR 212 («нет дайджеста — нет установки»): лучше честно
сказать «не сохранено», чем сделать вид, что сохранено.

### 4.5 Потоки

Чтение из хранилища может **заблокировать** интерфейс (запертая связка
ключей macOS спрашивает пользователя; Secret Service — это поход в D-Bus).
Поэтому чтение ключа выполняется **вне GUI-потока**, а результат возвращается
в GUI-поток (тот же приём, что в `runChatExchange` — `QtConcurrent::run` +
`QFutureWatcher`).

Кэш в памяти на время сессии: ключ читается один раз и переиспользуется до
изменения (запись/удаление сбрасывают кэш). Пока приложение работает, ключ всё
равно лежит в памяти процесса (в `ConnectionConfig`) — это та же граница
доверия, что и у любого приложения, читающего свой ключ.

## 5. Интерфейс

### 5.1 Настройки → Рантайм → внешний сервер

Нынешняя форма (три поля модели + общий URL + общий ключ) заменяется на:

```
Режим подключения              [Внешний сервер ▾]
Таймаут подключения (мс) [5000]   Время ожидания ответа (мс) [600000]

Общий сервер — значение по умолчанию для всех задач
  Базовый URL   [http://localhost:8080                    ]
  API-ключ      [••••••••••••]  [Заменить] [Удалить]
                ключ хранится в системном хранилище (macOS Keychain)

Задачи
  Задача                 │ Эндпоинт              │ API-ключ │ Алиас модели
  Распознавание          │ [http://localhost:…]  │ [••••]   │ [Unlimited-OCR]
  с разметкой            │                       │          │
  Распознавание без      │                       │          │
  разметки               │                       │          │
  Распознавание блока    │                       │          │
  Разметка               │                       │          │
  Проверка               │                       │          │
  Исправление            │                       │          │
                                  [Сбросить переопределения]
```

Правила, видимые в интерфейсе:

- **Пустой эндпоинт задачи = общий эндпоинт** (в подсказке поля — общий URL).
- **Пустой ключ задачи = общий ключ.**
- **Алиас** — тот же ключ `tasks/<role>/modelName`, который уже редактируется.
- **Показ ключа:** сохранённый ключ **никогда не показывается** — в поле
  маска `••••`, рядом «Заменить» и «Удалить». Введённый (ещё не сохранённый)
  ключ можно показать чекбоксом «Показать», как сейчас. Это поведение
  GitHub/AWS/Vercel: секрет не выводится обратно, его заменяют.
- Названия кнопок называют действие (правка → «Сохранить», удаление →
  «Удалить»), а не «применить» — по устойчивому правилу интерфейса проекта.

### 5.2 Окно «Модели» (внешний режим)

Сейчас в таблице моделей во внешнем режиме есть редактируемое поле «имя
модели» — это **тот же** алиас, что и в настройках рантайма. Два редактора
одного значения — источник расхождений. Поэтому:

- **владельцем алиаса становится вкладка «Внешний сервер»** (там, где
  задаётся подключение: эндпоинт + ключ + алиас);
- в окне «Модели» ячейка алиаса в внешнем режиме становится **только для
  чтения** с подсказкой «изменяется в Настройках → Рантайм».

Профиль модели (выбор в выпадающем списке) и квантование в окне «Модели»
остаются как есть — это другое свойство.

### 5.3 Мастер настройки (шаг «Внешний сервер»)

Шаг мастера показывает **только общий эндпоинт и общий ключ** (быстрый старт);
таблица по задачам — в настройках. Для этого `RuntimeTabExternal` получает
свойство `compact`.

### 5.4 Локализация

Новые строки — через `qsTr()`; `resources/i18n/llocr_ru.ts` обновляется
(`lupdate`).

1. **`SecretStore`**: общий класс + три бэкенда + CMake + `test_secret_store`.

3. **Разрешение подключения**: `RuntimeController` — эндпоинт/алиас/ключ по

5. **Тесты и документация**: тесты выше, ADR 226/227, правка ADR 48, обновление

Каждый этап оставляет приложение собираемым; после каждого — `scripts/check.sh`.

## 9. Риски

| Риск | Что делаем |
|------|-----------|
| Запертая связка ключей macOS блокирует чтение | чтение вне GUI-потока; при отмене пользователем — понятная ошибка, а не зависание |
| Нет keyring-демона на Linux | ключ только в памяти, интерфейс говорит об этом прямо (§4.4) |
| Перенос старого ключа ломает работу | миграция идемпотентна; при недоступном хранилище старый ключ не трогаем |
| Ключ утекает в лог | ключ не попадает ни в один лог и ни в одну команду приложения (правило §7.6 сохраняется); в тестах — проверка, что значение ключа не встречается в выводе |
| Два редактора одного алиаса | владелец один — вкладка внешнего сервера; в окне «Модели» ячейка только для чтения |

## 10. Решения, которые нужно утвердить

1. **Модель эндпоинтов:** общий эндпоинт + необязательное переопределение по
   задачам (пусто = общий). *Рекомендация: так* — один сервер остаётся в один
   клик, шесть разных серверов тоже возможны.
2. **Алиас редактируется в «Настройки → Рантайм»**, в окне «Модели» он
   только для чтения. *Рекомендация: так* — у значения один владелец.
3. **Без системного хранилища ключ не сохраняется вовсе** (только память до
   перезапуска), зашифрованного файла нет. *Рекомендация: так* — честно, без
   самодельной криптографии.
4. **Токен Hugging Face (`hf/token`) переезжает в то же хранилище** в этом же
   заходе. *Рекомендация: да* — ADR 48 называл оба секрета, оставлять один
   открытым текстом бессмысленно. Читателей у него всего два.
5. **Путь запроса остаётся частью протокола** (`/v1/chat/completions`,
   `/v1/systemone`) и не настраивается. *Рекомендация: так* — нестандартный
   префикс провайдера выражается базовым URL.

## 11. Что получилось (октябрь 2026)

Реализовано по этому плану; ниже — что в коде отличается от плана и почему.

**Сделано как в плане:**

- `src/config/SecretStore.{h,cpp}` + три бэкенда: `SecretStore_mac.cpp`
  (Security.framework, C API — без Objective-C), `SecretStore_win.cpp`
  (Credential Manager), `SecretStore_linux.cpp` (Secret Service поверх D-Bus,
  `Qt6::DBus` только на Linux). Новых зависимостей нет.
- `SettingsStore`: ключи `tasks/<role>/baseUrl`, `apiKeyForRole` /
  `setApiKeyForRole` / `apiKeySetForRole`, `effectiveBaseUrlForRole`,
  миграция `provider/apiKey` и `hf/token` при старте, очистка секретов при
  сбросе настроек.
- `RuntimeController::resolveExternal` — эндпоинт задачи (с откатом на общий)
  и её алиас; ключ приходит из хранилища.
- Интерфейс: вкладка «Внешний сервер» (общий сервер + таблица шести задач),
  поле ключа `Common/SecretKeyField.qml` (маска, «Показать», «Удалить»),
  строка задачи `Settings/TaskConnectionRow.qml`, компактный режим в шаге
  мастера, окно настроек шире (860 px).
- Окно «Модели»: ячейка алиаса в внешнем режиме только для чтения, алиас
  больше не пишется оттуда.
- Переводы `resources/i18n/llocr_ru.ts` (12 новых строк), ADR 226 и 227,
  правка ADR 48, `docs/01-overview.md`, `docs/04-components.md`,
  `docs/05-roadmap.md`, `AGENTS.md` (правило 8 — секреты не в `QSettings`).

**Отличия от плана:**

1. **Внешнее разрешение стало асинхронным** (ADR 26 требовал синхронного).
   Причина — сам смысл: чтение связки ключей может заблокировать (запертая
   связка macOS спрашивает пользователя), а план обещал чтение вне GUI-потока.
   Первое разрешение по роли читает ключ в воркере и отдаёт ответ в
   GUI-поток; следующие разрешения берут готовую связь из кэша
   (`m_resolvedCache`, который сбрасывается при любом изменении настроек).
   Тест переписан: `externalResolvesWithItsOwnEndpointKeyAndAlias` ждёт
   ответа и проверяет, что второй вызов отвечает сразу.
2. **Пространство имён секретов — общее для процесса**
   (`SettingsStore::setSecretNamespace`), а не свойство экземпляра: тестам
   нужен свой namespace, иначе тест писал бы в связку ключей самого
   приложения. `tests/testsettings.h` ставит `llocr-test/` и убирает за собой
   оставленные секреты.
3. **Секреты процесса живут в кэше `SecretStore`**: значение читается из
   системы один раз и держится в памяти до выхода из приложения; если система
   отказала в записи, значение остаётся в этом же кэше — до перезапуска. Пра-
   вило «свой ключ задачи, иначе общий» живёт в `SecretStore::readFirst`, а
   воркер читает по **идентификаторам** (`SettingsStore::secretIdsForRole`):
   он не касается объекта настроек, поэтому его безопасно читать из фонового
   потока в любой момент жизни приложения.
4. **Строки таблицы перезагружаются и сохраняются сами** по счётчику
   (`reloadToken` / `commitToken`): элемент `Repeater` для линтера — обычный
   `QQuickItem`, и вкладка не может вызвать метод строки по имени.
5. **Кнопка «Удалить» у ключа всегда на месте**, но выключена, когда ключа
   нет: иначе ширина строки прыгала бы в момент сохранения ключа.
6. **Запасного хранилища с собственным шифром нет** — как и в плане: ключ
   живёт в памяти до закрытия приложения, и интерфейс говорит об этом.
7. **Ключ не показывается обратно**: поле показывает маску, введённый ключ
   можно показать чекбоксом «Показать» (он ещё не сохранён).

## 12. Что получилось: разбор четырёх проблем внешнего рантайма (октябрь 2026)

Четыре жалобы на внешний сервер (omlx, `http://127.0.0.1:8000`) разобраны
замерами: каждый замер снят тем запросом, каким шлёт приложение
(`scripts/probe-ocr-reply.py` для OCR, `curl` для System One и fix), и
сверен с baseline'ом llama.cpp.

1. **Пустой журнал.** Не дефект omlx: у внешнего сервера нет процесса, вывод
   которого можно прочитать, — журнал окна показывал пустоту. Теперь след
   ведёт клиент (`core/RequestJournal`): по записи на каждый HTTP-вызов —
   адрес, модель, размеры, статус, время и начало ответа; окно журнала во
   внешнем режиме показывает его (ADR 228). След в памяти: страница — это
   документ пользователя. API-ключ в след не попадает.
2. **Транслит русского (MinerU).** Не дефект приложения и не omlx: сырой
   ответ модели уже транслитом («Полное Термунесское солоТиБлене
   ИлЛинДрческОй»). Та же страница через llama.cpp (GGUF) и через
   `GLM-OCR-bf16` (тоже mlx-community) читается верно, текстовый запрос к
   MLX-сборке отвечает тем же транслитом — сломана MLX-конверсия
   `MinerU2.5-2509-1.2B-bf16` (токенизация кириллицы). Записано в
   `docs/24-mineru.md` (§7).
3. **d3-mini: «Unprocessable Entity», «body -> model: Field required».**
   Дефект приложения: тело System One собиралось из `state`, `images` и
   `questions` — без `model`, а протокол это поле требует (llama.cpp: имя
   загруженной модели или её алиас; сервер-роутер использует его для
   маршрутизации). Теперь алиас едет в теле (ADR 229); правка — в
   `docs/21-d3.md` (§6), где было написано обратное.
4. **fix-модель gemma-4: «В ответе нет вариантов».** Причина найдена и
   воспроизведена: запрос не помещался в окно сервера (16384) — приложение
   его не знало и отправляло `max_tokens` блока-таблицы (8192) плюс промпт;
   omlx в таком случае **выгружает модель и обрывает запрос**, отвечая
   **HTTP 200** телом `{"error": {"message": "Request aborted because model
   '…' is being unloaded"}}` — **без `choices`**. Приложение читало такой
   ответ как «нет вариантов». Исправлено двумя правилами: окно сервера
   читается из `/v1/models` и бюджет ответа обрезается под него (ADR 231), а
   ответ без ответа называет причину — «сервер ответил ошибкой: …» вместо
   «В ответе нет вариантов» (ADR 230). Отдельно: `reasoning_budget_tokens`
   (ADR 193) читает llama.cpp, а omlx его игнорирует — мысли съедают весь
   `max_tokens`, и ответ приходит без `content` (`finish_reason: length`).
   Задача fix в такой ситуации спрашивает ещё раз, без размышлений, и
   говорит об этом в подвале; следующие запросы к тому же серверу идут без
   мыслей сразу.

Дополнительно: бюджет ответа во внешнем режиме считается от окна сервера —
оно публикуется в `/v1/models` (`max_model_len`) и теперь читается при
разрешении подключения (ADR 231). Без этого правило ADR 193 («мысли уступают
место ответу») во внешнем режиме не работало: окно было неизвестно, и мысли
забирали весь бюджет.

## 13. Ключ не применяется: связка принадлежит той сборке, что его записала

Симптом: пользователь вводит ключ в «Настройки → Рантайм → Внешний», выходит
из настроек, и сервер отвечает `401 {"error":{"message":"API key required"}}` —
то есть запрос уходит **без** заголовка `Authorization`.

Замеры (на машине пользователя):

| что | результат |
| --- | --- |
| элемент в связке | есть: `org.llocr.app` / `provider/apiKey`, создан прежней ad-hoc-сборкой (`cdat 12:59`, `mdat 16:56`) |
| чтение чужого бинарника | `security find-generic-password -w` **зависает** на запросе подтверждения — элемент привязан к коду, который его создал |
| идентичность прежней сборки | `cdhash H"30284915…"` (ad-hoc) |
| идентичность текущей сборки | `identifier llocr and certificate leaf = H"9c022c3b…"` (сертификат «LLocr Dev», ADR 232) |
| ответ сервера без ключа | `401 API key required` |

Две разные идентичности кода — значит, элемент связки текущей сборке не
достаётся: чтение либо ждёт подтверждения, либо отказывает. Приложение при
этом отправляло запрос без ключа, а пользователь видел только текст сервера:
ни слова о том, что ключ лежит в связке и недоступен.

Что сделано (ADR 233):

1. **Вид отказа.** Хранилище различает `NotFound` (ключа просто нет — серверу
   без авторизации он не нужен, запрос уходит) и `Refused` (элемент есть, но
   не отдаётся — запрос **не уходит**, а статус называет причину и способ:
   ответить на запрос связки «Always Allow» или удалить элемент в «Связке
   ключей» и ввести ключ заново).
2. **Причина едет с подключением.** Раньше она жила в `thread_local`-переменной
   и снималась в рабочем потоке запроса — до интерфейса не доходила никогда.
   Теперь вид отказа и его текст возвращаются из рабочего потока и кладутся в
   `ResolvedConnection::error`.
3. **401 переводится своими словами:** «сервер отказал в запросе (HTTP 401):
   ключ не отправлен или не принят», а текст сервера остаётся в сообщении.
4. **Вкладка «Внешний» показывает причину** (`Settings.refreshSecretState()`),
   а удаление ключа, которому связка отказала, сообщает об отказе, а не молчит.

Разовые действия пользователя: ответить на запрос связки «Always Allow» (элемент
перепривязывается на сертификат, и с этого момента ключ переживает любые
пересборки) — либо удалить элемент `org.llocr.app` / `provider/apiKey` в
«Связке ключей» и ввести ключ заново в подписанной сборке.
