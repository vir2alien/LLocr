# 11. Авто-режим: конвейер «разметка → распознавание → проверка → исправление → проверка»

> Английский оригинал: [docs/11-auto-pipeline.md](11-auto-pipeline.md)
>
> Что делает кнопка «Авто-проход» в группе «Целевые страницы» шапки, как
> устроен конвейер и почему он разбит на этапы. Решение — ADR 257.

## 1. Что это

Кнопка «Авто-проход» в группе «Целевые страницы» (ADR 256; до того —
заглушка) запускает **авто-прогон**: полный цикл обработки выбранных
страниц без участия оператора. Область — страницы, выбранные в ленте
миниатюр; пустое выделение означает весь документ (поле диапазона рядом
с кнопкой формулирует этот выбор словами).

Прогон состоит из пяти этапов:

| # | Этап | Задача | Что делает |
|---|-------|------|--------------|
| 1 | **Разметка** | `layout` | Находит блоки на странице. У блоков ещё нет текста. |
| 2 | **Распознавание блоков** | `blockRecognition` | Транскрибирует каждый блок: кроп → текст. |
| 3 | **Проверка** | `decision` | Судит блоки, **включённые в настройках проверки** (и подозреваемых на дубликаты): соответствует ли текст изображению. |
| 4 | **Исправление** | `fix` | Отправляет проблемные блоки (Mismatch, Review) универсальной модели: OK / FIX / REVIEW. |
| 5 | **Проверка исправленного** | `decision` | Судит **исправленный** слой: верна ли коррекция. |

Прогон идёт **по этапам, а не по страницам**: сначала размечаются все
страницы, затем распознаются все, затем проверяются, затем исправляются,
затем проверяются снова. Причина — цена переключения модели (ADR 252):
управляемый llama-server держит одну загруженную модель, и переход между
задачами (`layout` → `blockRecognition` → `decision` → `fix`) её
перезагружает. Прогон по страницам давал бы 4 переключения модели на
страницу вместо 4 на документ.

## 2. Граница этапа

Этап — это объект с одним контрактом (`src/app/AutoPipelineStage.h`):

```cpp
class AutoPipelineStage : public QObject
{
    Q_OBJECT
public:
    using Scope = QList<int>;

    AutoPipelineStage(QString title, QObject *parent = nullptr);

    QString title() const;

    // Empty — the stage can run; otherwise — why it is skipped.
    virtual QString skipReason(const Scope &pages) const = 0;
    // Start the work; the end — the finished() signal, an early refusal — failed().
    virtual void start(const Scope &pages) = 0;
    virtual void stop() = 0;
    virtual int progressDone() const { return 0; }
    virtual int progressTotal() const { return 0; }

signals:
    void finished();
    void failed(const StatusMessage &message);
};
```

Три свойства контракта:

* **Этап ничего не знает о соседях.** Разметка не знает о проверке,
  проверка не знает об исправлении. Единственная связь — сигнал
  `finished()`.
* **Этап сам говорит, может ли он работать.** `skipReason()` возвращает
  пустую строку, когда этап готов, иначе причину («нет модели для этой
  задачи», «нечего распознавать»). Причина уходит в футер: пользователь
  видит, что было пропущено и почему.
* **Этап умеет останавливаться.** `stop()` гасит текущую работу; конвейер
  дальше не идёт.

Конвейер (`src/app/AutoPipelineController.h`) держит **список этапов** и
проходит его по порядку:

```cpp
m_autoPipeline->setStages({
    m_autoMarkupStage,        // 1
    m_autoRecognitionStage,   // 2
    m_autoVerificationStage,  // 3
    m_autoFixStage,           // 4
    m_autoRecheckStage,       // 5 — the same AutoVerificationStage, another title
});
```

Добавить этап — значит добавить класс и одну строку в этот список.
Ни оркестратор, ни фасад, ни QML не меняются.

## 3. Семантика отказа и пропуска

| Случай | Что происходит |
|------|--------------|
| Этап не может работать (нет модели, нечего делать) | Этап пропускается, причина уходит в футер, прогон продолжается. |
| Модель ответила ошибкой на отдельном блоке | Очередь помечает блок и переходит к следующему — так уже работают ручные очереди. Прогон не падает. |
| Этап не удался целиком | Причина уходит в футер, прогон переходит к следующему этапу. |
| Пользователь нажал стоп | Текущий этап гаснет, следующие не запускаются. |

Финальная строка футера перечисляет, что было пропущено и почему. Это
решение за пользователя: прогон, дошедший до конца с двумя пропущенными
этапами, полезнее прогона, остановившегося на первом «нет модели».

## 4. Что делает этап «проверка исправленного»

Это **тот же** этап проверки, что и этап 3, — отдельного кода для него
нет. Разделение происходит при наборе блоков: очередь берёт блоки, чей
**эффективный слой** (ADR 164) не имеет вердикта.

* До исправления эффективный слой — текст OCR: когда у текста есть вердикт
  (Ok / Mismatch), блок уже отвечён и в пятом этапе не участвует.
* Исправление кладёт исправленный текст в слой коррекции и **сбрасывает
  его вердикт** (`BoxTransitions::fixApplied`): слой коррекции становится
  эффективным, и блок снова «без вердикта» — именно его судит пятый этап.
* Блок, который исправление не смогло прочитать (REVIEW), получает
  `correctedCheckStatus = Review` — он отвечён и ждёт оператора; пятый
  этап его не трогает.

Поэтому пятый этап — это ровно тот же вызов `checkPagesEnabledBlocks(pages)`,
что и третий: сборщик сам находит «блоки без вердикта на эффективном
слое».

## 5. Интерфейс

Кнопка **«Авто-проход»** (группа «Целевые страницы» шапки):

* неактивна, когда нет документа, нет модели разметки или распознавания
  (`Controller.autoPipelineAvailable`) или выполняется другая работа
  (`pipelineIdle`);
* превращается в кнопку остановки во время прогона — тот же приём, что
  у кнопок «Разметить», «Проверить» и «Исправить»;
* спрашивает перед запуском, когда в области есть результаты: разметка
  заменяет блоки и тексты страниц.

**Статусная строка в футере** (`TaskStatus.qml`) показывает текущий этап
и его прогресс: `Auto 3/5: Verification 12 / 40`. Пустой прогресс (у
разметки он по страницам, у проверки — по элементам) показывается без
чисел. Между этапами заголовок пуст — строка показывает только
`Auto 3/5`.

## 6. Место для будущих моделей

Требование: «разные блоки распознаются разными моделями» должно стать
возможным без переписывания конвейера.

Ограничение рантайма: **одна задача — одна модель**. `ConnectionRole`
(`core/ConnectionRole.h`) — слот модели, и переключение роли перезагружает
сервер. Поэтому «разные блоки — разные модели» в терминах приложения — это
**разные задачи**, а не разные модели внутри одной задачи.

Что к этому уже готово:

1. **Этап — единица работы.** Дополнительная задача = дополнительный этап
   в списке. Оркестратор, фасад и QML не меняются.
2. **Набор блоков отделён от исполнения.** `BlockWorkList` собирает списки
   (`unrecognizedBlocks`, `enabledBlocks`, `fixableBlocks`), а очереди ролей
   исполняют их (`RecheckQueue::run`, `DecisionQueue::run`,
   `RemedyQueue::runFix` — ADR 286). Этап сам решает, какие блоки идут в
   какой прогон.
3. **Фильтр типов блоков.** Сборщики принимают опциональный фильтр типов:
   сегодня он пуст (все типы), завтра этап задачи выдал бы фильтр «эти
   типы — мои». Фильтр — это
   `std::function<bool(const QString &blockType)>`.

Чтобы добавить «формулы распознаёт модель A, текст — модель B», нужно:
добавить новую задачу в `core/ConnectionRole.h` и в профили моделей,
добавить таблицу «тип блока → задача» в настройки и добавить этап, который
набирает свои блоки с фильтром и запускает очередь дважды — по разу на
задачу. Ни одна существующая строка конвейера не меняется.

## 7. Цена прогона

* **Переключения модели.** Управляемый сервер перезагружает модель на
  границе задач: `layout` → `blockRecognition` → `decision` → `fix` →
  `decision`. Это 4–5 перезагрузок за прогон. Внешний рантайм (ADR 226)
  не перезагружает ничего: у каждой задачи там свой адрес.
* **Внешний рантайм.** У каждой задачи свой эндпоинт, ключ и алиас модели
  (ADR 226) — прогон идёт через те же этапы, переключаясь между адресами.
* **Время.** Этапы 3 и 5 судят каждый блок отдельным запросом; на тяжёлом
  документе это самая долгая часть.

## 9. Решения

1. **Прогон идёт по этапам, а не по страницам** — цена переключения
   модели.
2. **Отказ этапа не роняет прогон** — причины собираются и показываются
   в футере.
3. **Нет модели — этап пропускается**, а не блокирует запуск.
4. **Разметка всегда с нуля** (с подтверждением): прогон — полный цикл.
5. **Пятый этап — тот же этап проверки**: сборщик сам находит блоки без
   вердикта на эффективном слое.
6. **Граница модульности — контракт этапа**, а не набор кнопок.

## 10. Что оставлено намеренно

Отложено сознательно (следующий шаг, а не дефект):

* **Разные модели для разных типов блоков.** Шов готов (набор отделён от
  исполнения в `BlockWorkList`, фильтр типов), но новой задаче всё ещё
  нужна своя очередь: новая задача в `core/ConnectionRole.h` + новая
  очередь + новый этап.
* **Дублирование в этапах очереди.** Три этапа очереди повторяют хвост из
  connect/stop/progress друг друга: закрытая база убрала бы это. (Сами
  сборщики свернулись в `BlockWorkList`, а двойной набор
  `skipReason`/`start` исчез — список причины кэшируется, ADR 286.)
* **Экспорт не закрыт конвейером.** Кнопка экспорта не учитывает этап
  разметки (ручная разметка ведёт себя так же), поэтому полусобранный
  снимок можно экспортировать во время прогона. Сохранение проекта
  закрыто.
* **Вторая разметка после остановки.** Повторный проход разметки (для
  повёрнутой страницы) стартует даже после того, как прогон был остановлен.
* **Подсказки позиций (location) в `resources/i18n/llocr_ru.ts`**
  расходятся с `lupdate` по всему файлу (давнее расхождение, не следствие
  авто-режима); поиск идёт по контексту и тексту, а `lrelease` собирает
  файл.
* **Цена прогона на настоящих моделях не измерена** — все тесты идут через
  mock-сервер, где нет перезагрузки модели.
