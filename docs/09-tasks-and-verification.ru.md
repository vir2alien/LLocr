## 1. Четыре задачи

Каждый профиль модели объявляет, какие задачи он обслуживает
(`roles.<task>`); те же строковые идентификаторы проходят через
`ConnectionRole`, настройки (`tasks/<task>/…`) и QML. Список живёт в одном
месте — `src/core/ConnectionRole.h` (ADR 215, 252).

| Идентификатор задачи | Название в UI | Что делает |
|---|---|---|
| `layout` | Разметка | Разметка страницы: модель возвращает позиционированные блоки без текста |
| `blockRecognition` | Распознавание блока | OCR одного кропа блока (простая транскрипция) |
| `decision` | Проверка | Бинарный вердикт «текст соответствует изображению» — визуальный дифф |
| `fix` | Исправление блока | Универсальная модель подтверждает / исправляет / отказывает кандидату |

Каждая из четырёх задач называет **свой рантайм** (ADR 318): ключ
`tasks/<role>/runtimeMode` говорит, работает задача на локальном
llama-server (`managed`) или на своём внешнем эндпоинте (`external`).
Управляемые задачи делят **один** llama-server, и модель (пере)загружается
при переключении задачи (`RuntimeController::serverRunsRole`). Распознавание
и проверка взаимоисключающие на уровне `AppController`, поэтому переключение
никогда не убьёт запущенную работу.

Что нужно задаче, следует из её рантайма, и оба вердикта — по задаче:

| Рантайм задачи | Что нужно задаче | Кто говорит |
|---|---|---|
| `managed` | её модель на диске (файл из профиля запуска задачи) | `taskModelAvailable(role)` |
| `external` | её алиас модели — имя, под которым сервер знает модель | `taskModelAvailable(role)` |

`roleConfigError(role)` спрашивает то же самое словами: внешнюю задачу вовсе
не спрашивают про локальный сервер, а управляемой без собственной модели
отказывают с «Модель разметки не выбрана» / «Модель decision не выбрана» /
… — по задаче. **Глобальная** проверка мягче: конфигурация корректна, когда
каждая заданная управляемая модель лежит на диске и хотя бы одна управляемая
задача имеет модель (ADR 319) — управляемая задача без собственной модели
берёт модель работающего сервера. Если управляемых задач нет вовсе, то нет и
сервера: кнопка Start/Stop скрыта, а ручной старт отказывает.

**Самопроверка** бьёт по управляемой задаче: по задаче распознавания, когда
она управляемая, иначе по первой управляемой задаче в каноническом порядке
(`RuntimeController::selfTestRole()`); если управляемых задач нет, она
отказывает.

Однопроходные страничные задачи `pageOcr` / `rawPageOcr` вырезаны (ADR 252) —
текст страницы собирается из распознавания блоков, после ручной разметки
(`layout`) либо модельного прохода разметки.

### Кроп, который видит модель (ADR 287)

Блочные задачи отправляют кроп бокса блока, вырезанный из рендера страницы
(300 DPI для PDF). Перед кодированием в запрос политика роли модели может
перемасштабировать его (`src/models/CropScaling.{h,cpp}`):

- **ступень кегля** (fix/read): `cropGlyphHeightByBlock` сопоставляет меткам
  блоков целевой кегль — измеренную высоту букв кропа. Кроп с меньшими
  буквами растягивается, только вверх; метки вне карты проходят без
  изменений. Комплектные роли fix qwen3.5 ставят 32 px для
  `equation`/`formula`: на кегле ~18 px (кроп 300 DPI) мелкая печать теряет
  акценты (чёрту над τ), при 32 px читается чисто.
- **бюджет vision-токенов** (blockRecognition): `cropMaxVisionTokens`
  ограничивает оценку prompt-токенов кропа; превышение сжимается, пока не
  поместится. mineru ставит 3072 — плотная таблица в разрешении страницы
  переполнила бы слот, обрезанный сервером до `n_ctx_train`.

Обе ступени — данные профиля: роль без этих полей отправляет кроп ровно как
раньше, а decision/layout не затронуты.

## 2. Матрица «модель → задачи»

В `resources/profiles/models/` поставляется восемь профилей; вырезанные
профили живут в `archive/models/profiles/` (ADR 251). Ровно один профиль на
задачу несёт `"default": true` — он питает автовыбор (ADR 169).

| Профиль | Задачи | Дефолт для |
|---|---|---|
| `mineru.json` | layout, blockRecognition | layout, blockRecognition |
| `glm-ocr.json` | blockRecognition | — |
| `minicpm-jev.json` | decision | decision |
| `qwen3.5-4b.json` | fix | fix |
| `qwen3.5-9b.json` | fix | — |
| `gemma-4-e4b.json` | fix | — |
| `gemma-4-12b.json` | fix | — |
| `gemma-4-26b-a4b.json` | fix | — |

Принцип: **OCR-модели только распознают, decision только проверяет,
универсальные модели только исправляют.** Профиль никогда не сочетает
несовместимые задачи. Руководства по моделям: `docs/13-model-mineru.md`,
`docs/14-model-glm-ocr.md`, `docs/17-model-minicpm-jev.md`,
`docs/15-model-gemma-4.md`, `docs/16-model-qwen3.5.md`.

## 3. Два слоя текста (ADR 164)

Каждый текстовый блок несёт два независимых слоя:

- **text** — `box.text`, результат OCR; любой результат распознавания
  (страница, блок, повторное распознавание, чтение) попадает сюда и
  **стирает** коррекцию и оба вердикта;
- **correction** — `box.correctedText`, вывод fix-модели.

**Эффективный текст** — коррекция, когда она есть, иначе текст. Каждый слой
несёт собственный вердикт (`checkStatus`/`confidence` против
`correctedCheckStatus`/`correctedConfidence`). Автоматического переноса
коррекции в текст нет: экспорт, пересборка текста страницы и предпросмотр
всегда используют эффективный текст. Повтор исправления/чтения (ADR 291)
стирает слой коррекции намеренно (`BoxTransitions::correctionReverted`)
прямо перед повторной отправкой блока — кандидатом исправителя снова
становится распознанный текст. Переходы — чистые функции в
`src/core/BoxTransitions.*`, покрытые `test_box_transitions`.

## 4. Протокол исправления (`full_block`, ADR 181/192)

Запрос к fix-модели (собирается в `src/models/FixModel.cpp`):

- `system` = общий контракт исправления
  (`resources/profiles/requests/fix-requests.json`);
- `user` = `[промпт типа блока, кандидат, image]` — кандидат в рамке
  `OCR candidate:\n<CANDIDATE>\n…\n</CANDIDATE>`; сохранённая коррекция
  повторно не отправляется, кандидат — собственный эффективный текст блока;
- каждый параметр профиля запроса задачи уходит в тело как поле верхнего
  уровня (`VisionChatModel::buildRoot`) — кроме стоп-слов в запросе с
  рассуждениями (ADR 332).

Контракт выражен явно (ADR 333). Системный промпт называет ширину правки — «один
символ, или последовательность символов, или целое слово — и ничего больше»,
каждое изменение видно на картинке, — и правила вокруг него: ничего не
добавляется, чего нет на картинке, и ни одна неоднозначность не разрешается
угадыванием; буква, нарисованная одинаково в двух алфавитах, сама по себе не
ошибка (алфавит кандидата сохраняется, если только картинка отчётливо не
показывает другой); разметка, которой нет у кандидата, не добавляется (префикс
заголовка Markdown, кодовая ограда, маркер списка, разделитель таблицы).
Триггеры REVIEW перечислены: символ, который надо исправить, обрезан кропом,
закрыт, перекрыт, выцвел или слишком мелк, чтобы его разобрать, — либо
кандидат пуст. Промпт типа несёт четыре части: `Correct:` — что здесь можно
исправить, `Leave:` — что остаётся как у кандидата, `Never:` — чего
исправление делать не должно, и указание ответа.

Ответ — ровно один из:

- `OK` — исправлять нечего; блок сохраняет свои байты;
- `FIX` + **полный исправленный блок** — `FixDiffGate` сравнивает его
  с кандидатом: эквивалентные (переиначенные) блоки сохраняют собственные
  байты кандидата; пустой ответ, `FIX none` или ответ, обрезанный бюджетом
  токенов (`finish_reason: length`), понижается до REVIEW; всё остальное
  попадает в Review как отклонение;
- `REVIEW` — изображение нечитаемо/повреждено; красный статус, коррекция
  не сохраняется.

Fix-модель может сначала подумать: профиль объявляет `reasoning: true`,
бюджет — глобальная настройка `check/fixReasoningBudgetTokens`,
подставляемая в каждый запрос (ADR 193/268), а `RequestBudget` при обрезке
жертвует рассуждениями раньше ответа.

## 5. Протокол чтения (`read_block`, ADR 259–267, 331)

Те же fix-модели обслуживают задачу чтения («Распознать (LLM)») по другому
контракту: запрос — это ровно изображение, системный промпт и промпт блока —
**распознанный текст не передаётся никогда**. Ответ **и есть текст блока**:
читатель пишет блок по картинке, а собственный вердикт у него один —
`REVIEW` (блок прочитать не удалось). Вердикт протокола правки (`OK`) текстом
блока не является и попадает в Review с причиной; ответ, где ключевое слово
`FIX` ещё осталось (профиль с формулировкой до ADR 331), теряет это слово и
сохраняет блок (ADR 331). Гейт тот же — `FixDiffGate`, поэтому чтение,
воспроизведшее текст, сохраняет байты блока и снимает устаревший Mismatch.
Исходы — собственные статусы `Read` / `ReadFixed` / `ReadDamaged`; прогон
заканчивается своей сводкой
(«Прочитано блоков: переписано — N, подтверждено — M, не прочитано — K»).
Тексты промптов живут в `resources/profiles/requests/read-requests.json`;
fix-роль может их переопределить (`readSystemPrompt`/`readBlockPrompts`) —
ни одна поставляемая модель этого не делает, за всех отвечает общий читатель
(ADR 267). Семейство, у которого была своя формулировка, — пара Qwen3-VL —
вырезано (ADR 335); её профиль с формулировкой лежит в архиве.

Контракт выражен явно и здесь (ADR 334). Системный промпт называет оси
сохранения (алфавит, регистр, начертание, положение, пробелы, переносы по
слогам, переводы строк и абзацев, парность скобок), правило тождественных
начертаний (буква, нарисованная одинаково в двух алфавитах, — не другая
буква: сохраняется алфавит документа), правило недобавления (ничего не
добавлять, ничего не дополнять, что не прочитано целиком) и правило
артефактов сканера (артефакты, просвечивание с оборота и знаки, которые не
текст, — игнорируются). Разделители формул — канонические: формула в строке
между `\(` и `\)`, формула в отдельной строке между `\[` и `\]`, никогда `$`
или `$$`. Триггеры REVIEW те же пять, что и в контракте исправления, —
обрезано, закрыто, перекрыто, выцвело, слишком мелко для разбора, — и строка
REVIEW остаётся в **каждом** промпте типа чтения: выход — единственное, что
промпт типа не должен терять.

Какие блоки берёт чтение, решает область действия (ADR 311, ADR 322): страница
без вердиктов даёт все текстовые блоки; страница, где проверка ответила хоть
что-то, — только блоки, отклонённые моделью проверки, тот же набор, что берёт
«Исправить», так что число на кнопке читается как число «Исправить» всюду, где
проверка сказала своё слово.

## 6. Задача проверки (визуальный дифф, ADR 235/254)

Decision-модель (MiniCPM-OCR Jev) — бинарный классификатор, а не генератор:
запрос POST-ится на `/v1/systemone` ровно с двумя картинками (кроп, затем
кандидат, отрендеренный обратно в картинку `src/app/CandidateRenderer.cpp`)
и текстом кандидата строкой `state`; ответ — одна вероятность
P(согласуется). `match ≥ threshold` → Ok, иначе Mismatch; кроп, который
модель не может прочитать, уходит в Review через задачу исправления. Пороги
— по типам блоков (`matchThresholdByBlock` в профиле → роль → настройка) и
**измерены**, а не угаданы (ADR 184/258): text 0.92, equation 0.87,
table 0.4, base 0.5 на корпусе OCR_TEST. Формула доходит до проверки в
канонической форме (`core/LatexText`, ADR 194), поэтому обе задачи судят
одни и те же байты.

## 7. Формулы (ADR 194–196)

- Каноническая LaTeX-форма вычисляется в момент распознавания и хранится в
  блоке — панель, экспорт, проверка и исправление видят одни и те же байты.
- Формула, чей LaTeX не проходит `LatexText::check`, отбрасывается сразу
  после распознавания: статус «неверный синтаксис» (красный), панель
  называет, что именно сломано, а блок исключается из проверки и
  исправления, пока не будет распознан заново.
- Markdown-блок кода (code fence) внутри формулы — несущая разметка: он
  снимается; оставшийся бэктик — отдельный дефект.
- Формула, разбитая на несколько фрагментов «$$…$$», отображается
  несколькими блоками формул; невидимый разделитель `\left.`/`\right.`
  составляет пару с любой скобкой.

## 8. Статусы блока и страницы

**Блок** — состояние говорит шестью словами (ADR 338): **Распознан** (серая —
никто не судил блок, но текст в нём есть), **Есть ошибки** (красная —
проверяющая модель отвергла текст), **Повреждён** (красная — блок не удалось
прочитать), **Неверный синтаксис** (красная — сломан LaTeX формулы),
**Нет ошибок** (зелёная — проверяющая модель подтвердила текст или
пользователь утвердил его) и **Отредактирован** (жёлтая — текст написал
пользователь). У блока, который вовсе не несёт текста (одна разметка), статуса
нет: ни точки, ни слова. Слово стоит в шапке панели рядом с именем типа
блока, точка этой шапки несёт цвет (ADR 339), а рамка на превью несёт
состояние блока цветом (ADR 238): нет рамки = только разметка, серая =
распознан, красная = проблема (Mismatch, Review, неверный синтаксис), зелёная =
проблемы нет (Ok, утверждён). Рамка говорит о вердикте, который модель
оставила блоку, а шесть слов — о его состоянии; исключение одно: текст,
написанный рукой, жёлтый в шапке, и рамка такого блока тоже жёлтая (ADR 341):
рамка говорит, чем блок является сейчас.
Рамка следует за
**эффективным** слоем; число уверенности (опция
`check/showConfidence`) печатается цветом рамки. Статусы исправителя никогда
не звучат в рамке — он не проверяющий (ADR 240). Статусы читателя — да:
зелёная — прочитан, красная — прочитать не удалось (ADR 261). «Утвердить
блок» сохраняет `BoxCheckStatus::Approved`, и утверждение можно отозвать
(ADR 185/187); введённый вручную текст — `BoxCheckStatus::Edited`
(ADR 187). Ни один слой принадлежащего пользователю блока не стирается и не
перезапускается повторным запуском (ADR 291). Перемещение или изменение
размера блока стирает его содержимое — блок снова разметка (ADR 241).

**Страница** — страница говорит теми же словами (ADR 338): нет блоков
разметки — нет статуса вовсе; разметка есть, распознаны не все блоки —
**Размечено** (серая); все блоки распознаны, но один из них не суждён —
**Распознано** (серая); все блоки суждены и один из них с ошибкой —
**Есть ошибки** (красная); все блоки суждены или утверждены и один из них
написан вручную — **Отредактировано** (жёлтая); все блоки суждены без ошибки
— **Проверено** (зелёная). Утверждённый блок считается суждённым с зелёным
результатом, а ошибка важнее блока, написанного руками. Под словом — два
независимых значения (ADR 165):

- сохранённый режим распознавания (`PageRecognitionMode`): none / markup
  only / recognized / markup+recognized — «только разметка» автоматически
  становится «с разметкой», как только у всех блоков, кроме изображений,
  появится текст;
- вычисляемый агрегат проверки по включённым типам блоков + подозреваемым
  на дубликаты: «Проверено» — только когда у каждого подлежащего проверке
  блока есть вердикт на его эффективном слое; любой Mismatch/Review →
  «Есть ошибки».

## 9. Интерфейс

Шапка (`MainWindow/Header.qml`, ADR 270/171): «Документ» (меню проекта,
импорт, экспорт), «Целевые страницы» (поле диапазона страниц +
«Авто-проход»), «Разметка и OCR» (Разметить / Распознать (OCR)), «Проверки
и AI-коррекция» (Проверить / Исправить / Распознать (LLM)), «Настройки».
Всё действует на выделение в ленте миниатюр (пустое выделение = весь
документ).

- «Проверить» запускает проход проверки по блокам выделенной области
  (`checkScopeEnabledBlocks()`) — проверка и исправление — отдельные
  действия; автоматические переключатели проверки/исправления удалены
  (ADR 178).
- «Исправить» несёт бейдж `scopedPendingFixCount` (ADR 188) и запускает
  задачу исправления по проблемным блокам всей области.
- «Распознать (LLM)» запускает задачу чтения по блокам выделенных страниц
  (ADR 260/266): на странице без вердиктов — по всем текстовым блокам; на
  странице, где проверка ответила хоть что-то, — только по блокам, отклонённым
  моделью проверки, тому же набору, что берёт «Исправить» (ADR 311, ADR 322).
  Блоки, принадлежащие пользователю, в очередь не попадают никогда; счётчик
  едет на кнопке (ADR 264) и равен числу запросов, которые сделает прогон.
- Пока прогон активен, кнопка запущенного действия становится кнопкой
  остановки; соответствие — по флагам/фазам (ADR 171).

Каждая задача перезапускается над областью, где уже есть её результаты,
только после вопроса с тремя вариантами (`RerunConfirmDialog`, ADR 291):
«Отмена» / «Переделать всё» / «Только где не сделано»; область, где ничего
не сделано, запускается сразу. «Только где не сделано» держит обычный
список работы задачи (блоки без текста, блоки без вердикта, проблемные
блоки, ещё не перераспознанные); «Переделать всё» расширяет его и на
сделанные блоки. Стирание едет с прогоном, а не с режимом: обработка блока
очищает собственный уровень задачи в стеке и всё над ним — распознавание
стирает текст, исправления и вердикты по приходу ответа (ADR 164),
проверка стирает вердикты судимого слоя, запрос исправления/чтения стирает
сохранённый результат средства по блоку прямо перед отправкой.
Принадлежащие пользователю блоки (Edited/Approved) не стираются и не
перезапускаются никогда.

Тулбар страницы: навигация по страницам, кнопки добавления блоков
(T / изображение / таблица / Σ / код + меню ▾ со всеми типами, ADR 177),
поворот. Выбранный блок несёт плавающую мини-панель (распознать / проверить
/ исправить / удалить). Панель блока — инспектор блока (ADR 185–187,
ADR 339): шапка модуля несёт состояние, переключатель слоёв читает
**OCR | VLM | Разница**, а под ним стоит один текстовый слой — шапка слоя
несёт пометку, оценку и действие утверждения, подсветка различий прямо в
тексте (`core/TextDiff.h`), утверждение/отзыв, ручная правка.

Доступность: кнопки, требующие модель задачи, гаснут, когда модель не
выбрана/не скачана (управляемый рантайм: файла нет; внешний: алиас пуст) —
считает `AvailabilityPresenter` (ADR 213/214) по рантайму самой задачи
(ADR 318).

Автоконвейер сцепляет пять этапов (разметка → распознавание → проверка →
исправление → проверка исправленного); см. `docs/11-auto-pipeline.md`.

## 10. Настройки

- Выбор модели/квантизации на задачу живёт в единственном окне «Модели»
  (ADR 168): строки `task | рантайм ⟨Managed | External⟩ | model ▾ | quant ▾ | ⚙` —
  колонка рантайма — сегментный переключатель на два положения, а не выпадающий
  список; шестерёнка открывает вкладки **Launch** (профиль параметров запуска)
  и **Request** управляемой задачи, а внешней — вкладки **Подключение**
  (эндпоинт, ключ, алиас модели) и **Request**; блок «файлы на диске» с
  защищённым удалением.
- Ключи настроек:
  `tasks/<task>/{modelPath, mmprojPath, draftPath, requestProfileId,
  modelName, runtimeMode}` — файлы запуска blockRecognition сохраняют прежний
  префикс `check/` (ADR 146). Режим рантайма — собственный выбор задачи
  (ADR 318); глобальный `provider/mode` — только его умолчание. Миграции
  настроек нет: несовпадение схемы один раз
  сбрасывает настройки (ADR 253).
- `check/` хранит поведенческие ключи: `showConfidence` и бюджеты
  рассуждений `check/fixReasoningBudgetTokens` /
  `check/readReasoningBudgetTokens` (ADR 268, правятся в Настройки →
  Проверка вместе с фильтром типов блоков).
- `decision/matchThreshold` остаётся базовым порогом; пороги по типам
  приходят из профиля модели.
- Тексты запросов общие на задачу (`fix-requests.json`,
  `read-requests.json`, ADR 182); роль может переопределить формулировки
  (ADR 267).
