# 09. Задачи и конвейер проверки

> Английский оригинал: [docs/09-tasks-and-verification.md](09-tasks-and-verification.md)
>
> Текущее состояние (октябрь 2026). Поэтапная программа переработки, которая
> ввела эту архитектуру, завершена (её решения записаны как ADR в
> `docs/07-glossary.md`); затем релизная чистка вырезала девять моделей и
> однопроходные страничные задачи (ADR 251–255). Этот документ описывает то,
> что поставляется сегодня, и почему. Русское зеркало:
> `docs/09-tasks-and-verification.ru.md`.

## 1. Четыре задачи

Каждый профиль модели объявляет, какие задачи он обслуживает
(`roles.<task>`); те же строковые идентификаторы проходят через
`ConnectionRole`, настройки (`tasks/<task>/…`) и QML. Список живёт в одном
месте — `src/core/ConnectionRole.h` (ADR 215, 252).

| Идентификатор задачи | Название в UI | Что делает |
|---|---|---|
| `layout` | Разметка | Разметка страницы: модель возвращает позиционированные блоки без текста |
| `blockRecognition` | Распознавание блока | OCR одного кропа блока (простая транскрипция) |
| `decision` | Проверка | Бинарный вердикт «текст соответствует изображению» — визуальный дифф |
| `fix` | Исправление блока | Универсальная модель подтверждает / исправляет / отказывает кандидату |

Один управляемый llama-server обслуживает все задачи; модель (пере)загружается
при переключении задачи (`RuntimeController::serverRunsRole`). Распознавание
и проверка взаимоисключающие на уровне `AppController`, поэтому переключение
никогда не убьёт запущенную работу.

Однопроходные страничные задачи `pageOcr` / `rawPageOcr` вырезаны (ADR 252) —
текст страницы собирается из распознавания блоков, после ручной разметки
(`layout`) либо модельного прохода разметки.

## 2. Матрица «модель → задачи»

В `resources/profiles/models/` поставляется девять профилей; вырезанные
профили живут в `archive/models/profiles/` (ADR 251). Ровно один профиль на
задачу несёт `"default": true` — он питает автовыбор (ADR 169).

| Профиль | Задачи | Дефолт для |
|---|---|---|
| `mineru.json` | layout, blockRecognition | layout, blockRecognition |
| `glm-ocr.json` | blockRecognition | — |
| `minicpm-jev.json` | decision | decision |
| `qwen3.5-4b.json` | fix | fix |
| `qwen3.5-9b.json` | fix | — |
| `gemma-4-e4b.json` | fix | — |
| `gemma-4-12b.json` | fix | — |
| `qwen3-vl-4b.json` | fix | — |
| `qwen3-vl-8b.json` | fix | — |

Принцип: **OCR-модели только распознают, decision только проверяет,
универсальные модели только исправляют.** Профиль никогда не сочетает
несовместимые задачи. Руководства по моделям: `docs/13-model-mineru.md`,
`docs/14-model-glm-ocr.md`, `docs/17-model-minicpm-jev.md`,
`docs/15-model-gemma-4.md`, `docs/16-model-qwen3.5.md`.

## 3. Два слоя текста (ADR 164)

Каждый текстовый блок несёт два независимых слоя:

- **text** — `box.text`, результат OCR; любой результат распознавания
  (страница, блок, повторное распознавание, чтение) попадает сюда и
  **стирает** коррекцию и оба вердикта;
- **correction** — `box.correctedText`, вывод fix-модели.

**Эффективный текст** — коррекция, когда она есть, иначе текст. Каждый слой
несёт собственный вердикт (`checkStatus`/`confidence` против
`correctedCheckStatus`/`correctedConfidence`). Автоматического переноса
коррекции в текст нет: экспорт, пересборка текста страницы и предпросмотр
всегда используют эффективный текст. Переходы — чистые функции в
`src/core/BoxTransitions.*`, покрытые `test_box_transitions`.

## 4. Протокол исправления (`full_block`, ADR 181/192)

Запрос к fix-модели (собирается в `src/models/FixModel.cpp`):

- `system` = общий промпт проверяющего
  (`resources/profiles/requests/fix-requests.json`);
- `user` = `[промпт типа блока, кандидат, image]` — кандидат в рамке
  `OCR candidate:\n<CANDIDATE>\n…\n</CANDIDATE>`; сохранённая коррекция
  повторно не отправляется, кандидат — собственный эффективный текст блока;
- каждый параметр профиля запроса задачи уходит в тело как поле верхнего
  уровня (`VisionChatModel::buildRoot`).

Ответ — ровно один из:

- `OK` — исправлять нечего; блок сохраняет свои байты;
- `FIX` + **полный исправленный блок** — `FixDiffGate` сравнивает его
  с кандидатом: эквивалентные (переиначенные) блоки сохраняют собственные
  байты кандидата; пустой ответ, `FIX none` или ответ, обрезанный бюджетом
  токенов (`finish_reason: length`), понижается до REVIEW; всё остальное
  попадает в Review как отклонение;
- `REVIEW` — изображение нечитаемо/повреждено; красный статус, коррекция
  не сохраняется.

Fix-модель может сначала подумать: профиль объявляет `reasoning: true`,
бюджет — глобальная настройка `check/fixReasoningBudgetTokens`,
подставляемая в каждый запрос (ADR 193/268), а `RequestBudget` при обрезке
жертвует рассуждениями раньше ответа.

## 5. Протокол чтения (`read_block`, ADR 259–267)

Те же fix-модели обслуживают задачу чтения («Перераспознать») по другому
контракту: запрос — это ровно изображение, системный промпт и промпт блока —
**распознанный текст не передаётся никогда**. Ответ — `FIX` (полный блок)
или `REVIEW` (`OK` вне схемы и попадает в Review с причиной). Гейт тот же —
`FixDiffGate`, поэтому чтение, воспроизведшее текст, сохраняет байты блока
и снимает устаревший Mismatch. Исходы — собственные статусы
`Read` / `ReadFixed` / `ReadDamaged`; прогон заканчивается своей сводкой
(«Прочитано блоков: переписано — N, подтверждено — M, не прочитано — K»).
Тексты промптов живут в `resources/profiles/requests/read-requests.json`;
fix-роль может их переопределить (`readSystemPrompt`/`readBlockPrompts`) —
семейство Qwen3-VL так и делает, потому что читает общую формулировку как
проверку коррекции (ADR 267).

## 6. Задача проверки (визуальный дифф, ADR 235/254)

Decision-модель (MiniCPM-OCR Jev) — бинарный классификатор, а не генератор:
запрос POST-ится на `/v1/systemone` ровно с двумя картинками (кроп, затем
кандидат, отрендеренный обратно в картинку `src/app/CandidateRenderer.cpp`)
и текстом кандидата строкой `state`; ответ — одна вероятность
P(согласуется). `match ≥ threshold` → Ok, иначе Mismatch; кроп, который
модель не может прочитать, уходит в Review через задачу исправления. Пороги
— по типам блоков (`matchThresholdByBlock` в профиле → роль → настройка) и
**измерены**, а не угаданы (ADR 184/258): text 0.92, equation 0.87,
table 0.4, base 0.5 на корпусе OCR_TEST. Формула доходит до проверки в
канонической форме (`core/LatexText`, ADR 194), поэтому обе задачи судят
одни и те же байты.

## 7. Формулы (ADR 194–196)

- Каноническая LaTeX-форма вычисляется в момент распознавания и хранится в
  блоке — панель, экспорт, проверка и исправление видят одни и те же байты.
- Формула, чей LaTeX не проходит `LatexText::check`, отбрасывается сразу
  после распознавания: статус «неверный синтаксис» (красный), панель
  называет, что именно сломано, а блок исключается из проверки и
  исправления, пока не будет распознан заново.
- Markdown-блок кода (code fence) внутри формулы — несущая разметка: он
  снимается; оставшийся бэктик — отдельный дефект.
- Формула, разбитая на несколько фрагментов «$$…$$», отображается
  несколькими блоками формул; невидимый разделитель `\left.`/`\right.`
  составляет пару с любой скобкой.

## 8. Статусы блока и страницы

**Блок** — состояние несёт рамка (ADR 238): нет рамки = только разметка,
серая = распознан, красная = проверен с проблемой (Mismatch, Review,
неверный синтаксис), зелёная = проверен чисто (Ok, утверждён, введён
вручную). Рамка следует за **эффективным** слоем; число уверенности (опция
`check/showConfidence`) печатается цветом рамки. Статусы исправителя никогда
не звучат в рамке — он не проверяющий (ADR 240). Статусы читателя — да:
зелёная — прочитан, красная — прочитать не удалось (ADR 261). «Утвердить
блок» сохраняет `BoxCheckStatus::Approved`, и утверждение можно отозвать
(ADR 185/187); введённый вручную текст — `BoxCheckStatus::Edited`
(ADR 187). Перемещение или изменение размера блока стирает его содержимое —
блок снова разметка (ADR 241).

**Страница** — два независимых значения (ADR 165):

- сохранённый режим распознавания (`PageRecognitionMode`): none / markup
  only / recognized / markup+recognized — «только разметка» автоматически
  становится «с разметкой», как только у всех блоков, кроме изображений,
  появится текст;
- вычисляемый агрегат проверки по включённым типам блоков + подозреваемым
  на дубликаты: «проверено» — только когда у каждого подлежащего проверке
  блока есть вердикт на его эффективном слое; любой Mismatch/Review →
  «есть ошибки».

## 9. Интерфейс

Шапка (`MainWindow/Header.qml`, ADR 270/171): «Документ» (меню проекта,
импорт, экспорт), «Целевые страницы» (поле диапазона страниц +
«Авто-проход»), «Разметка и OCR» (Разметить / Распознать блоки), «Проверки
и AI-коррекция» (Проверить / Исправить / Перераспознать), «Настройки».
Всё действует на выделение в ленте миниатюр (пустое выделение = весь
документ).

- «Проверить» запускает проход проверки по блокам выделенной области
  (`checkScopeEnabledBlocks()`) — проверка и исправление — отдельные
  действия; автоматические переключатели проверки/исправления удалены
  (ADR 178).
- «Исправить» несёт бейдж `scopedPendingFixCount` (ADR 188) и запускает
  задачу исправления по проблемным блокам всей области.
- «Перераспознать» запускает задачу чтения по каждому текстовому блоку
  выделенных страниц, кроме принадлежащих пользователю (ADR 260/266);
  счётчик едет на кнопке (ADR 264).
- Пока прогон активен, кнопка запущенного действия становится кнопкой
  остановки; соответствие — по флагам/фазам (ADR 171).

Тулбар страницы: навигация по страницам, кнопки добавления блоков
(T / изображение / таблица / Σ / код + меню ▾ со всеми типами, ADR 177),
поворот. Выбранный блок несёт плавающую мини-панель (распознать / проверить
/ исправить / удалить). Панель блока — инспектор версий (ADR 185–187): две
карточки, подсветка различий прямо в тексте (`core/TextDiff.h`),
утверждение/отзыв, ручная правка.

Доступность: кнопки, требующие модель задачи, гаснут, когда модель не
выбрана/не скачана (управляемый рантайм: файла нет; внешний: алиас пуст) —
считает `AvailabilityPresenter` (ADR 213/214).

Автоконвейер сцепляет пять этапов (разметка → распознавание → проверка →
исправление → проверка исправленного); см. `docs/11-auto-pipeline.md`.

## 10. Настройки

- Выбор модели/квантизации на задачу живёт в единственном окне «Модели»
  (ADR 168): строки `task | model ▾ | quant ▾ | ⚙`, вкладки Launch/Request
  за ⚙, блок «файлы на диске» с защищённым удалением.
- Ключи настроек:
  `tasks/<task>/{modelPath, mmprojPath, draftPath, requestProfileId,
  modelName}` — файлы запуска blockRecognition сохраняют прежний префикс
  `check/` (ADR 146). Миграции настроек нет: несовпадение схемы один раз
  сбрасывает настройки (ADR 253).
- `check/` хранит поведенческие ключи: `showConfidence` и бюджеты
  рассуждений `check/fixReasoningBudgetTokens` /
  `check/readReasoningBudgetTokens` (ADR 268, правятся в Настройки →
  Проверка вместе с фильтром типов блоков).
- `decision/matchThreshold` остаётся базовым порогом; пороги по типам
  приходят из профиля модели.
- Тексты запросов общие на задачу (`fix-requests.json`,
  `read-requests.json`, ADR 182); роль может переопределить формулировки
  (ADR 267).
