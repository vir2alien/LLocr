# 04. Компоненты

> Английский оригинал: [docs/04-components.md](04-components.md)

Обозначения статусов: ✅ реализовано · 🟡 частично · ⬜ не начато

## 4.1 OCR-модели и транспорт (llama.cpp, OpenAI-совместимый API)
- **OcrModel** ✅ (`src/models/`): адаптер OCR-LLM. Базовый `OcrModel`
  кодирует изображение (base64 data
  URL), собирает тело chat-completions в стиле OpenAI (`buildRequestBody`)
  и разбирает ответ (`parseResponse`);
  асинхронность (`QPromise`/`QFuture`), таймаут на запрос и **`abort()`**
  для Stop. Поведение конкретной модели — это **данные** — профиль модели
  несёт промпты, парсер по умолчанию и параметры запроса/запуска;
  `OcrModel::create(modelId, role)` читает его, а подклассы по задачам
  (`BlockRecognitionModel`, `DecisionModel`, `LayoutModel`, `FixModel`) несут
  формы ответов на проводе (ADR 58). Новые LLM добавляются новыми JSON
  профиля — новый класс парсера только под новую форму ответа. Адаптеры
  удалённых моделей ушли в архив вместе с ними (ADR 251).
- **LlamaClient** ✅ (`core/LlamaClient.h`): тонкий транспорт — заранее
  проверяет TCP-соединение (таймаут подключения), отправляет POST с JSON
  на `/v1/chat/completions` с опциональным bearer-токеном, ограничивает весь
  запрос таймаутом ответа (ADR 148) и поддерживает `abort()`; выносит
  наружу сообщение об ошибке сервера. Бывший слой провайдеров сократился
  ровно до этого.
- Конфигурация ✅: базовый URL, API-ключ (опционально), таймауты подключения
  и ответа — в `ConnectionConfig`;
  адаптер OCR-модели (`model/recipeId`, по умолчанию `mineru`), имя модели
  и параметры тела запроса — **один профиль запроса на OCR-модель**
  (параметры DRY, температура, максимум токенов; ADR 59). **Промпт**
  распознавания берётся из `promptVariants()` выбранного адаптера модели
  (ADR 58).
- **Проверка (decision + fix)** ✅ (`DecisionController`/`DecisionModel` +
  `FixController`/`FixModel`, ADR 68/74/78/79 → ADR 252/254): модель
  **decision** (MiniCPM-OCR Jev, задача `decision` в «Моделях») выносит
  суждение о распознанном блоке — запрос несёт кроп блока, кандидат,
  отрендеренный обратно в изображение, и текст кандидата; noul-голова
  отвечает P(consistent) за один проход, и вердикт маршрутизируется в
  Ok / Mismatch порогом по типу блока (`matchThresholdByBlock` в профиле,
  ADR 254). Она
  использует то же разрешённое подключение (имя модели с учётом роли —
  ADR 73), а единственный управляемый экземпляр перезагружается под задачу
  (ADR 74). Проверка идёт по текущей странице (`checkEnabledBlocksOnPage`)
  и по всем распознанным страницам («Проверить всё», `checkAllEnabledBlocks`)
  — очередь спрашивает только блоки, у которых ещё нет ответа, поэтому
  повторное распознавание проверяет только вновь распознанные блоки.
  Исправление — отдельное действие («Исправить», ADR 178): отвергнутые блоки
  уходят модели исправления отдельным запуском. Перечитывание — третье
  действие («Перераспознать», ADR 259, ADR 260): модель исправления пишет
  блок с изображения, и распознанный текст блока никогда не передаётся —
  запрос несёт изображение, системный промпт и промпт блока (ADR 266).
  Протокол выбирает действие (`CheckRequest::fixProtocol`), а не модель.
  Итог читающего виден: его состояние говорит за блок в рамке (зелёная —
  прочитан, красная — нечитаем), он объясняется словами читающего, а запуск
  заканчивается своей сводкой («Прочитано блоков: переписано — N,
  подтверждено — M, не прочитано — K», ADR 261). В режиме Managed сервер
  переключается между моделями задач автоматически (ADR 74), в режиме
  External запрос просто запускается (ADR 91).
  Последовательная очередь проверки (список задач, прогресс, остановка)
  живёт в очередях ролей (ADR 286): **`DecisionQueue`** ведёт визуальную
  сверку, **`RecheckQueue`** — повторное распознавание, **`RemedyQueue`** —
  исправление и чтение, над общим исполнителем `BlockQueue` и одним
  `BlockRunGate`. Списки блоков собирает `BlockWorkList`; результаты
  доходят до `AppController` сигналами (ADR 86) — `check*` API класса
  `AppController` для QML не изменился.
  Очередь переживает переключение страниц (паритет с распознаванием),
  поэтому пакетная проверка продолжает идти, пока пользователь листает
  (ADR 91).
  > **Как работает проверка.** Проверка быстра: модель decision лишь
  > отвечает, насколько вероятно, что текст совпадает с изображением, блок
  > за блоком. Совпавшие блоки становятся зелёными; отвергнутые — красными.
  > Исправление — отдельный шаг: кнопка «Исправить» отправляет отвергнутые
  > блоки модели исправления. Управляемый рантайм переключает загруженную
  > модель между двумя задачами; внешний рантайм обслуживает обе.
  Список на вкладке Blocks опирается на прокси-модели с фильтром по группам
  (`BlockGroupFilterModel` над общей `VerificationBlocksModel`, выставлены
  как `Verification.blockModelContent/Captions/Service`, ADR 82);
  встроенные списковые компоненты (`Common/RuntimeBuildsList`) выставляют
  `implicitHeight` (ограничение через `maxVisibleRows`,
  `<= 0` = без ограничения), чтобы потребители привязывали высоту, а не
  вычисляли количество строк заново (ADR 82). Список моделей — одна строка
  на модель с выбором квантизации на строке (`ModelQuantModel` за
  `Common/TaskModelsTable`, ADR 122) — разделение установленное/пресет,
  которое он заменил, исчезло. Строки таблицы задач — четыре задачи
  приложения, и их список приходит из C++ (`Settings.taskRoles` →
  `core/ConnectionRole.h`, ADR 215): таблица не хранит его копию.
  Диспетчеризация по задачам (заголовок, подсказка сэмплирования, модели
  квантизации, профили запросов) — одна таблица в `RoleProfiles.qml` —
  строка на задачу, столбец на свойство (ADR 217). Конвейер установки
  пресетов с HF живёт в `ModelInstallTransaction` (prepare → download →
  finalize, ADR 85); `ModelInstaller` остаётся QML-фасадом над пресетами,
  реестром и видами с фильтром по ролям.

## 4.2 Настройки
Настройки разделены на **отдельные немодальные окна**, открываемые из меню
шапки (ADR 70): **Интерфейс**, **Вывод**, **Проверка**, **Рантайм** и
**Модели**. Настройки интерфейса применяются сразу; остальные окна фиксируют
изменения по **«Сохранить»** и отбрасывают по **«Отмене»**. В окнах
**Интерфейс**, **Вывод** и **Рантайм** есть ограниченная окном кнопка
**«Вернуть настройки по умолчанию»** (ADR 75), которая через сеттеры свойств
записывает подходящие строки реестра `kDefaults`, построенного на таблице;
у окна **Модели** вместо этого сбросы по задачам (восстановление профилей
в Launch/Request).

**Сегментный переключатель** (`Common/SegmentedToggle.qml`) — один компонент
на всё приложение: один блок с общим фоном, карточка на выбранном сегменте
и равные сегменты внутри блока (ADR 285). Он управляется извне — сообщает
о выборе (`activated(index)`) и никогда не выставляет `currentIndex` сам;
стрелки и пробел перемещают выбор.

Единственный управляемый экземпляр llama-server обслуживает обе роли по
одной за раз: `RuntimeController` (пере)загружает модель под задачу (ADR 74).
Параллельные роли возможны только против внешних серверов, которым задаются
имена моделей по ролям (ADR 73). Пресеты моделей живут в одном каталоге:
встроенный `:/models/default-presets.json` + пользовательский
`models/catalog.json` (ADR 42; см. 4.17).

Сохранение обеспечивает `SettingsStore` (`QSettings`, сгруппированные ключи
`provider/*`, `model/*`, `parser/id`, `output/*`, `export/*`, `runtime/*`,
`launch/*`, `check/*`, `hf/*`, `tasks/<role>/*`). Состояние интерфейса
(тема, язык, геометрия окна) сохраняется под `ui/*`. Сбрасываемые ключи
зарегистрированы в массиве `kDefaults`, построенном на таблице (ADR 50);
`resetToDefaults()` сбрасывает всю таблицу, ограниченные окном сбросы
используют те же строки (ADR 75).

**Секреты не лежат в `QSettings`**: API-ключ и токен Hugging Face живут
в хранилище секретов ОС — macOS Keychain, Windows Credential Manager,
Linux Secret Service (ADR 227). Файл настроек хранит только эндпоинты
и алиасы. Сохранённый ключ никогда не показывается обратно: поле несёт
маску и принимает новый.

> **Режим** распознавания (`External` / `Managed`) выбирается мастером
> первого запуска; существующие профили остаются на `External` (ADR 26/31).
> Вкладка **Launch** в окнах моделей редактирует профили параметров запуска
> llama-server; шаг **Launch** мастера первого запуска (порт, ctx-size,
> n-gpu-layers, `autoStart`, предпросмотр команды + самопроверка) покрывает
> тот же профиль на чистой установке.

> **Пока не в настройках:** промпт распознавания принадлежит выбранному
> **адаптеру OCR-модели** (`promptVariants()`, ADR 58) и не редактируется;
> поля `parser`/`prompt` пресетов моделей — лишь сохранённые метаданные.
> Диапазон координат bbox — опция парсера (`ParserOptions::bboxRange`, 1000
> по умолчанию, ADR 88), а не настройка. Параметры запроса по задачам живут
> в профиле запроса задачи (Settings → Models → ⚙ строки → Request).

Помодельные настройки задач (`tasks/<task>/{modelPath, mmprojPath, draftPath,
requestProfileId, modelName}`) доступны через обобщённые по задачам
аксессоры `…ForRole(role)` класса `SettingsStore`. Одна диспетчерская
таблица отображает роль в её аксессоры, поэтому новая задача — одна строка
таблицы, а не десять switch'ей (ADR 216); список задач приходит из
`core/ConnectionRole.h` (ADR 215).

## 4.4 Парсеры вывода
- **Один парсер на модель** ✅ (`DetTokenParserBase` + `MinerULayoutParser`): каждый читает форму ответа, которую пишет его собственная модель —
  обёрнутый поток `<|det|>label [x1,y1,x2,y2]<|/det|>` с JSON-экранированным
  содержимым (`\n` → перевод строки) и layout-разметку MinerU
  `<|box_start|>…<|ref_start|>` с её поглощением накрытых потомков. Движок
  (сканирование токенов → нормализованные рамки → Markdown через
  `rebuildText()`, подформаты OTSL и `<table>`, отбрасывание служебных
  токенов) общий; модель, отвечающая в другой форме, — новый подкласс,
  а не новая ветка в парсере, который делят все модели (ADR 112). Ответ без
  layout-заголовка сохраняет свой текст и записывает диагностику.
  Координаты нормализуются в [0,1] через `ParserOptions::bboxRange` (1000
  по умолчанию, привычное модельное пространство 0–1000). Парсеры,
  существовавшие только для удалённых моделей (`UnlimitedOcrParser`,
  `Lfm25VlParser`, `TeleOcrLayoutParser`, …), живут в `archive/parsers/`
  (ADR 251).
- `raw` ✅ — текст как есть (`RawParser`).
- `mineru-layout` ✅ — ручной проход разметки (ADR 149): строки
  `<|box_start|>…<|ref_start|>` в layout-ответе MinerU несут рамку, метку
  и токен поворота; парсер читает их структурно в позиционированные блоки
  **без текста** (ответ TeleOCR из архива требовал `prepareText()`, чтобы
  сначала переписать свою форму `<box:…><label:…>` в канонические токены —
  его парсер лежит в `archive/parsers/`); номера страниц сохраняются
  всегда — проход разметки описывает страницу, фильтр вывода относится
  к тексту.
- `auto` ✅ — **значение по умолчанию** (`parser/id = auto`, ADR 88).
  Не парсер: он разрешается в `OcrModel::defaultParserId()` выбранной модели
  внутри `AppController::effectiveParserId()`, поэтому смена OCR-модели
  никогда не оставит неподходящий парсер. Каждая модель объявляет парсер
  собственной формы ответа, и
  `test_ocr_models::everyModelDeclaresARegisteredParser` охраняет эту связь
  во время сборки.
- Создаются и настраиваются через `ParserFactory::create(id, ParserOptions)`;
  `selectableIds()` / `selectableDisplayNames()` питают **Settings → Output**
  (`AppController::parserNames` / `parserLabels`, один к одному; комбобокс
  показывает переведённую метку, настройка хранит id). Чтобы добавить парсер:
  реализуйте `IOutputParser` (`parse`, `rebuildText`, `id`, `displayName`),
  зарегистрируйте его в `ParserFactory::registeredIds()` и в ветке `create()`
  — в слое приложения ничего менять не нужно.
- Стили блоков: отображение метка → `BlockStyle` — это **данные**, в
  `resources/profiles/labels.json` (`default` + `overrides` по моделям,
  ключ — id модели), читается `BlockStyleMap` (`parsers/BlockStyle.{h,cpp}`)
  с вкомпилированной в качестве резерва прежней таблицей — `title` →
  заголовок, `image`/`chart`/`image_block` → заполнитель изображения,
  `image_caption`/`table_caption`/`table_footnote`/`page_number` → курсив,
  `equation` → формула, `table` → GFM pipe-таблица (`output/tablesAsHtml`
  вместо этого сохраняет HTML `<table>` модели, ADR 19), `ref_text` →
  обычный текст. Собственный словарь меток модели — правка JSON, а не
  изменение C++.
- `IOutputParser::rebuildText()` заново порождает Markdown страницы из рамок
  (используется после удаления рамки / подтверждённого FIX / изменения
  размера, чтобы индексы `image://ocr/crop/<N>` оставались согласованы).
  Это часть контракта парсера, а не свободная функция конкретного
  det-парсера, поэтому `AppController` больше не зависит от конкретного
  парсера (ADR 88).
- **Диагностика:** ответ, не давший ни одного layout-токена, всё равно
  сохраняется (как один блок `text`), но записывается в `OcrResult::notes`
  и показывается постранично как `Controller.parseWarning` в футере —
  случай «модель и парсер не совпали» раньше выглядел как успешное, пусть
  и уродливое, распознавание (ADR 88).

## 4.5 Загрузка изображений, PDF и DjVu
- Изображения: `QImage` (одно или несколько через `loadImages` /
  `appendImage`). ✅
- PDF: рендеринг постранично через **Qt PDF (`QPdfDocument`)** при ~150 DPI. ✅
- Зависимость DjVu: **DjVuLibre** через её публичный C-API декодирования
  (`ddjvuapi`), обёрнутая в `src/app/DjVuDocument.h/.cpp` и используемая
  `DocumentModel`. Декодер — **обязательная зависимость времени линковки**,
  а не внешний процесс `ddjvu` и не плагин изображений Qt. QML не обращается
  к библиотеке напрямую. CMake линкует `DjVuLibre::DjVuLibre` в каждую цель,
  компилирующую `DocumentModel.cpp`: `llocr`, `test_document_model` и
  `test_djvu_document`, плюс интеграционный тест контроллера
  `test_app_import`. См. ADR 65 и
  [настройку зависимости](06-dev-setup.md#djvulibre-optional-enables-djvu-input).
  Файлы `.djvu` и `.djv` делят с изображениями/PDF один путь открытия
  и drag-and-drop. Родное разрешение скана сохраняется до 40 мегапикселей
  и 16384 пикселей на сторону. Ориентация сохраняется; полноразмерные
  изображения рендерятся лениво через существующий кэш на четыре
  изображения. Ожидания декодера ограничены 30 секундами на операцию.
  Импорт DjVu готовит метаданные и миниатюры в воркере `QtConcurrent`
  с независимым декодером; принадлежащий GUI `QFutureWatcher` фиксирует
  подготовленные страницы под короткой блокировкой записи `m_documentLock`.
  Ни один воркер не трогает контроллер или живой документ. Файлы
  обрабатываются последовательно, чтобы сохранить порядок смешанного
  выбора. `importing` крутит спиннер футера и статус с именем файла/
  количеством файлов и не даёт пересекаться импорту, OCR, экспорту,
  удалению и перестановке страниц. Нечитаемые страницы становятся белыми
  заменителями с сохранением исходных индексов; при сбое метаданных берётся
  резервный размер 800×1000. `sourceError` хранит ошибку декодера; импорт
  сообщает количество предупреждений и первую ошибку, а выбор заменителя
  показывает его предупреждение в футере. OCR пропускает заменители: они
  остаются нераспознанными и не попадают в экспорт распознанного текста.
  Неудача открытия самого документа по-прежнему отвергает файл. Закрытие
  контроллера разрывает доставку, не дожидаясь воркера (пул потоков может
  ещё подождать при выходе из приложения). Отмена импорта и прогресс по
  страницам не реализованы. Загрузка PDF/растра и ленивый полноразмерный
  рендеринг сохраняют свои прежние синхронные пути.
- Многостраничные документы → обработка постранично, с пакетным запуском
  **«Распознать всё»** и лентой миниатюр страниц. ✅
- Страницы можно **удалять** (`removePage`) и **переставлять
  перетаскиванием** (`movePage`); страницы PDF/DjVu и изображения можно
  добавлять в открытый документ. ✅

## 4.6 Отрисовка рамок и редактирование блоков-изображений
- Оверлей bbox поверх предпросмотра через QML `Repeater`, привязанный к
  `BoxListModel` (нормализованные прямоугольники). ✅ (заполняется, когда
  используется модельный парсер).
- Блоки изображений/диаграмм (`label` = `image` / `chart`)
  **редактируемы**: их можно перемещать, масштабировать (8 ручек изменения
  размера) и удалять прямо на предпросмотре. Удаление/изменение геометрии
  проталкиваются через `AppController::removeBlock` / `onBoxRectChanged` —
  сначала мутируется документ, модель рамок лишь отражает его (ADR 92) —
  и отражаются обратно в Markdown страницы через
  `IOutputParser::rebuildText`. ✅

## 4.7 Навигация по страницам и миниатюры
- Лента миниатюр страниц слева (`PageListModel` + `OcrImageProvider`
  `image://ocr/page/N`). ✅
- Каждая миниатюра показывает маркер **распознана / не распознана**, маркер
  **изменена** и маркер **дубликата** (красный), если на странице были
  дублирующиеся рамки. ✅
- Страницы можно **удалять** (наведение → ✕) и **переставлять
  перетаскиванием** (захват для перетаскивания). ✅
- Клик по миниатюре или кнопки ‹ › выполняют навигацию — **разрешено,
  пока идёт распознавание**. ✅

## 4.8 Остановка / отмена
- Кнопка панели инструментов у запущенного действия превращается в контроль
  остановки, и остановка уходит тому запуску, которому принадлежит
  (`AppController::stopCheck()` для очереди проверки / перепроверки /
  исправления / прочтения, `stopLayout()`, `stopAutoPipeline()`); единой
  остановки больше нет. Каждый `ModelRequestController` выставляет флаг
  остановки, учитываемый в обеих фазах — и разрешения подключения, и
  выполняющегося запроса, — и прерывает выполняющийся запрос
  (`OcrModel::abort()` → `LlamaClient::abort()`); уже ответившие блоки
  сохраняют свои результаты. ✅

## 4.9 Редактирование текста
- Правая панель — **редактируемый** `TextArea` (только для чтения, пока
  текущая страница не распознана). ✅
- Правки хранятся **по страницам** в отдельном классе `PageEditStore`
  (владеет `AppController`, ключ — индекс страницы) и перекрывают
  распознанный текст и для отображения, и для экспорта. ✅
- Изменённая страница помечается (роль `edited` в `PageListModel`) и может
  быть **откачена** к исходному распознаванию (`revertCurrentPageEdits`). ✅
- Свежее распознавание страницы **заменяет собой** любую ручную правку
  на ней. ✅
- `PageEditStore` также перемапит индексы правок после удаления или
  перестановки страницы (`remapAfterRemove` / `remapAfterMove`). ✅
- QML синхронизируется безопасно: программные перезагрузки защищены
  (`textArea.syncing`), чтобы никогда не выглядеть пользовательским вводом,
  а неизменённая перезагрузка не сбрасывает каретку (важно при «распознать
  всё» во время редактирования).

## 4.10 Экспорт
Реализуется компонентом **`Exporter`**, оркестрируемым **`ExportController`**
(владеет `Exporter` + `ExportRenderer` и всем потоком экспорта;
`AppController::exportPages` — пересыльщик, ADR 86). **Markdown —
единственный внутренний источник истины** (ADR #5/#10). Экспорт использует
**эффективный** текст страницы — то есть правку пользователя, если она есть,
иначе сырой результат распознавания.

| Формат   | Реализация                                       | Статус |
| -------- | ------------------------------------------------ | ------ |
| TXT      | напрямую (разделители страниц)                   | ✅     |
| Markdown | напрямую (`## Page N`) — внутренний источник     | ✅     |
| HTML     | **рендер через конвейер предпросмотра** (`ExportRenderer`): marked + DOMPurify + KaTeX в headless `QWebEnginePage`, автономный файл (стили + шрифты KaTeX встроены); страницы разделены горизонтальной чертой; резерв — писатель экранированного текста | ✅ |
| DOCX     | через **Pandoc** (Markdown на stdin → .docx, нативные формулы Word); каждая исходная страница начинается с новой страницы (сырой разрыв страницы OpenXML) | ✅     |
| PDF      | **рендер через конвейер предпросмотра** (`ExportRenderer` + `QWebEnginePage::printToPdf`); каждая исходная страница начинается с новой страницы; резерв — встроенные `QPdfWriter` + `QTextDocument` | ✅ |

- Путь рендеринга HTML/PDF переиспользует бандл предпросмотра
  (`qrc:/preview/export.html`: marked + DOMPurify + KaTeX), поэтому экспорт
  совпадает с предпросмотром Markdown 1:1 (настоящие заголовки, таблицы,
  блоки кода, математика). Pandoc для PDF больше **не** нужен (старый путь
  Pandoc→LaTeX удалён); он остался только для DOCX (ADR 63).
- **Разбивка страниц** (`output/splitPages`, по умолчанию включена):
  страницы разделяются без каких-либо подписей «Страница N» — горизонтальная
  черта (`---`) между страницами в Markdown, строка тире в TXT, `<hr>` в
  HTML; PDF и DOCX начинают каждую исходную страницу с новой физической
  страницы (печатный CSS `break-before:page` / сырой разрыв страницы
  OpenXML). Выключено → страницы идут сплошным потоком без разделителей
  (ADR 64).
- Рендер идёт в **UI-потоке** (`ExportRenderer`, внеэкранная
  `QWebEnginePage`); тяжёлое кодирование кропа→PNG/base64 и запись файлов
  остаются в потоках-воркерах. Прогресс показывается в строке статуса
  («Экспорт… (n/N)»).
- Pandoc ищется один раз через `QStandardPaths::findExecutable("pandoc")`
  (`Exporter::isPandocAvailable()` / `pandocExecutable()`); если поиск по
  PATH не удался, опрашиваются и известные места установки — Windows:
  `%LOCALAPPDATA%\Pandoc`, `Program Files\Pandoc`, `Program Files (x86)\Pandoc`;
  macOS: `/usr/local/bin`, `/opt/homebrew/bin`, `/opt/local/bin` — запуск
  из GUI часто видит устаревший или урезанный PATH, даже когда Pandoc
  установлен.
- Диалог сохранения предлагает **DOCX только при наличии Pandoc**
  (`AppController::exportNameFilters`). PDF предлагается всегда благодаря
  встроенному резервному писателю.
- Блоки изображений выдаются как `![alt](image://ocr/crop/<boxIndex>)`.
  Поскольку эти ссылки не имеют смысла вне приложения, каждый путь экспорта
  сначала разрешает их: путь рендеринга встраивает их как `data:` URL
  (`Exporter::embedImagesAsDataUrls`), прямые писатели сохраняют настоящие
  файлы изображений рядом с выводом (`Exporter::resolveImageReferences`,
  используя кропнутые пиксели из `AppController::croppedImage`).
- Область экспорта выбирается для многостраничных документов: **все
  распознанные страницы**, **текущая страница** или **диапазон страниц**
  (экспортируются только распознанные страницы из выбора).

## 4.16 Локальный рантайм (управляемый llama.cpp)
Слой управляемого рантайма (`src/runtime/`) позволяет LLocr запустить,
держать и остановить локальный процесс **`llama-server`** (бывший план
локального рантайма, этапы A–H, завершён; решения записаны как ADR в
`docs/07-glossary.md`).

- **Режим подключения** (`External` / `Managed`) выбирается мастером первого
  запуска (ADR 31). В `External` ничего не запускается; приложение общается
  с существующим OpenAI-совместимым эндпоинтом. В `Managed` LLocr запускает
  сервер сам. ✅
- **`RuntimeController`** (QML-синглтон `Runtime`, создаётся в `main.cpp`,
  ADR 36) — фасад: `ensureConnectionReady()`, `cancelPendingStart()`,
  Start/Stop/Restart, проба/автоопределение, `estimateModelMemory()` и
  состояние для QML (`state`, `busyState`, `statusMessage`,
  `loadProgressPercent`, `configValid`, `lockedOut`). ✅
- **`SelfTestController`** (QML-синглтон `SelfTest`) — кнопка «Check»
  мастера: `runSelfTest()`/`runSelfTestQml()`, состояние `selftest*`;
  отдельный потребитель `ensureConnectionReady()` (выделение из
  review 3.4). ✅
- **`RuntimeLog`** (QML-синглтон `RuntimeLog`) — живой просмотр журнала
  сервера (`serverLog` + копировать/очистить/открыть), питаемый фасадом при
  каждом (пере)запуске. В режиме **External** считывать нечего — процесса
  сервера нет, поэтому окно вместо этого показывает собственный журнал
  запросов клиента (`core/RequestJournal`: эндпоинт, модель, размеры,
  статус, длительность и начало ответа — в памяти, без API-ключа,
  ADR 228). ✅
- **Процесс**: `LlamaServerProcess` (QProcess, только argv, кольцевой буфер +
  ротируемый файловый журнал, опрос живости, перезапуск после падения ≤3 раз
  за 5 мин, terminate→kill) с `ProcessGuard` (Job Object на Windows,
  `PDEATHSIG` на Linux, best-effort `owner.json` на macOS — ADR 30). ✅
- **Разрешение подключения**: разрешение Managed = запуск → GET `/health`
  (резерв `/v1/models`) → проверка `--alias` → `ResolvedConnection`;
  конкурирующие вызывающие делят один future; Stop отменяет ожидающий запуск
  (§G-core). ✅
- Установка (этап D) в **Settings → Runtime** через синглтон
  `RuntimeInstaller`: `ReleaseCatalog` (GitHub Releases + `sha256`), выбор
  бэкенда, `DownloadTask`/`DownloadManager`, укреплённый `ArchiveExtractor`
  (ZIP + `.tar.gz` через zlib), транзакционный `InstallTransaction`,
  «Проверить обновления», «Очистить неиспользуемые сборки». ✅
- **Гарантии отсутствия сирот** и матрица ошибка→сообщение (§7.5 прежнего
  плана) — решения, записанные в `docs/07-glossary.md`. ✅

## 4.17 Модели и каталог (Hugging Face)
Управление моделями живёт в окне настроек **Модели** (через учитывающий
роли синглтон `ModelInstaller`, этап E): таблица задач с установленными
моделями, каталог пресетов и поиск по HF — его часть (см. 4.2).

- **`ModelCatalog`** — tree API Hugging Face с пагинацией `Link: rel=next`,
  **закрепление за commit-SHA** (дерево и каждая загрузка используют
  закреплённый `sha`, поэтому файлы не могут измениться между просмотром
  и загрузкой), обнаружение `mmproj`/многотомных GGUF, поиск
  (`/api/models?search=…&filter=gguf`); gated-репозитории → обработка
  `401/403` со ссылкой на лицензию (ADR 29). ✅
- **`ModelPreset` / `ModelPresetCatalog`** — заранее проверенные пары
  `model+mmproj+parser+prompt+ctx`. Встроенный `:/models/default-presets.json`
  (только чтение) + пользовательский `models/catalog.json` (чтение/запись),
  слияние по `id` (пользователь выигрывает), импорт/экспорт/сброс
  (ADR 42/43). ✅
- **`ModelRegistry`** — сохраняет установленные модели в
  `<modelsDir>/index.json` (`QSaveFile`), восстанавливается повторным
  сканированием при порче, различает **managed** (внутри `modelsDir`,
  удаляемые) и **external** (предоставленные пользователем, никогда
  не удаляются, только «убрать из списка») и запрещает удаление активной
  модели, пока сервер в `Ready`. ✅
- **Загрузка и проверка** — каждый GGUF скачивается с докачкой (`sha256`
  из `lfs.oid` или пресета) и проверяется по магии (`GGUF`); многотомные
  модели забираются как одно целое. ✅
- **HF-токен** опционален (для gated-репозиториев); `401/403` → «gated
  repository» + ссылка на страницу лицензии/принятия (ADR 29/44/45). ✅
- Память: шаг **Launch** мастера показывает **оценку RAM для модели +
  KV-кэша** и предупреждает, когда итог выглядит большим против системной
  RAM (`ModelMemoryEstimator`, H.2). ✅
- **Карта, которая нужна модели** (ADR 191): оценка — это *требование* —
  веса, проектор, черновик спекулятивного декодирования (его веса *и*
  контекст, в котором он работает), KV-кэш, рабочий набор, vision-энкодер
  и накладные расходы сервера. Профили моделей поставляют архитектуру
  (блок `memory`) и отобранные размеры, поэтому и ещё не скачанная
  квантизация несёт это число; выпадающий список квантизации в окне задач
  показывает его (`VRAM ≥ 11.4 GiB`), а Settings → Launch показывает ту же
  разбивку против карты. Всё измерено по собственному отчёту llama.cpp:
  vision-энкодер — из его clip-резерва (ставка на токен изображения или весь
  рабочий набор для двух проекторов, чья цена не следует за числом токенов —
  gemma-4-E4B, чей энкодер работает без flash attention, и Unlimited-OCR из
  архива, чей проектор тайлил страницу); черновик, будучи моделью сам по
  себе (MTP-черновики gemma-4; DSpark-черновик LFM2.5-VL лежит в архиве) —
  из собственного KV-кэша и вычислительного буфера; кэш sliding-window-гибрида —
  из фиксированных ячеек, которые получают его скользящие слои. Модель вне
  каталога не называет карты — об энкодере, который она запустила бы,
  ничего не известно. ✅
  Метод, калибровка каждой поставляемой модели и чек-лист для новой:
  `docs/18-memory-estimate.md` (скрипты измерения:
  `scripts/measure-memory.sh`, `scripts/memory-from-log.py`).

## 4.18 Мастер первого запуска (этап F)
На чистом профиле (`setupVersion == 0 && !setupDismissed`) `Main.qml`
запускает `SetupWizard.qml` — **без сетевых проб** (ADR 31). Шаги:

1. **Welcome** — «Локальный сервер (рекомендуется)» против «У меня уже есть
   сервер/api»; выбор External завершает мастер (`setupVersion = 1`) и
   открывает Connection.
2. **Runtime** — скачать llama.cpp (автоопределение платформы/бэкенда +
   ручной выбор бэкенда) или указать существующий бинарник; прогресс/ошибки/
   повтор; подсказка про SmartScreen/антивирус.
3. **Model** — пресет из каталога / поиск по HF / локальный GGUF; размер,
   примерная VRAM, ссылка на лицензию.
4. **Launch** — порт, ctx-size, n-gpu-layers, `autoStart` (по умолчанию
   выключен, ADR 44), предпросмотр команды, предупреждение об оценке памяти
   (H.2), **Check** → `runSelfTestQml()` (запуск → health → `/v1/models` →
   один OCR-запрос).
5. **Done** — итог; `setupVersion = 1`.

Навигация: Назад / Далее / Пропустить; шаг нельзя пройти вперёд, пока не
выполнено его условие; ✕ выставляет `setupDismissed = true`. Все строки
в `qsTr` и переведены в `llocr_ru.ts`. ✅

## 4.19 Эскиз интерфейса (G-UI)
Когда рантайм подключён, главное окно показывает его состояние:

- **`Footer.qml` индикатор управляемого рантайма** — цветная точка + текст:

  | Состояние  | Точка | Значение                                   |
  | ---------- | ----- | ------------------------------------------ |
  | `Stopped`  | серая | сервера нет / не настроено                 |
  | `Starting` | жёлтая | сервер запускается, модель загружается (прогресс) |
  | `Ready`    | зелёная | сервер поднят, модель загружена, распознавание доступно |
  | `Failed`   | красная | запуск/проба не удались (сообщение из §7.5) |
  | External   | серая | режим External (управляемого сервера нет)  |

  Клик по индикатору открывает общий **`ServerLogWindow`**. (Бывший ярлык
  пустого состояния «открывает Settings → Runtime» убран при переработке
  настроек — ADR 70; несконфигурированный случай покрывают мастер
  и настройки.) ✅
- **`Footer.qml` переключатель Start/Stop** — рядом с индикатором, виден
  только в режиме Managed. Когда конфигурация валидна (`configValid`:
  бинарник и модель существуют), он запускает управляемый llama-server
  с выбранной моделью — тот же `Runtime.startServer()`, что и кнопка Start
  в Settings → Runtime, — поэтому сервер можно прогреть сразу после запуска
  приложения, не открывая настройки. Пока сервер в `Starting`/`Ready`,
  кнопка превращается в **Stop** (`stopServer()`); остановка подтверждается,
  когда выполняется задача распознавания (вежливость §H.1.4, как и у
  Restart). Неактивна, когда рантаймом владеет другой экземпляр
  (`lockedOut`) или конфигурация неполна (тултип подсказывает Settings →
  Runtime). ✅
- **Статус загрузки** — во время `StartingRuntime` футер показывает спиннер
  занятости (тот же, что для распознавания, увеличенный до 28 px) плюс текст
  статуса, извлечённый из stderr («Загрузка модели… N%» из
  `loadProgressPercent()`, H.7). Отдельный прогресс-бар футера убран как
  неинформативный — проценты в stderr llama.cpp обновляются слишком грубо,
  чтобы быть полезными; спиннер + текст статуса читаются лучше. ✅
- **Баннер перезапуска** — редактирование `launch/*` при сервере в `Ready`
  показывает «Параметры запуска изменились — требуется перезапуск» с кнопкой
  **Restart**. ✅
- **Показ ошибок** — сообщения `Failed` следуют матрице §7.5. ✅
- **Settings → Runtime** несёт Start/Stop/Restart, статус пробы, Показать
  журнал и установщик этапа D; окно **Модели** несёт таблицу задач
  с установленными моделями, каталог пресетов и поиск по HF. ✅

## 4.20 Файл проекта (`.llocr`)
Всё рабочее состояние можно сохранить в один автономный файл **`.llocr`**
и открыть обратно (меню Файл: «Открыть проект…», «Сохранить проект»
`Ctrl+S`, «Сохранить проект как…» `Ctrl+Shift+S`; ADR 131). ✅

- **Формат** — ZIP, служащий только хранилищем: `project.json` (схема
  версии 1, конверт `format`/`version`, как у хранилищ профилей) и
  **встроенные исходные файлы** под `sources/` (многостраничный PDF/DjVu
  хранится один раз для всех своих страниц). Пишется `runtime/ZipWriter`,
  читается `ArchiveExtractor`.
- **На страницу** — эффективный текст (включая ручные правки), распознанная
  база и флаг изменённости (ADR 102/103), рамки с
  `checkStatus`/`correctedText`/прямоугольниками (результаты проверки
  и правки блоков-изображений), `parseNote`, `hasDuplicates`, плюс ссылка
  на источник (id файла + индекс страницы). Текущая страница восстанавливается.
  Настройки уровня приложения (подключение, модели, парсер, промпты
  проверки) — *не* состояние проекта.
- **Сохранение** (`AppController::saveProject` → `ProjectController`)
  снимает снимок в GUI-потоке, а пишет в воркере (`projectBusy` питает
  спиннер футера); файл пишется в `.tmp` и атомарно переименовывается.
  Исходный файл, которого больше нет, замещается живущим в странице
  отрендеренным изображением; если и его нет, сохранение отказывает
  и называет файл.
- **Открытие** (`AppController::openProject` → `ProjectController`)
  распаковывает в воркере в сессионный `QTemporaryDir`, принадлежащий
  контроллеру (извлечённые источники живут столько же, сколько документ),
  затем восстанавливает документ через публичный API `DocumentModel`
  (`appendFile`/`removePage`/`movePage`) — тот же путь ленивого рендеринга,
  выселения и повторного распознавания, что и при свежем импорте. Файл,
  импортированный дважды, восстанавливается последовательным потреблением
  слотов `(source, page index)` добавленных диапазонов.
- **Тесты** — `test_project_store` (запись и обратное чтение контейнера,
  валидация схемы, резервные пути) и
  `TestAppImport::projectSaveAndReopenRestoresTheWorkingState` (сквозной:
  распознать → править → переставить → сохранить → открыть).

## 4.21 Фасад контроллера (ADR 213)
`AppController` — ViewModel, к которой привязывается QML, и при этом
**фасад**: домены вокруг него живут в собственных классах в `src/app/`,
а фасад передаёт их состояние и сигналы. Имена свойств, их сигналы `NOTIFY`
и привязки QML не изменились — разделение для интерфейса незаметно.

- **`BlockInspector`** — выбранный блок: два слоя текста с их вердиктами,
  различия между ними, место блока в тексте страницы и подсветка выбранного
  диапазона.
- **`ProjectController`** — файл `.llocr`: чтение, запись, флаг занятости,
  путь и восстановление документа (§4.20).
- **`AvailabilityPresenter`** — матрица доступности: двадцать флагов панели
  инструментов и панели, отпечаток, охраняющий пересчёт (ADR 208), и область
  действия панели инструментов (выбор миниатюр).
- **`DecisionQueue` / `RecheckQueue` / `RemedyQueue`** — три очереди ролей
  над общим исполнителем `BlockQueue` и `BlockRunGate` (ADR 286): каждая
  владеет своим контроллером запросов и сама разрешает свои промпты; сбор
  блоков живёт в `BlockWorkList`, а фасад передаёт сигналы и хранит
  состояние показаний.
- **`LayoutController`** — проход разметки: он владеет layout-ролью
  активного профиля (промптом и парсером).

Документ, импорт, выбор парсера и строка статуса остаются в фасаде — это
его собственная работа. Каждый новый класс берёт нужное через структуру
`Deps` (ссылки и провайдеры) — идиома слоя.

## 4.22 Поворот страниц и проверка ориентации (ADR 218, 242, 243)
- **`DocumentPage::rotation`** (0/90/180/270) — поворот, который несёт
  страница; он применяется при рендеринге (`DocumentModel::renderFull` /
  `renderDetached`), поэтому предпросмотр, миниатюры, картинка для модели,
  кропы блоков и экспорт видят одну и ту же повёрнутую страницу.
  `DocumentPage::displaySize()` — размер, в котором страница показывается,
  и `pageAspect` парсера следует за ним.
- **Ручной поворот** — две кнопки на панели страницы поворачивают
  **текущую** страницу и сначала спрашивают, если она несёт распознавание
  (поворот его отбрасывает: блоки были прочитаны при старом повороте).
  Страница, повёрнутая вручную, помечается как таковая, и проверка
  ориентации её не трогает.
- **`app/PageOrientation`** — проверка, читающая **ось** текста из одной
  только картинки, в два этапа (ADR 243). Маска чернил берётся от локального
  (Sauvola) порога — глобальный Otsu режет страницу с градиентом освещения
  пополам —, внешние 2 % кадра игнорируются, и страница обрезается до
  ограничивающей рамки чернил: рамка сканера и тень корешка не попадают ни
  в один профиль. Сначала сметается наклон (±15°, поворот, который сильнее
  всего заостряет профиль строк, уточняется параболой), а квадрант решает
  **нормализованная автокорреляция** профилей — строчный профиль страницы
  текста повторяется с шагом интерлиньяжа, пока поперечный профиль остаётся
  гладким, — с абсолютным порогом, а не отношением, и только профиль,
  **чередующийся достаточно глубоко** (variation ≥ 0.65), может заявить ось:
  строчный профиль ныряет от чернил строки к бумаге промежутка, поперечный
  профиль текстового блока никогда не пустеет. Замыкание, перекрывающее
  слова строки, заодно считает похожие на строки компоненты: меньше десяти —
  и страница фотография или рисунок, а не текст. Измерено на корпусе проекта
  (десять страниц, по четыре поворота): ось была прочитана верно в каждом
  случае, когда её вообще удалось прочитать (прочитана в 36 из 40; страница
  таблиц читается в обе стороны и остаётся нерешённой), а наклон в 3° больше
  не прячет ось. Вердикт несёт угол исправления (`deskewDegrees`) и
  периодичность победившей оси (`confidence`) — за эти ручки и возьмётся
  автоповорот. Картинка **не** читает, где верх, — типографский знак этого
  несёт знак алфавита (в русском нижних выносных больше, чем верхних), так
  что это чтение поворачивало и лежащие правильно страницы — на корпусе
  проекта это чтение решило в 23 случаях и **ошиблось в 16 из них**
  (ADR 221, 242). 180° проекции не видят вовсе: одна картинка никогда
  не поворачивает страницу — она называет ось, и это всё, что она говорит.
- **`app/OrientationController`** — проверка, которая идёт до распознавания
  страниц (и до прохода разметки). Она читает одну только картинку: ни
  модели, ни сети, ни ожидания (ADR 242). У вердикта три исхода: страница
  **лежит боком** (ось так говорит; направление не читается, поэтому
  страница остаётся пользователю), **картинка не смогла прочитать страницу**
  (таблица, бланк — сказать о ней нечего) или страница лежит прямо
  и докладывать не о чем. Первые два помечают страницу:
  `DocumentPage::orientationProblem` (`PageOrientationProblem::Sideways` /
  `::Unclear`), маркер страницы в списке становится **красным**, а строка
  статуса называет причину («страница лежит боком… поверните вручную» /
  «ориентация не определяется»). Метка живёт со страницей: она переживает
  сохранение и повторное открытие (`.llocr`, §4.20) и уходит, когда
  пользователь поворачивает страницу вручную.
  Измеренный наклон в полградуса и больше **применяется** до чтения текста
  (ADR 244): проверка испускает `skewed(index, degrees)`, страница несёт
  `DocumentPage::skewDegrees`, а рендерер выпрямляет её после поворота на
  четверть (`PageRotation::deskewImage`, гладкая передискретизация по
  бумаге). Исправление складывается с выпрямлением, которое страница уже
  несёт, и самоустанавливается: следующая проверка выпрямленной страницы
  меряет меньше порога и молчит. Распознавание, которое несла страница,
  отбрасывается — блоки были прочитаны с невыпрямленных пикселей, — а наклон
  едет со страницей в проекте `.llocr` рядом с поворотом. Поворот на четверть
  лежащей боком страницы всё ещё ждёт картинку: направление — не то, о чём
  может рассказать картинка. Чего картинка не знает, **доставляют
  layout-модели** (ADR 245): проход разметки сохраняет на рамке токен
  поворота, который несёт каждый блок (у MinerU это `<|rotate_…|>`; TeleOCR
  из архива нёс третий тег `<orientation>`), и страница, помеченная
  проверкой как боковая, получает `suggestedTurn`, когда девять десятых её
  блоков голосуют за одно направление, — показывается кнопкой в один клик
  «Повернуть влево / вправо» рядом с красной меткой. Приложение советует,
  пользователь поворачивает: на корпусе токены называют верное направление
  в 14 из 20 боковых страниц — далеко до планки, которая понадобилась бы
  автоповороту, а неверный совет дороже отсутствия ответа (ADR 242). Совет
  едет в проекте `.llocr` вместе с меткой и умирает при любом повороте
  страницы.
- Проверка — настройка (**Settings → Output → «Проверять ориентацию
  страницы»**, по умолчанию включена).
