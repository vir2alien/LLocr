# Модель: PaddleOCR-VL-1.6

> Ручной запуск, контракт запросов и подключение в приложении. English
> version: `docs/25-paddleocr-vl.md`.

## 1. Что это

**PaddleOCR-VL-1.6** (PaddlePaddle, ~0.9 млрд параметров) — компактная VLM
распознавания элементов. Её VLM отвечает на шесть обученных элементных
промптов (OCR, table, formula, chart, seal, spotting); разметка страницы в
апстрим-пайплайне — отдельная модель RT-DETR, в GGUF она **не входит**.
Поэтому в LLocr модель закрывает только **blockRecognition** —
потранскрибировную кропа блока по типу. Лицензия Apache-2.0.

## 2. Файлы

| файл | размер | назначение |
|---|---|---|
| `PaddleOCR-VL-1.6-GGUF.gguf` | ~0.94 ГБ | модель — единственный квант в официальном репозитории (f16) |
| `PaddleOCR-VL-1.6-GGUF-mmproj.gguf` | ~0.88 ГБ | vision-проектор, **обязателен** |

- Репозиторий: `PaddlePaddle/PaddleOCR-VL-1.6-GGUF` — официальная упаковка
  (профиль `resources/profiles/models/paddleocr-vl.json`). Официальный
  репозиторий закреплён за обоими файлами: лестницы квантов в другом месте
  нет, а пресет скачивает всё из одного репозитория.
- Сборка llama.cpp **не старше b8200** (PR #18825 от 19.02.2026 —
  исправление vision-энкодера, нужное этой модели).

## 3. Запуск

Слой модели не несёт **ни одного** флага — серверный вызов из карточки это
`--temp 0` без системного сообщения, температура едет в слое запроса;
остальное — платформенный и политический слои:

```
llama-server \
  --model <modelsDir>/PaddlePaddle__PaddleOCR-VL-1.6-GGUF/PaddleOCR-VL-1.6-GGUF.gguf \
  --mmproj <modelsDir>/PaddlePaddle__PaddleOCR-VL-1.6-GGUF/PaddleOCR-VL-1.6-GGUF-mmproj.gguf \
  --alias llocr-blockrecognition \
  --host 127.0.0.1 --port <авто> \
  --n-gpu-layers 99 --flash-attn on --parallel 1 \
  --cache-reuse 0 --no-context-shift --no-warmup
```

## 4. Контракт запроса

- Без системного сообщения. Один chat-запрос на блок: `[image_url кроп,
  text <промпт типа>]`.
- Промпты типов — из карточки: `OCR:` для текста, `Table Recognition:`,
  `Formula Recognition:`, `Seal Recognition:`; все остальные метки
  словаря разметки отображаются на эти четыре (в профиле лежит полная
  карта, включая `equation_block` → formula-промпт).
- Ответ — текст блока и ничего больше, читается как есть (`parser: raw`).
  Апстрим просит таблицы в OTSL и конвертирует на клиенте; за формат
  табличного ответа в LLocr отвечает тот же промпт в профиле — единственное
  место для правки.
- Сэмплирование: `temperature 0`, штрафы нейтральные, `stream false`.

## 5. Замечания по верификации

Отдельной калибровки нет; распознанные блоки идут через обычный конвейер
decision/fix (docs/20; задача проверки говорит на визуальном диффе
minicpm-jev, ADR 254).

## 6. Настройки в приложении

- Задача — **blockRecognition** (окно «Модели»); дефолт задачи — mineru
  (ADR 252).
- Установка — Settings → Models (репозиторий HF
  `PaddlePaddle/PaddleOCR-VL-1.6-GGUF`) или шаг оборудования мастера.

## 7. Известные ограничения

- **Разметки нет.** Layout-модель апстрим-пайплайна в GGUF не входит —
  профиль сознательно не объявляет задачу layout; для разметки нужна
  mineru (в архиве её несла teleocr).
- Единственный квант f16: меньше спуститься некуда, но модель настолько
  мала, что это редко имеет значение. В имени файла нет токена кванта,
  поэтому квант берётся из профиля модели.
- Промпты chart и spotting из карточки не подключены — задач
  транскрипции диаграмм и spotting на всю страницу у блоков в LLocr нет.
