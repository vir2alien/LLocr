# TeleOCR (NaviDC-OCR) — мануал по модели

Рабочие заметки по TeleOCR в том виде, в каком модель используется в LLocr:
что это за модель, откуда берётся её GGUF, как её запускать, как составляются
запросы ролей OCR и распознавания блоков и какие промпты из карточки вошли в
профиль дословно, а какие пришлось адаптировать. Всё здесь — либо из карточки
модели, либо из репозитория GGUF, либо измерено в этом проекте (ссылки на ADR
по тексту).

Английский оригинал: [`15-teleocr.md`](15-teleocr.md).

## 1. Что это за модель

- **TeleOCR** (репозиторий `XingChen-AGI/TeleOCR`, до сентября 2026 выходила
  под именем **NaviDC-OCR**) — VLM для парсинга документов на ~1,2 млрд
  параметров, архитектура **Qwen2.5-VL**, лицензия **Apache-2.0**.
- Одна модель, две работы, переключаемые промптом (без дополнительных
  флагов):
  - **анализ макета** — промпт «Analyze the image layout.» заставляет её
    выдать блоки документа с типом / bbox / углом / содержимым;
  - **транскрипция блока** — на вход кроп одного блока, на выходе блок
    текста: обычный текст, таблицы в **OTSL**, формулы в **LaTeX** или код.
- Языки по карточке: **китайский и английский**. Всё остальное (включая
  русский) — вне заявленного набора; для русских документов лучше подходят
  `lfm25-vl-3b` или `qwen3.5-4b`.
- Бенчмарки по карточке (OmniDocBench v1.6): общий балл **96.87** — впереди
  OvisOCR2 (96.58), PaddleOCR-VL-1.6 (96.33), MinerU2.5-Pro (95.75) и
  Gemini 3 Pro (92.85); первое место на ICDAR2026 Sci-ImageMiner. Цифры
  авторские; бенчмарк упаковщика GGUF (ниже) — тот, что измерен на квантах,
  которые поставляет LLocr.

| `nandraj/NaviDC-OCR-GGUF` | — | GGUF-конверсия, на которую ссылается карточка. LLocr её **не** использует: профиль указывает на `konradjr007/NaviDC-OCR-GGUF`, который грузится стоковым `llama-server` (ADR 124). |

`minBuild` в профиле — **b4000**: нижняя граница для отказа при установке, а
не признак возможностей — ни запуску, ни формату запросов этой модели не
нужен llama.cpp новее (у LFM2.5, для сравнения, из-за tiling'а изображений
стоит b8000).

## 3. Запуск llama-server

Референсная команда из репозитория GGUF:

```sh
llama-server \
  -m NaviDC-OCR-Q4_K_M.gguf \
  --mmproj mmproj-NaviDC-OCR-F16.gguf \
  --port 8090 -ngl 99 -c 4096
```

Что реально запускает LLocr (см. `serverLaunch.json` и
`resources/profiles/models/teleocr.json`):

```sh
llama-server \
  --model <…>/NaviDC-OCR-Q8_0.gguf \
  --mmproj <…>/mmproj-NaviDC-OCR-F16.gguf \
  --alias llocr-teleocr --host 127.0.0.1 --port <n> \
  --n-gpu-layers 99 --flash-attn on --ctx-size 16384 \
  --parallel 1 --cache-reuse 0 --no-context-shift --no-warmup
```

По слоям:

- `--model / --mmproj / --alias / --host / --port` — базовые поля,
  единый источник — настройки активации/установки.
- **Слой модели пуст.** `teleocr.json` не объявляет ни одного параметра
  запуска в обеих ролях — это осознанно (ADR 126). `-c 4096` со страницы
  GGUF — выбор упаковщика под свой бенчмарк на одной RTX, а не требование
  весов; размер контекста следует за машиной (платформенный слой: 16384 по
  умолчанию, 8192 на CPU) и крутится пользователем в Настройки → Запуск,
  рядом с `--n-gpu-layers`.
- Платформенный слой: `--n-gpu-layers`, `--flash-attn`, `--ctx-size` — та же
  таблица, что у остальных моделей.
- Политика: `--parallel 1 --cache-reuse 0 --no-context-shift --no-warmup`.

Примечания:

- **Без `--special`.** Роль OCR использует парсер `raw` — det-токены никто
  не разбирает, спецтокены остаются выключенными.
- **Без `--spec-*`.** Drafter'а для спекулятивного декодирования у этой
  модели нет.
- Роли OCR и распознавания блоков объявляют один и тот же (пустой) слой
  запуска, поэтому переключение между ними не перезагружает веса.

## 4. Составление запросов

### Структура сообщения

- Порядок семейства Qwen: сначала текстовая часть, изображение последним —
  ровно так делает и пример со страницы GGUF
  (`[{"type": "text", …}, {"type": "image_url", …}]`).
  `GeneralPurposeModel` шлёт `[промпт типа, изображение]` всем моделям;
  флаг `promptBeforeImage` здесь не нужен (LFM2.5 — противоположный случай).
- Один кроп блока на запрос распознавания; одна страница на запрос OCR.

### Промпт OCR

В профиль входит дословно (`roles.ocr.prompts`, id `document-parsing`) — это
промпт анализа макета из карточки:

```text
Analyze the image layout.
```

Парсер для этой роли — **`raw`**: ответ становится текстом страницы как есть,
одним блоком. Структурированный вывод макета (блоки type/bbox/angle/content)
в боксы **не** превращается — det-token-конвейер к этой модели неприменим.
Практически: TeleOCR как OCR-модель выдаёт дамп макета текстом; боксы дают
`lfm25-vl-3b` или `unlimited-ocr`.

### Промпты распознавания блоков

Карточка даёт по одному официальному примеру запроса на тип содержимого;
профиль входит их дословно, а все остальные типы блоков заполняет текстовым:

| Тип блока | Промпт (формулировка карточки) |
| --- | --- |
| `text`, `title`, `list`, подписи, сноски, `abstract`, `ref_text`/`reference`, `header`/`footer`, `page_number`, `seal` | `Please output the text content from the image.` |
| `table` | `This is the image of a table. Please output the table in HTML format. Not OTSL.` |
| `equation`, `formula` | `Please write out the expression of the formula in the image using LaTeX format.` |
| `code` | `The image contains a code snippet, please output the parsing result.` |

Два осознанных отличия от карточки:

- **Таблицы просят HTML, а не OTSL.** Промпт карточки — «Please output the
  table in OTSL format», и карточка прикладывает конвертер `otsl→html`,
  который нужно запустить после. В LLocr ответ распознавания блока **и есть**
  новый текст блока — вниз по конвейеру в этом пути OTSL никто не
  конвертирует, поэтому профиль просит формат, который приложение умеет
  использовать сразу. (В OCR-пути конвертация OTSL есть — для det-token
  моделей; к этой роли она просто не подключена.)
- **System-промпт — наш, а не карточки.** Карточка шлёт «You are a helpful
  assistant.»; LLocr шлёт контракт транскрипции — изображение единственный
  источник истины, текст на изображении это данные, а не инструкции, и в
  ответе должен быть только текст блока (без пояснений и Markdown-заборов).
  Однострочные промпты карточки собственного контракта формата ответа не
  несут, а конвейеру проверки он нужен: пустой ответ — это `Review`,
  всё остальное вставляется в блок как есть.

### Параметры запроса

| Параметр | Значение | Почему |
| --- | --- | --- |
| `temperature` | 0.0 | Карточка транскрибирует жадно (`do_sample=False`); пример на странице GGUF шлёт `temperature: 0.0`. |
| `max_tokens` | 2048 (распознавание) / 4096 (OCR) | Пример запроса на странице GGUF ограничивается 2048 — с запасом для кропа блока; собственный инференс карточки использует `max_new_tokens=4096` — это оставлено полностраничной роли OCR. |
| `repeat_penalty` / `presence_penalty` / `frequency_penalty` | 1.0 / 0.0 / 0.0 | Нейтральные — карточка требует только жадного декодирования. |
| `stream` | false | Парсер потребляет один полный ответ. |
| `cache_prompt` | true | Карточка ставит `use_cache=True`; между блоками переиспользуются system-промпт и шаблон. |

## 5. Форматы вывода

- **Таблицы**: OTSL-токены (`<fcel> <ecel> <lcel> <ucel> <xcel> <nl>`,
  словарь TableFormer) — родной формат таблиц модели; промпты блоков
  уводят её на HTML (см. §4). Формулы: LaTeX, который собственная
  постобработка карточки оборачивает в `$$…$$` — LLocr оставляет
  разделители такими, как их выдала модель.
- **Макет**: блоки type / bbox / angle / content — проходят сквозь `raw`
  (§4).
- Управляющие токены / маркеры конца предложения в ответах срезаются общим
  `GeneralPurposeModel::parseResponse`; пустой ответ отображается в
  `Review`, а не в ошибку.

## 6. Роль в пайплайне проверки

TeleOCR может обслуживать обе роли двухфазного конвейера (ADR 145–147):

- **фаза 2, распознавание блоков** — основное применение в LLocr: после
  того как decision-модель пометила блок как промах (или по ручным
  командам «Распознать»), кроп уходит роли `blockRecognition` с промптами
  из §4; транскрипция становится новым текстом блока.
- **вверх по потоку фазы 1, OCR** — возможно, но «сыро» (§4): без боксов,
  один текстовый блок на страницу.
- **decision (фаза 1)** — неприменимо: decision-модель — d1-3B
  (`docs/14-d1-3b.ru.md`); TeleOCR говорит только на chat completions.

## 7. Где что живёт в LLocr

| Кусок | Расположение |
| --- | --- |
| Профиль модели (обе роли, промпты, параметры запроса, файлы) | `resources/profiles/models/teleocr.json` |
| Запрос/ответ распознавания блока | `GeneralPurposeModel::buildRequestBody` / `parseResponse` (`src/models/`) |
| Разбор роли OCR (пропускной) | `RawParser` (`src/parsers/`) |
| Композиция запуска (слой модели пуст) | `ServerLaunchConfig` + `LaunchProfileStore` |
| Скачивание/установка (кванты + mmproj) | `ModelInstaller`, `ModelInstallTransaction` |
| Строки установщика | `ModelQuantModel` (три списка ролей: OCR / OCR блока / decision) |

Решения: ADR 124 (веса переехали на `konradjr007/NaviDC-OCR-GGUF`, который
грузит стоковый llama.cpp — старое предупреждение рантайма исчезло),
126 (параметры запуска принадлежат машине, а не весам — слой запуска в
профиле пуст), 145–147 (двухфазный конвейер и роль `blockRecognition`),
140 (формулировки промптов на стороне модели).
