# Модель: MinerU2.5-Pro-2605-1.2B

> Ручной запуск, контракт запросов и подключение в приложении. English
> version: `docs/24-mineru.md`.

## 1. Что это

**MinerU2.5-Pro-2605-1.2B** (opendatalab) — компактная document-parsing
VLM, обученная на двухшаговом протоколе mineru-vl-utils: разметка макета
по странице, сжатой в 1036², затем потранскрибировная блоков по типам.
Одношагового страничного промпта в её наборе нет. В LLocr занимает
**layout** (проход «Разметить страницу») и **blockRecognition** (второй
шаг) — модель по умолчанию на обе задачи: одна модель закрывает весь
конвейер «разметить → распознать блоки» (ADR 252). Лицензия Apache-2.0.

## 3. Запуск

Слой модели несёт один флаг; остальное — платформенный и политический
слои:

```
llama-server \
  --model <modelsDir>/mradermacher__MinerU2.5-Pro-2605-1.2B-GGUF/MinerU2.5-Pro-2605-1.2B-Q8_0.gguf \
  --mmproj <modelsDir>/mradermacher__MinerU2.5-Pro-2605-1.2B-GGUF/MinerU2.5-Pro-2605-1.2B.mmproj-Q8_0.gguf \
  --alias llocr-layout \
  --host 127.0.0.1 --port <авто> \
  --special \
  --n-gpu-layers 99 --flash-attn on --parallel 1 \
  --cache-reuse 0 --no-context-shift --no-warmup
```

- **`--special` обязателен.** Ответ разметки — это special-токенная
  разметка `<|box_start|>x1 y1 x2 y2<|box_end|><|ref_start|>ТИП<|ref_end|>`,
  а сервер по умолчанию вырезает special-токены. Это была первопричина
  первых ошибок «no layout blocks».
- У обеих ролей набор флагов идентичен — связка «разметить → распознать»
  не перезагружает веса.
- Сжатие страницы в 1036² делает приложение (`LayoutController`), повторяя
  апстрим-калибровку — страницу в родном разрешении на layout-промпт не
  отправлять.

## 4. Контракт запроса

- **layout** — системное сообщение «You are a helpful assistant.», затем
  `[image_url (страница 1036²), text "\nLayout Detection:"]`; сэмплирование
  `top_p 0.01`, `temperature 0`. Парсер `mineru-layout`
  (`llocr_parsers`) читает строки `<|box_start|>` структурно — модельный
  адаптер их вырезать НЕ должен (свой санитайзер был вторым слоем той же
  истории с пустым ответом). Затем парсер поглощает покрытых детей
  составными контейнерами (equation_block → equation, image_block →
  image, list → text/list_item; покрытие ≥ 0.9, контейнер строго больше)
  и перемечает их.
- **blockRecognition** — тот же конверт, текстовая часть
  `"\nText Recognition:"` / `"\nTable Recognition:"` /
  `"\nFormula Recognition:"` по типу блока; в профиле лежит промпт на
  каждую метку, которую может назвать разметка, плюс
  `presence_penalty 1.0` / `frequency_penalty 0.05` (апстримовый
  антициклический набор). Ответ читается как есть (`raw`).

Словарь разметки стилизован в профиле: `doc_title`/`paragraph_title` →
heading, `caption`/`footnote`/`header`/`footer` → italic,
`list`/`list_item` → text и т.д.

## 5. Замечания по верификации

Проверено вживую на корпусе eq_hard: разметка возвращает
позиционированные блоки, поглощение схлопывает покрытых детей (22 → 18
блоков на референсной странице). Распознанные блоки идут через обычный
конвейер decision/fix (docs/20; задача проверки говорит на визуальном
диффе minicpm-jev, ADR 254).

## 6. Настройки в приложении

- Задачи — **layout**, **blockRecognition** (окно «Модели»); mineru —
  дефолт обеих задач (ADR 252).
- Установка — Settings → Models (репозиторий HF
  `mradermacher/MinerU2.5-Pro-2605-1.2B-GGUF`) или шаг оборудования
  мастера.
- Сам проход разметки: тулбар страницы, «Разметить страницу» (ADR
  149–150).

## 7. Известные ограничения

- **Только два шага.** Обученного одношагового страничного промпта нет —
  просить сырую транскрипцию страницы out of distribution.
- Разметка ответа — служебный словарь: любой новый потребитель layout-ответа
  обязан обходить санитайзер сервис-токенов (регэксп `<|...|>` съедает
  данные).
- GGUF-репозиторий — сторонняя упаковка (`mradermacher`).
- **MLX-конверсия MinerU2.5 теряет кириллицу.** Замерено на
  `mlx-community/MinerU2.5-2509-1.2B-bf16` под omlx: layout-ответ приходит
  транслитом («Полное Термунесское солоТиБлене ИлЛинДрческОй» — латинские
  омоглифы и буквы через пробел), тогда как та же страница через llama.cpp
  (GGUF этого профиля) и через `GLM-OCR-bf16` (тоже mlx-community) читается
  верно. Текстовый запрос к MLX-сборке отвечает тем же транслитом, то есть
  дефект в токенизаторе этой конверсии, а не в приложении и не в сервере:
  для русских документов нужен MinerU в сборке llama.cpp или другая модель.
