# LFM2.5-VL-3B — мануал по модели

Рабочие заметки по LiquidAI/LFM2.5-VL-3B в том виде, в каком модель
используется в LLocr: что это за модель, как её запускать, как составлять
запросы, как выглядит её ответ и что нужно компенсировать на нашей стороне.
Всё здесь — либо из карточки модели, либо измерено в этом проекте (ссылки на
ADR по тексту).

Английский оригинал: [`13-lfm25-vl-3b.md`](13-lfm25-vl-3b.md).

## 1. Что это за модель

- **LiquidAI/LFM2.5-VL-3B** — мультимодальная вариация LFM2.5 для edge-развёртывания:
  языковой бэкбон LFM2.5-2.6B + визуальный энкодер SigLIP2 NaFlex 400M,
  ~3,1 млрд параметров, словарь 128 000 токенов, контекст 32 768 токенов.
- 16 языков, включая русский и английский.
- Позиционирование по карточке: однотурновые, высокоскоростные задачи с низкой
  задержкой. Модель **отвечает напрямую, без рассуждений** — thinking-режима
  нет, пространные chain-of-thought промпты ей только вредят.
- Полностраничный OCR с разметкой макета (layout annotation) — обученная
  базовая возможность; именно её использует LLocr. Обучен и grounding
  (боксы по запросу на естественном языке) — поэтому координаты в разметке
  вообще осмысленные.
- Родные форматы: **OTSL** (словарь TableFormer: `<fcel> <lcel> <ucel> <xcel>
  <nl>`) для таблиц, LaTeX для формул, обычный текст для остального.

Черновик опционален: целевая модель работает и без него, просто медленнее.
LLocr скачивает его вместе с моделью и записывает путь в `launch/draftPath`
(ADR 137).

## 3. Запуск llama-server

**Минимальная сборка: b8000.** Тайлинг изображений LFM2.5-VL появился в
llama.cpp в PR [#19454](https://github.com/ggml-org/llama.cpp/pull/19454);
более старые сборки неправильно обрабатывают большие страничные изображения.

Эталонная команда из карточки:

```sh
llama-server -hf LiquidAI/LFM2.5-VL-3B-GGUF:F16 \
  -hfd LiquidAI/LFM2.5-VL-3B-DSpark-GGUF:F16 \
  --spec-type draft-dspark --spec-draft-n-max 8 --spec-draft-n-min 0 \
  -ngl 99 -ngld 99 -fa on
```

Что фактически запускает LLocr (слои флагов — см. `serverLaunch.json` и
`resources/profiles/models/lfm25-vl-3b.json`):

```sh
llama-server \
  --model <…>/LFM2.5-VL-3B-Q8_0.gguf \
  --mmproj <…>/mmproj-LFM2.5-VL-3B-F16.gguf \
  --model-draft <…>/LFM2.5-VL-3B-DSpark-F16.gguf \
  --alias llocr-lfm25-vl-3b --host 127.0.0.1 --port <n> \
  --special --spec-type draft-dspark --spec-draft-n-max 8 --spec-draft-n-min 0 \
  --n-gpu-layers 99 --flash-attn on --ctx-size 16384 \
  --parallel 1 --cache-reuse 0 --no-context-shift --no-warmup
```

По слоям:

- `--model / --mmproj / --model-draft / --alias / --host / --port` — базовые
  поля, единый источник — настройки активации/установки;
- слой модели (владеет `lfm25-vl-3b.json`, обе роли):
  - `--special` — выводить служебные токены; они нужны det-токен парсеру;
  - `--spec-type draft-dspark` — спекулятивное декодирование с черновиком
    DSpark;
  - `--spec-draft-n-max 8` — черновик обучен с блоком 9; 8 — рекомендация
    карточки для Apple silicon;
  - `--spec-draft-n-min 0` — позволить черновику пропускать неуверенные шаги;
- платформенный слой (память машины): `--n-gpu-layers`, `--flash-attn`,
  `--ctx-size`. Для рецепта DSpark нужен `flash-attn on`;
- политика (как сервер обслуживается): `--parallel 1 --cache-reuse 0
  --no-context-shift --no-warmup`.

Примечания:

- **Спекулятивное декодирование точно при жадном декодировании** — целевая
  модель проверяет каждый предложенный токен, поэтому вывод совпадает с
  выводом целевой модели без черновика. С рекомендованными карточкой
  `temperature=0.2` (распознавание) реализация в llama.cpp также без потерь
  (отклонённые токены отбрасываются); acceptance rate виден в тайминговых
  логах сервера.
- На сборках без флагов `--spec-*` проба возможностей LLocr повторяет запуск
  без offending-флагов — модель деградирует до скорости без спекуляции,
  но никогда к неправильному выводу.
- Обе роли (OCR и проверка) объявляют **одинаковый** launch-слой намеренно:
  переключение задач переиспользует загруженные веса вместо перезагрузки, а
  DSpark ускоряет и проверку.

## 4. Составление запросов

### Структура сообщения

- Шаблон диалога — подобный ChatML; при отсутствии system-сообщения
  применяется дефолт карточки («You are a helpful assistant trained by Liquid
  AI.»).
- **Сначала текст, изображение — последним.** Все примеры LFM2.5 показывают
  текст пользователя, а затем тег `<image>`. В OpenAI-совместимом API это
  значит, что массив частей должен быть `[text, image_url]` — в LLocr это
  закодировано флагом `promptBeforeImage: true` в обеих ролях профиля
  (семейство Qwen документирует обратный порядок, поэтому флаг — данные
  конкретной модели).
- Одна страница на запрос: промпт говорит о страницах во множественном числе,
  но сообщение с одним изображением — это просто `image_index=0`.

### Промпт распознавания

Поставляется дословно в профиле (`roles.ocr.prompts`, id
`layout-annotation`) — это рекомендуемый промпт из карточки модели
(приведён в английской версии документа; отправляется на английском, менять
формулировки нельзя — это обученная форма).

### Параметры запроса

| Параметр | Значение | Почему |
| --- | --- | --- |
| `temperature` | 0.2 | Рекомендация карточки (вместе с top-k 50). |
| `top_k` | 50 | Рекомендация карточки. |
| `repeat_penalty` | 1.0 | Рекомендация карточки (выключен). |
| `max_tokens` | 8192 | Полная размеченная страница регулярно превышает 4k токенов. |
| `stream` | false | Парсер потребляет один цельный ответ. |

Для роли **проверки** сэмплинг жадный (`temperature 0`, штрафы выключены,
`stream false`, `cache_prompt true`) — структурному протоколу OK/FIX/REVIEW
нужна детерминированность, а жадное декодирование сохраняет точность
спекуляции DSpark.

## 5. Координаты: канва 2:3

Модель привязывает боксы **не к странице**. Координаты, которые она
возвращает, откалиброваны на портретную канву **2:3** (высота:ширина = 1.5):
страница вписывается в эту канву, и боксы относятся к вписанному изображению.

Обозначим `a = H/W` (соотношение сторон страницы, у портретных `a > 1`):

- **`a ≤ 1.5`** (любая обычная портретная страница, A4 — 1.414) — ширина
  заполняет канву, высота леттербоксится и центрируется:
  - `x_model = x_true` (точно),
  - `y_model = y_true · (a/1.5) + 500 · (1 − a/1.5)`.
  - A4: `y_model ≈ 0.945 · y_true + 27.5` (из 1000). Измерено на реальном
    ответе: остатки ≤ 4 единиц; без этой коррекции все блоки съезжают вверх
    примерно на 5% высоты страницы.
- **`a > 1.5`** (выше, чем 2:3) — высота заполняет, ширина леттербоксится:
  - `y_model = y_true` (точно),
  - `x_model = x_true · (1.5/a) + 500 · (1 − 1.5/a)`.

**Компенсация в LLocr:** `Lfm25VlParser` переопределяет хук `calibrateRect()`
обратным отображением, а `ParserOptions::pageAspect` несёт `H/W` страницы
(заполняется из `DocumentPage::pixelSize`, A4 по умолчанию). Если будущее
обновление LiquidAI или llama.cpp уберёт леттербокс — удаление переопределения
вернет тождественное отображение (ADR 136).

Рисовать боксы модели на странице без этой коррекции нельзя — оверлей уедет
вверх до ~5% высоты страницы.

## 6. Особенности вывода, которые поглощает парсер

Парсер `lfm2.5-vl` (семейство det-токенов) обрабатывает артефакты
транскрипции модели; всё перечисленное в LLocr исправляется. Список — чтобы
сырые ответы можно было читать при отладке (`LLOCR_RAW_DEBUG=1` сохраняет
каждый запрос/ответ):

- **Таблицы приходят в OTSL** (`<fcel> <lcel> <ucel> <xcel> <nl>`), и токены
  утекают также в блоки `text` и `equation` — везде, а не только внутри
  `table`. Конвертируются в GFM-таблицы (или настоящий HTML с
  rowspan/colspan при включённых «Таблицы как HTML»).
- **Дрейф подписей таблиц**: модель иногда пишет подпись как
  `<label>…</label>` + строки OTSL в `<content>` — переписывается в синтетическую
  пару `table_caption` + `table`.
- **Формулы приходят обёрнутыми в доллары**: `$C_{MHA}(T) = L_m + T$. (5)` —
  обёртка снимается, номер в конце становится `\tag{n}`, вложенный инлайн
  `\(...\)` внутри display `\[…\]` распаковывается.
- `image_block` превращается в placeholder изображения, как `image`/`chart`;
  в alt-тексте остаётся только первая строка.
- Дубликаты (модель повторяет абзац со сдвинутыми координатами)
  детектируются по тексту, дотягиваются (tail-join) или отбрасываются и
  помечаются `duplicateSuspect` для прохода проверки.

## 7. Использование в роли проверки

Профиль объявляет роль `check` рядом с `ocr` (ADR 138) — LFM2.5-VL-3B можно
выбрать верификатором блоков:

- Те же веса, тот же launch-слой — переключение OCR ↔ проверка не
  перезагружает сервер, а DSpark ускоряет проверку бесплатно.
- Структурный протокол: ответ должен быть ровно `OK`, `FIX` + перевод строки +
  полный исправленный блок или `REVIEW`. Профиль несёт собственный
  system-промпт и промпты на каждый тип блоков, первый абзац которых —
  обязательный контракт формата ответа: маленькая direct-answer модель
  значительно лучше держит формат, когда он повторён в запросе и оформлен как
  её обученные структуры «строка-заголовок + содержимое» (ADR 139/140).
- Известный вырожденный вывод: голый `FIX` без исправленного блока. LLocr
  отображает его в `REVIEW` (нужен человек) вместо ошибки. Исправленный текст
  без строки `FIX` остаётся ошибкой — его не отличить от комментария.
- Структура сообщения: промпт типа, затем OCR-кандидат, затем изображение
  (`promptBeforeImage` действует и для check-роли).

## 8. Где что лежит в LLocr

| Часть | Расположение |
| --- | --- |
| Профиль модели (промпт, launch-слой, параметры запроса, check-роль, модуль DSpark, `promptBeforeImage`) | `resources/profiles/models/lfm25-vl-3b.json` |
| Парсер (`lfm2.5-vl`): конвертация OTSL, калибровка, правки формул | `src/parsers/` (`Lfm25VlParser`, база `DetTokensParser`) |
| Карта «метка → стиль» (включая `image_block`, `code`) | `resources/profiles/labels.json` |
| System-промпт и промпты блоков верификатора | check-роль профиля (единственный источник; общего файла промптов больше нет) |
| Скачивание/установка DSpark | `ModelInstallTransaction` (любая модель с `files.mtp`) |
| Композиция флагов запуска | `ServerLaunchConfig` + `LaunchProfileStore` (таблица запуска показывает только `n-gpu-layers`, `flash-attn`, `ctx-size`) |

Решения: ADR 87 (адаптер модели и парсер), 112 (калибровка как хук парсера),
135 (обработка дубликатов), 136 (калибровка 2:3 и правки формул), 137 (модуль
DSpark), 138–140 (check-роль, промпты верификатора, обработка голого FIX),
141 (упрощение таблицы запуска), 143 (аудит порядка частей).
