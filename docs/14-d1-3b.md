# d1-3B — model manual

Working notes for LiquidAI/d1-3B as it is used in LLocr: what the model is,
how to launch it, how the `/v1/systemone` request and its answer are shaped,
how the match threshold is applied, and where everything lives in the code.
Everything here is either from the model card or measured in this project (see
the ADR references).

A Russian mirror of this document lives in
[`14-d1-3b.ru.md`](14-d1-3b.ru.md).

## 1. What the model is

- **LiquidAI/d1-3B** — a **decision model** post-trained from
  LFM2.5-VL-3B (LFM2.5-2.6B language backbone + SigLIP2 NaFlex 400M vision
  encoder, ~3.1B parameters, 128,000-token vocabulary, 32,768-token context).
- It answers named, typed questions over a *state* (text, JSON, images, or a
  mix) in **one forward pass with zero generated tokens**. It is not a chat
  model and does not write text — there is nothing to sample, and no verdict
  format a small model could violate.
- Multimodal: images and text live in the same state. On eleven public image
  benchmarks it scores 74.1 (its own base LFM2.5-VL-3B: 73.9); with the
  images removed the same questions score 45.1, so the answers really come
  from the images.
- Best decision model under 10B on the Decision Index 0.2.1 (48.57).
- Speed per the card (warm calls, one request): 8 ms on an RTX 4090, 30 ms on
  an Apple M5 Pro; a 384 px image adds ~17–60 ms depending on hardware.
- 16 languages; license `lfm1.0`.
- Positioning per the card: yes/no, a pick from named options, a rating —
  routing, classification, extraction checks, LLM-as-a-judge scoring, and
  **visual inspection**. The last one is what LLocr uses.

No speculative-decoding drafter exists for d1 — and none is needed: the model
generates zero tokens, so a drafter has nothing to accelerate.

## 3. Launching llama-server

**No minimum build is pinned.** The `/v1/systemone` endpoint is newer than
any build LLocr pins for other models; an old runtime starts the model fine
and fails per-request with an HTTP 404 instead, which the verification queue
surfaces as an error. If decision checks fail with "No answers in response"
or an endpoint error, update the runtime in Settings → Runtime first.

The model card's reference command:

```sh
llama-server -hf LiquidAI/d1-3B-GGUF:Q8_0
```

What LLocr actually starts (the flag layers, see `serverLaunch.json` and
`resources/profiles/models/d1-3b.json`):

```sh
llama-server \
  --model <…>/d1-3B-Q8_0.gguf \
  --mmproj <…>/mmproj-d1-3B-Q8_0.gguf \
  --alias llocr-decision --host 127.0.0.1 --port <n> \
  --ctx-size 8192 \
  --n-gpu-layers 99 --flash-attn on \
  --parallel 1 --cache-reuse 0 --no-context-shift --no-warmup
```

Layer by layer:

- `--model / --mmproj / --alias / --host / --port` — core fields,
  single-sourced from the activation/install settings.
- Model layer (owned by `d1-3b.json`, the `decision` role):
  - `--ctx-size 8192` — the state text and the image embeddings must fit in
    one prompt; the model reads both in a single pass. (The model supports
    32,768; a block crop plus a block-sized candidate never gets near that,
    and the smaller window starts faster on machines without flash
    attention.)
- Platform layer (the machine's memory): `--n-gpu-layers`, `--flash-attn`,
  `--ctx-size` — same table as for the other roles.
- Policy: `--parallel 1 --cache-reuse 0 --no-context-shift --no-warmup`.

Notes:

- **No `--special`, no `--spec-*` flags.** Nothing parses special tokens out
  of the reply (there is no reply text at all), and there is no drafter.
- The decision role declares its own launch layer and its own weights, so a
  verification run always performs exactly one role switch to it and one back
  (see §6). Unlike LFM2.5-VL this model shares nothing launch-related with
  the OCR role.
- `cache_prompt` is not set for decision requests: with zero output tokens
  there is no decode phase to reuse, and every request carries a different
  crop anyway.

## 4. The `/v1/systemone` request

Decision models do not use `/v1/chat/completions`. The request is POSTed to
`{base}/v1/systemone` (`LlamaClient::endpointUrl` takes the path;
`DecisionModel::buildRequestBody` builds the body):

```json
{
  "state": "1. Introduction",
  "images": ["data:image/png;base64,…"],
  "questions": {
    "match": {
      "type": "noul",
      "instructions": "The state is a text fragment recognized from the
                       attached image by an OCR model. Does the image show
                       exactly this text?"
    }
  }
}
```

- **`state`** — in LLocr, the OCR candidate text of the block. It is data,
  not an instruction.
- **`images`** — the block crop, encoded as a data URL (PNG), exactly like
  the chat requests send it.
- **`questions`** — a named map. LLocr asks exactly one question, `match`,
  of type **`noul`** (yes/no). The question wording travels in the model
  profile (`roles.decision.systemPrompt` of `d1-3b.json`); when a profile
  carries none, `VerificationQueueController` falls back to the generic
  question above.
- The card documents two more question types — `choice` (named options) and
  `score` (2–10 ordered levels) — LLocr does not use them; `noul` is all a
  matches/does-not-match gate needs.

### The answer

```json
{
  "answers": { "match": { "noul": 0.97 } },
  "usage": { "input_tokens": 42, "output_tokens": 0 }
}
```

`output_tokens` is always 0 — the probability is read straight off the
model's head in the single pass. `DecisionModel::parseResponse` accepts all
three spellings seen across endpoint versions: a bare number
(`"match": 0.97`), `{"noul": 0.97}`, and `{"probability": 0.97}`. Anything
else (missing `match`, no `answers`, malformed JSON) is an error, never a
silent verdict.

## 5. The match threshold

The raw probability is thresholded on the client, in
`VerificationQueueController` (the threshold itself lives in
`SettingsStore::decisionMatchThreshold`, key `decision/matchThreshold`):

- **P(match) ≥ threshold → the block is marked Ok.** Anything below goes to
  phase 2 (re-recognition).
- Default **0.5**; clamped to [0, 1]. The Decision window exposes it as
  «Match threshold (%)» (a 0–100 spin box, step 5).
- The comparison is `>=`: with the default, a 0.50 probability still counts
  as a match.
- Lowering the threshold sends more blocks to the (expensive) re-recognition
  pass; raising it trusts the decision model more. The card describes the
  answers as **calibrated**, so 0.5 is a meaningful default, not a knob
  picked at random.

## 6. Role in the verification pipeline

ADR 145 split the old single-model check stage into two phases:

1. **OCR** — unchanged.
2. **Decision** — every queued block (same enablement rules as before:
   block-type filter, `duplicateSuspect` blocks included, non-empty text) is
   sent to the decision model. Matches are marked **Ok**; misses are queued.
   A *failed* decision request (network, 404, malformed reply) is not a
   verdict: the block stays unchecked and the error is reported, instead of
   the block being silently re-recognized on a broken stage.
3. **Block recognition** — the failures go to the `blockRecognition` role
   (formerly `check`), which simply transcribes the crop; the transcription
   becomes the new block text (`Fixed`).

The phases run back to back, so one verification run costs **at most two
server role switches** — one to the decision model, one back (the second
phase reuses the switch: after phase 1 the server is on the decision model,
and the next OCR request switches it back). If the OCR and block-recognition
roles share one model, those switches collapse per the usual same-weights
rule.

Manual entries are unchanged: «Check page», «Check all» and the per-block
«Verify» all run the same two-phase queue; the `autoCheck` setting triggers
it after recognition, as before.

## 7. External mode

In External mode the decision request goes to the configured base URL +
`/v1/systemone`, with the model id taken from the «Model name (decision)»
field of the external settings (`decision/modelName`). The endpoint is a
llama.cpp extension: an OpenAI-compatible server that only speaks
`/v1/chat/completions` will answer 404 and every decision check fails. When
serving all three roles from one external llama-server, load the decision
model into it — or run it as a second server and point a separate profile at
it.

## 8. Where things live in LLocr

| Piece | Location |
| --- | --- |
| Model profile (decision role, question wording, launch layer, quantizations) | `resources/profiles/models/d1-3b.json` |
| HTTP client of the endpoint (request build, answer parse) | `src/models/DecisionModel.{h,cpp}` |
| Per-block driver (resolve → judge, abort) | `src/app/DecisionController.{h,cpp}` |
| Two-phase queue, threshold comparison, fallback question | `src/app/VerificationQueueController.cpp` |
| Settings (paths, profile id, external name, threshold) | `src/config/SettingsStore.{h,cpp}` — `decision/*` group |
| Launch composition (`ConnectionRole::Decision`) | `src/runtime/ServerLaunchConfig.cpp`, `RuntimeController.cpp` |
| Download/activation (third role list) | `ModelInstaller`, `ModelInstallTransaction`, `ModelQuantModel` |
| UI (window, model list, threshold) | `Settings/ModelSettingsWindow.qml`, `Settings/LocationTab.qml`, `Common/ModelDownloadList.qml` |

Design decisions: ADR 145 (the two-model pipeline, the role rename
`check` → `blockRecognition`, the decision role, the registry/settings
migration), 122 (the one-row-per-model installer list the decision window
reuses), 133/134 (stop semantics and the ask-only-unanswered queue rule,
both inherited unchanged).
