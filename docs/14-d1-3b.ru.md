# d1-3B — мануал по модели

Рабочие заметки по LiquidAI/d1-3B в том виде, в каком модель используется в
LLocr: что это за модель, как её запускать, как устроены запрос к
`/v1/systemone` и его ответ, как применяется порог совпадения и где что лежит
в коде. Всё здесь — либо из карточки модели, либо измерено в этом проекте
(ссылки на ADR по тексту).

Английский оригинал: [`14-d1-3b.md`](14-d1-3b.md).

## 1. Что это за модель

- **LiquidAI/d1-3B** — **decision-модель**, дообученная из LFM2.5-VL-3B
  (языковой бэкбон LFM2.5-2.6B + визуальный энкодер SigLIP2 NaFlex 400M,
  ~3,1 млрд параметров, словарь 128 000 токенов, контекст 32 768 токенов).
- Она отвечает на именованные типизированные вопросы по *состоянию* (state:
  текст, JSON, изображения или их смесь) **за один проход forward с нулём
  сгенерированных токенов**. Это не chat-модель и не генератор текста —
  сэмплировать нечего, и нет формата вердикта, который маленькая модель могла
  бы нарушить.
- Мультимодальна: изображения и текст живут в одном состоянии. На одиннадцати
  публичных image-бенчмарках набирает 74.1 (её собственная база LFM2.5-VL-3B:
  73.9); без изображений те же вопросы дают 45.1 — то есть ответы действительно
  берутся из картинок.
- Лучшая decision-модель до 10B в Decision Index 0.2.1 (48.57).
- Скорость по карточке (прогретые вызовы, один запрос): 8 мс на RTX 4090,
  30 мс на Apple M5 Pro; изображение 384 px добавляет ~17–60 мс в зависимости
  от железа.
- 16 языков; лицензия `lfm1.0`.
- Позиционирование по карточке: да/нет, выбор из именованных опций, оценка —
  маршрутизация, классификация, проверки извлечения, LLM-as-a-judge и
  **визуальная инспекция**. Последнее — то, что использует LLocr.

## 3. Запуск llama-server

**Минимальная сборка не зафиксирована.** Эндпоинт `/v1/systemone` новее любой
сборки, которую LLocr фиксирует для других моделей; старый рантайм загрузит
модель нормально, но будет падать уже на запросе с HTTP 404, и очередь
проверки покажет это как ошибку. Если decision-проверки падают с «В ответе
нет ответов (answers)» или ошибкой эндпоинта — сначала обновите рантайм в
Настройки → Runtime.

Эталонная команда из карточки:

```sh
llama-server -hf LiquidAI/d1-3B-GGUF:Q8_0
```

Что фактически запускает LLocr (слои флагов — см. `serverLaunch.json` и
`resources/profiles/models/d1-3b.json`):

```sh
llama-server \
  --model <…>/d1-3B-Q8_0.gguf \
  --mmproj <…>/mmproj-d1-3B-Q8_0.gguf \
  --alias llocr-decision --host 127.0.0.1 --port <n> \
  --ctx-size 8192 \
  --n-gpu-layers 99 --flash-attn on \
  --parallel 1 --cache-reuse 0 --no-context-shift --no-warmup
```

По слоям:

- `--model / --mmproj / --alias / --host / --port` — базовые поля, единый
  источник — настройки активации/установки;
- слой модели (владеет `d1-3b.json`, роль `decision`):
  - `--ctx-size 8192` — текст состояния и эмбеддинги изображения должны
    поместиться в один промпт; модель читает и то и другое за один проход.
    (Модель поддерживает 32 768, но кроп блока с блоком-кандидатом туда и
    близко не подходит, а меньшее окно быстрее стартует на машинах без
    flash attention.)
- платформенный слой (память машины): `--n-gpu-layers`, `--flash-attn`,
  `--ctx-size` — та же таблица, что и у остальных ролей;
- политика: `--parallel 1 --cache-reuse 0 --no-context-shift --no-warmup`.

Примечания:

- **Никаких `--special` и `--spec-*`.** Из ответа нечего парсить по
  служебным токенам (текста ответа нет вообще), и черновика нет.
- Роль decision объявляет собственный launch-слой и собственные веса, поэтому
  прогон проверки делает ровно одно переключение роли на неё и одно обратно
  (см. §6). В отличие от LFM2.5-VL эта модель не разделяет с OCR-ролью ничего
  из launch-конфигурации.
- `cache_prompt` для decision-запросов не выставляется: при нуле выходных
  токенов нет decode-фазы, которую можно переиспользовать, а каждый запрос
  несёт новый кроп.

## 4. Запрос к `/v1/systemone`

Decision-модели не используют `/v1/chat/completions`. Запрос отправляется на
`{base}/v1/systemone` (`LlamaClient::endpointUrl` принимает путь; тело строит
`DecisionModel::buildRequestBody`):

```json
{
  "state": "1. Introduction",
  "images": ["data:image/png;base64,…"],
  "questions": {
    "match": {
      "type": "noul",
      "instructions": "The state is a text fragment recognized from the
                       attached image by an OCR model. Does the image show
                       exactly this text?"
    }
  }
}
```

- **`state`** — в LLocr это текст OCR-кандидата блока. Это данные, а не
  инструкция.
- **`images`** — кроп блока, закодированный в data URL (PNG), ровно как в
  chat-запросах.
- **`questions`** — именованная карта. LLocr задаёт ровно один вопрос,
  `match`, типа **`noul`** (да/нет). Формулировка вопроса хранится в профиле
  модели (`roles.decision.systemPrompt` в `d1-3b.json`); если в профиле её
  нет, `VerificationQueueController` подставляет общий вопрос выше.
- В карточке описаны ещё два типа вопросов — `choice` (именованные опции) и
  `score` (2–10 упорядоченных уровней) — LLocr их не использует; для шлюза
  «совпадает/не совпадает» достаточно `noul`.

### Ответ

```json
{
  "answers": { "match": { "noul": 0.97 } },
  "usage": { "input_tokens": 42, "output_tokens": 0 }
}
```

`output_tokens` всегда 0 — вероятность снимается прямо с головы модели за
один проход. `DecisionModel::parseResponse` принимает все три написания,
встречавшиеся в разных версиях эндпоинта: голое число (`"match": 0.97`),
`{"noul": 0.97}` и `{"probability": 0.97}`. Всё остальное (нет `match`, нет
`answers`, битый JSON) — ошибка, а не молчаливый вердикт.

## 5. Порог совпадения

Сырая вероятность сравнивается с порогом на клиенте, в
`VerificationQueueController` (сам порог живёт в
`SettingsStore::decisionMatchThreshold`, ключ `decision/matchThreshold`):

- **P(match) ≥ порога → блок помечается Ok.** Всё, что ниже, уходит на этап 2
  (повторное распознавание).
- По умолчанию **0,5**; ограничен диапазоном [0, 1]. В окне Decision-модели —
  «Порог совпадения (%)» (спинбокс 0–100 с шагом 5).
- Сравнение — `>=`: при пороге по умолчанию вероятность 0,50 всё ещё считается
  совпадением.
- Понижение порога отправляет больше блоков на (дорогой) проход повторного
  распознавания; повышение — больше доверяет decision-модели. Карточка
  описывает ответы как **калиброванные**, поэтому 0,5 — осмысленное значение
  по умолчанию, а не случайная крутилка.

## 6. Роль в пайплайне проверки

ADR 145 разделил старый однокомпонентный этап проверки на две фазы:

1. **OCR** — без изменений.
2. **Decision** — каждый блок очереди (те же правила допуска, что и раньше:
   фильтр по типам блоков, включая `duplicateSuspect`, непустой текст)
   отправляется decision-модели. Совпадения помечаются **Ok**; промахи
   ставятся в очередь. *Неудавшийся* decision-запрос (сеть, 404, битый ответ)
   вердиктом не является: блок остаётся непроверенным, ошибка показывается —
   вместо того чтобы молча переконструировать блок на сломанном этапе.
3. **Распознавание блоков** — промахи уходят роли `blockRecognition` (бывшая
   `check`), которая просто транскрибирует кроп; транскрипция становится новым
   текстом блока (`Fixed`).

Фазы идут друг за другом, поэтому один прогон проверки стоит **максимум два
переключения роли сервера** — на decision-модель и обратно (второе переключение
переиспользуется: после фазы 1 сервер стоит на decision-модели, и следующий
OCR-запрос вернёт его назад). Если роли OCR и распознавания блоков делят одну
модель, эти переключения схлопываются по обычному правилу одинаковых весов.

Ручные входы не изменились: «Проверить страницу», «Проверить всё» и
потблочный «Проверить» запускают ту же двухфазную очередь; настройка
`autoCheck` запускает её после распознавания, как и раньше.

## 7. Внешний режим

Во внешнем режиме decision-запрос уходит на настроенный base URL +
`/v1/systemone`, а идентификатор модели берётся из поля «Имя модели
(decision)» внешних настроек (`decision/modelName`). Эндпоинт — расширение
llama.cpp: OpenAI-совместимый сервер, говорящий только на
`/v1/chat/completions`, ответит 404, и все decision-проверки упадут. Если все
три роли обслуживает один внешний llama-server — загрузите в него ещё и
decision-модель; либо поднимите её вторым сервером и направьте на него
отдельный профиль.

## 8. Где что лежит в LLocr

| Часть | Расположение |
| --- | --- |
| Профиль модели (роль decision, формулировка вопроса, launch-слой, квантизации) | `resources/profiles/models/d1-3b.json` |
| HTTP-клиент эндпоинта (сборка запроса, разбор ответа) | `src/models/DecisionModel.{h,cpp}` |
| Поблочный драйвер (resolve → judge, отмена) | `src/app/DecisionController.{h,cpp}` |
| Двухфазная очередь, сравнение с порогом, запасной вопрос | `src/app/VerificationQueueController.cpp` |
| Настройки (пути, id профиля, внешнее имя, порог) | `src/config/SettingsStore.{h,cpp}` — группа `decision/*` |
| Композиция запуска (`ConnectionRole::Decision`) | `src/runtime/ServerLaunchConfig.cpp`, `RuntimeController.cpp` |
| Скачивание/активация (третий список ролей) | `ModelInstaller`, `ModelInstallTransaction`, `ModelQuantModel` |
| UI (окно, список моделей, порог) | `Settings/ModelSettingsWindow.qml`, `Settings/LocationTab.qml`, `Common/ModelDownloadList.qml` |

Решения: ADR 145 (двухмодельный пайплайн, переименование роли `check` →
`blockRecognition`, роль decision, миграция реестра/настроек), 122
(однострочный список установщика, который переиспользует окно decision-модели),
133/134 (семантика Stop и правило «спрашивать только неотвеченные», оба
наследуются без изменений).
