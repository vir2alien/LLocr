# 07. Глоссарий и принятые решения

> Английский оригинал: [docs/07-glossary.md](07-glossary.md)

## Термины

- **OCR** — распознавание текста с изображений.
- **Задачи (Tasks)** (ADR 252) — четыре задачи моделей, которые профиль
  объявляет строковым идентификатором; те же идентификаторы называют файлы
  профилей (`roles.<task>`), перечисление (`ConnectionRole::BlockRecognition,
  Decision, Layout, Fix`), настройки и QML. Список четырёх идентификаторов
  живёт в `core/ConnectionRole.h` и больше нигде (ADR 215).
  **blockRecognition** — транскрипция одного блока (обычная: промпт типа +
  кроп, без кандидата — прежний текст не отправляется, ADR 163);
  **decision** — быстрый шлюз «да/нет» на `/v1/systemone` (визуальный дифф
  `systemone_visual_diff_v1` — его единственный протокол, ADR 254/235);
  **layout** — ручной проход разметки страницы (ADR 150); **fix** —
  универсальная модель подтверждает / исправляет / отказывает кандидату
  (OK/FIX/REVIEW, ADR 163). Настройки каждой задачи живут в
  `tasks/<task>/{modelPath, mmprojPath, draftPath, requestProfileId,
  modelName}` — файлы запуска blockRecognition сохраняют прежний префикс
  `check`; в `check/` остаётся только ключ поведения `showConfidence`, а
  `decision/matchThreshold` остаётся на месте (переключатели
  `autoCheck`/`autoFix` удалены, ADR 178). У каждой задачи свой магазин
  профилей запроса (пользовательские файлы `requestBlock.json`,
  `requestDecision.json`, `requestLayout.json`, `requestFix.json`; прежние
  `request.json` / `requestValidate.json` переименовываются при загрузке;
  QML-синглтоны `RequestProfilesBlock` … `RequestProfilesFix`). Привязка
  моделей к задачам, скачивание и управление живут в окне «Модели». Прежняя
  лексика выживает там, где переименование стоило бы пользовательских данных
  или лишней перетасовки: `CheckController`/`CheckRequest`/`CheckResult`,
  `Phase::Recheck` очереди; индекс реестра переименовывает прежний тег
  `"check"` при загрузке и отбрасывает каждый тег, не являющийся каноническим
  именем роли — запись, оставшаяся без роли, ждёт повторной активации в
  Настройки → Модели (ADR 146); откат неизвестного имени на BlockRecognition
  живёт в `connectionRoleFromName` и в диспетчеризации настроек/QML.
- **OCR-модель (адаптер)** — рецепт для отдельной модели
  (`models/OcrModel.h`): как разговаривать с конкретной OCR-LLM — варианты
  промптов, парсер вывода по умолчанию и (через базовый класс) тело запроса
  chat-completions в стиле OpenAI и разбор ответа. Создаётся вызовом
  `OcrModel::create(modelId, role)` по идентификатору модели задачи (рецепт
  по умолчанию — `mineru`); адаптеры вырезанных моделей ушли вместе с ними
  (ADR 251) — уцелевшие рецепты суть профили моделей в
  `resources/profiles/models/`.
- **ConnectionConfig** — структура **транспортных** настроек (базовый URL,
  API-ключ, тайм-аут подключения, тайм-аут ответа), прежде `ProviderConfig`.
  Она отдельна от настроек модели: когда начинается распознавание,
  `RecognitionController` собирает `OcrRequest` (модель + промпт + параметры
  тела запроса) из `SettingsStore` и `ConnectionConfig` (подключение) для
  транспорта.
- **LlamaClient** — тонкий HTTP-транспорт (`core/LlamaClient.h`): собирает
  URL эндпоинта `/v1/chat/completions` (`endpointUrl`), предварительно
  проверяет TCP-подключение по тайм-ауту соединения, отправляет JSON через
  POST с необязательным bearer-токеном и тайм-аутом ответа на весь запрос,
  поддерживает `abort()` и выносит наверх сообщение об ошибке сервера.
  Бывший слой провайдеров сокращён ровно до этого (ADR 58, ADR 148).
- **OcrRequest** — полезная нагрузка одного запроса: `image`, `prompt`,
  `modelId` и упорядоченные параметры тела запроса (`RequestParameter`).
  Определён в `core/OcrRequest.h`.
- **Параметры DRY-сэмплинга (DRY sampling parameters)** — настройки сэмплера
  llama.cpp «Don't Repeat Yourself» (`dry_multiplier`, `dry_base`,
  `dry_allowed_length`, `dry_penalty_last_n`), часть **профиля запроса**,
  отправляются в теле запроса. Изначально настроены для модели
  Unlimited-OCR (сейчас в архиве, ADR 251).
- **Парсер вывода (Output parser)** — стратегия разбора ответа модели в
  структурированный результат (`raw`, парсер разметки `mineru-layout`; по
  умолчанию `auto`), выбирается в Настройки → Вывод. Парсеры, существовавшие
  только ради вырезанных моделей, живут в `archive/parsers/` (ADR 251).
- **BlockStyle** — отображение меток блоков модели (`title`, `image`,
  `chart`, `equation`, `table`, `ref_text`, подписи, …) в стили рендеринга
  Markdown (`BlockStyle.h`).
- **bbox** — координаты ограничивающей рамки распознанного фрагмента для
  наложения на предпросмотр (порождается собственным парсером модели).
- **Статус блока (Block status)** — состояние проверки отдельного блока,
  показывается точкой слева от блока (ADR 164, два слоя): каждый блок несёт
  `box.text` (результат OCR) и `box.correctedText` (коррекция fix-модели);
  точка отражает **эффективный** слой (коррекцию, когда она есть, иначе
  текст) и отвечает на один вопрос — проверен ли текст, на который вы
  смотрите? Блок разметки без текста не показывает точки; **серый** =
  распознан, вердикта на этом слое нет (включая «исправлено» — сохранённая
  коррекция, у которой пока нет собственного вердикта); **зелёный** =
  decision-модель подтвердила (Ok); **красный** = отклонён (Mismatch) или
  нечитаем/повреждён (Review). Янтарное состояние повторного распознавания
  убрано (`BoxCheckStatus::ReRecognized` удалён без перенумерации — вместо
  двухвариантной семантики ADR 153). Значок уверенности следует тому же
  слою. Оттенок блока следует его типу, а не статусу: text/table/formula/image —
  у каждого своя заливка и цвет рамки.
- **Блок изображения/графика (Image/chart block)** — блок с меткой `image`
  или `chart`; редактируется на предпросмотре (перемещение / изменение
  размера / удаление) и экспортируется как вырезанное изображение.
- **Предпросмотр Markdown (Markdown preview)** — клиентский рендер Markdown
  текущей страницы через Qt WebEngine + marked + KaTeX, переключается в
  правой текстовой панели.
- **RAG** — Retrieval-Augmented Generation; здесь — индексация сканов в
  векторную БД. Отложено (ADR 6), кода нет.
- **Модель документа/страниц (Document / page model)** — `DocumentModel`
  хранит страницы; `PageListModel` питает ленту миниатюр (флаги
  распознано/изменено/дубликат/текущая, без блоков).
- **Маркер распознавания (Recognized marker)** — индикатор на странице,
  показывающий, распознана ли она; у изменённых страниц и страниц с
  блоками-дубликатами есть дополнительные маркеры.
- **Режим подключения (Connection mode)** — `External` (подключение к уже
  работающему OpenAI-совместимому серверу; приложение ничего не запускает)
  или `Managed` (приложение запускает и владеет локальным `llama-server`).
  Выбирается мастером первого запуска; существующие профили по умолчанию —
  `External`.
- **ResolvedConnection** — готовое к использованию подключение, возвращаемое
  `RuntimeController::ensureConnectionReady()`: `baseUrl` + `apiKey` +
  `modelId` + два тайм-аута (ADR 148). В `External` зеркалит настройки; в
  `Managed` вычисляется из запущенного сервера (loopback-URL + `--alias`).
- **RuntimeController** — фасад управляемого рантайма (QML-синглтон
  `Runtime`, создаётся один раз в `main.cpp`, ADR 36): владеет разрешением
  подключения, жизненным циклом сервера, самопроверкой, оценкой памяти; QML
  не должен создавать его сам.
- **AppBusyState** — общее для приложения монопольное состояние занятости:
  `Idle`, `StartingRuntime`, `Recognizing`, `StoppingRuntime`,
  `Downloading`, `Installing`.
- **RuntimeState** — конечный автомат управляемого сервера:
  `NotConfigured → Stopped → Starting → Ready → Stopping → Stopped`, плюс
  `Failed`; вместе с `configValid` управляет `canRecognize`.
- **ensureConnectionReady()** — единственная асинхронная точка входа, которой
  пользуется распознавание; External разрешается немедленно, Managed
  запускает сервер, ждёт `/health`, запрашивает `/v1/models` и проверяет
  алиас. Работает на колбэках (ревью 3.3): параллельные вызывающие
  регистрируют колбэк и делят одно выполняющееся разрешение (дедупликация,
  ADR 37).
- **runSelfTest() / runSelfTestQml()** — независимая сквозная проверка
  (запуск → health → `/v1/models` → один OCR-запрос со встроенным тестовым
  изображением); используется шагом Launch мастера настройки.
- **Алиас (alias)** — `--alias <name>`, переданный управляемому
  `llama-server`; он становится `modelId`, которым пользуются клиенты
  (`/v1/models` обязан его показывать).
- **Managed / External (рантайм)** — см. **Режим подключения**. «Managed
  runtime/model» помечает также файлы внутри каталога `models/` приложения
  (удаляемые), в противоположность **внешним** GGUF-файлам от пользователя
  (никогда не удаляются, только перечисляются).
- **Пресет модели (Model preset)** — скачиваемая запись
  `repo + revision + model/mmproj/mtp files + sha256`, разворачиваемая из
  списка квантизаций профиля модели (`ModelPresetCatalog::expand`, один
  пресет на квант; например MinerU Q8_0), сливается с пользовательским
  `catalog.json` по `id` (ADR 42/43). Пресет устанавливает файлы своего
  `profileId` — профиль владеет ролью, запуском и парсером (ADR 58).
- **Профиль запроса (Request profile)** — упорядоченный набор параметров
  тела запроса, отправляемых llama.cpp рядом с `model`/`messages` (параметры
  DRY, temperature, max_tokens, stream, …). Встроенные разворачиваются из
  профилей моделей, обслуживающих задачу (`ModelProfiles::requestWithMaxOutput`);
  пользовательские копии на задачу живут в
  `<AppData>/LLocr/profiles/requestBlock.json`, `requestDecision.json`,
  `requestLayout.json`, `requestFix.json`, сливаются по `id` (ADR 56);
  **активный профиль следует выбору модели задачи** (blockRecognition:
  `model/recipeId`; decision/layout/fix: `tasks/<task>/requestProfileId`) —
  неизвестные идентификаторы откатываются к первому встроенному профилю
  (ADR 59). Один `RequestProfileStore` на задачу (QML-синглтоны
  `RequestProfilesBlock` … `RequestProfilesFix`) ими владеет.
- **Профиль запуска (Launch profile)** — именованный пресет командной строки
  llama-server (ctx-size, n-gpu-layers, флаги, …), помеченный
  `os`/`backend`. Встроенные пресеты поставляются в
  `:/profiles/serverLaunch.json`; пользовательские копии на пресет живут в
  `<AppData>/LLocr/profiles/serverLaunch.json` (полные копии, чтобы
  пользовательские удаления сохранялись). Выбор (`launch/profileId`)
  автоматически следует бэкенду установленного рантайма (ADR 57); им владеет
  `LaunchProfileStore` (QML-синглтон `LaunchProfiles`).
  `--model/--mmproj/--alias/--host/--port` никогда не являются частью
  профиля.
- **ModelRegistry** — хранит установленные модели в `<modelsDir>/index.json`;
  различает управляемые и внешние, восстанавливается пересканированием,
  охраняет удаление.
- **GGUF** — формат моделей llama.cpp; модели со зрением состоят из
  основного `.gguf` (+ необязательный проектор `mmproj`; поддерживаются
  многокомпонентные файлы `model-00001-of-N`).

## Принятые решения (ADR-lite)

Журнал сгруппирован по темам. Каждая запись хранит исходный номер ADR, так
что ссылки из кода и документов остаются валидными; небольшие связанные
решения слиты в одну запись и называют номера, которые они поглотили.
Полностью заменённые решения и решения, удалённые вместе со своей
возможностью, перечислены в приложении в конце файла.

### Стек и сборка

- **1.** Приложение — Qt6/C++/QML — стек покрывает все требования к GUI.
- **2.** Система сборки — CMake, не qmake — стандарт для кроссплатформенного
  C++.
- **4.** Транспорт говорит на OpenAI-совместимом API chat-completions
  (`/v1/chat/completions`) — единственный тип подключения, поддерживаемый
  практически всеми локальными рантаймами.
- **5.** Внутренний формат документа — Markdown; экспорт сходится к Markdown
  как единственному источнику — DOCX через Pandoc, отрисованные HTML/PDF
  через конвейер предпросмотра (см. ADR 63).
- **6.** RAG (индексация сканов в векторную БД, сначала задумывался как
  отдельный Python-сервис) отложен и не начат — сначала OCR; был набросан
  только бэкенд-интерфейс RAG, кода RAG не существует. (Поглощает ADR 3.)
- **7.** Ввод PDF использует Qt PDF (`QPdfDocument`), не MuPDF/Poppler — без
  дополнительной нативной зависимости, поставляется с Qt6, достаточно при
  ~150 DPI.
- **14.** Модульные тесты живут в `tests/` (Qt Test), включаются флагом
  `LLOCR_BUILD_TESTS`.
- **50.** `SettingsStore::resetToDefaults()` построена на таблице: по одной
  строке `SettingDefault{kQSettingsKey, Q_PROPERTY name, QVariant default}`
  на каждый сбрасываемый ключ, запись через `QMetaProperty::write()`, чтобы
  охранные проверки, валидация и NOTIFY сохранялись; состояние `ui/window*`
  сознательно исключено, а порядок держит `baseUrl` перед `connectionMode`.
- **54.** Инструментарий Windows — MSVC 2022 64-bit (NMake Makefiles JOM);
  MinGW не поддерживается, потому что в Qt-пакете MinGW нет Qt WebEngine
  (предпросмотр Markdown) — сборка с конфигурацией MinGW чисто падает на
  WebEngine; macOS/Linux не затронуты.
- **58.** Абстракция провайдера удалена (`ILlmProvider`/`OpenAiProvider`
  вырезаны). Остались две ортогональные абстракции: `OcrModel` (src/models/)
  — рецепт для отдельной OCR-LLM (варианты промптов, парсер по умолчанию,
  сборка запроса и разбор ответа) — и `LlamaClient` (src/core/) — тонкий
  транспорт; `ProviderConfig` переименован в `ConnectionConfig`,
  `OcrRequest` живёт в `core/OcrRequest.h`, а промпт принадлежит адаптеру
  модели, а не контроллеру.
- **66.** Импорт DjVu — поэтапная фоновая подготовка: `QtConcurrent::run`
  запускает статический `DocumentModel::prepareDjVu()` с независимым общим
  декодером, принадлежащий GUI `QFutureWatcher` фиксирует `PreparedDjVu`
  под коротким `m_documentLock`, смешанные выборки файлов выполняются
  последовательно, а отдельное состояние `importing` крутит спиннер и
  закрывает перекрывающиеся операции, не задевая занятость распознавания.
- **69.** Поддержка DjVu опциональна на этапе конфигурирования
  (`LLOCR_WITH_DJVU`, по умолчанию ON): без DjVuLibre сборка предупреждает и
  продолжается с `LLOCR_DJVU_AVAILABLE=OFF`, код DjVu компилируется под
  `LLOCR_HAVE_DJVU`, а вызовы во время выполнения возвращают понятную ошибку
  (установите DjVuLibre и пересоберите, либо конвертируйте в PDF);
  `test_djvu_document`/`test_app_import` собираются только при включённом
  DjVu.
- **84.** Хранилища профилей делят один слой JSON-персистентности,
  `ProfileStorage` (`removeFileIfExists` / `writeJsonAtomic` / `readJson`);
  каждое хранилище держит свои тексты `tr()` и форму JSON; шаблон
  `ProfileStoreBase` был сознательно отклонён; `test_profile_storage`
  покрывает помощники напрямую.
- **86.** `AppController` разделён: `VerificationQueueController` владеет
  конечным автоматом очереди проверки (пересекает границу сигналом
  `blockChecked(page, box, result)` и никогда не меняет документ), а
  `ExportController` владеет всем конвейером экспорта (`collectPages`,
  `ExportScope`, пути pandoc/built-in и отрисованных HTML/PDF,
  `pdfPageLayout`); QML API `AppController` остался неизменным в роли
  пересылок. (Владелец автомата очереди изменён ADR 286: очереди ролей
  заменили `VerificationQueueController`; правило «результаты — сигналами»
  не изменилось.)
- **92.** Удаление блока имеет ровно одну точку входа,
  `AppController::removeBlock(index)`: сначала меняется документ, затем
  зеркалятся `BoxListModel` (простой `removeBox()`, не Q_INVOKABLE, без
  сигнала `boxRemoved`), `PageEditStore` и выделение, затем срабатывают
  сигналы; QML (`ImagePreview`, `BlockEditPanel`) вызывает контроллер,
  никогда не модель. Тесты: `TestAppImport::blockRemovalUpdatesDocumentAndView`,
  `TestBoxModel::removeBoxIsNotQmlCallable`.
- **95.** Определение для опциональной зависимости не должно менять
  раскладку класса: `DocumentModel.h` включает `app/DjVuDocument.h`
  безусловно (он лишь forward-объявляет структуры `ddjvu_*`) и объявляет
  члены DjVu безусловно; `LLOCR_HAVE_DJVU` выбирает только реализацию
  в .cpp — обёртка членов в `#ifdef` — нарушение ODR и тихая порча памяти.
- **101.** Дерево QML — настоящий модуль Qt (`qt_add_qml_module`, URI
  `LLocr`, файлы подхватываются глобом с `CONFIGURE_DEPENDS`, раздаются с
  `qrc:/qt/qml/LLocr/…`, что загружает `main.cpp`); QML-синглтоны несут
  `QT_QML_SINGLETON_TYPE`, инертные макросы `QML_ELEMENT` удалены, а
  C++-сервисы остаются зарегистрированными вручную в `main.cpp`. Модуль
  теперь объявлен рядом с целью `llocr`, файлы лежат в `src/qml/`
  (см. ADR 176).
- **103.** Страница владеет своим текстом: все записи идут через
  `AppController::setPageText()`, все чтения через `pageText()`, а
  `PageEditStore` хранит только базовую линию для отката и маркер
  «изменено». Повторный ввод видимого текста — no-op, откат возвращает
  распознанный текст, а `ExportController` читает `page.result.text` как все
  остальные.
- **106.** Код разделён на слоевые цели, слинкованные в порядке
  `llocr_core` → `llocr_config` → {`llocr_models`, `llocr_parsers`} →
  `llocr_runtime` → `llocr_app` → `llocr`; что слою можно использовать,
  решает граф линковки (`LaunchProfileStore`/`LaunchParametersModel` сидят в
  `llocr_runtime`, `RequestProfileStore` — в config,
  `ProcessGuard_{win,mac,linux}.cpp` — в runtime). Тесты линкуют те же цели
  вместо повторного перечисления исходников.
- **117.** Один шаблон `ProfileStore<T>` (`app/ProfileStore.h`) владеет
  встроенным списком, пользовательскими переопределениями, слиянием при
  чтении и сохранением только различий для
  `LaunchProfileStore`/`RequestProfileStore`, с единой политикой конверта
  `schemaVersion` (`ProfileStorage::readEnvelope`/`writeEnvelope`). Политика
  слияния остаётся на каждом типе (`LaunchProfile::merge` заменяет набор
  параметров, `RequestProfile::merge` сливает попараметрически), а мёртвый
  `launch/presetId` исчез. `VerificationPromptStore` сознательно держит свою
  форму, но пользуется тем же конвертом.
- **118.** Дисциплина GUI-потока (поглощает ADR 104, 105, 209): потоковый
  контракт документа записан — `DocumentModel`/`AppController` резидентны в
  GUI-потоке с двумя сознательными пересечениями (воркер экспорта,
  разрешающий кропы под блокировкой документа, и провайдер изображений),
  вызывающие идут через блокирующий аксессор, а сама блокировка остаётся.
  Ничто, что ходит по файлам или ждёт процесс, не выполняется в GUI-потоке —
  проба рантайма (`RuntimeLocator::probeCached` на воркере), хеширование
  докачиваемых файлов и дайджесты проекторов — всё на воркерах. Рендер
  страницы для предпросмотра тоже происходит на воркере:
  `DocumentModel::renderDetached` + `AppController::previewImage` отвечают
  из кэша со счётчиком поколений и меткой «Rendering page…». Хендл документа
  принадлежит открывшему его потоку: `QPdfDocument` и контекст DjVuLibre
  несят привязку к потоку создателя, обёртки знают своего владельца, рабочий
  поток держит собственный хендл на документ для рендеринга, а общее
  состояние провайдеров охраняется (кэш миниатюр — собственным мьютексом,
  документ — блокировкой документа).
- **131.** Проект — самодостаточный ZIP `.llocr`: `project.json` (схема
  версии 1: исходники + упорядоченные страницы с текстом, базовой линией,
  блоками, `checkStatus`/`correctedText`) плюс вложенные оригинальные
  исходники. Пишет его `runtime/ZipWriter`, схемой владеет
  `app/ProjectStore`, сохранение — снимок в GUI + запись в воркере (атомарные
  tmp+rename), а открытие извлекает в сессионный `QTemporaryDir` и затем
  пересобирает документ через публичный API `DocumentModel`. Настройки
  уровня приложения не являются состоянием проекта.
- **176.** QML-модуль объявлен рядом с целью `llocr`, а дерево QML живёт в
  `src/qml` — модуль, объявленный в корне, неверно регистрировал цепочку
  метатипов в зависимости от генератора Windows, а из `src/` qmlcachegen
  больше не порождает путь `llocr_../…` с завершающей точкой, который Win32
  не может ни создать, ни прочитать. `CMakePresets.json` `dev-win`
  переключён на Ninja; сборки с нуля проходят с обоими генераторами.
- **204.** Проект собирается с `-Wall -Wextra` (`/W4` на MSVC, три
  предупреждения Qt-заголовков заглушены), и всплывшие предупреждения
  исправлены. Пропущенный `case` в `switch` или путаница signed/unsigned не
  должны проходить молча — именно это сделало видимыми десять switch-ей по
  ролям в хранилище настроек (замечание ревью D-020).
- **205.** Осиротевшие QML-файлы `Common/ModelDownloadList.qml`,
  `Common/InstallModelDialog.qml` и `Common/SplitToolButton.qml` удалены
  вместе с контекстами перевода; список моделей живёт в
  `Common/TaskModelsTable.qml`, а список сборок рантайма — в
  `Common/RuntimeBuildsList.qml`, где продолжает жить паттерн строки,
  описанный в ADR 122 и ADR 158.
- **210.** Группа скачивания моделей держит `QPointer`-ы вместо сырого
  указателя на задачу (менеджер выселяет задачу, как только накопится
  десять) и помнит байты завершённых задач, чтобы прогресс группы не
  откатывался, когда менеджер их выселяет.
- **213.** `AppController` — фасад, а не god-класс: пять из восьми доменов
  его свойств стали классами в `src/app/` — `BlockInspector` (выбранный
  блок, две версии текста с вердиктами, дифф, позиция в тексте страницы),
  `ProjectController` (файл проекта), `AvailabilityPresenter` (матрица
  доступности), `VerificationQueueController` (уже владел своим состоянием),
  `LayoutController` (проход разметки). Имена свойств, привязанных к QML, и
  NOTIFY-сигналы не изменены, новые классы получают зависимости через
  `Deps`, а домены документа/импорта, выбор парсера и строка состояния
  остаются в фасаде. (Классы домена проверки изменены ADR 286: очереди
  ролей заменили `VerificationQueueController`.)
- **214.** Список области действия панели (выделение на ленте миниатюр;
  пустое выделение = весь документ) вычисляет только `AvailabilityPresenter`,
  и фасад спрашивает у него и действия (`recognizeScopePages`,
  `checkScopeEnabledBlocks`, …), и флаги доступности — число страниц на
  кнопке и флаги не могут разойтись.
- **247.** Каждое предупреждение сборки MSVC разобрано: чужой шум заглушен
  (C4702 из Qt-шаблонов присоединился к трём заглушенным предупреждениям
  Qt-заголовков), свои предупреждения исправлены. Постоянное правило:
  `switch` по `enum class` в функции с возвращаемым значением держит ветку
  `default` — диапазон хранения enum шире списка перечислителей, поэтому
  MSVC никогда не считает switch исчерпывающим; clang и gcc этого не
  проверяют.

### Рантайм и установка

- **12.** Поддерживаются только OpenAI-совместимые серверы (в стиле
  llama.cpp) — один ясный тип подключения; параметры подключения, модели,
  парсера и тела запроса живут в `SettingsStore` (QSettings за окнами
  настроек), а промпт принадлежит адаптеру OCR-модели (см. ADR 58).
- **26.** Два режима подключения, `External` (подключение к уже работающему
  OpenAI-совместимому серверу; приложение ничего не запускает) и `Managed`
  (приложение запускает и владеет локальным `llama-server`); транспорт
  остаётся развязанным с управлением процессами (`LlamaClient` +
  `OcrModel`, без `QProcess` в транспорте).
- **27.** Управляемый сервер — только llama.cpp (`llama-server`, минимум
  сборка b4000) — один предсказуемый CLI; у Ollama/LM Studio свои менеджеры,
  а старые сборки слишком сильно дрейфуют.
- **28.** Установки рантайма приходят с GitHub Releases llama.cpp
  (`ggml-org/llama.cpp`), распаковываются нашим кодом (vendored `miniz`) с
  проверкой `sha256` — источник дайджеста согласно ADR 236; размер файла не
  является доказательством целостности.
- **29.** Модели скачиваются напрямую с Hugging Face с закреплённым SHA
  коммита и проверкой `sha256` против `lfs.oid` — без зависимости от Python,
  а `main` изменчив между просмотром и скачиванием.
- **30.** Гарантия отсутствия сирот-процессов (no-orphan) для управляемого
  сервера: сильная на Windows (Job Object +
  `JOB_OBJECT_LIMIT_KILL_ON_CLOSE`) и Linux (`prctl(PR_SET_PDEATHSIG)` через
  `ProcessGuard`), по мере возможностей на macOS (`owner.json` + обнаружение
  при следующем запуске) — у macOS нет аналога PDEATHSIG.
- **31.** Мастером первого запуска движет только `runtime/setupVersion`,
  без сетевых проб здоровья; уже существующие профили считаются
  настроенными (`setupVersion=1`), чистый профиль стартует с
  `setupVersion=0` — недостижимый сервер не должен определять состояние
  настройки.
- **32.** В `Managed` `baseUrl` и `modelId` вычисляются из запущенного
  сервера (loopback + `--alias`) — процесс — единственный источник истины —
  а настройка `model/name` никогда не перезаписывается, так что настройки
  `External` переживают переключения режимов.
- **34.** Поддерживаются оба вида архивов рантайма, `.zip` и `.tar.gz`,
  различаются по расширению в `ArchiveExtractor::extractArchive` (llama.cpp
  публикует ZIP на Windows, но tar.gz на macOS/Linux, а на macOS вообще без
  ZIP-ассета); симлинковые `.dylib` тарболлов macOS пересоздаются как
  относительные ссылки.
- **36.** `RuntimeController` — синглтон, создаваемый в `main.cpp` до
  загрузки QML-движка; QML не может создать его сам (детерминированное
  время жизни, без дубликатов).
- **37.** `RecognitionController` получает подключение только через
  `ensureConnectionReady()` (External разрешается немедленно; Managed
  запускает/ждёт позже) — он ничего не знает о режимах, процессах и
  проверках здоровья; параллельные вызывающие делят одно выполняющееся
  разрешение (дедупликация).
- **39.** Установка рантайма транзакционна: staging → проверка → проба →
  атомарный rename → фиксация настроек; любой сбой удаляет
  `staging/<uuid>` и оставляет настройки нетронутыми (см. ADR 28, ADR 34).
- **40.** Скачивания `.part` всегда живут в целевом каталоге, никогда в
  общем `downloads/` — rename между файловыми системами не атомарен, а
  модели часто живут на внешнем диске.
- **41.** Определение возможностей сервера = белый список сборок +
  уточнение по разобранному `--help` + один автоповтор без провинившегося
  флага при «unknown argument», кэшируется как
  `capabilities-<sha1(path+mtime)>.json` — CLI llama.cpp дрейфует между
  сборками, а слепая сборка argv ломает совместимость.
- **44.** `runtime/autoStart` по умолчанию выключен — иначе GUI
  резервировал бы несколько ГБ RAM/VRAM при каждом запуске, даже в простое.
- **46.** Локи разделены вместо одного глобального лока приложения:
  `.install.lock` (установки/очистка рантайма), `.registry.lock` на каждую
  запись (`ModelRegistry`) и `.instance.lock` как шлюз владельца рантайма
  (`SingleInstanceGuard`); лок владельца перепроверяется при открытии
  настроек Рантайм (`RuntimeController::refreshSingleInstanceLock()`), так
  что второй экземпляр перехватывает владение, как только владелец выйдет —
  без перезапуска приложения.
- **49.** Самопроверка и кольцевой буфер журнала сервера — отдельные
  синглтоны (`SelfTestController`, `RuntimeLog`), а не роли
  `RuntimeController` — фасад остаётся маленьким, а логика
  самопроверки/журнала не дублируется.
- **51.** Проба `--version` + `--help` делит один бюджет настенного времени:
  `--version` получает весь `timeoutMs`, `--help` — остаток; при исчерпании
  `--help` пропускается, и флаги откатываются к белому списку сборок —
  зависший бинарник больше не может заморозить UI на 2 × timeoutMs.
- **52.** Успешные пробы сохраняются в
  `<cacheDir>/capabilities-<sha1(path+mtime+size)>.json` и выдаются
  `probeCached()` при следующем запуске приложения (сила ключа совпадает с
  находящимся в памяти `ProbeKey`, так что любая замена бинарника
  инвалидирует); свежая проба «Проверить» и путь установки по замыслу не
  кэшируются (см. ADR 41).
- **53.** Проба бинарников llama.cpp использует один терпеливый тайм-аут
  120 с (поток установки и Check/Start в `RuntimeController`), без
  kill/retry — первый запуск на macOS компилирует Metal-шейдеры и блокирует
  `--version`; убийство каждой попытки на 5-й секунде перезапускает
  компиляцию вечно, тогда как один терпеливый прогон прогревает кэш.
- **57.** Профили запуска заменяют плоские настройки `launch/*`:
  `ServerLaunchConfig` выдаёт ключевые флаги
  (`--model/--mmproj/--alias/--host/--port`, единый источник), затем строки
  активного профиля дословно; встроенные пресеты в
  `:/profiles/serverLaunch.json` помечены `os`/`backend`, полные
  пользовательские копии на пресет — в
  `<AppData>/LLocr/profiles/serverLaunch.json` (удаления сохраняются);
  выбор `launch/profileId` автоматически следует установленному бэкенду;
  `--model/--mmproj/--alias/--host/--port` никогда не являются частью
  профиля, а `estimateModelMemory` читает `ctx-size`/`cache-type-*` из
  активного профиля.
- **60.** Установленные сборки llama.cpp переключаются без повторного
  скачивания: `InstallTransaction::scanInstalledBuilds()` перечисляет
  `<runtimeDir>/llama.cpp-*`, `RuntimeInstaller::activateBuild(index)`
  активирует одну коммитом только настроек (`serverPath` + `installedBuild` +
  `runtimeBackend`); «Очистить неиспользуемые сборки» отклоняется, пока не
  активна ни одна сборка.
- **61.** Запущенный управляемый сервер — источник истины для распознавания:
  `ensureConnectionReady()` применяет основанный на настройках гейт
  `configValid`, только когда нужен запуск — уже Ready/Starting сервер
  разрешается прямо к проверке алиаса через `/v1/models`; взамен
  `startServer()` отказывает в Managed-запуске без выбранной модели, так
  что Ready-сервер без модели возникнуть не может.
- **62.** Выбор модели переживает сброс настроек без повторного скачивания:
  `ModelInstaller` читает реестр через свежие `RuntimePaths`, предоставляет
  `refreshInstalled()` (пересканирование остаётся ручным — оно выкинуло бы
  внешние записи, не подтверждённые файлами) и `activatePreset(index)`;
  шаг моделей в мастере и окно «Модели» предлагают активацию установленных
  моделей, а отказы старта/распознавания называют записанный путь модели.
- **73.** Имена моделей внешнего сервера — на каждую роль: разрешение кладёт
  имя модели роли в `ResolvedConnection.modelId` (распознавание против
  задачи проверки), а пустое имя отправляется как есть — llama-server
  игнорирует поле `model` запроса, а «model not found» многомодельного
  сервера выдаётся дословно, без тихого отката.
- **74.** Единственный управляемый llama-server (пере)загружается под каждую
  задачу: `ensureConnectionReady(role)` сравнивает model/mmproj, с которыми
  запущен сервер, с настройками роли и останавливает/перезапускает при
  расхождении (`beginRoleSwitch()`); общий алиас остаётся
  `launch/modelAlias`; распознавание и проверка взаимоисключающие на уровне
  `AppController`, так что переключение роли никогда не убьёт выполняющуюся
  задачу; когда путь модели роли пуст, побеждает живой сервер (см. ADR 61).
- **83.** Защита от затирания настроек: QML-шаг, который сохраняет при
  скрытии, обязан сохранять только после того, как поля были загружены при
  показе (`StepExternal.valuesLoaded` — жадно созданные невидимые элементы
  срабатывают `onVisibleChanged` до всякой загрузки), а
  `applyStartupMigration()` самолечит внешний профиль, затёртый при старте,
  восстанавливая stash переключения режима (`provider/lastExternalBaseUrl`);
  регрессионные тесты в `test_settings_store`.
- **85.** Конвейер установки HF-пресетов (подготовка → скачивание →
  финализация) живёт в `runtime/ModelInstallTransaction.{h,cpp}`
  (`InstallPlan`, владение `DownloadManager`/`DownloadGroup`, гейт поколения
  подготовки, complete/cancel), зеркаля `RuntimeInstaller`/
  `InstallTransaction`; `ModelInstaller` — только QML-фасад с неизменным
  публичным API; чистая логика выбора (`repoDirName`, `selectModelFiles`)
  публична и покрыта юнит-тестами в `test_model_install_transaction` (ничьи
  по размеру группы разрешаются по ключу, а не по сиду QHash).
- **93.** Разрешения `RuntimeController` ключуются по `ConnectionRole`: в
  выполняющийся батч присоединяются только запросы той же роли, другая роль
  уходит в `m_deferredResolves` и продвигается `startResolveForRole(role)`
  (он выполняет переключение роли, см. ADR 74); `cancelPendingStart()`
  сначала сбрасывает отложенный батч, а `completeResolve()` никогда не
  затирает начатое разрешение. Тест:
  `TestEnsureConnection::crossRoleRequestDuringResolveIsNotAnsweredWithTheWrongRole`.
- **97.** Индекс моделей обновляется read-modify-write под собственным
  локом: `ModelRegistry::update(modelsDir, mutate, error)` держит
  `.registry.lock` на чтение и запись, а `save()` — лок + `writeIndex` —
  два экземпляра, устанавливающие одновременно, больше не потеряют записи
  друг друга.
- **98.** Неудачная загрузка каталога релизов (тайм-аут / 403 / не-200 /
  кривое тело) никогда не выбрасывает офлайн-кэш: `fetchReleasesLocal()`
  откатывается к последней известной хорошей версии через не зависящий от
  возраста `readCacheFile()`, с watchdog-таймером на вложенном цикле событий
  и подставляемым эндпоинтом, чтобы политика была тестируемой.
  `ReleaseCatalog::resetCache()` исчез.
- **107.** Запись о владельце llama-server считывается обратно: `ServerOwner`
  проверяет `<rootDir>/owner.json` (pid жив + совпадение пути образа,
  исчезнувший родитель как улика там, где платформа не может сообщить
  образ), а `RuntimeController` выставляет
  `orphanDetected`/`orphanInfo`/`terminateOrphan()` с «Остановить» в футере
  — процесс никогда не убивается без клика. `DownloadGroup::progress()`
  суммирует по задачам, которые сам поставил в очередь, а не по агрегату
  менеджера.
- **108.** Единая HTTP-политика для слоя рантайма: `HttpClient` владеет
  тайм-аутом передачи, ручными перенаправлениями с бюджетом переходов,
  только-https (кроме явно разрешённого loopback), системным прокси и
  правилом, что заголовок `Authorization` никогда не следует за
  перенаправлением на другой хост. Через него идут `ModelCatalog`,
  `ReleaseCatalog`, `DownloadTask` (своя логика докачки) и вызов
  `/v1/models` в `RuntimeController`.
- **109.** Один `InstalledState` отвечает, где живут рантайм и его лок
  установки: единственный экземпляр, создаваемый в `main.cpp`, передаётся
  `RuntimeController`, `RuntimeInstaller`, `ModelInstaller` и
  `ModelInstallTransaction`, выводит `RuntimePaths` из настроек при каждом
  вызове и пересоздаёт `QLockFile`, когда каталог переезжает
  (`pathsChanged` → пересканирование установленных сборок).
- **112b.** Обе установки публикуются атомарным rename через `StagedInstall`
  (runtime/StagedInstall.{h,cpp}): staging → `commit()` (отодвинуть в
  сторону, переименовать на место, убрать бэкап) → деструктор удаляет
  незакоммиченный staging. `ModelInstallTransaction` берёт тот же
  `.install.lock`, что и установка рантайма, скачивает в
  `<staging>/model-<org>__<repo>` и коммитит в `<modelsDir>/<org>__<repo>`;
  имена staging детерминированы, поэтому возобновлённая установка находит
  свои `.part`-файлы. (Номер 112 в исходном журнале был продублирован; эта
  запись несёт второе решение.)
- **116.** Одна сверка решает между настройками, `index.json` и файловой
  системой: `reconcileInstalled()` (runtime/InstalledReconcile.{h,cpp})
  заявляет приоритет — существование и измеримые факты о файлах принадлежат
  файловой системе, курируемые метаданные — индексу, настройки — это
  указатели: о них сообщают, но их никогда не отбрасывают молча, — и считает
  отсутствующий каталог моделей неизвестным, а не пустым. У
  `ModelRegistry::load()` один путь вместо четырёх веток пересканирования.
- **126.** `ctx-size` принадлежит машине, а не весам: он живёт в
  платформенных профилях `serverLaunch.json` на os+backend (по умолчанию
  16384, 8192 для `cpu`), правится в Настройки → Запуск, а параметры запуска
  на модель остаются тем, что решают веса (`image-min/max-tokens`,
  `dry-sequence-breaker`, `special`). `compose()` заполняет пробелы по
  имени, так что ни один параметр не доходит до командной строки дважды;
  `n-predict` позже вообще убрали из слоя запуска (см. ADR 144).
- **127.** Тег сборки — число: `ServerCapabilities::buildAtLeast()` разбирает
  сравнения `minBuild` численно (`QString::compare` считал любую
  пятизначную сборку старше четырёхзначной), а
  `ModelInstaller::syncProfileToActiveModel()` при каждом
  `refreshInstalled()` заново выводит сохранённый профиль из репозитория
  активной записи, так что переименованная или перемещённая модель не может
  оставить устаревший выбор.
- **128.** Опции ручных путей исчезли: управляемое — значит, сборка
  рантайма, установленная приложением (`Settings.serverPath` пишет только
  установщик/`activateBuild`), а модель — значит, из каталога — пикеры
  бинарника/модели, флаги источника «Specify model files» и `StepBinary.qml`
  мастера удалены, осиротевшие ключи настроек сброшены при старте.
  Пользователь, выбравший свой бинарник, продолжает работать: `serverPath`
  по-прежнему то, что запускает `startServer()`.
- **133.** Стоп останавливает работу, а не сервер: `CheckController::stop()`
  больше не вызывает `RuntimeController::cancelPendingStart()` —
  управляемый сервер есть состояние всего приложения со своим явным
  управлением (переключатель в футере, Настройки → Рантайм).
  `RecognitionController::stop()` сохраняет любезность, ведь запуск
  распознавания существует только ради этого запроса.
- **148.** Тайм-аут провайдера разделён: `provider/connectionTimeoutMs`
  (5 с, асинхронный pre-flight через `QTcpSocket`) ограничивает только
  TCP-подключение и быстро отвергает мёртвый эндпоинт,
  `provider/responseTimeoutMs` (300 000) ограничивает весь запрос для
  Managed и External одинаково; сохранённый `provider/timeoutMs` мигрирует
  в тайм-аут ответа.
- **159.** `runtime/stopOnExit = false` соблюдается от начала до конца:
  `LlamaServerProcess::detachFromProcess()` оставляет запись о владельце
  для следующей проверки на сироты и направляет stdout сервера в файл
  журнала (дозапись), пока сервер отсоединён. Тот же гигиенический батч
  заставил `DownloadTask::closeFile()` завершать обрезанное скачивание с
  переведённым сообщением, tar `fieldString()` останавливаться только на
  NUL, а `BoxCheckStatus` обрёл гейт `boxCheckStatusFromInt(int)`.
- **202.** Неудачная проверка каталога релизов так и говорит: откат к кэшу
  объявляется как «Показан сохранённый список релизов — проверка не
  удалась: …», временная метка кэша остаётся нетронутой, а проверка
  повторяется при следующем запуске.
- **203.** Комбобокс релизов на вкладке рантайма следует установщику: выбор
  читается из него (`syncReleaseBox()`), а бокс отслеживает изменения
  каталога и выбора, вместо того чтобы брать первый релиз списка.
- **226.** Внешний рантайм зеркалит внутренний: те же задачи, что и в
  управляемом режиме (см. ADR 215), каждая со своим эндпоинтом
  (`tasks/<role>/baseUrl`), своим API-ключом и своим алиасом модели; пустое
  поле означает общее значение. Алиас правится в одном месте — на вкладке
  «Внешний сервер» настроек рантайма; окно «Модели» показывает его только
  для чтения.
- **228.** Внешний сервер не ведёт журнал процесса, поэтому след ведёт
  клиент: `RequestJournal` (в `llocr_core`) пишет по записи на каждый
  HTTP-вызов — адрес, модель, размеры запроса/ответа, HTTP-статус, тайминги,
  голова ответа — и окно журнала показывает его во внешнем режиме. След
  живёт только в памяти (страница — документ пользователя) и никогда не
  содержит API-ключ.
- **231.** Правила провода внешнего сервера (поглощает ADR 229, 230): тело
  запроса всегда называет модель (`ConnectionConfig::modelId` — алиас роли
  для внешнего, серверный `--alias` для управляемого), поэтому серверы,
  требующие `model`, больше не отвечают 422; сервер, игнорирующий
  `reasoning_budget_tokens` и сжигающий бюджет на размышления, получает
  повтор запроса исправления без мышления, причём последующие запросы к
  этому серверу идут без размышлений и причина называется; а внешнее
  контекстное окно читается из `max_model_len` в `/v1/models` (один запрос
  на сервер, с ключом той роли) в `ResolvedConnection::contextSize`,
  зрительный минимум принят в 1024 токена, потому что бюджет изображения не
  публикуется.
- **236.** Дайджест релиза и устойчивость скачивания (поглощает ADR 212):
  правило «нет дайджеста — нет установки» стоит, но дайджест берётся из
  поля `digest` ассета GitHub API (`sha256:<hex>`, чужие алгоритмы и
  обрезанный hex отклоняются) с таблицей из тела релиза как запасным
  вариантом — апстрим перестал публиковать таблицу в теле. Оборванная
  передача (нет HTTP-ответа, обрыв в середине тела, HTTP 5xx) повторяется
  самой задачей скачивания — до трёх попыток с паузами 2 с / 5 с, продолжая
  через `.part` с `If-Range`; HTTP 4xx, отказ дайджеста и нехватка места не
  повторяются, а сбой группы сообщает ошибку задачи («Скачивание не
  удалось: %1»), а не общее сообщение о подключении.
- **262.** Дамп сэмплеров llama.cpp (`sampler chain:` / `sampler params:`)
  отфильтровывается из журнала управляемого сервера в
  `LlamaServerProcess::appendLine` — сэмплеры с префиксом `?` это
  отключённые дефолты сервера, а не настройки приложения, а уровень журнала
  4 (см. ADR 250) оставлен для разбивки по памяти.
### Модели и задачи

- **8.** Распознавание можно отменить (`abort()`) — пользователь должен уметь
  останавливать долгие многостраничные прогоны.
- **17.** Парсер layout-токенов поглощает поток блоков `<|det|>…<|/det|>` и
  снимает JSON-экранирование содержимого (`\n` → новая строка, `\\` → `\`, …);
  прежняя голая форма `label [x1,y1,x2,y2] text` остаётся запасным вариантом;
  без разбиения по `<PAGE>` — на один запрос отправляется одна страница.
- **18.** Парсер вычищает служебные токены модели из содержимого —
  `<|end_of_sentence|>`, включая вариант с полноширинной вертикальной чертой
  (`｜` U+FF5C), варианты с `▁` (U+2581) и любые случайные обёртки `<|…|>` —
  чтобы маркер EOS никогда не протекал в распознанный текст (общий
  `core/ServiceMarkers.h`).
- **19.** Блок `table` рендерится как GFM-таблица с пайпами, собранная из
  HTML `<table>` модели: `colspan`/`rowspan` укладываются в плотную сетку, но
  растянутое значение записывается один раз в левую верхнюю ячейку, которую
  оно покрывает; строка из одной широкой ячейки становится заголовком раздела
  на всю ширину; математика в ячейках идёт через `convertMath`;
  `table_caption`/`table_footnote` рендерятся курсивом; настройка
  «Сохранять таблицы в HTML формате» (`output/tablesAsHtml`, по умолчанию
  выключена) вместо этого пропускает `<table>` дословно (см. ADR 64).
- **20.** Det-токен `ref_text` (записи библиографии/ссылок) разбирается как
  `text` и рендерится обычным абзацем, сохраняя свою метку и не получая
  дополнительного оформления Markdown.
- **21.** Параметры DRY-сэмплинга (`dry_multiplier`, `dry_base`,
  `dry_allowed_length`, `dry_penalty_last_n`) выведены в настройки и
  отправляются в теле запроса (часть профиля запроса) — они ощутимо влияют на
  качество распознавания llama.cpp и настраиваются без перекомпиляции.
- **25.** Дублирующиеся ограничивающие рамки схлопываются и помечаются флагом
  (`OcrPage::hasDuplicates`, роль дубликата в `PageListModel` → красный
  маркер) — модель может выдать один и тот же регион дважды; парсер
  дедуплицирует его, а UI выносит это наружу.
- **42.** Каталоги пресетов разделены: встроенные только для чтения
  (`:/models/default-presets.json`, позже `:/profiles`) + пользовательский
  `<AppData>/…/catalog.json`, слияние по `id` (пользователь побеждает) —
  файлы внутри ресурсов Qt нельзя редактировать, а пользователь должен иметь
  возможность добавлять и менять пресеты.
- **43.** Пресет закрепляет точную связку модель + mmproj + парсер + промпт +
  ctx-size — `det_tokens` и промпт специфичны для модели; произвольная
  vision-GGUF даёт нечитаемый вывод.
- **56.** Профили запроса заменяют отдельные настройки запроса: тело запроса
  (после `model`/`messages`) собирается в порядке профиля, встроенный
  `:/profiles/request.json` + пользовательские копии сливаются по имени
  параметра (пользователь побеждает; файл пишется, только когда значения
  отличаются от дефолтных); UI = таблица черновика с Сохранить/Отмена/Вернуть
  настройки по умолчанию; значения сохраняют свой JSON-тип, а
  `dry_sequence_breakers` по умолчанию `["\uE000"]`, потому что llama.cpp
  отвечает 400 на пустой массив.
- **59.** Профили запроса — на модель: файл — массив, ключуемый уникальным
  `id` профиля (идентификатор OCR-модели), а активный профиль следует выбору
  модели задачи (`model/recipeId` для blockRecognition; неизвестные id
  откатываются к первому встроенному профилю); прежние одно-профильные файлы
  v1 принимаются как профиль по умолчанию, чтобы пользовательские значения
  выжили; комбобокс модели живёт на вкладке Request, и его переключение
  сразу переключает черновой профиль.
- **67.** Нечитаемые страницы DjVu становятся явными белыми заглушками вместо
  отказа от всей книги: исходный индекс и ограниченные метаданными размеры
  сохраняются, `DocumentPage.sourceError` и `PreparedDjVu.warnings`
  персистятся, число предупреждений и первая деталь показываются в UI; OCR
  пропускает заглушки — они остаются нераспознанными и исключаются из
  экспорта распознанного текста; сбои открытия документа остаются фатальными.
- **72.** Хранилища профилей разделены по ролям модели: у каждой роли свои
  файлы профиля запроса, профиля запуска и каталога скачивания плюс
  QML-синглтоны, а `RequestProfileStore`/`LaunchProfileStore` несут `Role`,
  выбирающий файл пользовательских переопределений и ключ настроек активного
  id; прежние двухролевые имена (`request.json`/`requestValidate.json`,
  `serverLaunchValidate.json`, `catalogValidate.json`) принимаются/
  переименовываются при загрузке; рантайм и мастер настройки продолжают
  потреблять профили распознавания.
- **80.** Списки установленных моделей фильтруются по роли: `ModelEntry`
  несёт персистентный список `roles` в `index.json`, записываемый при
  установке и сливаемый (никогда не выбрасываемый) при переустановке с
  другой роли; модель попадает в список, когда она активная модель роли,
  несёт тег роли или — для прежних записей с пустыми ролями — выводится из
  раскладки файлов (проектор mmproj → OCR, чистый текст → верификатор);
  `parser`/`prompt` сознательно ничего не доказывают. Прежний тег `"check"`
  переименовывается при загрузке (см. ADR 146).
- **87.** OCR-модель добавляется рецептом, а не операцией: один
  класс-адаптер + один встроенный профиль запроса с тем же id + записи
  каталога пресетов, всё управляется данными через существующие поверхности
  настроек. Особенности ответа конкретной модели живут в парсере: OTSL-токены
  таблиц (`<fcel>/<lcel>/<ucel>/<xcel>/<nl>`) конвертируются в GFM-таблицу с
  пайпами — или в настоящую HTML-таблицу с живыми `rowspan`/`colspan` при
  `output/tablesAsHtml` — где бы токены ни встретились, не только в блоках
  `table` (OtslTable), с укреплением `convertMath` против обрезанных формул
  и тильда-артефактов.
- **88.** Парсеры вывода — слой на модель, управляемый данными:
  `ParserFactory::create(id, ParserOptions)` конфигурирует парсер один раз
  при создании (`keepPageNumbers`, `tablesAsHtml`, `bboxRange`, `modelId` —
  диапазон bbox 0–1000 это данные, допуск 1 % от него); `IOutputParser`
  владеет `rebuildText(const OcrPage&)` и `displayName()`; `parser/id` по
  умолчанию `auto`, разрешается через `OcrModel::defaultParserId()`;
  отображение метка→стиль — данные в `resources/profiles/labels.json`
  (`BlockStyleMap`, вкомпилированный запасной вариант для тестов); сбои
  разбора всплывают через `OcrResult::notes` → `Controller.parseWarning`
  вместо молчаливого единого куска текста.
- **89.** Разделение парсера четвёртого этапа (`Preprocessor[]` →
  `TokenScanner` → `BlockStyler` → `BlockFormatter[]`) сознательно отложено:
  при одном парсере на модель (см. ADR 112) шов модели живёт в иерархии
  классов, а плоский движок делится, только когда придёт модель с
  по-настоящему другой формой ответа (JSON, чужой XML, дробные координаты).
- **96.** `ParserFactory::create()` отвергает `auto` — `kAutoId` это значение
  настроек, а не id парсера (`create("auto")` возвращает `nullptr` с
  предупреждением; незарегистрированный id по-прежнему деградирует в `raw`)
  — и активация модели больше не копирует `ModelEntry::parser` в
  `Settings.parserId` (см. ADR 88).
- **102.** Одно пространство индексов в парсере det-токенов: он строит
  `page.boxes` и ничего больше, затем выставляет
  `page.text = rebuildText(page)` — тот же рендерер, который приложение
  вызывает после правки. Параллельные списки `blocks`/`rawCoords` исчезли, а
  обнаружение дубликатов сравнивает нормализованные прямоугольники прямо по
  `page.boxes` (допуск 1 %, пропуская фрагменты с
  `BoundingBox::positioned == false`).
- **110.** OCR-модель идентифицируется по id, никогда по отображаемому имени:
  `model/recipeId` называет адаптер, а UI привязывает комбобоксы через роли
  `modelId`/`displayName`. Введённая здесь отдельная настройка
  `model/requestProfileId` позже удалена — id модели единственный селектор
  профиля запроса, так что выбор модели никогда не может молча подменить или
  закрепить профиль сэмплинга.
- **111.** Один chat-обмен и один кодировщик изображений для адаптеров
  моделей: `runChatExchange<Result>()` (models/ChatExchange.h) владеет полным
  кругом (тело собирается на воркере, POST, разбор, разрешение promise),
  `encodeImageDataUrl()` — единственный кодировщик, а
  `ConnectionConfig::timeoutMs` совпадает со 120 с в `SettingsStore`. Хуки
  тела/разбора остаются `static`, чтобы запросы завершались и после
  уничтожения адаптера.
- **112.** Один парсер на модель, названный по модели: `DetTokenParserBase`
  держит общий движок (сканирование токенов → нормализованные блоки →
  Markdown через `rebuildText()`, подформаты OTSL и `<table>`, вычистка
  служебных токенов), каждый парсер отвечает за паттерн заголовка /
  экранирование `\n` / починку до токенизации, а профиль называет свой
  парсер в `roles.<role>.parser`. Критерий: новая модель — один JSON-профиль,
  один небольшой подкласс и две строки CMake.
- **122.** Один список моделей — строка есть модель, а её квантизации
  выбираются на строке (`ModelQuantModel`): кванты на диске, которых профиль
  не перечисляет, остаются в строке (не скачиваются, но активируются и
  удаляются), модели без профиля получают свою строку, а выбранная
  квантизация запоминается на профиль (`models/quant/<profileId>`).
  `ModelInstallTransaction::preserveExistingFiles()` переносит файлы, которые
  установка не пишет, в staging до коммита, так что публикация сохраняет
  соседние квантизации. Поверхность окна моделей сама позже была переработана
  (см. ADR 168).
- **123.** Порядок моделей роли — одно правило — `ModelProfiles::forRole()`
  (сначала рекомендуемый профиль с `default: true`, остальные по названию) —
  его вызывают и список моделей, и пикеры профиля запроса, и ему следует
  откат неизвестного id. Пикер профиля check-роли, введённый здесь, позже
  удалён вместе с остальными пикерами (см. ADR 129); механика выжила как
  комбобокс «Профиль модели» режима External.
- **124.** `runtimeNote` профиля говорит только то, что всё ещё правда:
  механизм (`ModelProfiles::runtimeNoteFor()` + вкладка Launch, шаг мастера и
  диалог скачивания) остаётся для следующей незапускаемой модели, но
  устаревшее примечание TeleOCR «needs a patched llama-server» исчезло — его
  веса `konradjr007/NaviDC-OCR-GGUF` грузятся в стоковой сборке. `minBuild`
  по-прежнему не может выразить «нужен пропатченный core».
- **129.** Профиль разрешается приложением, а не выбирается: комбобоксы
  «Профиль» и кнопки «Восстановить профиль» ушли со вкладок Request/Launch, а
  черновик следует выбору (`RequestProfileStore::followActiveProfile()` по id
  моделей, `LaunchProfileStore::ensureProfileResolved()` при смене бэкенда).
  Режим External сохраняет единственный комбобокс «Профиль модели» над
  `RequestProfileListModel`, который пишет те же id настроек, что и
  автоматические пути.
- **132.** «Распознать всё» пропускает страницы, у которых уже есть результат;
  «Распознать» — нет: предикат пропуска это
  `PageSkip { None, Unreadable, AlreadyRecognized }` с `SkipResolver`,
  решает флаг батча, а `firstPageToRecognize()` выходит до
  `setBusy()`/`ensureConnectionReady()`, когда ничего не осталось — холостой
  клик никогда не запускает сервер и не грузит модель.
- **135.** Обработка дубликатов идёт дальше bbox: после прохода точных
  прямоугольников (ADR 102) парсер выбрасывает блок, чей текст существенно
  повторяет более ранний (нормализованное равенство или дословный прогон
  ≥ 8 слов, покрывающий ≥ 60 %), пристыковывает уникальный хвост
  возобновлённого блока к более раннему блоку и помечает выживших
  `BoundingBox::duplicateSuspect` (персистится в `.llocr`). Подозреваемые
  проверяются независимо от фильтра типов блоков; предохранитель короткого
  текста держит заголовки и подписи вне сети.
- **136.** Правки вывода LFM2.5-VL (модель в архиве, паттерн механизма
  остаётся): блоки формул теряют внутренние обёртки `$…$` (хвостовое `(n)`
  становится `\tag{n}`), а letterbox-вставки координат парсер отображает
  обратно (`calibrateRect()` с `ParserOptions::pageAspect`, несущим геометрию
  страницы) — проход дубликатов по точным прямоугольникам сравнивает
  калиброванные прямоугольники.
- **144.** Спекулятивное декодирование через MTP draft-модели как
  поставляется: `--spec-type draft-mtp --spec-draft-n-max 4` в профилях
  fix-моделей; сюда привели исследовательские ADR 137–143. Draft-модуль —
  полноправные данные профиля модели (`files.mtp` с репо/закреплённым sha,
  `ModelEntry::draftPath`, `launch/draftPath` → `--model-draft`, sidecar-драфты
  сканируются как `ModelFileKind::Draft`), а слитый набор также утвердил
  проводку запроса: бюджет генерации живёт в запросе (`max_tokens`; ни
  `n-predict`, ни запасного слоя запуска — таблица Launch показывает машинные
  `n-gpu-layers`/`flash-attn`/`ctx-size`), id модели — единственный селектор
  профиля запроса, порядок частей провода — данные на модель
  (`promptBeforeImage`), а формулировки верификатора живут только в данных
  модели (общие вкладки промптов `verifyPrompts.json` исчезли — окно проверки
  сохраняет включение по типам блоков).
- **146.** Роль check названа `blockRecognition` везде, где переименование
  ничего не стоит (ключи ролей профиля, `ConnectionRole::BlockRecognition`,
  миграция сохранённого `"check"` в реестре при загрузке); прежняя лексика
  выживает там, где она перетасовала бы пользовательские данные (ключи
  настроек `check/*`, `CheckController`/`CheckRequest`/`CheckResult`, UI
  «Модель OCR блока»).
- **150.** Ручной проход разметки страницы — задача `layout` с собственными
  полными настройками модели (`ConnectionRole::Layout`, группа настроек
  `layout/*`, окно «Модель разметки» — отмена общей с check конфигурации
  ADR 149). `LayoutController` ставит страницы в очередь (текущая/все),
  сплющивает каждую в откалиброванный по апстриму квадрат 1036×1036, а парсер
  разметки переписывает строки блок/метка ответа в канонические токены;
  `AppController::applyLayout` заменяет блоки страницы — содержимое в ответе
  игнорируется, текст приходит поблочно через blockRecognition. ADR 252 влил
  роль в матрицу задач.
- **169.** Каждая задача поставляется с явной моделью по умолчанию —
  `roles.<task>.default: true`, ровно одна на задачу, машинно проверяется
  `test_model_preset_catalog::roleDefaultsFollowTheShippedProfiles`. Это слой
  данных для автоподбора: квант — первая запись профиля, чей курируемый/
  измеренный размер влезает в машину.
- **179.** Оценка памяти говорит правду: `ModelMemoryEstimator` читает
  заявленную архитектуру, настоящую размерность головы
  (`attention.key_length`), проектор и рабочий набор ubatch, считая только
  attention-слои (гибридный Qwen3.5 держит KV в 8 из 32 слоёв), и сообщает
  занимаемую память против VRAM карты во вкладке Launch.
- **182.** Тексты запросов задачи живут в собственных профилях запроса —
  `resources/profiles/requests/fix-requests.json` и `read-requests.json`,
  называемых `"promptProfile"` роли — тогда как профили моделей хранят то,
  что по-настоящему на модель: параметры запуска и запроса, бюджет вывода,
  калибровку проверки и маршрутизацию. Роль, называющая неизвестный профиль
  запроса, — ошибка загрузки; OCR-модели держат свои промпты инлайн, потому
  что их задачи различаются по моделям.
- **191.** Выпадающий список квантов отвечает на вопрос «какая карта нужна
  этой квантизации»: `✓ Q8_0 — 9.1 GiB · VRAM ≥ 11.4 GiB`. Профиль модели
  несёт блок `memory` (архитектура плюс курируемые `sizeBytes`/`draftBytes`),
  поэтому `ModelMemoryEstimator` вычисляет потребность целого сервера либо из
  заголовка GGUF, либо из профиля — одна формула на собственных числах
  llama.cpp (точный KV-кэш, рабочий набор в пределах 12 %, зрительный
  кодировщик, измеряемый на токен изображения, контекст draft,
  `kvBytesFixed` для гибридов со скользящим окном, голова `nextn` не держит
  KV-кэша); вкладка Launch сравнивает с картой потребность, а не голые
  буферы. Метод и калибровка: `docs/18-memory-estimate.md`,
  `scripts/measure-memory.sh`, `scripts/memory-from-log.py`.
- **198.** `ModelRegistry::update()` читает индекс под локом записи,
  проверяет версию и пересобирает сломанный индекс из каталога моделей перед
  изменением — модели на диске истина, индекс их кэш; вызывающий узнаёт об
  этом через `update(..., bool *rebuilt)`.
- **207.** Id парсера — свойство профиля, а не экземпляра модели:
  `OcrModel::defaultParserIdFor(modelId)` читает профиль (с тем же откатом,
  что применяет `create()`), вместо того чтобы строить `OcrModel`, который
  сконструировал бы `LlamaClient` с `QNetworkAccessManager`; контроллер
  помнит id на профиль.
- **215.** Список задач живёт один раз в `core/ConnectionRole.h`
  (`connectionRoles`, `connectionRoleIds`): состояние рантайма — это
  `std::array<bool, connectionRoleCount>`, индексируемый ролью, QML читает
  `Settings.taskRoles`, мастер настройки читает
  `ModelInstaller::defaultTaskChoices`; `static_assert` и
  `TestSettingsStore::theTaskListIsTheSingleSource` держат список и разбор
  имён в согласии.
- **216.** Настройки на задачу в `SettingsStore` диспетчеризуются одной
  таблицей (запись на роль: пути запуска — модель, mmproj, draft — профиль
  запроса, имя модели) вместо десяти веток
  `switch (connectionRoleFromName(role))`;
  `TestSettingsStore::theRoleDispatchReachesEveryRole` доказывает, что
  диспетчеризация попадает в свою задачу.
- **217.** `RoleProfiles.qml` разрешает задачу из одной таблицы (строка =
  задача, столбец = свойство) вместо шести цепочек условий; тексты остаются
  значениями, переведёнными в собственном контексте файла, столбцы, читающие
  синглтоны, — функции, чтобы биндинги продолжали отслеживать настройки, а
  мёртвая ветка `quantModels("all")` исчезла.
- **218.** Поворот — свойство страницы: `DocumentPage::rotation`
  (0/90/180/270) применяется там, где страница рендерится
  (`DocumentModel::renderFull`/`renderDetached`), `pageAspect` вычисляется из
  повёрнутого размера, а поворот сбрасывает страницу в состояние до
  распознавания. Ручной поворот (две кнопки панели страниц) трогает только
  текущую страницу, спрашивает подтверждение, когда есть результат, и помечает
  страницу «повёрнута вручную», чтобы проверка ориентации её не трогала.
  Ориентацию читает только пиксельная проверка — модельный арбитраж,
  задуманный здесь и в ADR 221, удалён (см. ADR 242, ADR 243).
- **220.** Задача доходит до профиля: `OcrModel::create(id, role)` и
  `roleForTask()` выбирают роль задачи, когда модель её объявляет, и и
  промпт, и парсер приходят из той роли (`effectiveParserIdFor(profileId,
  role)`, роль в ключе кэша) — модель, обслуживающая несколько ролей, больше
  не отвечает промптом и парсером первой найденной роли.
- **222.** Проектор распознаётся по `mmproj` в имени файла
  (`ModelCatalog::fileKind` → `ModelFileKind::Vision`); установщик
  (`ModelInstallTransaction::selectModelFiles`) и
  `ModelRegistry::scanModelsDir` берут первый проектор, и каждая
  поставляемая модель называет свой проектор `mmproj*` — поле профиля,
  объявлявшее проектор, выброшено (его единственного пользователя удалил
  ADR 223).
- **223.** MiniCPM-o 4.5 измерена как fix-модель и не поставляется: она
  возвращает вердикт без исправленного блока (2 Ok / 0 Fix / 5 Review,
  CER 0.147 → 0.147), так что она остаётся на стенде
  (`OCRtest/fix_models/profiles/minicpm-o-4.5.json`) без профиля в каталоге
  приложения — возможность заявляется только вместе с измерением.
- **224.** Читатель HTML (`src/parsers/HtmlMarkup.cpp`) знает
  самозакрывающиеся теги — `/` после имени тега закрывает элемент, так что
  `<br/>` больше не проглатывает остаток страницы как своих детей — а блок,
  помеченный моделью как `Equation-Block`, несущий прозу вне `<math>`,
  получает метку `text`, а не конвейер формул.
- **225.** Формула внутри ячейки таблицы — математическая разметка
  приложения, а не тег `<math>`: `serializeHtml` сохраняет таблицы как HTML,
  но конвертирует `<math>` в `$…$`, так что KaTeX рендерит ячейку в
  предпросмотре и в каждом экспорте, несущем HTML.
- **242.** Проверка ориентации — только пиксельная: изображение читает ось
  текста, и страница, лежащая боком или нечитаемая для неё, помечается
  красным (маркер страницы плюс статус «лежит боком» / «ориентация не
  определена») и остаётся как есть — пользователь поворачивает её сам, а
  поворот снимает маркер. Модельная часть ADR 221 удалена целиком:
  `orientation-requests.json`, `DecisionController::askChoice` и поле
  `questions` (`Role::questions`, `DecisionBlock::questions`) исчезли.
- **243.** Детектор ориентации двухстадиен (`app/PageOrientation`): маска
  чернил локальным порогом Сауволы, кроп bbox, выравнивание наклона
  развёрткой ±15° с шагом 0.5° (максимум суммы квадратов разностей профилей,
  параболическое уточнение), затем квадрант по нормализованной
  автокорреляции профиля строк (окно 12…60 px, порог ≥ 0.15), причём ось
  выбирает глубина чередования cv ≥ 0.65; closing 1×25 мостит слова в полосы
  и считает линейные компоненты (меньше десяти → «не знаю»). Вердикт несёт
  `deskewDegrees` и `confidence`; 180° всё ещё не читается (проекции
  инвариантны к полуобороту), а проверка остаётся быстрой (десятки мс на
  страницу).
- **244.** Вердикт ориентации выпрямляет страницу: ось, прочитанная с
  `deskewDegrees` ≥ 0.5°, сигнализирует `skewed`, и `AppController` применяет
  её к `DocumentPage::skewDegrees` — рендер выправляет наклон гладким
  ресемплингом в белое (`PageRotation::deskewImage`); коррекция накапливается,
  сама оседает ниже порога, сбрасывает распознавание и сохраняется в `.llocr`
  рядом с поворотом. Четверть-поворот всё ещё ждёт источник направления —
  токены поворота модели разметки (см. ADR 245).
- **245.** Токены поворота разметки доходят до страницы как предложение в
  один клик: `<|rotate_up/left/right/down|>` MinerU после каждого блока
  парсеры хранят в `BoundingBox::orientation`, `applyLayout` голосует, и
  страница, помеченная пиксельной проверкой как лежащая боком, получает
  кнопку «Повернуть влево/вправо», поворачивающую её через обычный
  `rotatePage`. Автоповорот по токенам сознательно выключен — направление
  угадывается в 14 случаях из 20, а неверный поворот хуже неповернутой
  страницы (ADR 242).
- **246.** Разметка сама поворачивает лежащую боком страницу и размечает
  заново: при включённом (по умолчанию) «поворачивать боковую страницу после
  разметки автоматически» прогон разметки один раз поворачивает страницу
  (`turnPage`, снимая маркер и только что прочитанную разметку) и начинает
  второй проход разметки; голос считается прямо из строк ответа
  (`OcrPage::orientationVote`, победителю нужно ≥ 9/10 «не вверх» и ≥ 6/10
  от всех строк). Ложную метку «боком» у оглавления чинит глубина
  чередования. Дыра в 180° честная — дешёвого детектора 0/180 пока нет;
  направление остаётся догадкой модели (14/20). При выключенной настройке
  работает подсказка ADR 245 в один клик.

### Проверка и исправление

- **134.** Очередь проверки спрашивает только блоки, у которых ещё нет
  ответа: фильтр `checkStatus != NotChecked` безусловен для «Проверить
  страницу» и «Проверить всё» (`collectEnabledBoxes()`), пустая очередь
  сообщает «Проверять нечего: уже проверенных блоков: N.», а явная
  перепроверка отдельного блока по-прежнему работает — повторно распознанный
  блок возвращается в очередь.
- **155.** Поблочный цикл проверки не платит налогов на подключение:
  `RuntimeController` кэширует последний успешный `ResolvedConnection` на
  роль (инвалидируется переходами состояния и сменами настроек, сбои никогда
  не кэшируются), каждая модель владеет одним `LlamaClient` (keep-alive через
  запросы на страницу / на блок), а `availabilityChanged` срабатывает только
  на реальном переключении флага.
- **163.** Протокол задачи `fix` — OK / FIX / REVIEW: запрос несёт промпт
  верификатора профиля, промпт типа блока, OCR-кандидата в рамке
  `<ocr_candidate>…</ocr_candidate>` (один канонический кандидат —
  сохранённая коррекция никогда не отправляется повторно) и кроп, в порядке
  согласно `promptBeforeImage`. OK не сохраняет коррекцию (см. ADR 185), FIX
  сохраняет исправленный текст, REVIEW помечает блок повреждённым, пустой FIX
  деградирует в REVIEW, а любой другой ответ — ошибка запроса. Формулировки
  провода позже были уточнены (см. ADR 181).
- **164.** Двухслойная проверка блока: каждый блок несёт
  `box.text`/`box.correctedText` с независимыми вердиктом + уверенностью
  (`checkStatus`/`confidence` против
  `correctedCheckStatus`/`correctedConfidence`, чистые функции
  `BoxTransitions`). Любой результат OCR попадает в слой текста и стирает
  коррекцию целиком, результат исправления попадает в слой коррекции, задача
  проверки судит эффективный слой, «Отменить исправление» откатывает, а
  автоматического повышения нет — экспорт, текст страницы и предпросмотр
  используют эффективный текст. `BoxCheckStatus::ReRecognized` (значение 2)
  удалён без перенумерации, убрав янтарное двухвариантное состояние ADR 153.
- **165.** Страница несёт два независимых статуса: персистентный
  `PageRecognitionMode {None, MarkupOnly, RawOcr, MarkupOcr}` (`.llocr` v2;
  MarkupOnly становится MarkupOcr, как только у каждого не-image блока есть
  текст) и вычисляемый агрегат проверки по включённым типам блоков +
  подозреваемым дубликатам — «проверено» только когда у каждого подлежащего
  блока есть вердикт на его эффективном слое, любой Mismatch/Review делает
  его «есть ошибки».
- **173.** P(match) вердикта задачи проверки персистится в `project.json`
  (`BoundingBox::confidence`/`correctedConfidence`, −1 = нет, аддитивное
  поле, без подъёма версии), так что калибровка порога — один прогон вместо
  итерации на каждый порог-кандидат — оценочный стенд пересчитывает кривую
  FN/FP при любом пороге-кандидате из сохранённых значений.
- **178.** Автоматической проверки и автоматического исправления больше нет:
  `check/autoCheck`/`check/autoFix` (и более старый `check/autoRecheck`)
  удалены со всем путём кода (enum `FixMode`, `m_fixQueue`, обработчик

  отдельная очередь, которую кнопка «Исправить» запускает по проблемным

- **192.** Протокол исправления говорит полными блоками: контракт

- **194.** Формула нормализуется там, где распознаётся: каноническая форма
  (`core/LatexText`) носится блоком с момента, когда распознавание
  приземлилось (`BoxTransitions::latexResultApplied`), так что панель,
  экспорт, проверяющий и исправляющий видят одни и те же байты
  (`FixDiffGate::normalizeLatexCandidate` исчез). `LatexText::check`
  валидирует синтаксис без движка LaTeX (скобки, окружения, пары
  `\left`/`\right`, математические ограничители, оборванная команда,
  недостающий аргумент `\frac`/`\text`/`\sqrt`); не прошедшая формулу

  `BoxCheckStatus::InvalidSyntax`) — и исключается из проверки и исправления
  до нового распознавания.
- **195.** Markdown-фенс кода внутри формулы — разметка-носитель, а не
  содержимое формулы: он разворачивается, когда формула приземляется
  (`LatexText::canonical`, вместе с каноническими пробелами ADR 194), а
  несбалансированный фенс или оставшийся бэктик — собственный дефект —
  «неверный синтаксис», причина «блок кода внутри формулы»
  (`LatexText::Problem::CodeMarkup`). Текст страницы пересобирается из блоков
  после применения канонической формы (`applyFormulaVerdicts` →
  `rebuildTextFromBlocks`), так что пробелы модели и фенс никогда не доходят
  до документа, предпросмотра или экспорта.
- **196.** Формула, разбитая моделью на несколько фрагментов «$$…$$»,
  рендерится несколькими выключными блоками — каждый фрагмент на своей
  строке, отдельный номер уравнения становится `\tag` — а носители «$$»
  балансируются и не являются проблемой синтаксиса. Невидимые ограничители
  `\left.`/`\right.` паруются с любой скобкой, поэтому корректные
  многострочные формулы больше не помечаются сломанными; синтаксические
  вердикты пересчитываются при открытии проекта
  (`BoxTransitions::syntaxVerdictRefreshed`).
- **206.** Охрана доступности стоит впереди работы: `updateAvailability()`

- **257.** Авто-режим — список стадий, а не кнопка: кнопка авто-прогона ведёт
  разметка → распознавание блоков → проверка → исправление → проверка
  исправленного как контракты `AutoPipelineStage`
  (`skipReason`/`start`/`stop`/`finished`/`failed`) в
  `AutoPipelineController`. Стадии выполняются по стадиям, а не по страницам

- **258.** Пороги визуального диффа измерены на корпусе OCR_TEST (177

  0.92, equation 0.87, table 0.4, базовый 0.5 — FN 10 (13.7 %) / FP 41

- **259.** У fix-роли есть второй протокол, `read_block`: модель пишет блок

- **260.** Перечитывание — действие, а не свойство модели: протокол едет с

  исправляет — перечитывание ручное. Правило шлюза `\tag{n}` ≡ `(n)` теперь

- **261.** Результат чтения виден: состояния читателя говорят рамкой

- **286.** Очередь проверки разделена на очереди ролей. `BlockWorkList`

  принятого субсекундного мерцания кнопки остановки в дораспуске.

  слияние 2×2 — откалибрована по prompt-токенам MinerU2.5-Pro с точностью
  ~1%); mineru ставит 3072 — это удерживает prompt плотной таблицы внутри
  слота, обрезанного сервером до `n_ctx_train`. Обе ступени работают при
  сборке запроса (`BlockRecognitionModel::buildRequest`,
  `FixModel::buildRequest` — на рабочем потоке, до кодирования картинки, там
  же, где уже применяется `imageLongestEdge`), и обе выключены у профилей,
  которые их не называют, — поведение всех остальных моделей не меняется.
  Известный предел: длина ответа на плотную таблицу ограничена её
  содержимым, а не кропом, поэтому бюджет защищает prompt, а не время
  генерации.
- **291.** Задача, уже выполнявшаяся над областью, спрашивает перед
  повторным запуском: шесть кнопок шапки (разметка, распознавание,
  проверка, исправление, перераспознавание, авто) открывают один диалог —
  «Отмена» / «Переделать всё» / «Только где не сделано» — а область, где
  ничего не сделано, запускается сразу, так что вопрос появляется только
  там, где реально теряются результаты. Режим —
  `AppController::RerunMode {RedoAll, SkipDone}` (QML:
  `Controller.RerunMode.*`), диалог — `src/qml/Common/RerunConfirmDialog.qml`,
  а флаги «по задаче есть результаты» едут в `AvailabilityPresenter` рядом
  с предикатами включённости (ADR 286). Режимы различаются списком работы,
  а не машиной: SkipDone держит сборщики ADR 286 (без текста / включённые /
  ждущие исправления; чтение сужается до `notReadBlocks` — читаемые минус
  прочитанные), RedoAll расширяет их и на сделанные блоки
  (`reRecognizableBlocks`, `recheckableBlocks`, `refixableBlocks`,
  `readableBlocks` — каждый блок, который задача может обслужить, включая
  распознанные и несущие вердикт). Принадлежащий пользователю блок
  (Edited/Approved на любом слое) ни в одном режиме не перезапускается и не
  стирается. Стирание следует за стеком — повтор стирает свой уровень и всё
  над ним: распознавание стирает по приходу ответа (`ocrResultApplied`
  очищает слой коррекции и оба вердикта, ADR 164 — без нового кода),
  проверка стирает вердикт судимого слоя перед каждым запросом
  (`verificationStarted`), а повтор исправления/чтения стирает результат
  средства по блоку прямо перед сборкой запроса — prepare-хук `BlockQueue`
  запускает `BoxTransitions::correctionReverted` (слой коррекции и
  `fixStatus` уходят, слой текста и его вердикт остаются), так что
  кандидатом исправителя снова становится распознанный текст. Стирание —
  just-in-time, по блоку: несостоявшийся или прерванный прогон оставляет
  результаты ещё не обработанных блоков целыми, а отказавший ответ больше
  ничего не пишет. Разметка заменяет результат страницы целиком, как прежде.
  Автоконвейер (ADR 257) получает те же два ответа: RedoAll — старый прогон,
  разметка с нуля по всем страницам области; SkipDone — режим продолжения:
  этап разметки фильтрует свою область до неразмеченных страниц (полностью
  размеченная область пропускает этап с «Нет страниц для разметки»), а этапы
  распознавания/проверки/исправления держат полную область, пропуская
  сделанные блоки через свои сборщики. Правит ADR 257 (в части — разметка
  больше не всегда с нуля).

### UI

- **9.** Навигация остаётся живой во время распознавания — пользователи
  листают другие страницы, пока идёт батч.
- **10.** Экспорт пишет TXT/MD/HTML напрямую; DOCX идёт через Pandoc
  (нативные формулы Word); PDF использует конвейер рендера предпросмотра
  (см. ADR 63) — путь Pandoc→LaTeX PDF удалён.
- **11.** Миниатюры не несут ограничивающих рамок — лента сигнализирует
  только распознано/изменено/дубликат/текущая; блоки принадлежат
  центральному предпросмотру.
- **13.** Геометрия окна сохраняется (`WindowSettings` + `SettingsStore`
  `ui/*`): положение, размер и видимость переживают сессии.
- **16.** i18n через Qt Linguist (`qsTr`/`tr` + `.ts`/`.qm`), язык выбирается
  в настройках (System/English/Русский), по умолчанию System, перевод на
  лету; сохраняется как `ui/language`, встроенный `.qm` загружается на старте
  и при смене.
- **22.** Предпросмотр Markdown рендерится на клиенте через Qt WebEngine +
  комплектные marked + KaTeX (`resources/preview/`) — LaTeX/таблицы/
  изображения рендерятся локально без сетевого доступа; ссылки
  `image://ocr/crop/*` конвертируются в `data:`-URI перед рендером.
- **23.** Страницы можно удалять и перетаскиванием менять порядок в ленте
  миниатюр; `PageEditStore` и `PageListModel` перемапливают индексы после,
  чтобы правки следовали за своей страницей.
- **24.** Блоки изображения/графика редактируются на предпросмотре
  (перемещение/изменение размера/удаление) и экспортируются как вырезанные
  изображения; `rebuildPageText()` перегенерирует Markdown страницы, потому
  что ссылки на изображения вшивают индекс блока (`image://ocr/crop/<N>`),
  так что удаление заставляет пересборку ради согласованности индексов.
- **55.** Восстановленное положение окна проверяется против текущих экранов
  (`WindowSettings::visiblePosition`): сохранённые x/y применяются, только
  пока полоса заголовка окна пересекается с подключённым экраном, иначе окно
  центрируется на ближайшем экране (поправка к ADR 13).
- **63.** Экспорт HTML/PDF переиспользует конвейер рендера предпросмотра:
  безголовый `QWebEnginePage` грузит `qrc:/preview/export.html` (marked +
  DOMPurify + KaTeX), кропы вкладываются как `data:`-URL, CSS из
  `Exporter::exportStyleSheet()` общий для обоих выводов; PDF откатывается на
  `QPdfWriter`, HTML — на писатель экранированного текста; DOCX остаётся
  только через Pandoc (Chromium не умеет выдавать OOXML); кодирование кропов
  идёт на воркере, рендер — в UI-потоке (ограничение `QWebEnginePage`).
- **64.** Группа настроек Output — пять ключей: `output/splitPages` (по
  умолчанию on; разделители страниц без меток "Page N"),
  `output/keepPageNumbers` (по умолчанию on; выбрасывает колонтитулы при
  разборе — о расширенной области действия см. ADR 280),
  `output/tablesAsHtml` (по умолчанию off, см. ADR 19), `export/pdfLandscape`
  + `export/pdfMarginMm` (0–50 мм, по умолчанию 15 → `QPageLayout` в
  `AppController::pdfPageLayout()`).
- **70.** Настройки — отдельные немодальные окна, открываемые из меню шапки
  (`SettingsDialog`/`SDTabBar` удалены): «Интерфейс» применяется сразу со
  своим ограниченным «Вернуть настройки по умолчанию», остальные фиксируются
  при сохранении; один экземпляр llama-server обслуживает все роли, модель
  (пере)загружается под задачу; авто-обнаружение в `RuntimeController` и
  ярлык вкладки в футере удалены как дубли потока мастера/установщика.
- **75.** Окна Output и Runtime имеют ограниченный по области, немедленный
  «Вернуть настройки по умолчанию» (`SettingsStore::resetOutputDefaults()` /
  `resetRuntimeDefaults()` фильтруют таблицу дефолтов ADR 50 и пишут через
  сеттеры свойств); область действия Runtime сознательно исключает каталоги
  хранения, флаги автостарта и ключи запуска.
- **77.** Размеры текста UI компенсируются по платформе в `Theme.qml`
  (`platformTextScale = 4/3 на macOS` — единственное место, где выбирается
  размер в пунктах; ни один QML-файл не хардкодит `font.pointSize`): 1 pt —
  это 1 px на macOS, но 1.33 px на Windows, так что без множителя текст
  выходил на ~25 % мельче относительно пиксельно-размерных контролов.
  (Заменён ADR 293: размеры в px с коэффициентом по ОС, компенсация убрана.)
- **79.** Режим подключения — единственный выбор в комбобоксе, и содержимое
  каждого окна следует ему: в режиме External окно моделей показывает только
  уведомление «Настроить рантайм…», в Managed предлагает источники
  скачивания; Запустить/Стоп/Перезапустить/Показать журнал живут в футере, а
  не в окне настроек; установленные сборки получают построчное «Открыть
  папку» (`RuntimeInstaller::openBuildFolder()`).
- **81.** Мастер настройки — самодостаточный линейный поток (интро +
  язык/тема, карточки рабочего режима, пишущие `provider/mode`, шаги по

  а не лаунчер окон настроек; шаги рендерятся по видимости, потому что набор
  шагов различается по режимам, футер показывает «Шаг N из M», а мастер
  доступен из меню настроек.
- **82.** Встроенные списки (`ModelInstalledList`/`ModelPresetList`/
  `RuntimeBuildsList`) публикуют
  `implicitHeight = min(count, maxVisibleRows) * rowHeight`, и потребители

- **113.** QML заявляет правила; C++ их решает: баннер «Параметры запуска

  `Runtime.serverPathValid`/`modelPathValid`/`configValid` — путь, который
  задан, но отсутствует на диске, не конфигурация.
- **114.** Сообщение хранится непереведённым и рендерится при чтении:
  `StatusMessage` (core/StatusMessage.{h,cpp}) несёт дословный текст или

- **115.** Списки установщика — list-модели с объявленными ролями —

- **151.** Разделение интерфейса стоит: действия над документом в шапке,

  `useCorrectedText` — по одному слову статуса на карточку плюс общее
  состояние в шапке, подкраска изменений по словам на месте
  (`core/TextDiff.h`, никогда зачёркивание, переключатель «Различия»),
  моноширинный шрифт для кодоподобных блоков, действия «Утвердить»/
  «Сбросить исправление» с прыжком Ctrl/⌘+Return к следующему проблемному
  блоку и ручная правка «Изм.» на карточку.
- **187.** Утверждение можно отозвать: кнопка подтверждения читается
  «Отозвать утверждение» и возвращает вердикт, который утверждение заменило
  (`checkStatusBeforeApproval`/`correctedCheckStatusBeforeApproval`,
  опциональные ключи `project.json`, версия схемы остаётся 2). Написанный
  вручную текст — собственное состояние `BoxCheckStatus::Edited` («Изменён
  вручную», без счёта), правка выходит через «Сохранить»/`Esc`
  (Ctrl/⌘+Return сохраняет вместо утверждения), а карточка версии имеет одну
  равномерную рамку.
- **188.** Панель теряет свой цветовой шум (никаких зелёных кнопок — цвета
  это вердикты и акцент версии в поле зрения), переключатель «Различия»
  появляется, только когда есть вторая версия, а значок «Исправить (N)»

  счёт). `scopedProblemBlockCount` переименован в `scopedPendingFixCount`.
- **189.** Клик по блоку выделяет его, а перетаскивание панорамирует
  страницу; блок двигается только в режиме правки (кнопка перемещения на
  мини-панели; галочка, клик снаружи, другое выделение или смена страницы
  выводят из него; хендлы изменения размера видны только там). Новый блок
  рисуется на странице (`AppController::addBlockAt`, курсор-перекрестие +
  чип оттенка, `Esc` или второй клик отменяют), а слово статуса блока без
  текста — «Разметка» без точки.
- **190.** Структурное изменение — не ручная правка: маркер «изменено»
  означает ровно "пользователь ввёл текст вручную" — ставится одним
  `setCurrentPageText()`, снимается откатом. Удаление блока двигает цель
  отката вперёд и никогда не заменяет текст пользователя, а изменение
  конвейера, приземлившееся на страницу с ручной правкой, сливается в этот
  текст (общая часть заякоривает изменение, формулировка пользователя
  побеждает там, где они расходятся).
- **199.** Индекс страницы зажимается документом, а не манифестом: проект, у
  которого все вложенные файлы отсутствуют, открывается на странице 0

  `std::clamp` и разногласием модели/контроллера о текущей странице.
- **200.** Черновик таблицы моделей — набор записей `list<QtObject>` (`key`,

  `wysiwyg` с рендером формул KaTeX, а raw-вкладка «Текст (MD)» — обычный
  `TextArea` — не меняется вовсе: tap-to-block и подсветка диапазона блока
  живут там. Markdown идёт в страницу через `runJavaScript` (`pushPage`),
  правки возвращаются через `QWebChannel`-мост (`app/EditorBridge` — первый
  канал веб→QML в приложении): страница сообщает lute-нормализованный
  `getValue` последнего пуша как эталон, и вычитка, совпавшая с ним, — эхо,
  а не правка. Кропы едут как `data:` URI (существующий кэш
  `encodePreviewMarkdown`, теперь ещё и собирающий карту data↔crop) и
  переписываются назад в `image://ocr/crop` в `setCurrentPageTextFromEditor`
  до записи в модель. Страница тегирует свои DOM-блоки порядком, который
  считает `blockBoxMap` (ranges `renderPageText`): клик по блоку выбирает
  рамку, выбор рамки подсвечивает и прокручивает к её блокам; страница,
  отредактированная до неузнаваемости, деградирует так же, как уже деградирует
  поиск в raw-тексте. Пуши гейтятся по фокусу редактора — перестройка,
  прилетевшая посреди набора, ждёт blur, как `pendingReload` raw-поля, —
  а каждая вычитка несёт токен пуша своей основы и привязку к странице в
  контроллере: вычитка от заменённого документа или от ушедшей страницы
  отбрасывается вместо записи в чужое место
  (`test_app_import::editorPullCannotLandOnAnotherPage`). Первая настоящая
  правка сохраняет страницу целиком в lute-нормализованном markdown (принято; якоря `mergePipelineChange` после
  этого могут чаще не находить — по-блочная запись — документированный
  запасной путь v2, если нормализация окажется нетождественной на
  нетронутых блоках). Экспортный конвейер (ADR 63) не тронут. CSP
  `editor.html` — только локальные источники; загрузчик ассетов Vditor
  инжектит скачанные скрипты инлайном, поэтому в `script-src` рядом с
  `'wasm-unsafe-eval'` (WASM Lute) стоит `'unsafe-inline'` — сетевой
  поверхности у страницы нет. `test_editor_page` грузит страницу headless —
  это оффлайн-гейт всего стека.

### Безопасность и секреты

- **33.** ⛔ Никакого автоматического подключения к процессу, слушающему
  настроенный порт — `/health==200` не доказывает ни личность процесса, ни
  модель; чужой процесс нельзя взять во владение, а занятый настроенный
  порт — жёсткая ошибка.
- **35.** ⛔ Никакого автоматического снятия `com.apple.quarantine` — никогда
  не обходить защиту ОС для скачанных исполняемых файлов; скачивания через
  QNetworkAccessManager и так обычно не на карантине.
- **38.** Управляемый сервер привязывается только к loopback
  (`127.0.0.1`/`::1`); другие хосты требуют `runtime/allowNonLoopback=true`
  (продвинуто, с явным предупреждением), а клиентский `baseUrl` остаётся
  `127.0.0.1`, даже когда сервер привязан в другое место.
- **45.** Заголовок `Authorization` сбрасывается при любом перенаправлении на
  другой хост — иначе HF-токен утёк бы на CDN/хост, куда указывает
  перенаправление.
- **94.** Дамп сырого запроса/ответа — opt-in через `LLOCR_RAW_DEBUG=1`
  (никогда не ключуется по имени приложения, из-за чего он был включён в
  каждой релизной сборке), а тело запроса дампится до POST, чтобы
  записывались и прерванные запросы — дамп пишет полные base64-изображения
  страниц в `<AppData>/raw-debug/` неповернутыми — риск приватности и роста
  занимаемого диска. Тест: `TestOcrModels::rawDebugDumpIsOptIn`.
- **197.** Поле `file` манифеста `.llocr` — недоверенный ввод: оно
  валидируется (относительный путь, без сегмента `.`/`..`, без буквы диска,
  разрешённый путь остаётся внутри папки извлечения) вместо вклейки в путь
  извлечения — `QDir::filePath()` ни нормализует `..`, ни отказывает
  абсолютному аргументу; проект, называющий внешний файл, открывается без
  него. Тест: `TestProjectStore::manifestFileOutsideTheProjectIsNotOpened`.
- **211.** Единая URL-политика: первый URL запроса проходит тот же фильтр,
  что и перенаправление (`HttpClient::get`), URL пагинации должен совпадать
  по схеме, хосту и порту с запросом (`HttpClient::isSameOrigin`), иначе
  каталог останавливается с сообщением, а `http` остаётся зарезервированным
  за loopback — URL пагинации Hugging Face больше не носит токен на другой
  хост.
- **227.** API-ключи и HF-токен живут в хранилище секретов ОС (macOS Keychain
  через Security.framework, Windows `CredWrite`/`CredRead`, Linux Secret
  Service через `Qt6::DBus`; без новых библиотек); файл настроек хранит
  только эндпоинты и алиасы. Старый ключ открытым текстом мигрирует при
  старте; если хранилище отказывает, ключ живёт в памяти до выхода, и UI об
  этом говорит; сохранённый ключ никогда не показывается обратно — маска
  плюс «Заменить»/«Удалить».
- **232.** Элемент связки ключей macOS принадлежит сборке, которая его
  записала (ad-hoc-подпись привязывает `cdhash`, так что пересборка теряет
  ключ): dev-сборки подписываются самоподписанным сертификатом «LLocr Dev»
  (`scripts/macos-dev-sign.sh`, встроено в сборку, когда идентичность
  существует), а релизным нужен Developer ID. Приложение честно сообщает о
  сбоях, проверяет запись чтением обратно и обновляет существующий элемент
  на месте вместо «удалить и создать заново».
- **233.** Отказ хранилища секретов виден: `SecretStore::Status` различает
  `Ok`/`NotFound`/`Refused`/`Unavailable`/`Failed`, `Refused` блокирует
  запрос, а статус называет причину и лекарство (запрос Keychain или удалить
  протухший элемент `provider/apiKey`), 401 переводится в собственные слова
  приложения («ключ не отправлен или не принят»), а просто отсутствующий
  ключ — не отказ. Причина отказа больше не умирает в `thread_local` на
  рабочем потоке.
- **271.** Управляемый сервер отвечает только на одноразовый токен: каждый
  `LlamaServerProcess::spawn()` чеканит свежий `QUuid`, передаваемый как
  `--api-key` (новый при каждом `start()`, включая авторестарт после
  падения), `api-key` — зарезервированное имя аргумента
  (`LaunchProfile::reservedArgNames()`), все пробы приложения (опрос health,
  `/v1/models`) несут `Authorization: Bearer`, а сервер, переживший
  приложение, хранит свой токен в `owner.json` (`ServerOwnerRecord::token`)
  для сценария attach. Сценарий аудита безопасности #1.
- **272.** Файл модели без опубликованного sha256 не скачивается:
  `ModelInstallTransaction::enqueueFile` ставит `requireSha256 = true`
  (обобщает правило рантайма ADR 212 на модели), а транспорт отказывает
  ответам без `Content-Length` в обеих ветках, 200 и 206 — чанковый ответ
  без границы не сможет заполнить диск под видом модели. Сценарий аудита
  безопасности #9.
- **274.** Экспорт и конвертация считают распознанный текст недоверенным
  (поглощает ADR 273): экспортированный HTML несёт CSP
  `default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src
  data:` (скрипт, контрабандой вшитый в распознанный текст, остаётся
  инертным текстом), а `Exporter::pandocArgs` собирает
  `--from=markdown-raw_tex` (встроенный TeX никогда не доходит до файловой
  системы при LaTeX-конвертации) с `--output=<path>` единым токеном. Тесты:
  `test_exporter` (`pandocArgsDisableRawTex`, `pandocArgsOutputIsSingleToken`).
  Сценарии аудита безопасности #3, #4, #15.
- **275.** Управляемый сервер стартует только на loopback:
  `RuntimeController::startServer` требует, чтобы `launchHost` был
  `127.0.0.1`, `::1` или `localhost`, иначе ошибка, называющая явную
  настройку `allowNonLoopback` — одноразовый токен (ADR 271) защищает только
  локальную машину. Сценарий аудита безопасности #11.
- **276.** Кэш каталога релизов привязан к своему источнику: `ReleaseCatalog`
  пишет `sourceUrl` в файл кэша, а `readCacheFile` считает запись с любого
  другого URL чужой — подменённый или устаревший список с одного адреса
  никогда не выдаётся за другой, это просто промах кэша. Сценарий аудита
  безопасности #10.
- **277.** `ArchiveExtractor::kMaxArchiveBytes = 2 GiB` отвергает сам файл
  архива (плюс суммарный лимит и лимит на запись несжатых данных) до
  извлечения, а `ProjectStore` распаковывает `.llocr` с тем же лимитом. Имя
  записи zip с `\`, `:`, управляющим символом, абсолютным путём или `..`
  отвергается, а цели симлинков (включая pax `linkpath`) проходят ту же
  проверку. Сценарий аудита безопасности #12.
- **278.** Ключ открытым текстом никогда не проходит через аргументы
  запуска: `api-key` зарезервирован и вычищается из строки запуска
  пользователя (`ServerLaunchConfig::toArguments`), пользовательский профиль
  с любым неизвестным параметром отбрасывается целиком
  (`LaunchProfileStore::dropUserProfiles`), а
  `LaunchProfile::isSecretLikeName` (`token`, `password`, `*-key`, `*_key`)
  ставит сохранение такой строки за диалог подтверждения в `LaunchTab.qml`.
  Сценарий аудита безопасности #13.

### Тестирование и CI

- **99.** Каждый тест по умолчанию получает тайм-аут и безголовую платформу:
  цикл уровня каталога в `tests/CMakeLists.txt` применяет `TIMEOUT 300` и
  `QT_QPA_PLATFORM=offscreen` ко всем целям `add_test`. `test_export_renderer`
  вместо этого запускается с
  `QTWEBENGINE_CHROMIUM_FLAGS=--disable-gpu --no-sandbox --single-process`
  (rendezvous Chromium через Mach падает в ограниченных сессиях), а явный
  тайм-аут на тест всё равно побеждает.
- **100.** Одна команда проверки, и CI прогоняет ту же: `scripts/check.sh`
  делает configure-if-needed → сборку → `ctest --output-on-failure` →
  `clang-format --dry-run --Werror` → `qmllint`, по умолчанию переиспользуя
  уже существующее дерево; недостающий инструмент деградирует в уведомление,
  никогда не в молчаливый пропуск.
- **121.** CI двухъярусный: свободный от Qt гейт формата (`scripts/check.sh
  --format-only` → clang-format по `src/` и `tests/`) на каждый push, полная
  матрица только на `workflow_dispatch`; группа конкурентности включает имя
  события, чтобы push не отменял ручной прогон. Qt 6.10.3 — официальная
  сборка онлайн-установщика, так что провижининг может пользоваться
  `jurplel/install-qt-action`/aqtinstall.

### Вырезанное

- **47.** Процесс-помощник watchdog на macOS (kqueue/NOTE_EXIT) закрыт — не
  поставляется: низкая ценность (один остаточный процесс сервера после
  жёсткого убийства GUI, и так обнаруживаемый при следующем старте) против
  высокой сложности (отдельный комплектуемый бинарник, подпись, плохая
  тестируемость); контракт no-orphan по мере возможностей остаётся
  (см. ADR 30).
- **78.** Свободный поиск/скачивание Hugging Face убраны из UI — модели
  устанавливаются из каталога пресетов или локального GGUF-файла
  (`HfSearchList.qml` удалён, `ModelCatalog::search()` и кнопки Import/
  Export каталога убраны); `hfToken` остаётся для скачивания гейтированных
  пресетов.
- **161.** Decision-модель d1-3B удалена: обвязка измерила AUC 0.668 на
  строковом состоянии, и ни одна формулировка не проверяла формулы или
  таблицы (перепробовано семь схем), поэтому её заменила схема
  структурированного состояния — профиль d1-3B и его руководство удалены,
  обвязка и исследование остались.
- **251.** Всё, вырезанное релизом, хранится в `archive/` — девять профилей
  моделей в `archive/models/profiles/`, их парсеры в `archive/parsers/`,
  руководства в `archive/models/docs/`, однопроходное распознавание страницы
  в `archive/single-pass/`, текстовый протокол проверки со своими запросами
  и калибровкой в `archive/decision-text/` — под git, вне всех CMake-целей,
  с `archive/README.md` как манифестом и тегом `archive/pre-cleanup`,
  держащим переплетённый код (`git show archive/pre-cleanup:<path>`).
- **252.** Матрица задач — четыре задачи — `blockRecognition`, `decision`,
  `layout`, `fix` (`core/ConnectionRole.h`); `pageOcr`/`rawPageOcr` вырезаны
  вместе с каждой моделью, которая их обслуживала. MinerU покрывает разметку
  и распознавание блоков (по умолчанию для обеих через
  `roles.<task>.default: true`), MiniCPM-OCR Jev проверяет, Qwen3.5-4B
  исправляет; GLM-OCR присоединился к распознаванию блоков, а Qwen3.5-9B /
  Gemma-4 (E4B/12B) — к исправлению (PaddleOCR-VL, добавленный на
  распознавание, снова вырезан ADR 255).
- **253.** Настройки сбрасываются один раз вместо миграции: вся
  миграционная механика (отложенные ключи, таблицы переноса ключей задач,
  разрешение устаревших модель/парсер, миграция ключа открытым текстом)
  удалена, а несовпадение `settings/schemaVersion` запускает
  `SettingsStore::resetToDefaults()` — переживают только `runtime/rootDir` и
  `runtime/modelsDir` (они указывают на диск пользователя), ключи, уже
  лежащие в хранилище секретов ОС, переживают (ADR 227), а ключ открытым
  текстом из времён до ADR 227 теряется и должен быть введён заново.
- **254.** Задача проверки говорит только визуальным диффом: текстовый
  протокол `systemone_single_question_v7` (`match`/`has_text`/`readable`)
  вырезан вместе с clef-flash и d3-flash/d3-mini; MiniCPM-OCR Jev
  (`systemone_visual_diff_v1`) — единственная решающая модель — кроп +
  отрендеренный кандидат + текст кандидата, одна вероятность совпадения от
  noul-головы, формулировка вопроса запечена в модель, калиброванные пороги
  — единственная настройка. Нечитаемый кроп попадает в Mismatch и идёт на
  REVIEW через задачу исправления.
- **255.** PaddleOCR-VL вырезан: его профиль и руководство
  (`archive/models/profiles/paddleocr-vl.json`,
  `archive/models/docs/25-paddleocr-vl.md`) лежат в `archive/` с остальными
  (ADR 251), на распознавании блоков остаются MinerU (по умолчанию) и
  GLM-OCR — поднять его до уровня MinerU значило бы второй шаг разметки со
  своим протоколом и парсером, поскольку его layout-модель RT-DETR не
  поставляется в GGUF.
