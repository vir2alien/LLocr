# 17. MiniCPM-OCR Jev

> Английский оригинал: [docs/17-model-minicpm-jev.md](17-model-minicpm-jev.md)

> Самодостаточное руководство по MiniCPM-OCR Jev в том виде, в каком её
> использует LLocr: какую задачу она обслуживает, как запустить для неё
> `llama-server`, как собрать её запросы вручную. Факты — из карточки
> модели, PR llama.cpp или измерены в этом проекте. Русское зеркало:
> `docs/17-model-minicpm-jev.ru.md`. OCR-модель, вместе с которой она
> обучалась, — MiniCPM-OCR 1.0 — вырезана в архив:
> `archive/models/docs/30-minicpm-ocr.md` (ADR 251).

## 1. Что это и какую задачу обслуживает

**MiniCPM-OCR Jev** (OpenBMB, 2 млрд параметров, Apache-2.0) — модель
**оценки качества** OCR для регионов текста, формул и таблиц: ствол
Qwen3.5-2B, у которого `lm_head` заменён **бинарной классификационной
головой**. Получив кроп региона, OCR-текст кандидата и картинку, которую
этот кандидат рисует, она отвечает на один вопрос — *согласуется ли этот
OCR-текст с исходной картинкой?* — и отвечает **P(согласуется), оценкой от
0 до 1, за один проход forward** (ни одного сгенерированного токена).
Decision AUROC 93.6 (×100) на JevOCRBench, 91.9–93.4 против разборов
MiniCPM-OCR 1.0, GLM-OCR, PaddleOCR-VL-1.6 и Xiaomi-OCR — отсюда
переносимость между парсерами LLocr. Это первая decision-модель
**визуального диффа** в LLocr: сверка сравнивает кроп с кандидатом,
*отрендеренным обратно в картинку*, а не текст кандидата, прочитанным как
знаки.

Из четырёх задач LLocr она обслуживает **decision** — проход проверки
(«Проверить»), дефолтной и единственной моделью которого она является
(ADR 252/254); весь проход едет по протоколу визуального диффа. Другую
задачу она нести не может (нет `lm_head` — генерация текста отвечает 501),
и проверка ориентации не пользуется decision-моделью вовсе (ADR 242).
Настройка и установка живут в Настройки → «Модели». Профиль
(`resources/profiles/models/minicpm-jev.json`) объявляет протокол
**`systemone_visual_diff_v1`** (`visualDiffDecisionProtocol()` в
`core/DecisionRequest.h`); `DecisionModel::buildRequestBody` ветвится по
нему, запросы уходят на `/v1/systemone` (расширение llama.cpp), и роль не
несёт **никакого профиля запросов** — `test_model_preset_catalog`
закрепляет эту пустоту.

## 3. Запуск llama-server

Приложение собирает команду в `ServerLaunchConfig::toArguments()`
(`src/runtime/ServerLaunchConfig.cpp`): сначала основные флаги (`--model
--mmproj --alias --host --port`), затем параметры, отсортированные по
`order`, из трёх слоёв — общий слой **политики** (`serverLaunch.json` →
`policy.parameters`), **платформенный профиль** (тот же файл, ключ
os + backend) и **слой модели** (`roles.decision.launch`); флаг слоя модели
заменяет одноимённую строку платформы (`LaunchProfileStore::compose`).
Windows, CUDA (платформенный профиль `win-cuda`):

```bat
llama-server.exe ^
  --model "C:\Users\me\AppData\Roaming\llocr\LLM OCR\models\openbmb__MiniCPM-OCR-Jev-gguf\MiniCPM-OCR-Jev-Q8_0.gguf" ^
  --mmproj "C:\Users\me\AppData\Roaming\llocr\LLM OCR\models\openbmb__MiniCPM-OCR-Jev-gguf\mmproj-model-f16.gguf" ^
  --alias llocr-decision ^
  --host 127.0.0.1 --port 8081 ^
  --parallel 1 --cache-reuse 0 --no-context-shift --no-warmup --verbosity 3 ^
  --n-gpu-layers 99 --flash-attn on --ctx-size 16384 --batch-size 2048 --ubatch-size 512
```

| флаг | значение | слой, который его ставит | зачем |
| --- | --- | --- | --- |
| `--model` / `--mmproj` | пути к кванту и проектору | core — настройки запуска задачи | веса; проектор **обязателен** — без него модель не видит изображение |
| `--alias` | `llocr-decision` | core — `roles.decision.alias` | имя, которое несёт поле `model` запроса |
| `--host` / `--port` | `127.0.0.1` / `8081` (дефолт `0` = выбрать автоматически) | core — настройки (`launchHost` / `launchPort`) | локальный сервер |
| `--parallel` | `1` | policy (`serverLaunch.json`) | один одновременный слот |
| `--cache-reuse` | `0` | policy | нет окна переиспользования контекста между запросами |
| `--no-context-shift` | — | policy | держать контекст стабильным, без KV-сдвига при переполнении |
| `--no-warmup` | — | policy | пропустить warmup-прогон при загрузке (быстрее старт) |
| `--verbosity` | `3` | policy | уровень журнала сервера для окна лога |
| `--n-gpu-layers` | `99` | platform `win-cuda` | все слои выгружены на GPU |
| `--flash-attn` | `on` | **слой модели** — заменяет платформенную строку по имени | дефолтный путь с выключенным flash attention материализует полный буфер внимания и раздувает требование памяти |
| `--ctx-size` | `16384` | **слой модели** — заменяет платформенную строку (которая тоже говорит 16384) | запрос несёт два изображения, поэтому он много длиннее чисто текстового; 16384 его покрывает (§5) |
| `--batch-size` | `2048` | слой модели | батч обработки промпта, размеченный под промпт с двумя изображениями |
| `--ubatch-size` | `512` | слой модели | держит рабочий набор на карте вместо разрезания графа на хост (ниже) |

macOS Metal и Linux CUDA идут с теми же флагами; Windows/Linux Vulkan и
`cpu` ставят `--flash-attn off` в платформенном слое — слой модели
перекрывает обратно на `on` (§7), а у `cpu` нет `--n-gpu-layers` вовсе.

Рецепт upstream — **не** то, что запускает приложение:

```
llama-server \
  -m ./models/MiniCPM-OCR-Jev-F16.gguf \
  --mmproj ./models/mmproj-model-f16.gguf \
  -ngl 99 \
  -c 32768 \
  --port 18499
```

`-ngl 99` и `--mmproj` значат здесь то же самое; `-c 32768` — контекст
upstream, приложение везёт вместо него 16384 (§5). Батчи уменьшены против
того, что модель способна принять: при `--ubatch-size 8192` llama.cpp
выносит 768 МиБ рабочего набора из 2.1 ГиБ на хост; при 512 все 68 МиБ
остаются на GPU — на карте в 6 ГиБ это 3407 против 4895 МиБ VRAM, и
авто-фит при загрузке проходит вместо отмены.

Движок обязан узнать модель на старте: в логе должны быть `decision model
type: openbmb-minicpm-ocr-jev` и `listening on`, а `GET /health` должен
ответить `{"status":"ok"}` — обе строки видны в окне журнала сервера
приложения.

## 4. Сборка запроса

`POST <server>/v1/systemone` с `Content-Type: application/json` —
расширение llama.cpp, не OpenAI chat. `Authorization: Bearer <key>` уходит
только когда настроен ключ (внешний режим; управляемому локальному серверу
ключ не нужен).

**Почему отдельный протокол, а не профиль запросов.** System One
decision-модели, которые приложение поставляло раньше (clef-flash,
d3-flash/d3-mini — в архиве, ADR 251), читают **структурированное
состояние** (тип блока, кандидат, оси нотации) и отвечают на **вопрос,
сформулированный клиентом**, через обученную noul-голову. Jev так не умеет:
формулировка задачи **зашита в промпт модели** (обучающий промпт: исходная
картинка → `OCR文本：<text>` → отрендеренная картинка → бинарная
инструкция), поэтому сервер отвергает запрос с `instructions` или
noul-вопрос с `criteria` — профиль запросов со своими текстами был бы
мёртвым грузом. Форма на проводе тоже другая: состояние — **голый
OCR-текст строкой** (не структурный объект), и запрос несёт **ровно два
изображения** — сначала исходный кроп, затем рендер кандидата. Остаётся
прежним *ответ*: noul-голова, возвращающая P(класса 1) без единого
сгенерированного токена, — тот же `answers.match`, который приложение уже
разбирает, и та же маршрутизация Ok/Mismatch по порогу.

Сервер закрепляет эту форму для этой модели (llama.cpp
`tools/server/server-decision.cpp`, ветка `openbmb-minicpm-ocr-jev`). Каждая
строка ниже — это 400, а не тихий откат:

| запрос | претензия сервера |
|---|---|
| `state` не строка | `"state" must be the OCR text` |
| вопросов больше одного | `this model answers exactly one question` |
| вопрос с `instructions` | `"instructions" is not used by this model, the task is part of its prompt` |
| noul-вопрос с `criteria` | `"criteria" is not supported for a noul question` |
| любое число изображений, кроме двух | `this model needs exactly 2 images (the original, then the rendered one), got N` |

Приложение отправляет текст как есть; механизм сервера, ломающий
спецтокены, включён только для LFM- (в архиве) и H2O-decision-моделей — у
Jev OCR-текст доходит до шаблона нетронутым («`ocr_text` уходит в модель
как есть», контракт upstream).

Тело (`DecisionModel::buildRequestBody` в `src/models/DecisionModel.cpp`;
структура запроса — `DecisionRequest` в `src/core/DecisionRequest.h`):

```json
{
  "model": "llocr-decision",
  "state": "<the candidate text, verbatim>",
  "images": ["data:image/png;base64,<crop>", "data:image/png;base64,<render>"],
  "questions": { "match": { "type": "noul" } }
}
```

`model` называет обслуживаемую модель — сервер, маршрутизирующий по этому
полю, отвергает запрос без него (Managed: алиас; External: имя модели
задачи). `state` — **эффективный** текст блока (ADR 164) — результат
распознавания или правка fix-модели, если она отработала первой, —
дословно. `images` — ровно два data URL, **сначала кроп, затем рендер** —
порядок, который закрепляет обучающий промпт.

**Кроп (первое изображение)** — регион блока, вырезанный из
**полноразрешающей** картинки страницы (`app/AppController` →
`croppedImage`); поворот и выпрямление применены к той картинке, которую
видит каждый потребитель страницы (`DocumentModel::renderFull`), поэтому
кроп — это тот самый регион, из которого читали текст.

**Рендер (второе изображение)** — текст кандидата, нарисованный как
картинка, — и именно нога рендера решает вердикт: модель сравнивает кроп с
картинкой, поэтому картинка, потерявшая хвост, или картинка, показывающая
сырую разметку, — это другой текст. `app/CandidateRenderer` рисует её
собственным стеком предпросмотра приложения (`qrc:/preview/preview.html`:
marked + KaTeX + DOMPurify): **отображаемый текст** блока
(`parsers/BlockRender.h` → `renderBlockText` — формула как блочная
математика `$$…$$`, таблица как markdown-сетка; разделители сырого текста
`\[…\]`, `<fcel>…<nl>` убили бы рендер) на белой странице **шириной
780 px**, напечатанной в PDF и **растрированной в 2×** (кап 4096 px на
сторону). Печатным полям Chromium добавляется 48 px запаса — вторая
страница это отказ (блок уходит на Review), а не картинка, — а растр
обрезается обратно по чернилам (отступ 2 px), потому что кандидат в белых
полях — это другой регион. Палитра принудительно светлая (`{dark: false}` в
вызове рендера страницы предпросмотра): без неё в тёмной теме картинка
вышла бы инвертированной, тогда как кроп остаётся тёмным по белому.
Обучающий рендерер upstream (Playwright+KaTeX из SDK) рисовал те же
фигуры; самодельный рендерер сдвигает абсолютные оценки, поэтому пороги
калибруются на собственных рендерах этого приложения (§6).

Score-сервис upstream принимает рядом с кандидатом `category` (`text` /
`formula` / `table`) и рисует кандидата сам; на пути llama.cpp поля
`category` нет — рендер поставляет вызывающий, поэтому категория становится
выбором рендерера, взятым из метки блока (`resources/profiles/labels.json`
отображает `formula` в стиль `equation`; `blockAliases` профиля отображает
её и для порогов).

Рендер происходит внутри очереди верификации, до запроса: блок, чей рендер
не удался (или приложение, собранное без рендерера), уходит на **Review** с
пометкой в футере — его никогда не судят по половине входа; формула,
которую приложение уже отвергло по синтаксису LaTeX, до стадии не доходит
(ADR 194) — это заодно precheck Jev. (На корпусе OCR_TEST сломанный рендер
забраковал 155 блоков из 195, среди них 97 % OCR-верных; после починки те
же блоки получают 0.92–0.99.)

**Ответ.** GGUF несёт две метки классификатора — *«the classes are fixed:
'0' is inconsistent, '1' is consistent»*. Ответ noul — вероятность опции
`true` (опции noul-вопроса — сначала `false`, затем `true`), поэтому
`answers.match.noul` — вероятность класса **1**, то есть P(согласуется) —
то же число, которое score-сервис upstream называет `prob_1`. Приложение
принимает и голое число под `match`, или `{"probability": x}`
(`DecisionModel::parseResponse`); вспомогательные ответы
(has_text/readable/diagnosis) не приходят вовсе — маршрутизация падает на
обычное деление по порогу.

Одно отличие, о котором стоит помнить при чтении документации upstream:
**сервис** upstream принимает голый base64 (без префикса `data:`) в
`original_image` / `render_image`, а **сервер llama.cpp** принимает data
URL в `images` — приложение говорит с сервером напрямую, поэтому отправляет
data URL.

## 5. Бюджеты

| бюджет | значение | источник |
| --- | --- | --- |
| окно контекста | 16384 в приложении | `roles.decision.launch` (`ctx-size`) — строка модели побеждает любой платформенный профиль, включая 8192 профиля `cpu` |
| окно контекста, рецепт upstream | 32768 | upstream `-c 32768` (§3) — запас, не требование |
| сгенерированные токены | **0** | список `request` профиля пуст — ответ считается noul-классификационной головой за один проход, поэтому по проводу не едет никакого `max_tokens` и машина `RequestBudget` из ADR 193 не применяется |
| токены изображения | бюджет 4096 на изображение; mmproj хранит собственный бюджет препроцессора чекпойнта (до 16384 объединённых токенов на изображение) | `memory.visionTokens` / проектор |

Замеренный запрос с двумя изображениями — **~6.7k токенов**, и 16384
покрывает его с запасом — более широкое окно покупает только KV-кэш;
`--parallel 1` оставляет единственный слот, который нужен модели.

## 6. Пороги

Пороги **измерены** на корпусе OCR_TEST (177 блоков в области проверки,
распознавание MinerU2.5-Pro, рендеры кандидата собственным
`CandidateRenderer` этого приложения, llama.cpp b11946; прогон и отчёт
лежат в `OCRtest/decision_models/test 2/iteration8`; правило ADR 184 —
порог измеряется против того запроса, с которым едет). Порог типа — колено
его кривой FN/FP(t): последняя ступень, где одна пойманная ошибка стоит не
больше одной ложной тревоги:

- **text 0.92**, **equation 0.87**, **table 0.4**, base (типы без записи)
  0.5 — ровно то, что везёт профиль (`roles.decision.matchThresholdByBlock`
  / `matchThreshold`).
- На корпусе: **FN 10 (13.7 %) / FP 41 (39.4 %)** против FN 29 / FP 15 у
  старого 0.5; d3-mini набрал FN 12 / FP 22 на том же корпусе.
- Остаточные FN — печатные гомоглифы (и/н, и/И, Π/II, ρ/p, г/r), интегралы
  (∯→∬, ∭→∬∬) и потерянные надчёркивания/пунктуация — вне досягаемости
  визуального диффа.
- **Таблицы отвергаются целиком** (все p < 0.02 при любом пороге):
  markdown-сеточный рендер вне распределения модели. Запись `table` — край
  измеренной области; каждая таблица и дальше попадает в Mismatch.

Пустые/нечитаемые кропы — не вопросы Jev: значений
`emptyThreshold`/`readableThreshold`, которые надо было бы поставлять, нет.

## 7. Известные ограничения

- **Нет генерации текста** — модель не может обслуживать другую задачу, и
  её эндпоинт безоговорочно отказывает `/v1/chat/completions` (501).
- **Только три категории.** Модель обучена на регионах текста, формул и
  таблиц; прочие типы блоков получают порог роли, а блок кода или печать —
  вне распределения.
- **Пороги действительны для конвейера рендера и корпуса этого
  приложения.** Они измерены (§6), но измерение стоит на корпусе OCR_TEST и
  на собственном рендерере приложения: документы, чья типографика резко
  отличается от рендера (машописные сканы), задвигают даже верный текст
  вниз по шкале, и он попадает в Mismatch — FP-хвост, который порогами не
  убрать.
- **Блок `memory` профиля выведен, а не измерен** (§6 в
  `docs/18-memory-estimate.md` помечает строку `minicpm-jev` как
  выведенную), и его зрительный член — бюджет **одного** изображения,
  тогда как запрос всегда несёт два изображения. Перегоните
  `scripts/measure-memory.sh`, если флаги запуска меняются.
- **`--flash-attn on` перекрывает платформенный слой** на бэкендах, где
  платформа его выключает (Vulkan, CPU) — так же, как у остальных
  зрительных моделей проекта (glm-ocr, qwen3.5; lightonocr, chandra-ocr-2 и
  minicpm-ocr лежат в архиве). На Vulkan это противоречит собственному
  замечанию платформы, что flash attention там экспериментален.
- **Нет самопроверки по эталонным случаям upstream** (текст, формула,
  таблица, с эталонной оценкой `observed_prob_yes`): прогон по ним проверил
  бы всю ногу сразу (кроп → рендер → запрос → оценка). Такой проверки в
  приложении сегодня нет.
