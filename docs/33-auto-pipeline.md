# 33. Авто-режим: конвейер «разметка → распознавание → проверка → правка → проверка»

> Что делает кнопка «Распознать N стр.» в блоке «Авто» главного меню, как устроен
> конвейер и почему он разбит на этапы. Решение — ADR 257; постановка —
> `docs/todo/todo.md` («Авто-режим»).

## 1. Что это

Кнопка «Распознать N стр.» в блоке «Авто» (ADR 256 — до сих пор была заглушкой)
запускает **авто-прогон**: полный цикл обработки выбранных страниц без
вмешательства оператора. Область действия — страницы, выбранные в панели
миниатюр; пустое выделение — весь документ (поле диапазона рядом с кнопкой
пишет этот выбор словами).

Прогон состоит из пяти этапов:

| # | Этап | Задача | Что делает |
|---|------|--------|------------|
| 1 | **Разметка** | `layout` | Находит блоки на странице. Текста у блоков ещё нет. |
| 2 | **Распознавание блоков** | `blockRecognition` | Транскрибирует каждый блок: кроп → текст. |
| 3 | **Проверка** | `decision` | Судит блоки, **включённые в настройках проверки** (и подозрительные на дубль): совпадает ли текст с картинкой. |
| 4 | **Исправление** | `fix` | Отправляет проблемные блоки (Mismatch, Review) универсальной модели: OK / FIX / REVIEW. |
| 5 | **Проверка исправленных** | `decision` | Судит **исправленный** слой: правильна ли правка. |

Этапы идут **по этапам, а не постранично**: сначала разметка всех страниц, потом
распознавание всех, потом проверка, потом правка, потом повторная проверка.
Причина — цена смены модели (ADR 252): управляемый llama-server держит одну
загруженную модель, и переход между задачами (`layout` → `blockRecognition` →
`decision` → `fix`) перезагружает её. Постраничный прогон дал бы 4 смены модели
на каждую страницу вместо 4 на документ.

## 2. Границы этапа

Этап — это объект с одним контрактом (`src/app/AutoPipelineStage.h`):

```cpp
class AutoPipelineStage : public QObject
{
    Q_OBJECT
public:
    using Scope = QList<int>;

    AutoPipelineStage(QString title, QObject *parent = nullptr);

    QString title() const;

    // Пусто — этап может идти; иначе — почему он пропускается.
    virtual QString skipReason(const Scope &pages) const = 0;
    // Начать работу; конец — сигналом finished(), ранний отказ — failed().
    virtual void start(const Scope &pages) = 0;
    virtual void stop() = 0;
    virtual int progressDone() const { return 0; }
    virtual int progressTotal() const { return 0; }

signals:
    void finished();
    void failed(const StatusMessage &message);
};
```

Три свойства контракта:

* **Этап ничего не знает о соседях.** Разметка не знает про проверку, проверка —
  про правку. Связь только через сигнал `finished()`.
* **Этап сам говорит, может ли он идти.** `skipReason()` возвращает пустую
  строку, если этап готов, иначе — причину («нет модели для этой задачи»,
  «нечего распознавать»). Причина уходит в подвал: пользователь видит, что
  было пропущено и почему.
* **Этап умеет остановиться.** `stop()` гасит текущую работу; конвейер после
  этого не идёт дальше.

Конвейер (`src/app/AutoPipelineController.h`) держит **список этапов** и
проходит его по порядку:

```cpp
m_pipeline.setStages({
    new AutoMarkupStage(...),        // 1
    new AutoRecognitionStage(...),   // 2
    new AutoVerificationStage(...),  // 3
    new AutoFixStage(...),           // 4
    new AutoVerificationStage(...),  // 5 — тот же класс, другое название
});
```

Добавить этап — значит добавить класс и одну строку в этом списке. Ни оркестратор,
ни фасад, ни QML при этом не меняются.

## 3. Семантика сбоев и пропусков

| Случай | Что происходит |
|--------|----------------|
| Этап не может идти (нет модели, нечего делать) | Этап пропускается, причина — в подвале, прогон идёт дальше. |
| Модель ответила ошибкой на отдельном блоке | Очередь отмечает блок и идёт к следующему — так уже работают ручные очереди. Прогон не падает. |
| Этап провалился целиком | Причина — в подвал, прогон идёт к следующему этапу. |
| Пользователь нажал «стоп» | Текущий этап гаснет, следующие не начинаются. |

Итоговая строка подвала перечисляет, что было пропущено и почему. Это решение
пользователя: прогон, который дошёл до конца с двумя пропущенными этапами,
полезнее, чем прогон, который встал на первом же «нет модели».

## 4. Что делает этап «проверка исправленных»

Это **тот же** этап проверки, что и этап 3, — отдельного кода для него нет.
Разделение происходит в сборе блоков: очередь берёт блоки, у которых на
**действующем слое** (ADR 164) нет вердикта.

* До правки действующий слой — текст OCR: у текста есть вердикт (Ok /
  Mismatch), значит блок уже отвечен и в пятом этапе не участвует.
* Правка кладёт исправленный текст в слой коррекции и **сбрасывает его
  вердикт** (`BoxTransitions::fixApplied`): слой коррекции становится
  действующим, и блок снова «без вердикта» — его и судит пятый этап.
* Блок, который правка не смогла прочитать (REVIEW), получает
  `correctedCheckStatus = Review` — он отвечен и ждёт оператора, пятый этап
  его не трогает.

Поэтому пятый этап — это ровно тот же вызов `checkPagesEnabledBlocks(pages)`,
что и третий: коллектор сам находит «блоки без вердикта на действующем слое».

## 5. Интерфейс

**Кнопка «Распознать N стр.»** (блок «Авто» главного меню):

* неактивна, когда нет документа, нет модели разметки или распознавания, либо
  идёт другая работа (`Controller.actionsIdle`);
* во время прогона превращается в кнопку «стоп» — тот же приём, что у кнопок
  «Разметить», «Проверить», «Исправить»;
* перед запуском спрашивает, если в области есть результат: разметка
  заменяет блоки и текст страниц.

**Строка состояния в подвале** (`TaskStatus.qml`) показывает текущий этап и
его прогресс: `Авто 3/5: Проверка 12 / 40`. Пустой прогресс (у разметки он
постраничный, у проверки — пообъектный) показывается без чисел. Между этапами
заголовок пуст — строка показывает только `Авто 3/5`.

## 6. Место для будущих моделей

Требование: «распознавание разных блоков разными моделями» должно стать
возможным без переписывания конвейера.

Ограничение рантайма: **одна задача — одна модель**. `ConnectionRole`
(`core/ConnectionRole.h`) — это слот модели, и переключение роли перезагружает
сервер. Поэтому «разные блоки — разные модели» в терминах приложения — это
**разные задачи**, а не разные модели внутри одной задачи.

Что для этого уже готово:

1. **Этап — единица работы.** Дополнительная задача = дополнительный этап в
   списке. Оркестратор, фасад и QML не меняются.
2. **Сбор блоков отделён от их выполнения.** Очередь проверки отдаёт список
   блоков (`unrecognizedBlocks`, `enabledBlocks`, `fixableBlocks`) и отдельно
   выполняет его (`recognizeBlocks`, `checkBlocks`, `fixBlocks`). Этап сам
   решает, какие блоки в какой запуск попадут.
3. **Фильтр по типу блока.** Сборщики принимают необязательный фильтр типов:
   сегодня он пуст (все типы), завтра этап задачи отдаёт фильтр «эти типы —
   мои». Фильтр — это `std::function<bool(const QString &blockType)>`.

Чтобы добавить «распознавать формулы моделью A, текст моделью B», нужно:
завести новую задачу в `core/ConnectionRole.h` и в профилях моделей, добавить
в настройки таблицу «тип блока → задача», и добавить этап, который собирает
свои блоки с фильтром и запускает очередь дважды — по очереди на задачу.
Ни одна существующая строка конвейера при этом не меняется.

## 7. Цена прогона

* **Смены модели.** Управляемый сервер перезагружает модель на границе задач:
  `layout` → `blockRecognition` → `decision` → `fix` → `decision`. Это 4–5
  перезагрузок на прогон. Внешний рантайм (ADR 226) ничего не перезагружает:
  там у каждой задачи свой адрес.
* **Внешний рантайм.** У каждой задачи свой endpoint, ключ и псевдоним модели
  (ADR 226) — прогон идёт по тем же этапам, переключаясь между адресами.
* **Время.** Этап 3 и 5 судит каждый блок отдельным запросом; на тяжёлом
  документе это самая длинная часть.

## 9. Решения

1. **Прогон идёт по этапам, а не постранично** — цена смены модели.
2. **Сбой этапа не роняет прогон** — причины собираются и показываются в подвале.
3. **Нет модели — этап пропускается**, а не блокирует запуск.
4. **Разметка всегда заново** (с подтверждением): прогон — это полный цикл.
5. **Пятый этап — тот же этап проверки**: коллектор сам находит блоки без
   вердикта на действующем слое.
6. **Граница модульности — контракт этапа**, а не набор кнопок.
