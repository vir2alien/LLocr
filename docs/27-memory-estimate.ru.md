# Требование по видеопамяти: как считается и как было откалибровано

> Число в выпадающем списке квантов (`VRAM ≥ 11.4 GiB`) — свойство всего
> сервера, а не файла. Документ объясняет, из чего складывается число, откуда
> берётся каждый коэффициент, как измерить модель, которой ещё нет в
> каталоге, и какие ловушки ждут между измерением и профилем.
> Английская версия: `docs/27-memory-estimate.md`. Само решение: ADR 191 в
> `docs/07-glossary.md`.

## 1. Что означает число

Строка выпадающего списка кванта читается так:

```
✓ Q8_0 — 9.1 GiB · VRAM ≥ 11.4 GiB
```

Первое число — размер файла, второе — **минимальная видеопамять, которая
нужна карте**, чтобы запустить модель, к которой относится файл: веса,
проектор, черновик и его собственный контекст, KV-кэш, рабочий буфер графа,
зрение и собственные накладные расходы сервера. Файл — самая маленькая часть
этого списка.

К одному и тому же числу ведут два пути:

- **файл** — модель, которая лежит на диске, читается из заголовка GGUF
  (`ModelMemoryEstimator::shapeFromFile`);
- **профиль** — у кванта, который ещё только скачивается, заголовка нет, поэтому
  профиль модели везёт архитектуру и измеренные коэффициенты
  (`resources/profiles/models/<id>.json`, блок `memory`).

Для каталога побеждает профиль (`RuntimeController::estimateModelMemory`),
потому что в нём есть и то, чего не скажет заголовок: стоимость зрения,
черновика и кэша со скользящим окном.

Требование — **не** сумма буферов. Это сумма плюс накладные расходы сервера,
чтобы число называло карту, на которой модель работает, а не карту, на
которой она едва запускается:

```
требование = буферы + (64 MiB + 8 % от буферов)
```

## 2. Формула

Все слагаемые `ModelMemoryEstimator::estimateMemory` (`src/runtime/`):

| Слагаемое | Формула | Откуда коэффициент |
| --- | --- | --- |
| Веса | размер файла GGUF | файл (`sizeBytes` кванта в профиле) |
| Проектор | размер файла `mmproj` | файл (`files.mmproj.sizeBytes`) |
| Черновик | размер файла черновика | файл (`memory.draftBytes`) |
| Контекст черновика | `draftContextBytes + draftKvBytesPerToken × ctx` | измерено (см. §5) |
| KV-кэш | `kvBytesPerToken × ctx + kvBytesFixed` | архитектура, для обычных моделей точно |
| Рабочий буфер | `ubatch × workingSetBytesPerToken + ctx × ubatch × workingSetContextBytes` | измерено либо выведено из формы |
| Зрение | `visionTokens × visionBytesPerToken` либо `visionBufferBytes` | измерено (см. §4) |
| Оверхед | `64 MiB + 8 %` | собственные аллокации сервера и запас аллокатора |

Значения по умолчанию, когда в профиле нет измеренного:

```
kvBytesPerToken         = 2 × nKvLayers × nKvHead × headDim × bytesPerValue
workingSetBytesPerToken = (nEmbd × 24
                           + headDim × (nHead + 2 × nKvHead) × 4
                           + nFf × 8
                           + nMoeLayers × nExpertUsed × nExpertFf × 12) × 1.12
workingSetContextBytes  = 2            (маска внимания f16 на токен контекста)
```

Множитель 1.12 — запас, который превращает смоделированный рабочий буфер в
требование: планировщик llama.cpp резервирует до 12 % больше, чем предсказывает
форма, и оценка не должна никогда занижать.

Окно контекста, ubatch и типы кэша берутся из launch-профиля
(`ModelMemoryEstimator::budgetFromLaunch`): платформенный профиль владеет
`ctx-size`, профиль модели — `ubatch-size`, а `cache-type-k/v = f32` удваивает
KV-кэш.

## 3. Блок `memory` в профиле модели

```json
"memory": {
  "nLayer": 48, "nKvLayers": 8, "nHead": 16, "nKvHead": 8, "headDim": 64,
  "nEmbd": 3840, "nFf": 15360,
  "visionTokens": 1120, "visionBytesPerToken": 55419,
  "draftBytes": 253708800, "draftKvBytesPerToken": 2048, "draftContextBytes": 387994092,
  "workingSetBytesPerToken": 267320, "workingSetContextBytes": 2,
  "kvBytesFixed": 1006632960
}
```

| Поле | Что означает |
| --- | --- |
| `nLayer` | слои декодера |
| `nKvLayers` | слои, чей кэш **следует за контекстом** (0 = все). У гибридной архитектуры их меньше: остальные держат скользящее окно |
| `nHead`, `nKvHead` | головы внимания и KV-головы этих слоёв |
| `headDim` | ширина одной KV-головы. Это `attention.key_length` из GGUF — **сумма по головам, а не ширина головы** (см. ловушки) |
| `nEmbd`, `nFf` | ширина эмбеддинга и feed-forward (рабочий буфер) |
| `nMoeLayers`, `nExpertUsed`, `nExpertFf` | слагаемые mixture-of-experts (рабочий буфер) |
| `visionTokens` | токены изображения, на которые наполняется бюджет задачи страницы |
| `visionBytesPerToken` | рабочий буфер кодировщика на один токен изображения |
| `visionBufferBytes` | весь рабочий буфер кодировщика, когда стоимость проектора не следует за числом токенов |
| `draftBytes` | веса черновика (отдельный GGUF) |
| `draftKvBytesPerToken` | KV-кэш **собственного контекста черновика**, на токен контекста |
| `draftContextBytes` | что ещё держит этот контекст: ячейки скользящего окна и буфер вычислений |
| `workingSetBytesPerToken` | измеренная стоимость одного токена рабочего буфера графа (0 = вывести из формы) |
| `workingSetContextBytes` | измеренная стоимость одного токена контекста в маске внимания (0 = 2) |
| `kvBytesPerToken` | измеренный KV-кэш на токен контекста (0 = вывести из формы) |
| `kvBytesFixed` | ячейки скользящих слоёв: за контекстом они **не** следуют |

## 4. Как измерить модель, которой нет в каталоге

Работу делают два скрипта:

- `scripts/measure-memory.sh` — поднимает llama-server с флагами приложения и
  пишет лог;
- `scripts/memory-from-log.py` — читает лог (или несколько) и печатает числа,
  включая поля блока `memory`.

Разобранный ниже пример измеряет LFM2.5-VL — модель из трёх файлов (веса,
проектор, черновик), потому walkthrough самый полный; сама модель лежит в
архиве (`archive/models/profiles/lfm25-vl-3b.json`, ADR 251), ход работы для
любой модели каталога тот же.

```sh
scripts/measure-memory.sh \
  --model "LiquidAI__LFM2.5-VL-3B-GGUF/LFM2.5-VL-3B-Q8_0.gguf" \
  --mmproj "LiquidAI__LFM2.5-VL-3B-GGUF/mmproj-LFM2.5-VL-3B-F16.gguf" \
  --draft  "LiquidAI__LFM2.5-VL-3B-GGUF/LFM2.5-VL-3B-DSpark-F16.gguf" \
  --ctx 16384 --flash-attn on --spec-type draft-dspark --spec-draft-n-max 8 --special
```

```
-- kv caches (main context)
      256.00 MiB   16384 cells    8 layers   -> 16384 B/token (follows the context)
-- vision (clip)
   warmup image 512x512   patch 16   merge 2   -> 1024 patches = 256 tokens
   vision           30.31 MiB   -> 124150 B/token
-- profile fields
   kvBytesPerToken 16384
   draftKvBytesPerToken 8192
   draftContextBytes 533190410
   draftBytes 567205280
   visionBytesPerToken 124150
```

Уже готовый лог разбирается без запуска сервера:

```sh
scripts/measure-memory.sh --parse build/measure/app-gemma4-12b.log
```

### Флаги

Измерять надо с теми флагами, с которыми приложение поднимает сервер: они
меняют резервирование.

| Флаг | Откуда | Почему важно |
| --- | --- | --- |
| `--parallel 1 --cache-reuse 0 --no-context-shift` | политика запуска (`resources/profiles/serverLaunch.json`) | один контекст, без переиспользования |
| `--ctx-size` | платформенный профиль (16384 на macOS) | от него растут KV-кэш и маска |
| `--ubatch-size` | профиль модели (512 по умолчанию, 2048 у gemma-4 12B, 512 у minicpm-jev; профили проверки в архиве несли 6144–8192) | от него растёт рабочий буфер |
| `--flash-attn on\|off` | платформенный профиль, перекрывается профилем модели (gemma-4 E4B выключает **его**) | с выключенным flash attention кодировщик держит матрицу внимания по всей странице |
| `--image-min-tokens` / `--image-max-tokens` | профиль модели | бюджет страницы модели |
| `--spec-type` / `--model-draft` | профиль модели | у черновика свой контекст |
| `--special` | профиль модели (MinerU, Qwen3.5; из архива — LFM2.5-VL) | некоторым моделям он нужен |
| `--device none --n-gpu-layers 0` | только для измерения | размеры буферов те же, а числа читаются без карты |

### Строки лога

| Строка | Что даёт |
| --- | --- |
| `llama_context: n_ctx / n_ubatch / n_batch` | бюджет, который взял сервер |
| `print_info: n_layer / n_embd / n_head / n_head_kv / n_embd_head_k / n_swa` | архитектура |
| `llama_kv_cache: size = X MiB (N cells, L layers)` | KV-кэши: тот, у которого `N == n_ctx`, следует за контекстом, остальные — ячейки скользящего окна |
| `sched_reserve: CPU compute buffer size = X MiB` | рабочий буфер (первый — основной контекст, те, что после `loading draft model`, — черновика) |
| `reserve_compute_meta: CPU compute buffer size = X MiB` | кодировщик зрения (первый) и, у gemma-4, аудиобашня (второй) |
| `get_dummy_batch: warmup with image size = W x H` | изображение, под которое сделан резерв зрения |
| `load_hparams: patch_size / n_merge` | геометрия сетки патчей |
| `[mtmd] estimated worst-case memory usage of mmproj is X MiB` | веса проектора плюс резерв clip — бесплатная сверка |

### Зрение

Резерв clip-графа задаётся **сеткой пикселей изображения**, а не бюджетом
токенов. Число токенов изображения равно

```
tokens = (W / patch_size) × (H / patch_size) / n_merge²
```

поэтому ставка проектора, который тянется за токенами, равна

```
visionBytesPerToken = резерв кодировщика / tokens
```

Warmup-изображение сервер масштабирует под бюджет изображения модели, поэтому
измерять надо с тем бюджетом, который использует приложение (бюджет страницы
для задачи страницы). Модель, чей проектор за токенами не следует, несёт
вместо ставки `visionBufferBytes` — см. ловушки.

## 5. Собственный контекст черновика

Черновик, который является **отдельным GGUF** (MTP-драфтеры gemma-4; DSpark-
драфтер LFM2.5-VL лежит в архиве), работает в собственном контексте: llama.cpp
даёт ему свой KV-кэш и свой буфер вычислений. Профиль несёт все три части:

```
draftBytes          веса файла черновика
draftKvBytesPerToken KV-кэш этого контекста, на токен контекста
draftContextBytes   остальное, что держит этот контекст: ячейки скользящего
                    окна и буфер вычислений спекулятивного графа
```

Числа берутся из лога: кэши после `loading draft model` и **наибольший**
`sched_reserve` после него (спекулятивный граф резервирует больше, чем один
черновик).

MTP-блок **внутри** модели (Qwen3.5) — это слой самой модели, а не отдельный
контекст: у него нет ни кэша, ни собственного буфера вычислений.

проверки в архиве (`clef-flash`, `d3-flash`, `d3-mini`) просили большой ubatch
(8192 и 6144 токена), и рабочий буфер был их крупнейшим слагаемым.
minicpm-jev — противоположный пример: те же две картинки, но ubatch 512 —
при 8192 llama.cpp выносил 768 МиБ графа вычислений на хост, и карте не
хватало места под веса. Модели страниц выглядят дешёвыми, потому что зрение
при их бюджете невелико, и дорогими, когда проектор нарезает страницу
(Unlimited-OCR — его плоский vision-буфер на 2 981 117 952 байта лежит в
архивном профиле).

## 7. Ловушки

Каждый пункт стоил одного измерения.

1. **Dummy-изображение — не настоящая страница.** Резерв clip-графа делается
   под dummy-изображение warmup, которое сервер масштабирует под бюджет
   изображения модели. Ставка — это резерв, делённый на **число токенов,
   которые даёт это изображение** (`(W/patch) × (H/patch) / n_merge²`), а не на
   бюджет: warmup у gemma-4-12B — 768×768, patch 48, merge 1, то есть 256
   токенов, а не 1120.

2. **С выключенным flash attention кодировщик держит всю матрицу внимания.**
   gemma-4-E4B работает с `--flash-attn off`, поэтому стоимость квадратична по
   числу патчей. Резерв warmup (276.77 MiB на 2304 патчах) — линейная часть плюс
   attention-член; attention-член — это разница с прогоном при flash on
   (101.27 MiB), и он растёт как квадрат:

   ```
   линейная  = 101.27 MiB / 2304 патчей       = 46 089 B/патч
   attention = (276.77 − 101.27) MiB / 2304²  = 35 B/патч²
   страница приложения: 1120 токенов × 9 патчей = 10 080 патчей
   → 46 089 × 10 080 + 35 × 10 080² = 3 802 MiB  (visionBufferBytes 3 986 933 350)
   ```

   `scripts/memory-from-log.py --app-patches N` считает это по двум логам
   (с flash on и с flash off).

3. **Проектор, нарезающий страницу, за токенами не следует.** Проектор
   Unlimited-OCR (модель лежит в архиве) режет страницу на три окна плюс общий
   вид: стоимость следует
   за пикселями плиток (9600 патчей), а не за токенами. В профиле вместо ставки
   лежит `visionBufferBytes` (2 981 117 952).

4. **У гибридной архитектуры два KV-кэша.** Модели gemma-4 держат кэш для
   полно-attention слоёв (следует за контекстом) и второй — для скользящих
   слоёв (фиксированное число ячеек: 3072 у 12B, 1024 у E4B). В профиле
   фиксированная часть лежит отдельно (`kvBytesFixed`), остальное растёт с
   контекстом.

5. **Длина ключа — сумма по головам.** Ширина ключа у gemma-4-12B была вчетверо
   больше настоящей, и кэш был завышен на 4 GiB. Ширина головы — это то, что
   лежит в кэше: `headDim = байты K на ячейку на слой ÷ 2 (f16) ÷ nKvHead`.

6. **Слои с KV-кэшем — не все слои модели.** У рекуррентного гибрида состояние
   лежит в SSM-тензорах, и у этих слоёв K и V нет вовсе (у LFM2.5-VL из архива
   кэш есть
   у 8 слоёв из 30); скользящий слой K и V несёт, но в собственном кэше (модели
   gemma-4). Голова спекулятивного декодирования (блок `nextn`) — отдельный
   слой-черновик: llama.cpp запускает его отдельным графом и **не** держит для
   него кэша.

7. **У черновика-файла свой контекст** — со своим KV-кэшем и своим буфером
   вычислений. Профиль долго объявлял веса черновика, но не читал их: черновик
   не стоил ничего.

8. **Ячейки скользящего окна зависят от ubatch.** Сервер выделяет под скользящий
   слой не размер окна, а кратное ему число, зависящее от батча. Читать из лога,
   а не вычислять.

9. **Спекулятивный граф резервирует больше, чем один черновик.** У черновика
   LFM (модель лежит в архиве) собственный резерв 258 MiB, а у графа «цель +
   черновик» — 508.49 MiB.
   Применимо большее число.

10. **`--no-warmup` прячет резерв зрения.** Политика запуска приложения
    пропускает warmup, и clip-граф резервируется под первый настоящий запрос.
    Для измерения warmup нужен (скрипт запускает его по умолчанию).

11. **Путь оценки по файлу путает гибридную архитектуру.** Путь по заголовку
    считает слои, у которых есть тензоры K и V, а за контекстом следуют только
    полно-attention слои — у gemma-4-12B это 48 слоёв вместо 8, так что кэш
    получается вшестеро больше, а фиксированная часть скользящего окна не
    учитывается вовсе. Авторитетен путь каталога (профиль).

12. **Бюджет изображения зависит от задачи.** Задача страницы наполняет
    собственный бюджет модели (`image-max-tokens`); кроп блока масштабируется
    до нижней границы, которую объявляет модель (`image-min-tokens`), и обычно
    остаётся маленьким. Число в списке — это бюджет страницы, то есть худший
    случай.

## 8. Чек-лист для новой модели

1. **Установить модель и проектор** (Настройки → Модели), а если модель
   везёт черновик — и его файл.
2. **Прочитать архитектуру** из заголовка GGUF (или с карточки модели): слои,
   слои с KV, KV-головы, длина ключа, ширина эмбеддинга и feed-forward,
   слагаемые mixture-of-experts.
3. **Измерить** с флагами приложения:
   ```sh
   scripts/measure-memory.sh --model "<repo>/<file>.gguf" \
       --mmproj "<repo>/<mmproj>.gguf" [--draft "<repo>/<draft>.gguf"] \
       --ctx <контекст платформы> --flash-attn <on|off> \
       --image-max-tokens <бюджет страницы модели> [--ubatch <ubatch модели>]
   ```
4. **Сверить KV-кэш** с формулой
   `2 × nKvLayers × nKvHead × headDim × 2 × ctx`: он должен совпасть с логом.
   Если не совпал — неверно разбиение по слоям или ширина головы (§7.4–7.6).
5. **Взять ставку зрения** из лога: резерв ÷ токены warmup-изображения. Если
   модель работает с выключенным flash attention или её проектор нарезает
   страницу — вместо ставки нести `visionBufferBytes` (§7.2–7.3).
6. **Взять рабочий буфер** из лога: строка `sched_reserve`. Один лог не
   разделяет два слагаемых — нужен второй прогон с другим ubatch или
   контекстом и решение двух уравнений; либо оставить вывод по умолчанию и
   проверить, что он не ниже измерения.
7. **Добавить три части черновика**, если он есть (§5).
8. **Записать блок `memory`** в профиль, а курируемые размеры — в `files`
   (`sizeBytes` кванта, проектора и черновика).
9. **Проверить результат**: требование должно быть больше суммы буферов, а
   требование самого крупного кванта — больше карты, которую рекомендует
   руководство модели. Формулу и список защищают `test_model_memory_estimator`
   и `test_model_installer`.
10. **Записать числа** в таблицу §6 и, если у модели есть своё руководство, в
    него тоже.

## 9. Чего не может оболочка агента

Песочница агентской сессии блокирует инструменты, которые меряют resident
memory, поэтому измерение приходится брать из собственного отчёта llama.cpp:

| Заблокировано | Вместо этого |
| --- | --- |
| `ps`, `pgrep`, `pkill` | читать собственный лог сервера: буферы печатаются там |
| `/usr/bin/time -l` (строка RSS требует запрещённого `sysctl`) | строки `sched_reserve` и `reserve_compute_meta` |
| `DYLD_INSERT_LIBRARIES` (интерпозер malloc вырезается) | резервирования в логе |
| запись в `/tmp` | каталог `build/` (в gitignore) или любой другой доступный |
| `timeout` | `sleep` + `kill $!` |
| Metal (карта агенту недоступна) | `--device none --n-gpu-layers 0`: размеры те же |
| фоновая задача, живущая дольше вызова | один вызов с достаточным лимитом — параллельная сборка одного дерева рушит другую |

Логи измерений лежат в `build/` (`build/measure/*.log`). Каталог в gitignore и
теряется вместе с чистым деревом — важные числа лежат в профилях и в §6.
