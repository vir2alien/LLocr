# 10. Внешний рантайм: эндпоинты и секреты по задачам

> Английский оригинал: [docs/10-external-runtime.md](10-external-runtime.md)

Как устроен внешний режим: один общий сервер плюс строка на задачу со своим
эндпоинтом, своим API-ключом и своим алиасом модели, а ключи — в хранилище
секретов ОС. Записи решений — ADR 226–235 в `docs/07-glossary.md`.

## 1. Подключения

Во внешнем режиме приложение общается с OpenAI-совместимыми серверами,
которыми не владеет и которые не запускает. Схема зеркалит управляемый
рантайм (ADR 226): те же четыре задачи (`core/ConnectionRole.h` — `layout`,
`blockRecognition`, `decision`, `fix`), и каждая задача несёт свой эндпоинт,
свой API-ключ и свой алиас модели.

| Что | Где | Если пусто |
|------|-------|----------|
| Общий базовый URL | `provider/baseUrl` (`SettingsStore`) | — |
| Эндпоинт задачи | `tasks/<role>/baseUrl` | пусто → общий URL |
| Алиас модели | `model/name`, `tasks/<role>/modelName` | — |
| Общий API-ключ | секрет `provider/apiKey` | — |
| API-ключ задачи | секрет `provider/apiKey/<role>` | пусто → общий ключ |

Правило — **пусто значит общее**, и интерфейс читает его буквально: пустая
ячейка эндпоинта показывает общий URL в подсказке, пустая ячейка ключа
сообщает, что используется общий ключ. Обратного правила нет — задача со
своим ключом никогда не откатывается к общему (`SecretStore::readFirst`
читает сначала собственный id задачи, потом общий).

Путь запроса не настраивается — он принадлежит протоколу:
`/v1/chat/completions` для каждой задачи, `/v1/systemone` для задачи
проверки (`LlamaClient::endpointUrl`). Провайдер с нестандартным префиксом
выражает его в самом базовом URL.

### Где это настраивается

**Настройки → Runtime → External**
(`src/qml/Settings/RuntimeTabExternal.qml`): блок общего сервера
(base URL + ключ) и по одному `Settings/TaskConnectionRow.qml` на задачу —
эндпоинт, ключ, алиас. Шаг External мастера первого запуска
(`Setup/StepExternal.qml`) показывает только общий сервер, в компактном
виде; таблица по задачам живёт в настройках. Окно **«Модели»** показывает
те же четыре задачи во внешнем режиме, но ячейка алиаса там только для
чтения — алиас принадлежит подключению и правится в одном месте (ADR 226).

### Разрешение

`RuntimeController::resolveExternal(role)` собирает статическую часть:
действующие базовый URL задачи и её алиас из настроек. Чтение ключа
**асинхронно по замыслу** — заблокированный keychain спрашивает пользователя
и заморозил бы интерфейс, — поэтому первое разрешение на роль читает
секреты в рабочем потоке и доставляет ответ в поток GUI; тем же проходом
запрашивается окно контекста сервера (§3). Разрешённые подключения
кэшируются по роли (`m_resolvedCache`) и сбрасываются при любом изменении
настроек или переходе состояния сервера. Чтение ключа, закончившееся
`Refused`, не кэшируется: ошибка едет в `ResolvedConnection::error`, и
запрос не уходит (§2).

## 2. Секреты

API-ключи и токен Hugging Face живут в хранилище секретов ОС
(`src/config/SecretStore.*`, слой `llocr_config`; ADR 227) — никогда в
`QSettings`, никогда в командной строке, никогда в логе, никогда в проекте
`.llocr`. Один интерфейс, три бэкенда, без новых зависимостей:

| Платформа | Бэкенд | API |
|----------|---------|-----|
| macOS | Keychain, универсальные пароли, сервис `org.llocr.app` | Security.framework (`SecItemAdd` / `SecItemCopyMatching` / `SecItemDelete`) |
| Windows | Диспетчер учётных данных, цель `LLocr:<id>` | `CredWriteW` / `CredReadW` / `CredDeleteW` |
| Linux | Secret Service, `org.freedesktop.secrets` | D-Bus через `Qt6::DBus` (только Linux) |

### «Нет ключа» и «отказано» — разные ответы (ADR 233)

`SecretStore::Status` различает эти случаи: `Ok`, `NotFound`, `Refused`,
`Unavailable`, `Failed`.

- **`NotFound`** — ключа нет. Это не сбой: сервер без аутентификации ключа
  не требует, и запрос уходит.
- **`Refused`** — запись есть, но принадлежит другой сборке (на macOS
  Keychain привязывает запись к коду, который её записал). Запрос **не**
  уходит — он бы упал с `401 API key required`, — и отказ едет вместе
  с подключением в `ResolvedConnection::error`, называя причину и выход
  (ответить на вопрос Keychain "Always Allow" либо удалить запись в
  Keychain Access и ввести ключ заново). Удаление ключа, которое хранилище
  отклоняет, сообщает об отказе вместо молчания. Серверный `401`
  переводится в собственные слова приложения; текст сервера остаётся в
  сообщении.

Вкладка External опрашивает состояние хранилища
(`RuntimeTabExternal.refreshSecretState()`), поэтому причина видна там, где
правится ключ.

### macOS: пересборка теряет ключ (ADR 232)

Идентичность ad-hoc подписанной dev-сборки — её код-хеш, поэтому пересборка
теряет каждый записанный ею ключ. `scripts/macos-dev-sign.sh --create` один
раз подписывает dev-сборку самоподписанным сертификатом "LLocr Dev";
неудачное чтение или запись доходит до UI, а не остаётся пустым полем.

### Правила хранения

- Когда хранилище отсутствует или отказывает в записи, ключ живёт в памяти
  процесса до выхода приложения, и UI говорит ровно это. Резерва в
  зашифрованном файле нет — самодельный шифр выглядел бы защитой, не будучи
  ею (отказ ADR 212).
- Секреты читаются один раз за сессию и кэшируются в процессе: транспорт
  запроса требует ключ при каждом вызове, а чтение хранилища может
  блокировать. Записи и удаления обновляют кэш
  (`SecretStore::forgetAllCached`).
- Сохранённый ключ никогда не показывается обратно: поле носит маску как
  собственный текст, единственный переключатель "Show" в шапке таблицы
  раскрывает набранное (никогда — сохранённое), а **пустое поле удаляет
  ключ** — отдельной кнопки удаления нет (ADR 283).
- Одноразовый сброс настроек (ADR 253) не трогает хранилище ОС: ключи,
  записанные туда, его переживают. Миграции ключей открытым текстом нет —
  ключ, остававшийся в файле настроек на момент смены схемы, потерян и
  вводится заново.
- Тестовые и инструментальные сборки пишут в собственном пространстве имён
  (`SettingsStore::setSecretNamespace`), поэтому тесты никогда не трогают
  keychain-записи приложения.

## 3. Поведение на проводе

- **Запрос уходит на эндпоинт задачи** — общий URL или переопределение
  задачи — с ключом задачи в заголовке `Authorization` и алиасом задачи
  как именем модели.
- **Запрос System One называет модель, которая отвечает** (ADR 229): поле
  `model` — часть протокола `/v1/systemone` — llama.cpp отвечает именем или
  алиасом загруженной модели, роутер использует поле для маршрутизации, а
  сервер, которому оно требуется, без него отвечает `422`.
- **Окно контекста внешнего сервера читается из `/v1/models`**
  (`max_model_len`, ADR 231): один запрос на сервер в момент разрешения,
  кэшируется по серверу, хранится в `ResolvedConnection::contextSize`.
  Бюджет генерации (`core/RequestBudget`) подрезает `max_tokens` до окна.
  Сервер не публикует бюджет image-токенов, поэтому оценка промпта берёт
  зрительный пол поставляемых моделей (70–1120 токенов; используется 1024).
  Запрос, не помещающийся в окно, опасен: некоторые серверы (omlx) отвечают
  **HTTP 200** с телом ошибки и без `choices`, выгрузив модель, — вот почему
  бюджет подрезается заранее.
- **Сервер, игнорирующий бюджет рассуждений, получает fix-запрос ещё раз
  без размышлений** (ADR 230): `reasoning_budget_tokens` (ADR 193) —
  параметр llama.cpp; omlx его игнорирует, размышления съедают весь
  `max_tokens`, и ответ возвращается без `content`. Задача исправления
  повторяет этот запрос с выключенными размышлениями, сообщает об этом в
  футере, и следующие запросы к тому же серверу пропускают размышления
  вовсе. Ответ без choices называет свою причину (ошибка сервера,
  израсходованный бюджет, пустой контент) вместо голого "no choices".
- **Клиент ведёт собственный журнал запросов** (`core/RequestJournal`,
  ADR 228): одна запись на HTTP-вызов — эндпоинт, модель, размеры запроса
  и ответа, HTTP-статус, длительность и голова ответа (ограниченный
  фрагмент). Окно лога показывает его во внешнем режиме, где нет серверного
  процесса, из которого можно читать вывод. Журнал живёт в памяти
  (последние 500 записей — страница это документ пользователя), и API-ключ
  в него не попадает никогда.

## 5. Проектные решения

- **ADR 226** — внешний рантайм зеркалит управляемый: эндпоинт, ключ и
  алиас на каждую задачу; пустое поле = общее значение; один редактор
  алиаса.
- **ADR 227** — секреты живут в хранилище секретов ОС, а не в файле
  настроек; никакого зашифрованного резерва, никакого пути миграции
  открытым текстом.
- **ADR 228** — внешний сервер журнал не ведёт, поэтому клиент ведёт
  собственный журнал запросов: в памяти, ключ в него не попадает.
- **ADR 229** — запрос System One несёт поле `model`: часть протокола,
  а не опция.
- **ADR 230** — сервер, игнорирующий бюджет рассуждений, один раз
  повторяется без размышлений, с пометкой в футере; ответ без choices
  называет свою причину.
- **ADR 231** — окно контекста приходит из `/v1/models` (`max_model_len`),
  и бюджет ответа подрезается до него.
- **ADR 232** — macOS Keychain привязывает ключ к сборке, которая его
  записала; dev-сборкам нужна стабильная идентичность подписи.
- **ADR 233** — `NotFound` и `Refused` — разные статусы; отказ едет
  с подключением и останавливает запрос.
- **ADR 235** — задача проверки на `/v1/systemone` говорит на протоколе
  визуального диффа `systemone_visual_diff_v1` (две картинки,
  P(согласованности), без инструкций).
- **ADR 283** — поле ключа — одновременно редактор ключа и его кнопка
  удаления: маска — текст поля, пустое поле удаляет ключ, один
  переключатель "Show" на таблицу.
