# Gemma 4 E4B / 12B QAT — руководство по моделям

Рабочие заметки по двум моделям Gemma 4 QAT в том виде, в каком их использует
LLocr: что это за модели, откуда берётся GGUF, как запускаются MTP-драфтер и
визуальный стек, как собирается fix-запрос и какие
рекомендации карточек LLocr выполняет буквально. Всё здесь — из карточек
моделей, гайдов Unsloth или измерено в этом проекте.

Английский оригинал — [`16-gemma-4.md`](16-gemma-4.md).

## 1. Что это за модели

- **Gemma 4** (Google DeepMind), чекпоинты **QAT**, переупакованные Unsloth —
  int4-веса, обученные с учётом квантования: качество близко к bfloat16 при
  ~72% меньшем расходе памяти. Лицензия Apache-2.0 (условия Gemma). Обе
  модели мультимодальные (текст + изображение; на E-серии есть аудио, но
  LLocr его не использует), 140+ языков, контекст 128K (E4B) / 256K (12B).
- **Gemma 4 E4B** — 4,5 млрд «эффективных» параметров (8 млрд с Per-Layer
  Embeddings), отдельный визуальный энкодер (~150 млн). ~5 ГБ без MTP,
  6,5–7 ГБ с драфтером.
- **Gemma 4 12B Unified** — 11,95 млрд, «безэнкодерная» архитектура: в
  transformers изображения идут прямо в декодер через линейные слои.
  llama.cpp по-прежнему поставляет проектор отдельным файлом `mmproj` и
  загружает его обычным способом. ~7 ГБ без MTP, 8–9 ГБ с драфтером.
- Визуальные бенчмарки карточки (OmniDocBench 1.5, среднее расстояние
  редактирования — меньше лучше): E4B **0.181**, 12B **0.164** (Gemma 3 27B:
  0.365). В целевые задачи карточка называет разбор документов, OCR и
  распознавание рукописного текста.

LLocr использует обе модели только в задаче **fix** (ADR 162/163) —
универсальные модели, подтверждающие / исправляющие / бракующие кандидата
распознанного блока (OK/FIX/REVIEW). Транскрипция остаётся за
det-token моделями, задача decision — за визуальным диффом minicpm-jev
(ADR 252/254).

Примечания:

- **MTP-драфтер** лежит в корне репозитория как близкий к оригиналу «smart
  Q4_0» (`mtp-gemma-4-*.gguf`); в папке `MTP/` — варианты BF16/F16/Q4_0/Q8_0.
  Поток `-hf` в llama.cpp находит драфтер автоматически; LLocr ставит явно,
  поэтому профиль объявляет файл, конвейер установки скачивает его из того же
  репозитория и записывает в `launch/draftPath` роли (передаётся как
  `--model-draft`).
- `minBuild` — **b9600**: поддержка Gemma4 MTP появилась в llama.cpp
  07–08.06.2026 (`llama : add Gemma4 MTP` #23398, `mtp: support for gemma-4
  E2B and E4B assistants` #24282 ≈ b9570); b9600 — первая сборка несколькими
  днями позже, уже с ранними исправлениями драфтера.
- Оценщик памяти читает GGUF-метаданные `gemma4.*` — предупреждение мастера
  настройки считает слои/головы по-настоящему.

## 3. Запуск llama-server

Команды из карточек:

```sh
# E4B — flash attention ВЫКЛ
llama-server -hf unsloth/gemma-4-E4B-it-qat-GGUF:UD-Q4_K_XL \
  --spec-type draft-mtp --spec-draft-n-max 4 -ngl 999 -fa off

# 12B — flash attention ВКЛ
llama-server -hf unsloth/gemma-4-12B-it-qat-GGUF:UD-Q4_K_XL \
  --spec-type draft-mtp --spec-draft-n-max 4 -ngl 999 -fa on
```

Что фактически запускает LLocr (платформенный слой из `serverLaunch.json`,
слой модели — из профилей):

```sh
llama-server \
  --model <…>/gemma-4-E4B-it-qat-UD-Q4_K_XL.gguf \
  --mmproj <…>/mmproj-F16.gguf \
  --model-draft <…>/mtp-gemma-4-E4B-it.gguf \
  --alias llocr-verify --host 127.0.0.1 --port <n> \
  --n-gpu-layers 99 --ctx-size 16384 \
  --spec-type draft-mtp --spec-draft-n-max 4 --temp 0 --parallel 1 \
  --no-warmup --jinja --reasoning-budget 0 --flash-attn off \
  --image-min-tokens 1120 \
  --cache-reuse 0 --no-context-shift
```

По слоям:

- `--model / --mmproj / --model-draft / --alias / --host / --port` — основные
  поля, единый источник — настройки активации/установки. Драфтер пользователь
  не выбирает: он скачивается вместе с моделью.
- **Слой модели** (`gemma-4-e4b.json` / `gemma-4-12b.json`):
  - `--spec-type draft-mtp --spec-draft-n-max 4` — настройки сервера из
    карточек. Драфтер делит KV-кэш с основной моделью и не меняет вывод
    (целевая модель проверяет каждый «черновой» токен); упаковщик мерил
    ускорение декодирования в 1,5–2,2 раза и советует подобрать 1–6 под
    машину.
  - `--temp 0 --parallel 1 --no-warmup` — серверные значения по умолчанию
    для однопоточного конвейера транскрипции (как в профилях qwen).
  - `--jinja` — чат-шаблон из GGUF разбирает «канал размышлений» Gemma 4,
    поэтому решает режим размышления из запроса, думает модель первой или нет
    (§4).
  - `--reasoning-budget 0` — серверный бюджет размышления по умолчанию: мысли
    нет, пока запрос её не попросит. Запрос fix несёт режим размышления и
    перекрывает дефолт (ADR 193).
  - `--image-min-tokens 1120` — Gemma 4 квантует каждое изображение в один
    из пяти бюджетов визуальных токенов: **70 / 140 / 280 / 560 / 1120**.
    Карточка рекомендует верхние бюджеты для OCR, разбора документов и
    мелкого текста — профиль закрепляет максимальный (§ Best practices 5).
  - `--ubatch-size 2048` — **только 12B**. 12B — «унифицированная» сборка:
    проектор подаёт патчи изображения сразу в основную модель, и этот декод
    идёт с non-causal attention — такую батчу нельзя резать по убатчам,
    всё изображение обязано влезть в одну. С серверным дефолтом 512
    llama-server капирует визуальный бюджет до 512 токенов, и любой кроп
    блока, растянутый до бюджета, попадает на несколько токенов *выше* капа
    (ресайз округляет обе стороны вверх до сетки патчей) — первый же декод
    изображения убивает сервер по ассерту `non-causal attention requires
    n_ubatch >= n_tokens`. 2048 вмещает закреплённый бюджет 1120 плюс
    овершут округления. E4B кодирует изображения в собственном проекторе
    каузальным путём и остаётся на дефолте.
  - `--flash-attn off` — **только E4B**: команда карточки для E4B идёт с
    выключенным flash attention. Карточка 12B говорит противоположное
    (`-fa on`) — и это совпадает с платформенным значением по умолчанию на
    Metal/CUDA, поэтому профиль 12B вообще не переопределяет `flash-attn`,
    а Vulkan/CPU оставляют платформенный `off`.
- Политика: `--parallel 1 --cache-reuse 0 --no-context-shift --no-warmup`
  (`parallel`/`no-warmup` повторены в слое модели, потому что MTP-черновик
  однопоточный; так же сделано в профилях qwen).

## 4. Сборка запроса

### Порядок модальностей в сообщении

- Лучшая практика карточки Gemma 4: **изображение до текста**.
  Предшественник `BlockRecognitionModel` (`GeneralPurposeModel`) раньше жёстко
  слал `[промпт типа, изображение]`;
  теперь он следует флагу `promptBeforeImage` из профиля — тому же флагу,
  который уже учитывает тело OCR. Gemma 4 (и все модели семейства Qwen)
  получают `[изображение, промпт типа]`; LFM2.5 из архива сохраняет свой
  обученный `[промпт типа, изображение]`.
- Размышления следуют за режимом запроса: `chat_template_kwargs:
  {"enable_thinking": …}` истинно ровно тогда, когда запрос несёт бюджет
  размышления больше нуля (ADR 193) — режим off оставляет прежнее поведение,
  а при включённом размышлении мысль приходит в `reasoning_content`, а в
  `content` — вердикт и исправленный блок. При выключенных размышлениях 12B
  всё равно выдаёт **пустой** блок размышлений (E-серия — нет); `--jinja`
  заставляет llama.cpp вырезать маркеры канала, так что `content` приходит
  чистым в обоих случаях.
- Один кроп блока на запрос; текст кандидата едет рядом, обрамлённый
  `<CANDIDATE>` (§ «Промпты fix»).

### Промпты fix

Профиль основан на `qwen3.5-9b.json` и переиспользует его набор промптов для
задачи fix (протокол `full_block`, ADR 192): верификационный системный
промпт (изображение — единственный источник истины; три вердикта OK /
FIX / REVIEW, а FIX несёт полный исправленный блок) плюс контрольный
список на каждый тип блока. Системный промпт называет язык документа
плейсхолдером `{{LANGUAGE}}`, который подставляет приложение (ADR 181).
Сообщение пользователя упорядочивает промпт типа, изображение блока и
кандидата, обрамлённого `<CANDIDATE>…</CANDIDATE>`. Промпт таблицы
закрепляет контракт той же сериализации — исправленная таблица отвечает в
формате кандидата (HTML на входе — HTML на выходе, Markdown на входе —
Markdown на выходе) — он нужен обоим семействам.

### Параметры запроса

| Параметр | Значение | Зачем |
| --- | --- | --- |
| `temperature` | 0.0 | Детерминированное жадное декодирование для протокола исправления. (Чатовое сэмплирование карточки — temp 1.0, top-p 0.95, top-k 64 — для разговора, а не для конвейера проверки.) |
| `repeat_penalty` / `presence_penalty` / `frequency_penalty` | 1.0 / 0.0 / 0.0 | Нейтральные. |
| `max_tokens` | 8192 | С запасом на кроп таблицы; совпадает с профилями qwen. `maxOutputByBlock` бюджетирует ответ по типу блока (номер страницы — 64, таблица — 8192) — бюджеты лежат в общем профиле запросов `fix-requests.json`, поэтому все четыре fix-модели отвечают с одинаковыми (ADR 192). |
| `stop` | `["</CANDIDATE>"]` | Обрывает ответ по вердикту, даже если модель готова генерировать дальше. В списке только маркер протокола: llama-server и сам останавливается на end-of-text токене модели, а если назвать его в списке stop, он сверяется с отрендеренным ответом и ответ срезается до пустоты. |
| `stream` | false | Парсер получает один полный ответ. |
| `cache_prompt` | false | Каждый запрос блока независим от общего KV-кэша драфтера. |

Опциональный режим размышления в задаче fix (ADR 193) пары gemma
**предложен**: в профиле модели стоит `reasoning: true`, поэтому запрос
исправления несёт бюджет размышления и те же четыре шага (off / low 512 /
med 1024 / high 1536), что предлагает общий профиль запросов.

Проверено на llama.cpp b11799 (модель `gemma-4-E4B-it-qat-UD-Q4_K_XL`,
сервер `--jinja --reasoning-budget 0`):

- шаблон чата gemma-4 знает переключатель `enable_thinking` и канал мысли
  (`<|channel>thought`), поэтому автопарсер llama.cpp выносит размышление в
  `message.reasoning_content`, а в `message.content` остаётся ответ — вердикт
  и исправленный блок;
- бюджет едет в запросе (`reasoning_budget_tokens`) и режет мысль на нужном
  токене: бюджет 32 дал мысль в ~32 токена и ответ после неё, бюджет 512 —
  полную мысль и тот же ответ;
- при бюджете 0 (режим off) мысли нет вовсе, ответ — как раньше.

Опцию в gemma-профили просто не положили — ограничения модели здесь нет.
Практическая оговорка: оборванная на середине мысль (маленький бюджет) у gemma
иногда вытекает в сам ответ — после исправленного блока появляется хвост с
объяснением. Поэтому режим «off» остаётся режимом по умолчанию, а бюджет
выбирают достаточно большим, чтобы мысль уложилась.

## 5. Форматы вывода

Вердикты протокола fix — `OK`, `FIX` с полным исправленным блоком, `REVIEW` —
раскладываются `FixModel` с дифф-гейтом (`FixDiffGate`) по слою коррекции:
`OK` оставляет текст, `FIX` сохраняет исправление в `correctedText`, `REVIEW`
помечает блок повреждённым; эквивалентный исправленный блок (модель переписала
то же самое) читается как `Ok`, а пустой ответ, `FIX none` и ответ, обрезанный
бюджетом токенов, деградируют в `Review` (ADR 139/163/192); ответ вне трёх
вердиктов — тоже в `Review` (ADR 181).

## 6. Роль в конвейере проверки

- **fix** — единственная задача обоих профилей (ADR 162/163): после того как
  decision-модель пометила блок как несовпадение (или по ручным командам
  «Исправить»), кандидат и кроп уходят задаче fix; `OK` сохраняет текст,
  `FIX` кладёт исправление, `REVIEW` помечает блок. Сам OCR-текст остаётся
  нетронутым для diff/отката (ADR 164).
- **blockRecognition** — не объявлена: транскрипция — работа
  det-token моделей.
- **decision** — неприменимо: задача проверки говорит на визуальном диффе
  MiniCPM-OCR Jev (ADR 254).

## 7. Где что живёт в LLocr

| Кусок | Расположение |
| --- | --- |
| Профили моделей (файлы, слои launch/request) | `resources/profiles/models/gemma-4-e4b.json`, `gemma-4-12b.json` |
| Тексты запросов fix (общие с остальными fix-моделями) | `resources/profiles/requests/fix-requests.json` |
| Запрос/ответ fix, порядок модальностей | `GeneralPurposeModel::buildRequestBody` / `parseResponse` (`src/models/`) |
| Скачивание драфтера и проводка `launch/draftPath` | `ModelInstallTransaction`, `ModelInstaller`, `ServerLaunchConfig` |
| Оценка памяти (ключи метаданных gemma4) | `ModelMemoryEstimator` |
| Строки установщика | `ModelQuantModel` (список задачи fix в «Модели по задачам»; управление в «Модели») |

Решения: ADR 88 (модели — данные: профиль несёт весь контракт), 126 (слои
launch: у машины — `flash-attn`/`ctx-size`, кроме случаев, когда этого
требуют веса; `-fa off` у E4B — такой случай), 145–147 (двухфазный конвейер),
162–164 (задача fix, двухслойная верификация).
