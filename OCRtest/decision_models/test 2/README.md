# Тест decision-моделей (corpus OCR_TEST, блоки теплообменников)

Один и тот же результат распознавания **MinerU2.5-Pro** (195 блоков, 10 страниц —
статья про Unlimited OCR + русская техническая литература про теплообменники с
формулами и таблицами) проверяется decision-моделями. Прогон каждой итерации
правок профилей — своя подпапка с `.llocr`-проектами; в корне лежит исходный
проект распознавания (без вердиктов — evaluate.py пропускает его сам):

```
OCR_TEST_MinerU2.5-Pro.llocr   ← исходное распознавание (не оценивается)
iteration1/                    ← базовый прогон 18.10 (clef v5, d3 v6, старые промпты)
iteration2/                    ← 19.10: clef переведён на v6, промпты по рекомендациям
iteration3/ … iteration6/       ← 20–22.10: пороги по кривым, каноническая формула, переписанные промпты
iteration7/                    ← 22.10: перекалибровка clef-flash и d3-flash (офлайн-стенд)
evaluate.py, truth.json, README.md
```

Папка — самодостаточный стенд: правите промпты/пороги профиля → перегоняете
проверку в приложении → кладёте новый `.llocr` в новую подпапку `iterationN/` →
одна команда даёт FP/FN по типам блоков. Код приложения не требуется.
Прогоны iteration7 сделаны **офлайн-стендом** `scripts/decision-eval/
score-project.py` (запрос приложения уходит на провод, бит в бит) — приложение
для них не нужно.

## Быстрый прогон

```sh
cd "OCRtest/decision_models/test 2"
python3 evaluate.py                # все итерации разом, консенсус по каждой подпапке
python3 evaluate.py iteration2     # только одна итерация
python3 evaluate.py --verbose      # + списки FN/FP с расхождениями и причинами
python3 evaluate.py --json out.json
```

Зависимости: `python3`, `pip install rapidfuzz`. Эталон берётся из
`../../ocr_models/materials` (gt.json + gt.py + compare.py); при другом
расположении — `--materials PATH`. Новая модель = ещё один
`OCR_TEST_<имя>.llocr` с **тем же** распознаванием в подпапке итерации.

## Методика

1. **Истина** — ручная поблочная транскрипция из `OCRtest/ocr_models`
   (эталон снят с 200-dpi рендеров, включая строки-«огрызки» соседних блоков;
   спорные места сверялись с кропами и рендерами).
2. **Критерий ошибки** — правила эквивалентности из самих профилей
   (`resources/profiles/models/*.json`): гомоглифы (н/H, ν/v, ρ/p), е/ё,
   регистр, потерянные штрихи/черты, лишняя/пропавшая пунктуация и фрагменты —
   **ошибка**; carrier-разметка (`\( \)`, `\tag{n}`, `\mathrm`/`\mathbf`,
   `\left`/`\right`, переносы `\\`, конвенции индексов `T_f1` vs `T_{f1}`) —
   **не ошибка** (при рендере её не видно).
3. Сравнение — нормализация `compare.py` (+ досечение `\(...\)` в текстовых
   блоках) и посимвольный CER. `CER>0` = ошибка, кроме явно перечисленного в
   `truth.json` (`clean_overrides`, каждый — с причиной).
4. **Вердикты**: статус бокса в `BoxCheckStatus` приложения: 0 = вне области
   проверки (исключён), 1 = Ok, 3 = Review (пустой/нечитаемый кроп),
   4 = Mismatch (fixable). Флаг = всё, что не Ok/0. FP = флаг на чистом блоке,
   FN = Ok на блоке с ошибкой. FN% считается от блоков с ошибками, FP% — от
   чистых.
5. **Свежесть истины**: `truth.json` хранит sha1 текста каждого блока. Если
   распознавание сменилось (другая OCR-модель или новая разметка), блоки с
   изменившимся текстом исключаются из оценки с предупреждением — их надо
   переразобрать (`--verbose`, решение занести в `clean_overrides` при
   необходимости). При правках **decision-промптов** тексты не меняются и
   истина остаётся валидной без дополнительных действий.
6. **Калибровка порогов по confidence** (ADR 173): прогоны, сделанные сборкой
   с сохранением confidence, печатают под каждой моделью кривую FN/FP(t).
   Направление: Ok = p ≥ t, поэтому **выше порог — меньше FN и больше FP**
   (снижение порога наоборот разменивает FP на FN). Кривая пересчитывает
   вердикт из сохранённого P(match): флаг при p < t, Review — флаг при любом t;
   Mismatch по диагнозу (fixable при высокой p) кривая не видит и слегка
   завышает FN. Одна сборка даёт всю кривую — перебор итераций не нужен.

### Итерации 5–6: каноническая формула и переписанные промпты

**Что менялось в приложении.** Формула теперь уходит в decision-запрос в
канонической форме — той же, что и в fix-задачу (`FixDiffGate::
normalizeLatexCandidate`): OCR-модели пишут LaTeX с пробелами («Bi _ {1}»),
и без нормализации checker читал пробелы как содержание. Байты блока не
меняются — меняется только то, что уходит на провод. Порт того же
преобразования в стенде (`scripts/decision-eval/variants.py`) сверяется со
значениями, которые выдаёт приложение; сверка идёт при каждом запуске
стенда (`run.py`, `score-project.py`).

**Что показали прогоны.**

- iteration5 (нормализация, старые промпты) — формулы посыпались: **FN 0 / FP
  29** при flat 0.85 (в iteration4 было 5/5). Нормализация убрала шум пробелов,
  но модель продолжила считать пробелы различием: её распределение p(match)
  уехало вниз по шкале.
- iteration6 (нормализация + новые промпты) — те же формулы **7/5** при 0.70,
  4/9 при 0.75, 1/15 при 0.80. Переписанные промпты («разметка — носитель, а не
  содержание») вернули формулы в разделение; кривая по тексту стала круче
  (0.80: FN 12/FP 7 против 14/6 у iteration4).

**Как считались пороги.** Вердикт — это порог по сохранённому P(match)
(Ok = p ≥ t), поэтому кривая FN/FP(t) пересчитывается из прогна без новых
запросов (`scripts/decision-calibrate.py`). Пороги взяты с iteration6 — это
единственный прогон, сделанный с текущими промптами и нормализацией:

| тип блока | кривая FN/FP(t) (iteration6) | порог |
| --- | --- | --- |
| text (45 ошибок / 52 чистых) | 0.80: 12/7 · 0.85: 5/14 | 0.85 |
| equation (20/30) | 0.70: 7/5 · 0.75: 4/9 · 0.80: 1/15 | 0.70 |
| table (6/3) | 0.60: 1/3 · 0.65: 0/3 | 0.65 |
| table_caption (1/10) | 0.80: 0/0 · 0.85: 0/1 | 0.80 |
| table_footnote (1/2) | 0.45: 0/0 · 0.50: 0/1 | 0.45 |
| list (0/1) | 0.75: 0/0 · 0.85: 0/1 | 0.75 |
| title, image_caption (0/6) | 0.85: 0/0 | 0.85 |

Точка выбрана по колену кривой (следующий шаг — equation 0.75 — стоит 4 FP на
3 FN, дороже прежней точки) и по цене перепроверки: **FN 12 / FP 22** против
прежних FN 14 / FP 22 — та же цена, на две ошибки меньше.

**Проверка, что прогон соответствует профилю.** Вердикт в проекте — чистый
порог по сохранённому confidence, поэтому из прогона восстанавливается порог,
которым он сделан: у iteration6 text ∈ (0.7972, 0.8012] → 0.80, equation ∈
(0.6927, 0.7014] → 0.70. Прогон и профиль обязаны совпадать: пороги, записанные
в профиль, но не применённые прогоном, дают цифры, которых никто не видел.

**Про остальные модели.** Тексты запроса общие для всех decision-моделей
(`decision-requests`), поэтому переписанные промпты сдвигают распределение и
clef-flash, и d3-flash тоже: их пороги измерены на старых промптах и после
переписывания запроса устарели. Перекалибровка — те же прогоны, что и у
d3-mini, только с их моделями (см. ниже).

### Итерация 7: перекалибровка остальных моделей

**Как сделан прогон.** Офлайн-стенд `scripts/decision-eval/score-project.py`:
запрос приложения (`v0_app_current`) уходит на провод по блокам корпуса, кропы
берутся из проекта (300 dpi, как у приложения), state — с отсортированными
ключами (приложение собирает его в `QJsonObject`), формула — в канонической
форме. Числа воспроизводятся **бит в бит** (проверено на iteration6 d3-mini:
те же P(match) до последнего знака), вердикты пишутся в тот же `.llocr`, что
пишет приложение, поэтому `evaluate.py` считает их как обычный прогон.
Область проверки и тексты блоков у всех трёх прогонов совпадают (сверено).

**Что показали прогоны.**

| модель | AUC по корзинам (старый запрос → текущий) | на старых порогах | пересчитанные пороги |
|---|---|---|---|
| clef-flash | формулы 0.782 → 0.715 · таблицы 0.889 → 0.722 · текст с формулами 0.870 → 0.821 · простой текст 0.860 → **0.479** | FN 18 / FP 32 | **FN 22 / FP 25** |
| d3-flash | формулы 0.755 · таблицы 0.778 · текст с формулами 0.888 · простой текст 0.669 | FN 38 / FP 8 | **FN 34 / FP 7** |
| d3-mini | формулы 0.852 · таблицы 0.611 · текст с формулами 0.929 · простой текст 0.711 | (iteration6) FN 19 / FP 19 | **FN 12 / FP 22** |

**Главный вывод: общий текст запроса стоил clef разделения.** Переписанные
промпты написаны под d3-mini, и на простом тексте clef теперь отвечает хуже
случайного (AUC 0.479 против 0.860 у iteration4). Пороги это не чинят: при
той же цене перепроверки, что у iteration4 (FP 36), лучшая точка clef — это
FN 18 / FP 31, против FN 11 / FP 36 раньше. Починить это можно только
отдельным текстом запроса для clef, а тексты запроса общие по решению
ADR 182.

**d3-flash — самая слабая из трёх** (FN 34 при FP 7 против 12 у d3-mini при
FP 22): её noul-голова систематически уверена, и на тексте это стоит 20
пропущенных ошибок из 45. Дешёвые ложные тревоги — не качество: на
перепроверку уйдут не те блоки.

**Как выбирались пороги.** `scripts/decision-eval/pick-thresholds.py`: колено
кривой типа — последняя ступень, где одна пойманная ошибка стоит не больше
одного FP; пара, держащая FP на нуле, берёт край чистой области; пара, платящая
FP, берёт самую дешёвую поимку; тип, которого в корпусе меньше трёх блоков,
не калибруется и оставляет значение профиля. Правило проверено на эталоне: на
iteration6 (d3-mini) оно воспроизводит её профиль в точности — FN 12 / FP 22.

| модель | пороги | FN / FP |
|---|---|---|
| clef-flash | text 0.80, equation/formula 0.75, table 0.50, table_caption 0.80, table_footnote 0.75, title 0.85 | FN 22 / FP 25 |
| d3-flash | text 0.80, equation/formula 0.75, table 0.90, table_caption 0.90, table_footnote 0.80, title 0.55 | FN 34 / FP 7 |
| d3-mini | text 0.85, equation/formula 0.70, table 0.65, table_caption 0.80, table_footnote 0.45, list 0.75, title 0.85 | FN 12 / FP 22 |

Уроки iteration2: carrier-правила убрали почти все FP на разметке; правило
и/н подняло clef на простом тексте (FN 8→3); d3-flash от новых промптов
ухудшилась (промпты идентичны d3-mini, пороги ниже, а флагов меньше — её noul
-голова систематически уверена). Остаточные FN iteration2 — одно-символьные
подмены в инлайн-математике (∂/d, ρ/p, ν/v, ū/и, ∯/∬) и и→н; 5 из 21
консенсусных пропусков — гомоглифы, неразличимые в печати (н/H, б/6, Π/II),
промптом недостижимы.

Уроки iteration3: mismatch-first + пороги дали clef FN 27→16 (11 новых TP,
в т.ч. 4 «script-only» гомоглифа — класс недостижимых промптом частично
достижим), цена — FP 10→24 (чистые блоки с p 0.68–0.80, у которых текст
равен эталону только после carrier-нормализации). Кривые показали: per-block
пороги d3-mini занижены для её калибровки — flat 0.85 даёт ≈FN 14 / FP 22,
лучше её прогона 30/7 и не хуже clef. d3-flash Q8 ≡ Q4 (42/6 у обоих,
расхождения ±2 некоррелированных блока). Жёсткое ядро — 12 ошибок, пропущенных
всеми: одно-символьные подмены в формулах (ρ/p, ∯/∬, г/r, ν/v, ж/к, ∂/d) с
p(match) 0.76–0.90 при чистых ≤ 0.80 — порогом недостижимы, промпты исчерпаны.

### Главные паттерны

- **FN**: доминирует курсивное `и↔н` в русском тексте (~30 блоков, ловится
  наполовину; clef на простом русском — 8 пропусков из 11). Общие слепые зоны:
  `∂`→`d` и `ρ`→`p` в текстовых блоках (текстовые промпты не описывают
  математику), потеря `ё`, штрихов (`Bi′`), черт (`ū`), огрызка строки
  (`ν=η/ρ`), у d3 — замены интегралов `∯`→`∬`, `∭`→`∬∬`.
- **FP**: clef флагает верную разметку `\tag`, `\mathrm`, `\left/\right` в
  формулах (11 из 21 FP); d3 — `\( \)`-обёртки в текстовых блоках (per-block
  statePrompt замещает ролевой и теряет правило «LaTeX — carrier»); d3-mini —
  короткие заголовочные строки, дословно совпадающие с кропом; clef — блок,
  начинающийся с середины слова.
- **Таблицы**: clef флагает все 9 (в т.ч. 3 верные); d3 пропускает латинизацию
  в ячейках (`моль/(м³·с)` → `(m³·c)`, ν→v, `\tilde` вместо черты).

### Рекомендации по промптам (проверяются этим стендом)

1. Вернуть «LaTeX/`\(...\)` — carrier» в каждый блочный statePrompt d3
   (`blockPrompts.*.statePrompt` замещает ролевой промпт).
2. Добавить правило и/н (курсивная печать) во все профили — крупнейший класс FN.
3. В equation-промпты: различия интегралов ∯/∬/∭, ρ/p, ν/v, ∂/d; пропавший
   фрагмент/пунктуация — ошибка; `\tag{n}` ≡ `(n)`.
4. В текстовые промпты: гомоглифы и диакритика в инлайн-математике (ρ/p, ν/v,
   π/п, φ/ф, ū, ′) — контент.
5. d3-mini: «короткая строка, дословно совпадающая с кропом — exact_match».
6. Пороги: Ok = p ≥ t, поэтому направление «дешёвых» FN — пороги **вверх**
   (каждый шаг вверх конвертирует часть TN в FP, но ловит ошибки из
   вероятностного хвоста). Базовая рекомендация дана до персистенции
   confidence; точную точку выбирать по кривой FN/FP(t) из evaluate.py.

## Ограничения

- Вердикты сравниваются с изображением кропа; эталон — ручная транскрипция как
  прокси. Спорные случаи адьюдикации сверены с кропами/рендерами; случаи
  «только начертание» (жирное `g` в тексте, `\mathrm` у формулы с жирным
  шрифтом в изображении) отнесены к «чистым» — это и есть FP clef на формулах.
- Статус 4 в проектах — это **Mismatch** боксового enum (`BoxCheckStatus`:
  0 NotChecked, 1 Ok, 3 Review, 4 Mismatch); Review (3) в прогонах не
  встречался — пустых/нечитаемых кропов в корпусе не было. Скрипт считает
  флагом и то и другое.
- Числитель/знаменатель: FP% = FP / чистые блоки, FN% = FN / блоки с ошибками;
  абсолютные значения в скобках.
