# OCRtest / manual — ручные стенды READ и FIX

Два скрипта для одиночных CLI-запросов к llama-server с ручными конфигами.
Всё редактируется в текстовых конфигах — по одному параметру на строку.

## Файлы

| Файл | Что это |
| --- | --- |
| `stand.py` | Общий движок: разбор конфига, запуск/переиспользование llama-server, запрос |
| `read.py` | Стенд READ: кроп → расшифровка |
| `fix.py` | Стенд FIX: кроп + кандидат → OK / FIX / REVIEW |
| `read.txt` | Конфиг READ |
| `fix.txt` | Конфиг FIX |
| `glyph.py` | Метрика масштаба кропа: медианная высота букв (кегль) |

## Воспроизводимость

`temperature = 0` убирает случайность сэмплинга, но результат остаётся
функцией от входа и окружения: **байты картинки (масштаб!)**, байты
промпта, флаги запуска, сборка и бэкенд llama-server (CUDA и Vulkan дают
разные числа), квант модели, состояние кэша промпта. Одинаковый результат
гарантирован только при совпадении всего набора — «одни и те же параметры»
на разных машинах или с другой картинкой это разные эксперименты.

Инструменты:

- тело каждого запроса пишется в `last_request_read.json` /
  `last_request_fix.json` (base64 картинки заменён отпечатком sha1) —
  побайтовое сравнение запросов между машинами и прогонами;
- `py glyph.py <кроп>` — кегль картинки: цель READ ~33 px (эталон `5.png`
  из tmp), кроп приложения при 300 DPI ~18 px, на нём модель теряет
  акценты.

Чек-лист расхождения результата: (1) тот же файл картинки (тот же sha1 в
дампе)? (2) тот же квант модели? (3) те же флаги запуска — в частности
`--reasoning-budget 0` (эксперимент шёл без размышлений) и
`--batch-size/--ubatch-size`? (4) та же сборка/бэкенд сервера? (5) нет ли
лишней текстовой части в запросе (эксперимент READ слал только картинку)?

## Запуск

```bat
py OCRtest\manual\read.py
py OCRtest\manual\fix.py
py OCRtest\manual\read.py другой-конфиг.txt --restart
```

Скрипт сам поднимает llama-server из конфига (лог — `server.log`) и ждёт
`/health`. Уже работающий сервер с теми же параметрами запуска
переиспользуется; при изменении блока «Сервер»/«launch» пересапается при
следующем запуске; `--restart` пересапает принудительно. Порт занят чужим
процессом — скрипт завершится с сообщением, сам чужой процесс не трогает.

READ и FIX используют один порт — стенд ведёт один сервер. Блоки запуска у
них разные (READ — reasoning-budget 256, FIX — 0, победители корпусного
прогона): переключение между скриптами пересапает сервер, правка запросов
внутри одного конфига идёт без пересапа.

## Формат конфига

Каждый параметр с новой строки: `ключ = значение`. Значение продолжается на
следующих строках **с отступом** (склеиваются переводом строки — так пишутся
многострочные system/prompt). Строки с `#` и пустые пропускаются. Ключи
регистронезависимые, с начала строки. Относительные пути — от папки конфига.

Переносы строк и `\n`:

- в `system`, `prompt`, `candidate` настоящий перенос — это строка с
  отступом; литерал `\n` остаётся двумя знаками `\` и `n` (намеренно: в
  LaTeX `\neq`, `\nu`, `\nabla` начинаются с `\n` и были бы испорчены);
- в `params` значения — JSON: `\n` внутри JSON-строки это настоящий
  перенос, а само JSON-значение можно переносить на следующие строки с
  отступом — строки копятся, пока не соберётся валидный JSON;
- продолжение без отступа не является продолжением: строка без `=`
  пропускается с предупреждением, а с `=` начинает новый ключ.

Ключи:

| Ключ | Смысл |
| --- | --- |
| `runtime` / `model` / `mmproj` | Путь до llama-server.exe и GGUF-файлов |
| `host` / `port` | Адрес сервера |
| `wait` / `timeout` | Ожидание загрузки модели и таймаут запроса, с |
| `max_tokens` | Лимит ответа |
| `launch` | Флаги llama-server — по одному на строку |
| `system` / `prompt` | Системный запрос и типовой запрос блока |
| `candidate` | Только FIX: кандидат (текст распознавания) |
| `image` | Путь до кропа |
| `params` | Поля тела запроса: `имя = json-значение`; JSON-значение можно переносить строками |

Результат печатается в консоль и сохраняется в `last_read.txt` /
`last_fix.txt` (UTF-8; консоль может показывать кириллицу искажённо — файл
верный).
