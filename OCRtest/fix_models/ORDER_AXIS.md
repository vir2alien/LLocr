# Ось порядка: картинка и кандидат в user-сообщении

## Вопрос

Приложение шлёт fix-запрос тремя частями user-сообщения:

```
тип-подсказка → картинка кропа → <CANDIDATE>кандидат</CANDIDATE>
```

Картинка уже **впереди** кандидата (`FixModel::buildRequestBody`, `src/models/FixModel.cpp:180-185`;
у всех поставляемых профилей `promptBeforeImage` отсутствует ⇒ `false`). Может ли
якорение — «модель повторяет написание кандидата вместо того, чтобы перечитать
картинку» — быть следствием **порядка**, а не самого присутствия кандидата?

## Что меряли

Одна модель (gemma-4-12b — лучший измеренный читатель), один корпус
(`corpus/corpus_probe5.json`, 5 формул), один промпт (приложения), кандидат в
сообщении везде. Меняется только **порядок частей**:

| вариант | порядок частей |
| ------- | --------------- |
| `fix` (база, как в приложении) | `тип-подсказка → картинка → кандидат` |
| `order_img_first` | `картинка → тип-подсказка → кандидат` |
| `order_cand_first` | `кандидат → картинка → тип-подсказка` |
| `order_img_last` | `тип-подсказка → кандидат → картинка` |

Метрика — как везде в стенде: CER к ручному эталону и доля прочитанных
индексов, через порт гейта (`gate.py`), то есть считается то, что приложение
реально применит к блоку.

## Результат

| вариант | CER | индексы | вердикты | с/запрос |
| ------- | --- | ------- | --------- | -------- |
| `fix` (база) | 0.050 | 0.74 | Fixed×5 | 102.3 |
| `order_img_first` | 0.040 | 0.84 | Fixed×5 | 116.1 |
| `order_cand_first` | 0.037 | 0.82 | Fixed×5 | 121.7 |
| `order_img_last` | 0.039 | 0.82 | Fixed×5 | 125.1 |
| `no_cand` (кандидата нет, из прошлого прогона) | **0.015** | **1.00** | Fixed×4, Review×1 | 128.8 |

По блокам:

| блок | CER кандидата | `fix` | `img_first` | `cand_first` | `img_last` |
| ---- | ------------- | ----- | ----------- | ------------ | ---------- |
| p03b03 | 0.256 | 0.049 | 0.049 | 0.049 | 0.062 |
| p03b05 | 0.097 | 0.082 | 0.082 | 0.082 | 0.082 |
| p03b12 | 0.161 | 0.018 | 0.018 | 0.018 | 0.018 |
| p03b14 | 0.213 | 0.066 | **0.016** | **0.016** | **0.016** |
| p05b09 | 0.041 | 0.033 | 0.033 | 0.021 | **0.017** |

## Что это значит

**Порядок — не рычаг.** Ни одна перестановка не приближает результат к
показателю «кандидата нет»: лучший из них (`cand_first`, 0.037) в 2.5 раза
хуже, чем `no_cand` (0.015). При этом разница между порядками укладывается в
шум одного-двух блоков (p03b14 и p05b09).

Картинка **уже впереди** кандидата, и якорение происходит. Значит виновато не
место кандидата в сообщении, а **его присутствие**: модель, у которой перед
глазами чужое написание, доточивает его вместо того, чтобы перечитать
картинку.

Единственный блок, где порядок заметно помог, — p03b14: там в кандидате
смесь скриптов (`\mathrm{H.впр}` — латинская H, кириллица), и любая из трёх
перестановок заставила модель перечитать индекс заново (0.066 → 0.016).
Но это ровно тот случай, где **отсутствие** кандидата даёт тот же результат
без всякой перестановки (0.016).

## Вывод для протокола

Новый протокол читает блок **без кандидата** — и это не «улучшение порядка»,
а единственная мера, которая работает: 0.050 → 0.015 на gemma-4-12b, и
0.154 → 0.076 на MiniCPM-o 4.5 (пять Review → пять Fixed).

Перестановку частей в приложение тащить не надо: она не даёт выигрыша,
которого не даёт отсутствие кандидата, и стоит +13–23 % времени на запрос.

## Оговорки

* Пять формул одной страницы — направление, а не статистика.
* Одна модель (gemma-4-12b), всё на CPU.
* Порядок измерялся при кандидате в сообщении; для протокола без кандидата
  порядок частей не имеет значения (частей две: тип-подсказка и картинка).
