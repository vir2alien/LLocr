# Можно ли починить fix-запрос — да, и виновник найден: кандидат

## Вопрос

Модели, которые хорошо **читают**, но плохо **чинят** (по замеру «распознать с нуля
против исправить»): gemma-4-e4b (чтение 0.069, починка 0.153), MiniCPM-o 4.5 (0.069 /
0.154, пять Review из пяти), gemma-4-12b (0.017 / 0.050). Можно ли поправить
fix-запрос так, чтобы эти модели чинили лучше?

## Что меряли

Тот же стенд (`probe.py`), тот же корпус из 5 формул (`corpus/corpus_probe5.json`),
одна и та же метрика (CER к ручному эталону, доля прочитанных индексов). Все варианты
fix проходят через порт гейта (`gate.py`) — считается то, что приложение применит.

Варианты fix-запроса:

| вариант | что меняется |
| ------- | ------------ |
| `v0_app` | запрос приложения как есть: кандидат в `<CANDIDATE>`, вердикт OK/FIX/REVIEW |
| `no_cand_raw` | **тот же запрос приложения, но кандидат из сообщения убран** — диагностика: изолируем сам кандидат |
| `no_cand` | протокол без кандидата: свой системный промпт («ты пишешь исправленный блок по картинке») + своя тип-подсказка, ответ `FIX` + блок или `REVIEW` |
| `no_cand_hint` | `no_cand` + подсказка о скрипте (`SCRIPT_HINT` из `variants.py`) |
| `no_cand_think` | `no_cand` + мышление (`reasoning_budget_tokens: 512`, `enable_thinking: true`) |
| `hint_think` | запрос приложения + подсказка + мышление (лучший рычаг для qwen3.5-4b по прежним прогонам) |
| `read` | эталон: распознавание с нуля, вне fix-протокола |

Мышление включается **в запросе** (`reasoning_budget_tokens` + `chat_template_kwargs`),
перезапуск сервера не нужен — проверено (`check_thinking.py`: 1457 символов
`reasoning_content` при `--reasoning-budget 0` на сервере).

## Что это значит

### 1. Виновник — кандидат, а не модель и не промпт

Кандидат рядом с картинкой **мешает модели читать**. Модель якорится на его написании
(`H.Bnp`, `M_Π`) и «доточивает» его же, вместо того чтобы перечитать индекс с
картинки. Убрать кандидат — и fix-рука начинает читать:

* gemma-4-12b: 0.050 → 0.015 (в 3.3 раза), индексы 0.74 → 1.00;
* MiniCPM-o 4.5: 0.154 и пять Review → 0.076 и пять Fixed;
* gemma-4-e4b: 0.153 → 0.102.

Диагностика `no_cand_raw` (промпт приложения, кандидат просто убран) отделяет причину
от следствия: у gemma-4-12b она даёт 0.019 — почти как связная версия. Значит выигрывает
именно **отсутствие кандидата**, а не переформулировка.

### 2. Слабой модели нужна связная формулировка

У MiniCPM `no_cand_raw` даёт «OK» на трёх блоках из пяти: в промпте приложения «OK»
означает «кандидат совпадает с картинкой», а кандидата нет — и модель выбирает
единственный вердикт, который в этом промпте вообще возможен без нагрузки. Связный
протокол (`no_cand`) убирает из схемы OK: модель обязана принести блок.

То есть правило не «убери кандидат», а **«убери кандидат и перепиши контракт под
это»**.

### 3. Подсказка о скрипте помогает слабым и мешает сильным

| модель | `no_cand` → `no_cand_hint` |
| ------ | --------------------------- |
| MiniCPM-o 4.5 | 0.076 → **0.051** |
| gemma-4-e4b | 0.102 → **0.087** |
| gemma-4-12b | 0.015 → 0.020 |

Модель, которая и так держит кириллицу (gemma-4-12b), от подсказки ничего не теряет и
почти ничего не выигрывает; модель, которая её теряет (MiniCPM, e4b), выигрывает
заметно. Подсказка — это страховка для слабого читателя, а не улучшение сильного.

### 4. Мышление в новом протоколе вредит

gemma-4-12b: 0.015 → 0.023; MiniCPM: 0.076 → 0.115. И на 40–50 % дороже по времени
(600 токенов ответа против 100).

Это не противоречит прежнему замеру, где мышление было решающим для qwen3.5-4b: там
оно компенсировало **плохого** читателя (qwen-4b читает 0.187 — хуже всех). Хорошему
читателю мышление только мешает: он уже читает правильно, а рассуждение уводит его
в переписывание.

### 5. Токеновый бюджет для формул мал

На p05b09 (пятиэтажная формула) ответ обрезается на 2048 токенах — это
`maxOutputByBlock.equation` в `fix-requests.json`. Обрезанный ответ гейт отправляет
в **Review** (fix), а в руке read даёт частично испорченный блок. Единственный Review
в руках `no_cand` — именно этот блок. Для длинных формул бюджет надо поднимать
(2048 → 4096).

## Что предлагается поменять в приложении

1. **Новый протокол fix без кандидата** — по профилю роли, а не глобально: в
   `FixModel::buildRequestBody` (`src/models/FixModel.cpp:49`) часть `ocrPart` не
   добавляется в сообщение; системный промпт и тип-подсказка берутся другие.
2. **Отдельные промпты в профиле запросов** (`resources/profiles/requests/fix-requests.json`):
   системный промпт «ты пишешь исправленный блок по картинке» с контрактом
   `FIX` + блок / `REVIEW`, и тип-подсказка для формулы, у которой нет отсылки
   «как в кандидате».
3. **Выбор протокола — по модели**, а не глобально: протокол без кандидата для
   моделей, которые читают (gemma-4-12b, MiniCPM-o 4.5, gemma-4-e4b), текущий — для
   тех, которые чинят (qwen3.5-9b: fix 0.077 против read 0.236).
4. **Подсказка о скрипте** — включать для моделей, которые её теряют.
5. **Поднять бюджет формулы** (`maxOutputByBlock.equation` 2048 → 4096).

Гейт при этом не меняется: он и сейчас сравнивает присланный блок с кандидатом и
оставляет байты кандидата, если блок эквивалентен. То есть на блоке, где и кандидат,
и чтение верны, приложение ничего не портит.

## Оговорки

* **Корпус смещён в сторону блоков с ошибками** — все пять выбраны как «сложные
  случаи», где у кандидата ошибки. Выигрыш измерен именно на них. На блоке, где
  кандидат верен, а модель читает хуже, протокол без кандидата может ухудшить блок;
  гейт защищает только случай «прочитали эквивалентно». Этот риск этим корпусом не
  измерен — нужен корпус с верными кандидатами.
* Пять блоков одной страницы одного документа.
* Всё на CPU (Metal в песочнице недоступен), ctx 8192 у gemma-4-12b.
* Промпт read и промпт no_cand — один и тот же текст, различается только контракт
  ответа. Это сделано намеренно: так измеряется влияние кандидата, а не формулировок.
