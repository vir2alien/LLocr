# fix_models — стенд для улучшения fix-задачи (qwen3.5-4b)

Задача: `qwen3.5-4b` (Q8) не исправляет **индексы формул** — подстрочные
индексы вроде `н.впр`, `п`, `т`, `в`, `у` он читает как латиницу (`H.Bnp`,
`Π`, `T`, `B`, `v`) и в ответе повторяет ошибку кандидата. `gemma-4-12b`
справляется, `qwen3.5-9b` — почти. Запрос рабочий (большая модель его
выполняет), значит вопрос в том, как именно дать маленькой модели нужную
информацию.

Материалы и стенд — здесь; код приложения не требуется.

> **Протокол поменялся (ADR 192).** Стенд измеряет приложение, поэтому порт
> гейта (`gate.py`) повторяет текущий `src/models/FixDiffGate.cpp`: после FIX
> приходит **полный исправленный блок**, а не span-правки (`span_hybrid`,
> ADR 180 — его малые модели не осилили). Все числа ниже сняты на старом
> контракте и описывают ту эпоху; новый прогон считается тем же стендом с
> новым гейтом. Порт гейта и профили моделей стенда обновлены под новый
> контракт; бюджеты ответов (`maxOutputByBlock` — бюджет должен вмещать целый
> блок) лежат в общем профиле запросов `fix-requests.json`, как и в
> приложении, и профили моделей стенда своей копии не держат.

## Короткий вывод

| что | эффект |
| --- | --- |
| **режим мышления** (`--reasoning-budget 512` + `enable_thinking: true`) | главный выигрыш: индексы 0.54 → 0.65 на проблемной странице |
| **подсказка о скрипте** в системном промпте | +0.08 индексов; сама по себе почти безвредна, в паре с мышлением — решающая |
| **увеличение кропа в 2 раза** (бикубическая) | работает **только вместе** с мышлением (сам по себе — минус) |
| повтор промпта (arXiv 2512.14982) | не помогает (×2 хуже, ×3 — как мышление без подсказки) |
| бюджет vision-токенов (`--image-min-tokens`) | не помогает: картинка и так кодируется в полном разрешении |
| «прочитать самому и потом исправить» (два шага) | хуже: собственная транскрипция модели хуже кандидата |
| контекст страницы рядом с кропом | не помогает |

Итог на проблемной странице (7 блоков): **CER 0.140 → 0.062, индексы
0.54 → 0.78, 4 улучшено / 1 испорчено** — против 2 / 0 у приложения как есть.
На всех 57 формулах книги: CER 0.055 → 0.040, индексы 0.87 → 0.91, а на
блоках с ошибками — 11 улучшено против 1 испорченного (было 8 / 3).

Цена: ~37–55 с на блок вместо 12–18 с.

## MiniCPM-V 4.7 1B (Q8) в роли fix

Отдельная проверка: новая модель (`openbmb/MiniCPM-V-4.7-1B-gguf`, квант
`Q8_0`, mmproj `mmproj-model-f16.gguf`, 1.08 ГБ + 1.11 ГБ) на **текущем
пайплайне приложения** — без мышления, без подсказок, без увеличения
картинки. Профиль модели лежит в `profiles/minicpm-v-4.7-1b.json` (формат
того же приложения; в `resources/profiles/models/` модель не добавлена —
список поставляемых fix-моделей зафиксирован в тесте
`test_model_preset_catalog::fixRolesShipTheCorrectionProtocol`, а решение о
поставке — за владельцем продукта).

Пять самых сложных блоков страницы 3 (все формулы, где испорчены индексы):
`p03b03`, `p03b05`, `p03b11`, `p03b12`, `p03b14`. Кандидат и эталон — те
же, что в остальных прогонах.

| | MiniCPM-V 4.7 1B (Q8) | qwen3.5-4b (Q8) |
| --- | --- | --- |
| вердикты | 5 Ok / 0 Fixed / 0 Review | 0 Ok / 5 Fixed / 0 Review |
| улучшено / испорчено | 0 / 0 | 2 / 0 |
| CER кандидата → после | 0.178 → 0.178 | 0.178 → 0.168 |
| индексы до → после | 0.40 → 0.40 | 0.40 → 0.46 |
| время на блок | 2.9 с | 12.9 с |
| токенов в ответе | ~99 | ~126 |

**Что происходит.** Модель не держит протокол `OK / FIX / REVIEW`: четыре
ответа из пяти — это `OK` + newline + `FIXed block:` + своя формула.
Приложение берёт первый вердикт (`FixModel::parseResponse` смотрит на
начало ответа) → считает блок проверенным и **выбрасывает** написанную
моделью формулу. Пятый ответ (p03b05) — просто `OK` (2 токена).

**Своё чтение тоже хуже.** То, что модель написала после «OK»:

| блок | CER её формулы (кандидата) | индексы (кандидата) |
| --- | --- | --- |
| p03b03 | 0.256 (0.256) | 0.44 (0.33) |
| p03b11 | 0.200 (0.164) | 0.43 (0.43) |
| p03b12 | 0.196 (0.161) | 0.43 (0.43) |
| p03b14 | 0.213 (0.213) | 0.38 (0.38) |

Индексы она читает так же неверно, как qwen без мышления — латиницей
(`H.vpr`, `H.vnp`, `M_n` вместо `н.впр`, `н.впр`, `п`), и вдобавок меняет
`p` на `\rho` (на зуме числителя — латинская `p`, то есть это галлюцинация
модели, а не чтение).

**Итог.** Как fix-модель в текущем пайплайне MiniCPM-V 4.7 1B непригодна: она
не исправляет ни одного индекса, отвечает вне протокола (и её ответ,
если бы он применялся, был бы хуже кандидата). Плюс — в 4.4 раза быстрее
qwen3.5-4b. Плюс один: при ответе «OK» приложение не трогает текст, то
есть риск порчи блока равен нулю — модель безопасна тем, что ничего не
делает.

Если модель всё же понадобится, минимальные условия применимости: (1)
отдельная задача/промпт, обучающий именно протокол `OK/FIX/REVIEW`
(сейчас промпт задачи общий, `fix-requests.json`, и написан он под
крупные модели); (2) гейт, который не доверяет первому слову ответа —
сейчас «OK» + формула трактуется как «всё верно».

## Ministral 3 3B (Q8) и 8B (Q4_K_M) в роли fix

пять самых сложных блоков страницы 3, тот же кандидат и эталон.

Скачано: `mistralai/Ministral-3-3B-Instruct-2512-GGUF`
(`Ministral-3-3B-Instruct-2512-Q8_0.gguf`, 3.65 ГБ +
`Ministral-3-3B-Instruct-2512-BF16-mmproj.gguf`, 0.84 ГБ) и
`mistralai/Ministral-3-8B-Instruct-2512-GGUF`
(`Ministral-3-8B-Instruct-2512-Q4_K_M.gguf`, 5.2 ГБ +
`Ministral-3-8B-Instruct-2512-BF16-mmproj.gguf`, 0.86 ГБ). Профили —
`profiles/ministral-3-3b.json`, `profiles/ministral-3-8b.json` (тот же
формат, что у приложения; stop — `</s>`, у Mistral нет `<|im_end|>`).

### Вся страница (7 блоков, включая два текста)

| модель | Ok / Fix / Rev | улучш/порч | CER до → после | индексы до → после | с/блок |
| --- | --- | --- | --- | --- | --- |
| MiniCPM-V 4.7 1B (Q8) | 7 / 0 / 0 | 0 / 0 | 0.147 → 0.147 | 0.50 → 0.50 | 2.4 |
| qwen3.5-4b (Q8) | 2 / 5 / 0 | 2 / 0 | 0.147 → 0.140 | 0.50 → 0.54 | 11.8 |
| qwen3.5-4b + мышление/подсказка/×2 | 3 / 4 / 0 | 4 / 0 | 0.147 → 0.062 | 0.50 → 0.74 | 48.6 |
| **Ministral 3 3B (Q8)** | 0 / 5 / 2 | 3 / 0 | 0.147 → 0.086 | 0.50 → 0.74 | 9.4 |
| **Ministral 3 8B (Q4_K_M)** | 0 / 6 / 1 | 4 / 2 | 0.147 → 0.076 | 0.50 → 0.87 | 16.9 |

### Почему они лучше qwen

Обе модели **читают кириллические индексы с картинки** — то, чего не
делает qwen3.5-4b без подсказки: `p_{\text{н.впр}}`, `T_{\text{н.впр}}`,
`Q_{\text{терм}}`, `Q_{\text{исп.впр}}` — и не подменяют их латиницей.
Никаких мер (мышление, подсказка, увеличение картинки) для этого не нужно:
для Mistral достаточно текущего пайплайна. Два блока из пяти 8B и один из
пяти 3B закрыты полностью (CER 0.016–0.018, индексы 1.0).

### Чем они хуже

* **Регистр.** `Н.ВПР` вместо `н.впр` (b12 у обеих) — по правилам задачи
  это ошибка, и индекс при этом не засчитывается.
* **Путаница букв в индексе.** `M_{\text{и.впр}}` вместо `M_{\text{н.впр}}`
  (b05 у обеих), `M_{\text{н}}` вместо `M_{\text{п}}` (b03 у 8B).
* **Структурная ошибка.** 3B в b11 перевернула дробь:
  `\frac{\overline{B}_1}{\overline{B}}` вместо `\frac{\overline{B}}{\overline{B}_1}`.
* **8B вставил лишний ``` в конец формулы** (b05) — гейт такую строку
  принимает, и она портит CER.
* **Протокол на текстовых блоках.** На формуле модели отвечают «целой
  формулой» (как и просит промпт) и всё сходится; на тексте промпт просит
  span-правки, а модель отвечает и span-правками, и полным блоком
  сразу — гейт такой ответ отправляет в Review («The reply carries a whole
  block; this block type expects span edits»). На b09 это вышло у обеих
  моделей, на b02 — у 3B (8B уложилась в span-формат и поправила
  `M_{\pi}` → `M_{п}`: CER 0.088 → 0.070, индексы 0.5 → 1.0).
* **Плата за размер.** 8B в 1.8 раза медленнее 3B и в 1.4 раза медленнее
  qwen3.5-4b, при этом портит два блока там, где 3B не портит ни одного.

### Итог по трём новым моделям

| | исправляет индексы | портит | протокол | скорость |
| --- | --- | --- | --- | --- |
| Ministral 3 3B (Q8) | да (0.50 → 0.74) | нет | формулы — да, текст — нет | 9.4 с/блок |
| Ministral 3 8B (Q4_K_M) | да, лучше всех (0.50 → 0.87) | 2 блока | формулы — да, текст — нет | 16.9 с/блок |
| MiniCPM-V 4.7 1B (Q8) | нет | нет | нет (OK + формула) | 2.4 с/блок |

Ministral 3 — первая модель, которая в текущем пайплайне приложения
делает то, ради чего в прошлом прогоне пришлось поднимать мышление и
писать подсказку: читает кириллицу в индексах. 3B — лучший баланс
(ничего не портит, в 1.3 раза быстрее qwen3.5-4b); 8B — лучшее качество
(индексы 0.87), но два испорченных блока и 1.8 раза медленнее 3B.

## Ministral 3 14B (Q4_K_M) — самая большая в серии

`unsloth/Ministral-3-14B-Instruct-2512-GGUF`:
`Ministral-3-14B-Instruct-2512-Q4_K_M.gguf` (8.24 ГБ) + `mmproj-F16.gguf`
(0.88 ГБ). Профиль — `profiles/ministral-3-14b.json`.

| модель | CER | индексы | улучш/порч | Review | с/блок |
| --- | --- | --- | --- | --- | --- |
| qwen3.5-4b (Q8) | 0.168 | 0.46 | 2 / 0 | 0 | 12.9 |
| Ministral 3 3B (Q8) | 0.086 | 0.74 | 3 / 0 | 2 | 9.4 |
| Ministral 3 8B (Q4_K_M) | 0.076 | 0.87 | 4 / 2 | 1 | 16.9 |
| **Ministral 3 14B (Q4_K_M)** | 0.097 | **0.56** | 3 / 0 | 2 | 26.8 |

(таблица по пяти самым сложным формулам; на всей странице — CER 0.097,
индексы 0.56, 3 улучшено / 0 испорчено, 2 Review, 26.8 с/блок.)

**Странность: 14B читает лучше всех, а чинит хуже 3B и 8B.** Диагностика
`read_only` (та же, что и для qwen: модель читает кроп сама, кандидата
перед ней нет):

| модель | индексы при своём чтении | CER своего чтения | индексы в fix-задаче |
| --- | --- | --- | --- |
| qwen3.5-4b | 0.39 | 0.316 | 0.46 |
| Ministral 3 3B | 0.82 | 0.136 | 0.74 |
| Ministral 3 8B | 0.70 | 0.170 | 0.87 |
| **Ministral 3 14B** | **0.92** | **0.050** | **0.56** |

Свободное чтение у 14B почти идеальное: `p_{\text{н.впр}}`,
`T_{\text{н.впр}}`, `\overline{B}` — всё верно. Но в fix-задаче (кандидат
рядом с картинкой) она пишет **смесь скриптов**: `p_{\mathrm{H.впр}}`
(латинская H из кандидата + кириллица из картинки), `M_{\Pi}` (латинская
Pi из кандидата), `T_{\mathrm{Н.ВПР}}` (заглавная кириллица), плюс
тащит из кандидата мусорные `\left| … \right|`. То есть 14B **якорится
на кандидате**: она «допиливает» кандидат, а не перечитывает индекс с
картинки. У 3B и 8B этого эффекта нет — они индекс переписывают.

Итог: 14B в fix-задаче бесполезна, хотя в задаче «прочитать» — лучшая из
всех. Практический вывод тот же, что и для qwen: **fix-протокол (кандидат
+ картинка) мешает модели читать**. Модель, умеющая читать (14B), под
протоколом теряет это умение; модель, не умеющая читать, (qwen) остаётся
неумеющей. Если 14B и использовать, то в задаче чтения/распознавания
(а не исправления), либо с протоколом, где кандидат не показывают.

## Как приложение шлёт fix-запрос (что воспроизводит стенд)

`VerificationQueueController::startNextVerify` → `FixController::fixBlock` →
`FixModel::buildRequestBody`:

* кандидат = `FixDiffGate::normalizeLatexCandidate(текст блока)` — пробелы
  перед скобками убраны (`\frac {p}` → `\frac{p}`);
* сообщения: `system` (промпт профиля запросов, `{{LANGUAGE}}` → Russian) и
  `user` с тремя частями: typePrompt по типу блока → картинка кропа →
  `OCR candidate:\n<CANDIDATE>…</CANDIDATE>`;
* `chat_template_kwargs: {enable_thinking: false}`;
* параметры запроса из профиля модели: temperature 0, repeat_penalty 1.0,
  stop `[<|im_end|>, <|endoftext|>, </CANDIDATE>]`, `max_tokens` — из
  `maxOutputByBlock` (1024 для формул и текста);
* ответ: `OK` / `FIX` + правки / `REVIEW`. Формула отвечает **целиком**
  (ADR 181), гейт применяет её как исправление, если она не эквивалентна
  кандидату.

Стенд считает не ответ модели, а **результат гейта** (`gate.py` — порт
`FixDiffGate.cpp`): `Ok` / `Fixed` / `Review` и итоговый текст блока.

## Метрики

* **CER** (посимвольный, после нормализации `compare.py`) кандидата и
  исправленного текста против эталона; `улучш` / `порч` — знак разницы.
* **Индексы** — доля под- и надстрочных групп эталона, присутствующих в
  тексте (мультимножества, не подстроки). Это и есть «прочитал ли индекс».
* **Вердикты** — `Ok` / `Fixed` / `Review` от гейта.

```sh
# другая модель: свой профиль + свой конфиг сервера
python3 run.py --model-profile profiles/minicpm-v-4.7-1b.json \
  --config configs/minicpm-v-4.7-1b.json --variant v0_app \
  --blocks p03b03,p03b05,p03b11,p03b12,p03b14 --out results/minicpm
```

Ответы кешируются по хешу запроса (`results/cache`), прогон resumable:
повторный запуск не тратит время. `--refresh` — обойти кеш.

Сервер поднимается с аргументами приложения (`--spec-type draft-mtp`,
`--image-min-tokens 1024`, `--reasoning-budget 0`, `--ctx-size 16384`, …);
варианты, меняющие серверные параметры, группируются по ним — сервер
перезапускается между группами (порт проверяется: старый сервер должен
умереть, иначе запросы уйдут к нему и «параметр не влияет» получится
ложно — на этом споткнулся первый прогон).

## Что сработало и почему

1. **Мышление — единственное, что даёт разбор по осям.** Без него модель
   переписывает формулу «по памяти» и тащит из кандидата ошибку индекса.
   С мышлением (бюджет 512) в `reasoning_content` появляется разбор
   «Script / Case / Face / Position» — и в `p03b03` индексы
   `p_{\mathrm{H.Bnp}}` → `p_{\mathrm{н.впр}}` становятся кириллицей.
   Бюджет 2048 — хуже: ответ не влезает в `max_tokens` блока, все семь
   блоков уходят в Review.
2. **Подсказка о скрипте.** Диагностика `read_only` показала: в **тексте**
   модель читает кириллицу правильно (`M_{\text{п}}` — верно!), а в
   **формуле** переводит индексы в латиницу (`н.впр` → `H.BIpp`). То есть
   ей не хватает знания, что это кириллица, а не начертание. Слова
   «прочитай кириллицей, а не латинскими двойниками» хватает.
   Вариант «правилом» (правило сформулировано через `{{LANGUAGE}}`,
   примеры транслитерации даны) работает не хуже явного списка букв —
   значит, в приложении подсказку можно писать один раз для всех языков.
   Совсем обобщённая формулировка («индексы — буквы алфавита документа»)
   работает заметно слабее: примеры в тексте подсказки важны.
3. **Увеличение кропа в 2 раза** даёт эффект **только вместе** с мышлением:
   картинка становится вдвое крупнее по пикселям, и индекс `н.впр` (в
   исходнике ~15 px высотой) перестаёт быть одним vision-токеном. Само по
   себе увеличение не помогает и даже чуть вредит — модель без разбора
   просто переписывает формулу.
4. **Бюджет vision-токенов нерелевантен.** `--image-min-tokens 4096`
   действительно поднимает число токенов картинки (2198 → 5283), но ответ
   не меняется: картинка и так кодируется в полном разрешении исходника,
   а лишние токены уходят в увеличение пустых полей. Потолок
   `--image-min-tokens 8192` упёрся в `image_max_pixels` mmproj и сервер
   не стартует (`image_max_pixels (4194304) is less than image_min_pixels
   (8388608)`).
5. **Повтор промпта (arXiv 2512.14982) не помогает.** ×2 — как базовая
   линия (CER 0.148, индексы 0.50), ×3 — на уровне мышления без
   подсказки, но дороже. Модель повторяет не чтение, а кандидат: если
   ошибка индекса есть в кандидате, она есть и во втором повторе.
6. **«Сначала прочитать, потом править» хуже.** Собственная транскрипция
   модели (`read_only`) хуже кандидата: на тексте с формулой она
   выдаёт мусор (`TenJ o ,П О В В О А А Н О е \ К Т О Н Ж I B y y`), на
   формулах — латиницу. Опораться ей не на что.
7. **Контекст страницы рядом с кропом** ничего не даёт: модель не
   «выводит» алфавит документа из соседнего текста.

## Как это переносится в приложение

Три правки, все в профилях и в одном месте кода:

1. **Мышление** — `resources/profiles/models/qwen3.5-4b.json`, роль `fix`:
   `reasoning-budget` 0 → 512. Плюс `enable_thinking: true`: сейчас
   `VisionChatModel::buildRoot` жёстко шлёт `chat_template_kwargs:
   {enable_thinking: false}` — нужен переключатель (например, поле в роли
   профиля модели, чтобы «мышление» включалось вместе с бюджетом).
   **Разбор ответа править не нужно:** llama.cpp кладёт мысль в
   `message.reasoning_content`, а `FixModel` читает только `content` —
   вердикт приходит чистым.
2. **Подсказка о скрипте** — `resources/profiles/requests/fix-requests.json`,
   абзац в системном промпте (текст блоков «скрипт» уже есть — туда и
   дописать). Формулировка «правилом» (с `{{LANGUAGE}}` и примерами
   транслитерации) обобщается на любой язык.
3. **Увеличение кропа** — код: `AppController::croppedImage` отдаёт сырой
   кроп; для fix-задачи нужен масштаб 2 (бикубический). Это настройка
   задачи (профиль/опция), а не общий дефолт превью.

Ожидаемый эффект в приложении: на проблемной странице индексы исправляются
в 2.2 раза чаще (0.54 → 0.78), на книге — CER 0.055 → 0.040, а число
испорченных блоков падает (3 → 1 на ошибочных). Цена — время: ~40–55 с на
блок вместо 12–18 с (мышление + картинка вдвое крупнее).

## Ограничения

* Малый корпус — 7 блоков; большие числа на нём (±1 блок) ничего не
  значат. Выводы «мышление и подсказка работают» подтверждены на 57
  формулах, но и там блоков с ошибками всего 28.
* Один квант (Q8), одна модель, один OCR-кандидат (MinerU2.5-Pro).
  Другие OCR-ошибки (латиница ↔ кириллица в тексте) в корпусе почти не
  представлены.
* Эталон `gt.json` местами неверен (например, `p03b13`: «Приближенно приar{B}ar{B}_1»);
  такие блоки в корпус не брались, но в других прогонах появятся — правки
  эталона живут в `corpus/overrides.json`.
* Метрика CER к эталону считает и различия записи (`\mathrm{н.впр}` против
  `н.впр`), поэтому абсолютные значения занижены; для сравнения вариантов
  это неважно (эталон один и тот же).
* Все ответы — greedy (temperature 0) и детерминированные; повторный
  прогон воспроизводится из кеша побайтово.
